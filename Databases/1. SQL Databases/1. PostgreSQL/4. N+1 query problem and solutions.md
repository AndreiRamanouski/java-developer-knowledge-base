# N+1 Query Problem and Solutions

## Deep Dive Interview Guide

This guide covers the N+1 query problem in Spring Boot with PostgreSQL, including detection techniques, multiple solutions, performance comparisons, and production best practices.

**Interview Tip**: N+1 questions test understanding of ORM behavior, lazy loading, query optimization, and performance tuning.

---

## Q4: N+1 query problem and solutions

**Short Answer**: N+1 problem occurs when loading N parent entities triggers N additional queries to fetch children (1 query for parents + N queries for children). Detect with Hibernate statistics or logging. Fix with: @EntityGraph (eager loading), JOIN FETCH (JPQL), @BatchSize (batching), @Fetch(SUBSELECT) (subquery), or DTO projections (avoiding entities). Choose based on: consistent needs (EntityGraph), dynamic needs (JOIN FETCH), medium sets (@BatchSize), or read-only (DTOs).

---

## 1. Understanding the N+1 Problem

### The Classic Example

```java
// Entity setup
@Entity
public class Author {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;
    
    @OneToMany(mappedBy = "author", fetch = FetchType.LAZY)  // LAZY by default
    private List<Book> books;
}

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String title;
    private String isbn;
    
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id")
    private Author author;
}

// Service with N+1 problem
@Service
public class BadAuthorService {
    
    @Autowired
    private AuthorRepository authorRepository;
    
    @Transactional(readOnly = true)
    public List<AuthorWithBooks> getAllAuthorsWithBooks() {
        // Query 1: Fetch all authors
        List<Author> authors = authorRepository.findAll();
        // SQL: SELECT * FROM authors;
        
        List<AuthorWithBooks> result = new ArrayList<>();
        
        for (Author author : authors) {  // N authors
            // Query 2, 3, 4, ..., N+1: Fetch books for each author
            List<Book> books = author.getBooks();  // Lazy loading triggers query!
            // SQL: SELECT * FROM books WHERE author_id = ?
            
            result.add(new AuthorWithBooks(author.getName(), books));
        }
        
        // Total queries: 1 + N
        // If 100 authors: 101 queries!
        // If 1000 authors: 1001 queries!
        
        return result;
    }
}
```

**What Happens Under the Hood:**

```sql
-- Query 1: Load all authors (1 query)
SELECT id, name FROM authors;
-- Returns 100 authors

-- Query 2: Load books for author 1 (N queries start here)
SELECT id, title, isbn, author_id FROM books WHERE author_id = 1;

-- Query 3: Load books for author 2
SELECT id, title, isbn, author_id FROM books WHERE author_id = 2;

-- Query 4: Load books for author 3
SELECT id, title, isbn, author_id FROM books WHERE author_id = 3;

-- ... 97 more queries ...

-- Query 101: Load books for author 100
SELECT id, title, isbn, author_id FROM books WHERE author_id = 100;

-- Total: 101 queries for what should be 1 or 2 queries!
```

### Why It's a Problem

```java
// Performance impact demonstration

@SpringBootTest
public class NPlus1PerformanceTest {
    
    @Test
    public void demonstratePerformanceImpact() {
        // Setup: Create 100 authors with 5 books each
        setupTestData(100, 5);
        
        // N+1 approach
        long start = System.currentTimeMillis();
        List<AuthorWithBooks> result = badAuthorService.getAllAuthorsWithBooks();
        long nPlus1Time = System.currentTimeMillis() - start;
        
        System.out.println("N+1 approach:");
        System.out.println("  Queries: 101");
        System.out.println("  Time: " + nPlus1Time + "ms");  // ~500ms
        
        // Optimized approach (we'll see later)
        start = System.currentTimeMillis();
        result = goodAuthorService.getAllAuthorsWithBooks();
        long optimizedTime = System.currentTimeMillis() - start;
        
        System.out.println("Optimized approach:");
        System.out.println("  Queries: 1");
        System.out.println("  Time: " + optimizedTime + "ms");  // ~50ms
        
        System.out.println("Performance improvement: " + (nPlus1Time / optimizedTime) + "x");
        // Result: 10x faster!
    }
}
```

**Real-World Impact:**

```
N=10:    ~10ms  → ~50ms   (5x slower)
N=100:   ~50ms  → ~500ms  (10x slower)
N=1000:  ~100ms → ~5000ms (50x slower)
N=10000: ~500ms → ~50000ms (100x slower) - TIMEOUT!

Network overhead compounds:
- Each query: ~1ms network latency
- 1000 queries: 1000ms just for network!
```

```java
@Component
public class HibernateStatisticsLogger {

        log.info("Entities inserted: {}", stats.getEntityInsertCount());
        log.info("Entities deleted: {}", stats.getEntityDeleteCount());
        log.info("Collections loaded: {}", stats.getCollectionLoadCount());
        log.info("Collections updated: {}", stats.getCollectionUpdateCount());

        log.info("Second level cache hits: {}", stats.getSecondLevelCacheHitCount());
```

### Statistics Aspect for Automatic Logging

```java
@Aspect
@Component
@Slf4j
public class QueryCountAspect {
    
    @Autowired
    private EntityManagerFactory entityManagerFactory;
    
    @Around("@annotation(org.springframework.web.bind.annotation.GetMapping) || " +
            "@annotation(org.springframework.web.bind.annotation.PostMapping)")
    public Object logQueryCount(ProceedingJoinPoint joinPoint) throws Throwable {
        SessionFactory sessionFactory = entityManagerFactory.unwrap(SessionFactory.class);
        Statistics stats = sessionFactory.getStatistics();
        
        // Clear before
        stats.clear();
        
        // Execute method
        Object result = joinPoint.proceed();
        
        // Log statistics
        long queryCount = stats.getQueryExecutionCount();
        String methodName = joinPoint.getSignature().toShortString();
        
        if (queryCount > 10) {
            log.warn("⚠️ Potential N+1 in {}: {} queries", methodName, queryCount);
        } else {
            log.info("✅ {} executed {} queries", methodName, queryCount);
        }
        
        return result;
    }
}
```

### Test with Statistics

```java
@SpringBootTest
public class NPlus1DetectionTest {
    
    @Autowired
    private EntityManagerFactory entityManagerFactory;
    
    @Autowired
    private AuthorRepository authorRepository;
    
    @Test
    public void detectNPlus1Problem() {
        // Clear statistics
        SessionFactory sessionFactory = entityManagerFactory.unwrap(SessionFactory.class);
        Statistics stats = sessionFactory.getStatistics();
        stats.setStatisticsEnabled(true);
        stats.clear();
        
        // Execute problematic code
        List<Author> authors = authorRepository.findAll();
        
        long queriesAfterFindAll = stats.getQueryExecutionCount();
        System.out.println("Queries after findAll: " + queriesAfterFindAll);  // 1

        }
        
        long totalQueries = stats.getQueryExecutionCount();
        System.out.println("Total queries: " + totalQueries);  // 1 + N
        
        // Assert N+1 detected
        int expectedQueries = 1 + authors.size();
        assertEquals(expectedQueries, totalQueries, "N+1 problem detected!");
    }
}
```

## 3. Solution 1: @EntityGraph for Eager Fetching

**When to use**: Consistent fetching needs across multiple methods.

### Basic @EntityGraph

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // Define entity graph inline
    @EntityGraph(attributePaths = {"books"})
    List<Author> findAll();
    
    // Named entity graph
    @EntityGraph(attributePaths = {"books"})
    Optional<Author> findById(Long id);
    
    // Multiple associations
    @EntityGraph(attributePaths = {"books", "address"})
    List<Author> findByNameContaining(String name);
}

// Service usage
@Service
public class AuthorService {
    
    @Autowired
    private AuthorRepository authorRepository;
    
    @Transactional(readOnly = true)
    public List<AuthorWithBooks> getAllAuthorsWithBooks() {
        // Single query with LEFT JOIN
        List<Author> authors = authorRepository.findAll();
        // SQL: SELECT a.*, b.* FROM authors a LEFT JOIN books b ON a.id = b.author_id
        
        return authors.stream()
            .map(author -> new AuthorWithBooks(
                author.getName(),
                author.getBooks()  // Already loaded, no additional query!
            ))
            .collect(Collectors.toList());
    }
}
```

### Named Entity Graph (Reusable)

```java

```

### Nested Entity Graphs

```java
// ✅ Pros:
// - Declarative (clean code)
// - Single query (optimal for small-medium datasets)
// - No code changes in service layer
// - Works with derived query methods
// - Reusable named graphs

// - Cartesian product with multiple collections (data duplication)
// - Fixed fetching strategy (can't be dynamic per request)
```

## 4. Solution 2: JOIN FETCH in JPQL

**When to use**: Dynamic fetching needs, different queries need different associations.

### Basic JOIN FETCH

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // Basic JOIN FETCH
    @Query("SELECT a FROM Author a JOIN FETCH a.books")
    List<Author> findAllWithBooks();
    
    // Multiple associations
    @Query("SELECT a FROM Author a " +
           "JOIN FETCH a.books " +
           "LEFT JOIN FETCH a.address")
    List<Author> findAllWithBooksAndAddress();
    
    // Conditional JOIN FETCH
    @Query("SELECT a FROM Author a " +
           "JOIN FETCH a.books b " +
           "WHERE b.publishedYear > :year")
    List<Author> findAuthorsWithRecentBooks(@Param("year") int year);
}

@Service
public class AuthorService {
    
    @Autowired
    private AuthorRepository authorRepository;
    
    @Transactional(readOnly = true)
    public List<AuthorWithBooks> getAllAuthorsWithBooks() {
        // Single query with INNER JOIN
        List<Author> authors = authorRepository.findAllWithBooks();
        
        return authors.stream()
            .map(author -> new AuthorWithBooks(
                author.getName(),
                author.getBooks()
            ))
            .collect(Collectors.toList());
    }
}
```

### DISTINCT with JOIN FETCH

```java
// Problem: Duplicate authors due to JOIN
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // ❌ Without DISTINCT: Returns duplicate Author objects
    @Query("SELECT a FROM Author a JOIN FETCH a.books")
    List<Author> findAllWithBooksBad();
    
    // Result: If author has 3 books, author appears 3 times in list!
    
    // ✅ With DISTINCT: Removes duplicates
    @Query("SELECT DISTINCT a FROM Author a JOIN FETCH a.books")
    List<Author> findAllWithBooksGood();
    
    // Result: Each author appears once, but with all books
}

// Why duplicates happen:
/*
SQL JOIN produces:
| author_id | author_name | book_id | book_title |
|-----------|-------------|---------|------------|
| 1         | John        | 1       | Book A     |
| 1         | John        | 2       | Book B     |
| 1         | John        | 3       | Book C     |
| 2         | Jane        | 4       | Book D     |

Without DISTINCT: 3 Author(id=1) objects + 1 Author(id=2) object
With DISTINCT: 1 Author(id=1) object + 1 Author(id=2) object
*/
```

### Multiple Collections (Cartesian Product Problem)

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // ❌ BAD: Multiple JOIN FETCH with collections causes cartesian product
    @Query("SELECT DISTINCT a FROM Author a " +
           "JOIN FETCH a.books " +
           "JOIN FETCH a.articles")
    List<Author> findAllWithBooksAndArticlesBad();
    
    // Result: Huge performance problem!
    // If author has 10 books and 5 articles: 50 rows returned!
    // If 100 authors with 10 books and 5 articles each: 50,000 rows!
    
    // ✅ GOOD: Use separate queries
    @Query("SELECT DISTINCT a FROM Author a JOIN FETCH a.books")
    List<Author> findAllWithBooks();
    
    @Query("SELECT DISTINCT a FROM Author a JOIN FETCH a.articles WHERE a.id IN :ids")
    List<Author> findByIdsWithArticles(@Param("ids") List<Long> ids);
}

@Service
public class AuthorService {
    
    @Transactional(readOnly = true)
    public List<Author> getAllAuthorsWithBooksAndArticles() {
        // Query 1: Fetch authors with books
        List<Author> authors = authorRepository.findAllWithBooks();
        
        // Query 2: Fetch articles for these authors
        List<Long> authorIds = authors.stream()
            .map(Author::getId)
            .collect(Collectors.toList());
        
        if (!authorIds.isEmpty()) {
            authorRepository.findByIdsWithArticles(authorIds);
            // This updates the already-loaded Author entities
        }
        
        return authors;
        // Total: 2 queries (much better than N+1 or cartesian product)
    }
}
```

### Pagination with JOIN FETCH

```java
// Problem: JOIN FETCH + pagination = warning!

@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // ⚠️ WARNING: Pagination in memory, not database!
    @Query("SELECT DISTINCT a FROM Author a JOIN FETCH a.books")
    Page<Author> findAllWithBooks(Pageable pageable);
    
    // Hibernate warning:
    // "HHH000104: firstResult/maxResults specified with collection fetch; 
    //  applying in memory!"
    
    // What happens:
    // 1. Hibernate loads ALL data from database
    // 2. Applies pagination in memory
    // 3. Very slow for large datasets!
}

// Solution 1: Fetch IDs first, then entities
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    @Query("SELECT a.id FROM Author a")
    Page<Long> findAllIds(Pageable pageable);
    
    @Query("SELECT DISTINCT a FROM Author a JOIN FETCH a.books WHERE a.id IN :ids")
    List<Author> findByIdsWithBooks(@Param("ids") List<Long> ids);
}

@Service
public class AuthorService {
    
    @Transactional(readOnly = true)
    public Page<Author> getAuthorsWithBooks(Pageable pageable) {
        // Query 1: Fetch paginated IDs
        Page<Long> idPage = authorRepository.findAllIds(pageable);
        
        // Query 2: Fetch entities with books for these IDs
        List<Author> authors = authorRepository.findByIdsWithBooks(
            idPage.getContent()
        );
        
        // Maintain order from ID page
        Map<Long, Author> authorMap = authors.stream()
            .collect(Collectors.toMap(Author::getId, a -> a));
        
        List<Author> orderedAuthors = idPage.getContent().stream()
            .map(authorMap::get)
            .collect(Collectors.toList());
        
        return new PageImpl<>(orderedAuthors, pageable, idPage.getTotalElements());
    }
}

// Solution 2: Use window functions (PostgreSQL-specific)
@Query(value = """
    SELECT * FROM (
        SELECT 
            a.*, b.*,
            ROW_NUMBER() OVER (PARTITION BY a.id ORDER BY a.id) as rn
        FROM authors a
        LEFT JOIN books b ON a.id = b.author_id
    ) sub
    WHERE rn = 1
    ORDER BY id
    LIMIT :limit OFFSET :offset
    """, nativeQuery = true)
List<Author> findAllWithBooksPaginated(@Param("limit") int limit, 
                                       @Param("offset") int offset);
```

**Pros and Cons:**

```java
// ✅ Pros:
// - Dynamic (different queries for different needs)
// - Full control over JOIN type (INNER vs LEFT)
// - Can add WHERE conditions
// - Works well with simple relationships
// - Better for one-to-one or many-to-one

// ❌ Cons:
// - Requires DISTINCT for one-to-many
// - Cartesian product with multiple collections
// - Pagination issues (in-memory)
// - More verbose than @EntityGraph
// - Can't use with derived query methods
```

## 5. Solution 3: @BatchSize Annotation

**When to use**: Medium-sized collections, when you want lazy loading with batching.

### Basic @BatchSize

```java
@Entity
public class Author {
    @Id
    private Long id;
    
    private String name;
    
    @OneToMany(mappedBy = "author")
    @BatchSize(size = 10)  // Fetch books for 10 authors at once
    private List<Book> books;
}

@Service
public class AuthorService {
    
    @Transactional(readOnly = true)
    public List<AuthorWithBooks> getAllAuthorsWithBooks() {
        // Query 1: Fetch all authors
        List<Author> authors = authorRepository.findAll();
        // SELECT * FROM authors;
        
        // Access books (triggers batched loading)
        for (Author author : authors) {
            author.getBooks().size();
        }
        
        // Query 2: Batch fetch books for first 10 authors
        // SELECT * FROM books WHERE author_id IN (1, 2, 3, ..., 10);
        
        // Query 3: Batch fetch books for next 10 authors
        // SELECT * FROM books WHERE author_id IN (11, 12, 13, ..., 20);
        
        // ... and so on
        
        // Total queries: 1 + (N / batchSize)
        // For 100 authors with batchSize=10: 1 + 10 = 11 queries
        // Much better than 1 + 100 = 101 queries!
        
        return mapToDto(authors);
    }
}
```

```java
// Choosing the right batch size

public class BatchSizeGuide {
    
    public void chooseOptimalBatchSize() {
        // Too small (1-5):
        // - Too many queries
        // - Poor performance
        // Example: 100 entities with size=5 → 20 queries
        
        // Sweet spot (10-25):
        // - Good balance
        // - Reasonable query count
        // - Not too much data per query
        // Example: 100 entities with size=10 → 10 queries
        
        // Too large (100+):
        // - Large IN clauses (less efficient)
        // - Memory pressure
        // - Query cache less effective
        // Example: 100 entities with size=100 → 1 query (but large IN clause)
        
        // Recommendation:
        // - Default: 10-25
        // - Low cardinality collections: 25-50
        // - High cardinality collections: 5-10
        // - Pagination size matching: Use same as page size
    }
}
```

## 6. Solution 4: @Fetch(FetchMode.SUBSELECT)

**When to use**: When you want all children loaded in a single additional query.

### Basic SUBSELECT

```java
@Entity
public class Author {
    @Id
    private Long id;
    
    private String name;
    
    @OneToMany(mappedBy = "author")
    @Fetch(FetchMode.SUBSELECT)  // Load all books in one subquery
    private List<Book> books;
}

@Service
public class AuthorService {
    
    @Transactional(readOnly = true)
    public List<AuthorWithBooks> getAllAuthorsWithBooks() {
        // Query 1: Fetch all authors
        List<Author> authors = authorRepository.findAll();
        // SELECT * FROM authors;
        
        // Access books (triggers subquery loading)
        authors.get(0).getBooks().size();
        
        // Query 2: Fetch ALL books for ALL authors in one subquery
        // SELECT * FROM books 
        // WHERE author_id IN (
        //     SELECT id FROM authors  -- Subquery
        // );
        
        // Total: 2 queries (optimal!)
        
        return mapToDto(authors);
    }
}
```

### Generated SQL


## 9. Decision Matrix

### Choosing the Right Solution

```java
public class SolutionDecisionTree {
    
    public Solution chooseSolution(Scenario scenario) {
        // Read-only queries?
        if (scenario.isReadOnly()) {
            return Solution.DTO_PROJECTION;  // Best performance
        }
        
        // Need to modify entities?
        if (scenario.needsModification()) {
            // Multiple collections?
            if (scenario.hasMultipleCollections()) {
                return Solution.SUBSELECT;  // No cartesian product
            }
            
            // High contention on same data?
            if (scenario.isHighContention()) {
                return Solution.JOIN_FETCH;  // Single query, atomic
            }
            
            // Variable collection sizes?
            if (scenario.hasVariableCollectionSizes()) {
                return Solution.BATCH_SIZE;  // Flexible loading
            }
            
            // Consistent fetching needs?
            return Solution.ENTITY_GRAPH;  // Declarative, clean
        }
        
        // Pagination required?
        if (scenario.needsPagination()) {
            return Solution.DTO_PROJECTION;  // No in-memory pagination
        }
        
        // Default
        return Solution.ENTITY_GRAPH;
    }
}
```

## Interview Follow-Up Questions - Detailed Answers

### Q1: "How would you detect N+1 in production without performance degradation?"

**Answer**: Use lightweight monitoring: query count logging with thresholds, APM tools (DataDog, New Relic), P99 latency alerts, and query execution plan analysis. Avoid enabling full Hibernate statistics in production (CPU overhead). Use sampling and async logging.

**Production-Safe Detection Methods**

```java
// Method 1: Query Count Threshold Monitoring (Lightweight)

@Aspect
@Component
@Slf4j
public class QueryCountMonitor {
    
    @Autowired
    private EntityManagerFactory entityManagerFactory;
    
    private static final int QUERY_THRESHOLD = 10;
    private final ThreadLocal<Long> queryCountStart = new ThreadLocal<>();
    
    @Around("@annotation(org.springframework.web.bind.annotation.RequestMapping) || " +
            "@annotation(org.springframework.web.bind.annotation.GetMapping)")
    public Object monitorQueries(ProceedingJoinPoint joinPoint) throws Throwable {
        // Only sample 10% of requests (low overhead)
        if (Math.random() > 0.1) {
            return joinPoint.proceed();
        }
        
        SessionFactory sf = entityManagerFactory.unwrap(SessionFactory.class);
        Statistics stats = sf.getStatistics();
        
        long startCount = stats.getQueryExecutionCount();
        long startTime = System.currentTimeMillis();
        
        try {
            return joinPoint.proceed();
        } finally {
            long endCount = stats.getQueryExecutionCount();
            long queryCount = endCount - startCount;
            long duration = System.currentTimeMillis() - startTime;
            
            if (queryCount > QUERY_THRESHOLD) {
                String methodName = joinPoint.getSignature().toShortString();
                log.warn("[N+1 Alert] {} executed {} queries in {}ms", 
                        methodName, queryCount, duration);
                
                // Send to monitoring system
                sendMetric("query.count.high", queryCount, 
                          Map.of("method", methodName));
            }
        }
    }
}
```

**Method 3: Database-Level Monitoring (Zero App Overhead)**

```sql
-- PostgreSQL: Enable pg_stat_statements (minimal overhead)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Find queries executed frequently (potential N+1)
SELECT 
    query,
    calls,
    total_exec_time,
    mean_exec_time,
    rows / calls as avg_rows_per_call
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat%'
  AND calls > 100  -- Executed > 100 times
  AND mean_exec_time < 5  -- Fast queries (< 5ms)
  AND rows / calls < 10  -- Few rows per execution
ORDER BY calls DESC
LIMIT 20;

-- These characteristics indicate N+1:
-- 1. High call count (100+)
-- 2. Fast execution (< 5ms) - simple SELECT
-- 3. Few rows per call (< 10) - fetching one entity's children
-- 4. Similar query structure repeated

-- Example N+1 pattern:
-- Query: SELECT * FROM books WHERE author_id = ?
-- Calls: 500
-- Mean time: 2ms
-- Rows/call: 3
-- Diagnosis: N+1 fetching books for each author

-- Monitor in real-time with cron job
CREATE OR REPLACE FUNCTION detect_n_plus_one()
RETURNS TABLE(
    query_text text,
    execution_count bigint,
    avg_time_ms numeric,
    n_plus_one_score numeric
) AS $$
BEGIN
    RETURN QUERY
    SELECT 
        query,
        calls,
        ROUND(mean_exec_time::numeric, 2) as avg_time_ms,
        -- N+1 score: high calls + fast queries + few rows
        ROUND((calls::numeric / 100) * 
              (1 / NULLIF(mean_exec_time, 0)) * 
              (10 / NULLIF((rows::numeric / calls), 0)), 2) as score
    FROM pg_stat_statements
    WHERE calls > 50
      AND mean_exec_time < 10
      AND rows / calls < 20
    ORDER BY score DESC
    LIMIT 10;
END;
$$ LANGUAGE plpgsql;

-- Run periodically and alert if score > threshold
```

```java
@Component
public class AsyncQueryLogger {
    
    private final ExecutorService executor = Executors.newSingleThreadExecutor();
    private final BlockingQueue<QueryEvent> eventQueue = new LinkedBlockingQueue<>(1000);
    
    @PostConstruct
    public void startLogger() {
        executor.submit(() -> {
            while (true) {
                try {
                    QueryEvent event = eventQueue.take();
                    processEvent(event);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        });
    }
    
    public void logQuery(String query, long duration) {
        // Non-blocking: drops if queue full
        eventQueue.offer(new QueryEvent(query, duration, LocalDateTime.now()));
    }
    
    private void processEvent(QueryEvent event) {
        // Analyze pattern offline
        if (detectsN PlusOne(event)) {
            // Send alert (email, Slack, PagerDuty)
            alertingService.sendAlert("N+1 detected: " + event.getQuery());
        }
        
        // Store in time-series database for analysis
        influxDB.write(event);
    }
    
    private boolean detectsNPlusOne(QueryEvent event) {
        // Pattern matching for N+1
        String query = event.getQuery().toLowerCase();
        return query.contains("where") && 
               query.contains("=") &&
               !query.contains("in") &&
               event.getDuration() < 10;  // Fast query
    }
}

@Data
@AllArgsConstructor
class QueryEvent {
    private String query;
    private long duration;
    private LocalDateTime timestamp;
```

### Q2: "What's the performance difference between @EntityGraph and JOIN FETCH?"

**Answer**: Functionally similar (both use LEFT JOIN), but differ in: 1) Declaration style (@EntityGraph is declarative, JOIN FETCH is imperative), 2) Flexibility (JOIN FETCH allows dynamic WHERE clauses), 3) DISTINCT handling (@EntityGraph handles automatically in some cases, JOIN FETCH requires explicit), 4) Performance is nearly identical (~2-5ms difference), choose based on use case not performance.

### Q3: "When would you use @BatchSize instead of JOIN FETCH?"

**Answer**: Use @BatchSize when: 1) Collection sizes vary widely (some authors have 1 book, others 100), 2) Pagination is required, 3) Memory is constrained (JOIN FETCH loads all data), 4) Lazy loading is preferred with optimization, 5) Want to avoid cartesian product with multiple collections. JOIN FETCH better for: consistent collection sizes, single query requirement, no pagination.

**Detailed Scenarios**

```java
// Scenario 1: Variable Collection Sizes

@Entity
public class Author {
    @Id
    private Long id;
    
    // Some authors have 1 book, others have 100+
    @OneToMany(mappedBy = "author")
    @BatchSize(size = 20)  // ✅ Good choice
    private List<Book> books;
}

// Why @BatchSize is better:
@Service
public class AuthorService {
    
    @Transactional(readOnly = true)
    public List<AuthorSummary> getAuthorSummaries() {
        List<Author> authors = authorRepository.findAll();
        
        // Only access books for authors that need it
        return authors.stream()
            .filter(a -> a.isPopular())  // Filter first
            .map(author -> {
                int bookCount = author.getBooks().size();  // Lazy load here
                return new AuthorSummary(author.getName(), bookCount);
            })
            .collect(Collectors.toList());
        
        // @BatchSize: Loads books for filtered authors only (20-30 authors)
        // JOIN FETCH: Would load books for ALL 100 authors (wasteful!)
    }
}

// With JOIN FETCH (inefficient):
@Query("SELECT DISTINCT a FROM Author a LEFT JOIN FETCH a.books")
List<Author> findAllWithBooks();  // Loads 100 authors * avg 50 books = 5000 book records!

// With @BatchSize (efficient):
List<Author> findAll();  // Loads 100 authors
// Then loads books only for 30 filtered authors: 30 * 50 / 20 = 75 queries
// Still better than loading all 5000 books upfront
```

```java
                process(author);

            entityManager.clear();

        // 100x less memory usage!
```

### Q4: "How do you handle N+1 with pagination?"

**Answer**: Never use JOIN FETCH with pagination (loads all data into memory). Solution: 1) Fetch paginated IDs first, then fetch entities with relationships in second query, or 2) Use @BatchSize with standard pagination, or 3) Use window functions with native query, or 4) Use DTO projections with GROUP BY.

**Solution 1: Two-Query Approach (Most Reliable)**

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // Query 1: Fetch paginated IDs only
    @Query("SELECT a.id FROM Author a ORDER BY a.name")
    Page<Long> findAllIds(Pageable pageable);
    
    // Query 2: Fetch entities with relationships for specific IDs
    @Query("SELECT DISTINCT a FROM Author a LEFT JOIN FETCH a.books WHERE a.id IN :ids")
    List<Author> findByIdsWithBooks(@Param("ids") List<Long> ids);
}

@Service
public class PaginationService {
    
    @Autowired
    private AuthorRepository authorRepository;
    
    @Transactional(readOnly = true)
    public Page<AuthorWithBooks> getAuthorsWithBooks(Pageable pageable) {
        // Step 1: Paginate on IDs (fast, database-level)
        Page<Long> idPage = authorRepository.findAllIds(pageable);
        // SELECT id FROM authors ORDER BY name LIMIT 20 OFFSET 0;
        
        if (idPage.isEmpty()) {
            return Page.empty(pageable);
        }
        
        // Step 2: Fetch full entities with relationships
        List<Author> authors = authorRepository.findByIdsWithBooks(
            idPage.getContent()
        );
        // SELECT a.*, b.* FROM authors a 
        // LEFT JOIN books b ON a.id = b.author_id
        // WHERE a.id IN (1,2,3,...,20);
        
        // Step 3: Maintain order from ID page
        Map<Long, Author> authorMap = authors.stream()
            .collect(Collectors.toMap(Author::getId, a -> a));
        
        List<Author> orderedAuthors = idPage.getContent().stream()
            .map(authorMap::get)
            .collect(Collectors.toList());
        
        // Step 4: Convert to DTOs
        List<AuthorWithBooks> content = orderedAuthors.stream()
            .map(author -> new AuthorWithBooks(
                author.getName(),
                author.getBooks()
            ))
            .collect(Collectors.toList());
        
        return new PageImpl<>(content, pageable, idPage.getTotalElements());
        
        // Total: 2 queries
        // Pagination: True database-level pagination
        // Memory: Only 20 authors + their books
    }
}
```

**Solution 3: Window Functions (PostgreSQL-Specific)**

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    @Query(value = """
        WITH ranked_books AS (
            SELECT 
                a.id as author_id,
                a.name as author_name,
                b.id as book_id,
                b.title as book_title,
                b.isbn as book_isbn,
                ROW_NUMBER() OVER (ORDER BY a.name, a.id) as author_rank
            FROM authors a
            LEFT JOIN books b ON a.id = b.author_id
        )
        SELECT DISTINCT
            author_id,
            author_name,
            book_id,
            book_title,
            book_isbn
        FROM ranked_books
        WHERE author_rank > :offset 
          AND author_rank <= :offset + :limit
        ORDER BY author_rank, book_id
        """, nativeQuery = true)
    List<Object[]> findAuthorsWithBooksPaginated(
        @Param("offset") int offset,
        @Param("limit") int limit
    );
}

@Service
public class WindowFunctionPaginationService {
    
    @Transactional(readOnly = true)
    public Page<AuthorWithBooks> getAuthorsWithBooks(Pageable pageable) {
        int offset = (int) pageable.getOffset();
        int limit = pageable.getPageSize();
        
        // Single query with window function
        List<Object[]> rows = authorRepository.findAuthorsWithBooksPaginated(offset, limit);
        
        // Group by author
        Map<Long, AuthorWithBooks> authorMap = new LinkedHashMap<>();
        for (Object[] row : rows) {
            Long authorId = ((Number) row[0]).longValue();
            String authorName = (String) row[1];
            Long bookId = row[2] != null ? ((Number) row[2]).longValue() : null;
            
            AuthorWithBooks author = authorMap.computeIfAbsent(
                authorId,
                id -> new AuthorWithBooks(authorName, new ArrayList<>())
            );
            
            if (bookId != null) {
                author.getBooks().add(new BookDTO(
                    bookId,
                    (String) row[3],  // title
                    (String) row[4]   // isbn
                ));
            }
        }
        
        // Get total count (separate query or pass as parameter)
        long total = authorRepository.count();
        
        return new PageImpl<>(
            new ArrayList<>(authorMap.values()),
            pageable,
            total
        );
        
        // Single query! But complex SQL
    }
}
```

### Q5: "Explain the cartesian product problem with multiple JOIN FETCHes."

**Answer**: Multiple collection JOIN FETCHes create cartesian product: rows multiply across collections (10 books * 5 articles = 50 rows per author). Results in: massive data duplication, slow queries, high memory usage, and duplicate entities. Solution: separate queries, use @Fetch(SUBSELECT), or restructure with @BatchSize.

**The Problem Visualized**

### Q6: "How would you optimize a query with 3 levels of nested collections?"

**Answer**: Never use JOIN FETCH for deep nesting (exponential cartesian product). Solutions: 1) Fetch each level separately (3-4 queries), 2) Use @Fetch(SUBSELECT) at each level, 3) Use @BatchSize with controlled loading, 4) DTO projection with recursive CTEs or JSON aggregation, 5) Restructure data model (may need denormalization).

**The Problem**

```java
// Three levels of nesting
@Entity
public class Author {
    @OneToMany
    private List<Book> books;
}

@Entity
public class Book {
    @OneToMany
    private List<Chapter> chapters;
    
    @ManyToOne
    private Publisher publisher;
}

@Entity
public class Chapter {
    @OneToMany
    private List<Section> sections;
}

// Nightmare query (DON'T DO THIS!)
@Query("SELECT DISTINCT a FROM Author a " +
       "JOIN FETCH a.books b " +
       "JOIN FETCH b.chapters c " +
       "JOIN FETCH c.sections")
List<Author> findAllDeep();

// Cartesian product:
// 100 authors * 10 books * 20 chapters * 5 sections = 100,000 rows!
// Actual entities: 100 + 1,000 + 20,000 + 100,000 = 121,100
// But returned rows: 100,000 (massive duplication)
// Query timeout guaranteed!
```

**Solution 1: Separate Queries by Level**

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    // Level 1: Authors + Books
    @Query("SELECT DISTINCT a FROM Author a LEFT JOIN FETCH a.books")
    List<Author> findAllWithBooks();
    
    // Level 2: Books + Chapters (for specific books)
    @Query("SELECT DISTINCT b FROM Book b LEFT JOIN FETCH b.chapters WHERE b.id IN :ids")
    List<Book> findBooksWithChapters(@Param("ids") List<Long> bookIds);
    
    // Level 3: Chapters + Sections (for specific chapters)
    @Query("SELECT DISTINCT c FROM Chapter c LEFT JOIN FETCH c.sections WHERE c.id IN :ids")
    List<Chapter> findChaptersWithSections(@Param("ids") List<Long> chapterIds);
}

@Service
public class NestedLoadingService {
    
    @Transactional(readOnly = true)
    public List<Author> loadAuthorsWithFullHierarchy() {
        // Query 1: Load authors with books
        List<Author> authors = authorRepository.findAllWithBooks();
        // SELECT a.*, b.* FROM authors a LEFT JOIN books b ...
        // Rows: 1,000 (100 authors * 10 books)
        
        // Extract book IDs
        List<Long> bookIds = authors.stream()
            .flatMap(a -> a.getBooks().stream())
            .map(Book::getId)
            .collect(Collectors.toList());
        
        if (!bookIds.isEmpty()) {
            // Query 2: Load chapters for these books
            List<Book> booksWithChapters = bookRepository.findBooksWithChapters(bookIds);
            // SELECT b.*, c.* FROM books b LEFT JOIN chapters c ...
            // Rows: 20,000 (1,000 books * 20 chapters)
            
            // Extract chapter IDs
            List<Long> chapterIds = booksWithChapters.stream()
                .flatMap(b -> b.getChapters().stream())
                .map(Chapter::getId)
                .collect(Collectors.toList());
            
            if (!chapterIds.isEmpty()) {
                // Query 3: Load sections for these chapters
                chapterRepository.findChaptersWithSections(chapterIds);
                // SELECT c.*, s.* FROM chapters c LEFT JOIN sections s ...
                // Rows: 100,000 (20,000 chapters * 5 sections)
            }
        }
        
        // Total queries: 3
        // Total rows: 1,000 + 20,000 + 100,000 = 121,000 (optimal!)
        // No duplication, no cartesian product
        
        return authors;
    }
}
```

**Solution 4: DTO Projection with Recursive CTE**

```java
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    @Query(value = """
        WITH RECURSIVE hierarchy AS (
            -- Level 1: Authors
            SELECT 
                a.id::text as path,
                1 as level,
                'author' as type,
                a.id,
                a.name as title,
                NULL::bigint as parent_id
            FROM authors a
            
            UNION ALL
            
            -- Level 2: Books
            SELECT 
                h.path || '/' || b.id::text,
                2,
                'book',
                b.id,
                b.title,
                b.author_id
            FROM books b
            JOIN hierarchy h ON b.author_id = h.id AND h.level = 1
            
            UNION ALL
            
            -- Level 3: Chapters
            SELECT 
                h.path || '/' || c.id::text,
                3,
                'chapter',
                c.id,
                c.title,
                c.book_id
            FROM chapters c
            JOIN hierarchy h ON c.book_id = h.id AND h.level = 2
            
            UNION ALL
            
            -- Level 4: Sections
            SELECT 
                h.path || '/' || s.id::text,
                4,
                'section',
                s.id,
                s.title,
                s.chapter_id
            FROM sections s
            JOIN hierarchy h ON s.chapter_id = h.id AND h.level = 3
        )
        SELECT * FROM hierarchy ORDER BY path
        """, nativeQuery = true)
    List<HierarchyNode> findFullHierarchy();
}

// Build tree from flat structure
@Service
public class HierarchyBuilder {
    
    public List<AuthorNode> buildTree(List<HierarchyNode> nodes) {
        Map<Long, Object> nodeMap = new HashMap<>();
        List<AuthorNode> authors = new ArrayList<>();
        
        for (HierarchyNode node : nodes) {
            switch (node.getLevel()) {
                case 1:  // Author
                    AuthorNode author = new AuthorNode(node);
                    authors.add(author);
                    nodeMap.put(node.getId(), author);
                    break;
                case 2:  // Book
                    BookNode book = new BookNode(node);
                    ((AuthorNode) nodeMap.get(node.getParentId())).addBook(book);
                    nodeMap.put(node.getId(), book);
                    break;
                case 3:  // Chapter
                    ChapterNode chapter = new ChapterNode(node);
                    ((BookNode) nodeMap.get(node.getParentId())).addChapter(chapter);
                    nodeMap.put(node.getId(), chapter);
                    break;
                case 4:  // Section
                    SectionNode section = new SectionNode(node);
                    ((ChapterNode) nodeMap.get(node.getParentId())).addSection(section);
                    break;
            }
        }
        
        return authors;
        // Single query! But complex
    }
}
```

```java
@Entity
public class AuthorSummary {

    @Column(columnDefinition = "jsonb")
    private String fullHierarchyJson;  // Pre-computed JSON tree
}

CREATE MATERIALIZED VIEW author_hierarchy_mv AS
SELECT 
    a.id as author_id,
    a.name as author_name,
    JSON_AGG(
        JSON_BUILD_OBJECT(
            'id', b.id,
            'title', b.title,
            'chapters', (
                SELECT JSON_AGG(
                    JSON_BUILD_OBJECT(
                        'id', c.id,
                        'title', c.title,
                        'sections', (
                            SELECT JSON_AGG(
                                JSON_BUILD_OBJECT('id', s.id, 'title', s.title)
                            )
                            FROM sections s
                            WHERE s.chapter_id = c.id
                        )
                    )
                )
                FROM chapters c
                WHERE c.book_id = b.id
            )
        )
    ) as hierarchy
FROM authors a
LEFT JOIN books b ON a.id = b.author_id
GROUP BY a.id, a.name;

-- Refresh periodically
REFRESH MATERIALIZED VIEW CONCURRENTLY author_hierarchy_mv;

// Query materialized view (instant!)
```

### Q7: "What's the trade-off between DTO projections and entity fetching?"

**Answer**: DTO projections: faster (50-70% less time), less memory (no Hibernate overhead), read-only, more boilerplate. Entity fetching: change tracking, lazy loading, cascade operations, less code, but slower and more memory. Use DTOs for reports/APIs, entities for CRUD operations.

**Performance Comparison**

```java

        setupData(1000, 10);  // 1000 authors, 10 books each

        long entityTime = System.currentTimeMillis() - start;
        
        // Query: SELECT a.*, b.* FROM authors a LEFT JOIN books b ...
        // Time: 180ms
        // Memory: 45MB (entities + Hibernate metadata + proxies)
        // Features: change tracking, lazy loading, cascade
        
        // Test 2: DTO projection
        entityManager.clear();
        start = System.currentTimeMillis();
        List<AuthorDTO> dtos = authorRepository.findAllDTOs();
        long dtoTime = System.currentTimeMillis() - start;

        System.out.println("DTO projection:  " + dtoTime + "ms, 18MB");
        System.out.println("DTO is " + ((entityTime - dtoTime) * 100 / entityTime) + "% faster");
        
        // Results:

        // DTO: 85ms, 18MB
        // DTO is 53% faster, uses 60% less memory
    }
```

### Q8: "How do you prevent N+1 in a GraphQL API?"

**Answer**: GraphQL exacerbates N+1 because resolvers execute independently. Solutions: 1) DataLoader pattern (batching), 2) @EntityGraph with complexity analysis, 3) Projection root with JOIN FETCH, 4) Query depth limiting, 5) Persisted queries. DataLoader is standard solution - batches and caches field resolutions.

**The GraphQL N+1 Problem**

```java
// GraphQL schema
type Query {
    authors: [Author]
}

type Author {
    id: ID!
    name: String!
    books: [Book]  // This causes N+1!
}

type Book {
    id: ID!
    title: String!
}

// Naive resolver implementation (N+1 problem)
@Component
public class AuthorResolver implements GraphQLQueryResolver {
    
    @Autowired
    private AuthorRepository authorRepository;
    
    @Autowired
    private BookRepository bookRepository;
    
    // Root query
    public List<Author> authors() {
        return authorRepository.findAll();
        // Query 1: SELECT * FROM authors;
    }
    
    // Field resolver (called for EACH author!)
    public List<Book> books(Author author) {
        return bookRepository.findByAuthorId(author.getId());
        // Query 2, 3, 4, ..., N+1: SELECT * FROM books WHERE author_id = ?
        // Called 100 times for 100 authors!
    }
}

// GraphQL query:
"""
{
  authors {
    id
    name
    books {
      id
      title
    }
  }
}
"""

// Result: 1 + N queries (N+1 problem!)
```

**Solution 1: DataLoader (Standard Solution)**

```java
// DataLoader batches and caches

@Configuration
public class DataLoaderConfig {
    
    @Bean
    public DataLoader<Long, List<Book>> bookDataLoader(BookRepository bookRepository) {
        return DataLoader.newDataLoader(authorIds -> {
            // This is called ONCE for all author IDs in the batch
            Map<Long, List<Book>> booksByAuthor = bookRepository
                .findByAuthorIdIn(authorIds)
                .stream()
                .collect(Collectors.groupingBy(book -> book.getAuthor().getId()));
            
            // Return books in same order as authorIds
            return CompletableFuture.supplyAsync(() ->
                authorIds.stream()
                    .map(id -> booksByAuthor.getOrDefault(id, Collections.emptyList()))
                    .collect(Collectors.toList())
            );
        }, DataLoaderOptions.newOptions()
            .setBatchingEnabled(true)
            .setCachingEnabled(true)
            .setMaxBatchSize(100)
        );
    }
}

@Component
public class AuthorResolver implements GraphQLQueryResolver {
    
    @Autowired
    private DataLoaderRegistry dataLoaderRegistry;
    
    public List<Author> authors() {
        return authorRepository.findAll();
        // Query 1: SELECT * FROM authors;
    }
    
    public CompletableFuture<List<Book>> books(Author author, DataFetchingEnvironment env) {
        DataLoader<Long, List<Book>> loader = env.getDataLoader("bookDataLoader");
        return loader.load(author.getId());
        // Batches all author IDs, then calls:
        // Query 2: SELECT * FROM books WHERE author_id IN (1, 2, 3, ..., 100);
        // Total: 2 queries!
    }
}

// How DataLoader works:
// 1. Collects all author IDs from current execution round
// 2. Waits for current round to complete
// 3. Calls batch function ONCE with all IDs
// 4. Returns results to individual resolvers
// 5. Caches results for subsequent calls
```

```java
            // Simple query
        }
```

**GraphQL vs REST N+1 Comparison**

```
REST API:
- Controlled endpoints
- Server decides what to fetch
- Easy to optimize (fixed queries)
- N+1 less common (can use JOIN FETCH)

GraphQL API:
- Dynamic queries
- Client decides what to fetch
- Hard to optimize (variable queries)
- N+1 very common (nested resolvers)
- Requires DataLoader pattern

Solution:
- Always use DataLoader
- Analyze selection set
- Limit query complexity
- Consider persisted queries
```
