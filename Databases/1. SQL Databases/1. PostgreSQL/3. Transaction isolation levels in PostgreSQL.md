# PostgreSQL Transaction Isolation Levels in Spring Boot

## Deep Dive Interview Guide

This guide covers transaction isolation levels in PostgreSQL with Spring Boot, including isolation configurations, concurrency anomalies, locking strategies, and performance implications.

**Interview Tip**: Transaction isolation questions test understanding of database concurrency, ACID properties, and data consistency trade-offs.

---

## Q3: Transaction isolation levels in PostgreSQL

**Short Answer**: PostgreSQL supports four isolation levels (READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE) but effectively implements three (READ UNCOMMITTED behaves as READ COMMITTED). Default is READ COMMITTED, which prevents dirty reads but allows non-repeatable reads and phantom reads. Use `@Transactional(isolation = Isolation.SERIALIZABLE)` for strongest consistency. Choose based on consistency needs vs performance: READ COMMITTED (fastest, 95% of cases), REPEATABLE READ (snapshot isolation), SERIALIZABLE (slowest, full isolation).

---

## 1. Understanding the Four Isolation Levels

### Overview Table

|Isolation Level|Dirty Reads|Non-Repeatable Reads|Phantom Reads|Performance|Use Cases|
|---|---|---|---|---|---|
|**READ UNCOMMITTED**|❌*|Yes|Yes|Fastest|N/A (PostgreSQL treats as READ COMMITTED)|
|**READ COMMITTED**|No|Yes|Yes|Fast|Default, most applications (95%)|
|**REPEATABLE READ**|No|No|No**|Medium|Financial transactions, reports|
|**SERIALIZABLE**|No|No|No|Slowest|Critical operations, compliance|

* PostgreSQL doesn't allow dirty reads even in READ UNCOMMITTED  
** PostgreSQL's REPEATABLE READ prevents phantom reads (stronger than SQL standard)

## 2. READ UNCOMMITTED

**Definition**: Allows reading uncommitted changes from other transactions (in theory).

**PostgreSQL Reality**: Treated as READ COMMITTED. PostgreSQL never allows dirty reads.

```java
// Configuration (behaves as READ COMMITTED in PostgreSQL)
@Transactional(isolation = Isolation.READ_UNCOMMITTED)
public void processOrder(Long orderId) {
    // In PostgreSQL, this is equivalent to READ_COMMITTED
    // No dirty reads possible
}
```

```sql
-- SQL equivalent
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
-- PostgreSQL upgrades this to READ COMMITTED automatically
```

**Why PostgreSQL Doesn't Support True READ UNCOMMITTED:**

```java
// PostgreSQL's MVCC (Multi-Version Concurrency Control) architecture
// makes READ UNCOMMITTED impossible without significant performance penalty

// PostgreSQL always works with committed snapshots
// Each transaction sees a consistent snapshot of data
// Uncommitted changes are stored separately and invisible to other transactions

// Result: READ UNCOMMITTED = READ COMMITTED in PostgreSQL
```

## 3. READ COMMITTED (Default)

**Definition**: Transactions can only read committed data. Each query sees a fresh snapshot.

**This is PostgreSQL's default** and recommended for most applications.

### Configuration

```java
// Default (no annotation needed)
@Transactional  // Uses READ COMMITTED by default
public void updateInventory(Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.setQuantity(product.getQuantity() - quantity);
    productRepository.save(product);
}

// Explicit configuration
@Transactional(isolation = Isolation.READ_COMMITTED)
public void processPayment(Long orderId) {
    // Each query sees latest committed data
}
```

```yaml
# application.yml - Set default isolation level
spring:
  jpa:
    properties:
      hibernate:
        connection:
          isolation: 2  # READ_COMMITTED (JDBC constant)
```

```sql
-- SQL equivalent
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Check current isolation level
SHOW transaction_isolation;
-- Output: read committed
```

### What READ COMMITTED Allows

```java
// Example: Non-repeatable reads (allowed)

@Service
public class OrderService {
    
    @Autowired
    private EntityManager entityManager;
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void demonstrateNonRepeatableRead(Long orderId) {
        // First read
        Order order1 = entityManager.find(Order.class, orderId);
        BigDecimal price1 = order1.getPrice();
        System.out.println("First read: " + price1);  // $100
        
        // Another transaction commits a price change here
        // (e.g., another user updates the price to $150)
        
        // Simulate delay
        try { Thread.sleep(5000); } catch (InterruptedException e) {}
        
        // Second read (within same transaction)
        entityManager.refresh(order1);  // Force reload
        BigDecimal price2 = order1.getPrice();
        System.out.println("Second read: " + price2);  // $150 (changed!)
        
        // Non-repeatable read: same query, different result
        // This is ALLOWED in READ COMMITTED
    }
}
```

```java
// Example: Phantom reads (allowed)

@Service
public class ReportService {
    
    @Autowired
    private OrderRepository orderRepository;
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void demonstratePhantomRead() {
        // First query: Count orders
        long count1 = orderRepository.count();
        System.out.println("First count: " + count1);  // 10 orders
        
        // Another transaction inserts a new order here
        
        // Simulate delay
        try { Thread.sleep(5000); } catch (InterruptedException e) {}
        
        // Second query: Count again
        long count2 = orderRepository.count();
        System.out.println("Second count: " + count2);  // 11 orders (increased!)
        
        // Phantom read: new rows appeared
        // This is ALLOWED in READ COMMITTED
    }
}
```

### Real-World Example

```java
@Service
public class BankTransferService {
    
    @Autowired
    private AccountRepository accountRepository;
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void transfer(Long fromAccountId, Long toAccountId, BigDecimal amount) {
        // This is SAFE with READ COMMITTED because:
        // 1. We read committed data only
        // 2. We hold locks on the rows we modify
        // 3. Other transactions see our changes only after commit
        
        Account fromAccount = accountRepository.findById(fromAccountId)
            .orElseThrow();
        Account toAccount = accountRepository.findById(toAccountId)
            .orElseThrow();
        
        // Check balance
        if (fromAccount.getBalance().compareTo(amount) < 0) {
            throw new InsufficientFundsException();
        }
        
        // Perform transfer
        fromAccount.setBalance(fromAccount.getBalance().subtract(amount));
        toAccount.setBalance(toAccount.getBalance().add(amount));
        
        accountRepository.save(fromAccount);
        accountRepository.save(toAccount);
        
        // Both updates are atomic
        // Other transactions see changes only after commit
    }
}
```

```java
// ✅ Web applications
// ✅ Microservices
// ✅ Most business logic

// Examples:
// - User registration
// - Product catalog updates
// - Order creation
// - Profile updates
// - Comment posting
```

## 4. REPEATABLE READ

**Definition**: Transactions see a consistent snapshot of data throughout their lifetime. Prevents non-repeatable reads.

**PostgreSQL Enhancement**: Also prevents phantom reads (stronger than SQL standard).

### Configuration

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void generateFinancialReport(LocalDate date) {
    // All queries see the same consistent snapshot
    // Even if other transactions commit changes
}
```

```sql
-- SQL equivalent
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM accounts WHERE balance > 1000;
-- Other transactions commit changes here
SELECT * FROM accounts WHERE balance > 1000;
-- Same results as first query (snapshot isolation)
COMMIT;
```

### What REPEATABLE READ Prevents

```java
// Example: No non-repeatable reads

@Service
public class ConsistentReadService {
    
    @Autowired
    private EntityManager entityManager;
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void demonstrateRepeatableRead(Long orderId) {
        // First read
        Order order1 = entityManager.find(Order.class, orderId);
        BigDecimal price1 = order1.getPrice();
        System.out.println("First read: " + price1);  // $100
        
        // Another transaction commits a price change here
        // (e.g., changes price to $150)
        
        // Simulate delay
        try { Thread.sleep(5000); } catch (InterruptedException e) {}
        
        // Second read (within same transaction)
        entityManager.clear();  // Clear persistence context
        Order order2 = entityManager.find(Order.class, orderId);
        BigDecimal price2 = order2.getPrice();
        System.out.println("Second read: " + price2);  // Still $100!
        
        // Repeatable read: same value even though other transaction committed
        // Transaction sees its own snapshot
    }
}
```

```java
// Example: No phantom reads (PostgreSQL-specific)

@Service
public class SnapshotReportService {
    
    @Autowired
    private OrderRepository orderRepository;
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void demonstrateNoPhantomReads() {
        // First query: Count orders
        long count1 = orderRepository.countByStatus(OrderStatus.PENDING);
        System.out.println("First count: " + count1);  // 10 orders
        
        // Another transaction inserts a new pending order here
        
        // Simulate delay
        try { Thread.sleep(5000); } catch (InterruptedException e) {}
        
        // Second query: Count again
        long count2 = orderRepository.countByStatus(OrderStatus.PENDING);
        System.out.println("Second count: " + count2);  // Still 10!
        
        // No phantom read: transaction sees consistent snapshot
        // Even though new row was inserted by another transaction
    }
}
```

### Serialization Failures

```java
// REPEATABLE READ can fail with serialization errors

@Service
public class ConcurrentUpdateService {
    
    @Autowired
    private ProductRepository productRepository;
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void updateInventory(Long productId, int quantity) {
        try {
            Product product = productRepository.findById(productId).orElseThrow();
            
            // Check if enough inventory
            if (product.getQuantity() < quantity) {
                throw new InsufficientInventoryException();
            }
            
            // Update inventory
            product.setQuantity(product.getQuantity() - quantity);
            productRepository.save(product);
            
        } catch (DataIntegrityViolationException e) {
            // If another transaction modified the same row
            // PostgreSQL throws: "could not serialize access due to concurrent update"
            throw new ConcurrentModificationException("Product was modified by another transaction");
        }
    }
}

// Handling serialization failures
@Service
public class RetryableService {
    
    @Retryable(
        value = ConcurrentModificationException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 100)
    )
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void updateWithRetry(Long productId, int quantity) {
        // Automatically retries on serialization failure
        // Up to 3 times with 100ms delay
    }
}
```

### Real-World Use Cases

```java
// Use Case 1: Financial reports

@Service
public class FinancialReportService {
    
    @Autowired
    private TransactionRepository transactionRepository;
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public FinancialReport generateMonthlyReport(YearMonth month) {
        // Ensure all queries see consistent data
        // Even if transactions are being processed
        
        LocalDateTime start = month.atDay(1).atStartOfDay();
        LocalDateTime end = month.atEndOfMonth().atTime(23, 59, 59);
        
        // All these queries see the same snapshot
        BigDecimal totalRevenue = transactionRepository
            .sumAmountByTypeAndDateBetween(TransactionType.REVENUE, start, end);
        
        BigDecimal totalExpenses = transactionRepository
            .sumAmountByTypeAndDateBetween(TransactionType.EXPENSE, start, end);
        
        long transactionCount = transactionRepository
            .countByDateBetween(start, end);
        
        return FinancialReport.builder()
            .month(month)
            .revenue(totalRevenue)
            .expenses(totalExpenses)
            .transactionCount(transactionCount)
            .netIncome(totalRevenue.subtract(totalExpenses))
            .build();
    }
}

// Use Case 2: Multi-step calculations

@Service
public class PricingService {
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public BigDecimal calculateOrderTotal(Long orderId) {
        // Ensure prices don't change during calculation
        
        Order order = orderRepository.findById(orderId).orElseThrow();
        
        // Calculate subtotal
        BigDecimal subtotal = order.getItems().stream()
            .map(item -> item.getPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        
        // Get discount (must be consistent)
        BigDecimal discount = discountService.calculateDiscount(order);
        
        // Get tax rate (must be consistent)
        BigDecimal taxRate = taxService.getTaxRate(order.getShippingAddress());
        
        // Calculate final total
        BigDecimal afterDiscount = subtotal.subtract(discount);
        BigDecimal tax = afterDiscount.multiply(taxRate);
        BigDecimal total = afterDiscount.add(tax);
        
        return total;
    }
}
```

## 5. SERIALIZABLE

**Definition**: Strongest isolation. Transactions execute as if they were serial (one after another).

**Trade-off**: Slowest performance, highest consistency.

### Configuration

```java
@Transactional(isolation = Isolation.SERIALIZABLE)
public void criticalOperation() {
    // Highest consistency guarantees
    // No concurrency anomalies possible
}
```

```sql
-- SQL equivalent
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- All operations here are serializable
COMMIT;
```

### How SERIALIZABLE Works

```java
// PostgreSQL uses Serializable Snapshot Isolation (SSI)

@Service
public class SerializableExampleService {
    
    @Autowired
    private AccountRepository accountRepository;
    
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        // PostgreSQL tracks read/write dependencies
        // Detects conflicts that would violate serializability
        
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();
        
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
        
        // If conflict detected, transaction aborts with:
        // "could not serialize access due to read/write dependencies"
    }
}
```

### Serialization Failures

```java
@Service
public class SerializationFailureHandler {
    
    @Retryable(
        value = SerializationException.class,
        maxAttempts = 5,
        backoff = @Backoff(delay = 200, multiplier = 2)
    )
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void performCriticalOperation(Long id) {
        try {
            // Critical operation
            // ...
        } catch (DataIntegrityViolationException e) {
            if (e.getMessage().contains("could not serialize")) {
                throw new SerializationException("Serialization conflict", e);
            }
            throw e;
        }
    }
}

// Custom exception for retries
public class SerializationException extends RuntimeException {
    public SerializationException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

### Real-World Use Cases

```java
// Use Case 1: Seat reservation system

@Service
public class SeatReservationService {
    
    @Autowired
    private SeatRepository seatRepository;
    
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void reserveSeat(Long showId, String seatNumber, Long userId) {
        // Prevent double-booking with absolute certainty
        
        Seat seat = seatRepository.findByShowIdAndSeatNumber(showId, seatNumber)
            .orElseThrow();
        
        if (seat.isReserved()) {
            throw new SeatAlreadyReservedException();
        }
        
        seat.setReserved(true);
        seat.setUserId(userId);
        seat.setReservedAt(LocalDateTime.now());
        
        seatRepository.save(seat);
        
        // Guaranteed no race conditions
        // If two transactions try to book same seat,
        // one will succeed, other will get serialization error
    }
}

// Use Case 2: Inventory with complex constraints

@Service
public class InventoryService {
    
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void allocateInventory(Order order) {
        // Ensure complex business rules are enforced
        // across multiple products
        
        for (OrderItem item : order.getItems()) {
            Product product = productRepository.findById(item.getProductId())
                .orElseThrow();
            
            // Complex rule: Total allocated inventory across all orders
            // for premium products cannot exceed 80% of stock
            if (product.isPremium()) {
                long totalAllocated = orderItemRepository
                    .sumQuantityByProductIdAndOrderStatus(
                        product.getId(), 
                        OrderStatus.PENDING
                    );
                
                long maxAllowed = (long) (product.getQuantity() * 0.8);
                
                if (totalAllocated + item.getQuantity() > maxAllowed) {
                    throw new AllocationLimitExceededException();
                }
            }
            
            // Allocate inventory
            product.setQuantity(product.getQuantity() - item.getQuantity());
            productRepository.save(product);
        }
        
        // All constraints enforced with serializable isolation
    }
}

// Use Case 3: Accounting systems

@Service
public class AccountingService {
    
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void postJournalEntry(JournalEntry entry) {
        // Ensure double-entry bookkeeping integrity
        
        BigDecimal debitTotal = BigDecimal.ZERO;
        BigDecimal creditTotal = BigDecimal.ZERO;
        
        for (JournalLine line : entry.getLines()) {
            Account account = accountRepository.findById(line.getAccountId())
                .orElseThrow();
            
            if (line.isDebit()) {
                account.setBalance(account.getBalance().add(line.getAmount()));
                debitTotal = debitTotal.add(line.getAmount());
            } else {
                account.setBalance(account.getBalance().subtract(line.getAmount()));
                creditTotal = creditTotal.add(line.getAmount());
            }
            
            accountRepository.save(account);
        }
        
        // Verify debits = credits
        if (debitTotal.compareTo(creditTotal) != 0) {
            throw new UnbalancedEntryException();
        }
        
        // Save journal entry
        journalEntryRepository.save(entry);
        
        // Serializable ensures no concurrent transactions
        // can violate accounting invariants
    }
}
```

## 6. Concurrency Anomalies Explained

### Dirty Read

**Definition**: Reading uncommitted changes from another transaction.

```java
// Scenario: Bank balance check

// Transaction A (Transfer):
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Not committed yet

// Transaction B (Balance check):
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Reads 900 (uncommitted)
COMMIT;

// Transaction A:
ROLLBACK;  -- Transfer cancelled, balance back to 1000

// Result: Transaction B saw balance of 900, but actual balance is 1000
// This is a DIRTY READ

// PostgreSQL: NEVER allows dirty reads (even in READ UNCOMMITTED)
```

### Non-Repeatable Read

**Definition**: Reading the same row twice and getting different values.

```java
@Service
public class NonRepeatableReadExample {
    
    @Autowired
    private EntityManager entityManager;
    
    // Transaction A: READ COMMITTED
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void checkPriceConsistency(Long productId) {
        // Read 1
        Product product1 = entityManager.find(Product.class, productId);
        BigDecimal price1 = product1.getPrice();  // $100
        
        // --- Transaction B commits price change to $150 ---
        
        // Read 2 (same transaction, same row)
        entityManager.refresh(product1);
        BigDecimal price2 = product1.getPrice();  // $150 (different!)
        
        // Non-repeatable read: same row, different value
        // Allowed in READ COMMITTED
        // Prevented in REPEATABLE READ and SERIALIZABLE
    }
}
```

```sql
-- SQL demonstration

-- Transaction A:
BEGIN;
SELECT price FROM products WHERE id = 1;  -- Returns 100
-- Wait...

-- Transaction B (concurrent):
BEGIN;
UPDATE products SET price = 150 WHERE id = 1;
COMMIT;

-- Transaction A (continues):
SELECT price FROM products WHERE id = 1;  -- Returns 150 (changed!)
COMMIT;

-- With READ COMMITTED: Non-repeatable read occurs
-- With REPEATABLE READ: Both queries return 100
```

### Phantom Read

**Definition**: Executing the same query twice and getting different row sets.

```java
@Service
public class PhantomReadExample {
    
    @Autowired
    private OrderRepository orderRepository;
    
    // Transaction A: READ COMMITTED
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void analyzeOrders() {
        // Query 1
        List<Order> orders1 = orderRepository.findByStatus(OrderStatus.PENDING);
        int count1 = orders1.size();  // 10 orders
        
        // --- Transaction B inserts a new pending order ---
        
        // Query 2 (same transaction, same query)
        List<Order> orders2 = orderRepository.findByStatus(OrderStatus.PENDING);
        int count2 = orders2.size();  // 11 orders (new row appeared!)
        
        // Phantom read: new row "appeared" (phantom)
        // Allowed in READ COMMITTED
        // Prevented in REPEATABLE READ and SERIALIZABLE (PostgreSQL)
    }
}
```

```sql
-- SQL demonstration

-- Transaction A:
BEGIN;
SELECT * FROM orders WHERE status = 'PENDING';  -- Returns 10 rows
-- Wait...

-- Transaction B (concurrent):
BEGIN;
INSERT INTO orders (status, ...) VALUES ('PENDING', ...);
COMMIT;

-- Transaction A (continues):
SELECT * FROM orders WHERE status = 'PENDING';  -- Returns 11 rows (phantom!)
COMMIT;

-- With READ COMMITTED: Phantom read occurs
-- With REPEATABLE READ (PostgreSQL): Both queries return 10 rows
```

### Summary Table

|Anomaly|Description|READ COMMITTED|REPEATABLE READ|SERIALIZABLE|
|---|---|---|---|---|
|**Dirty Read**|Read uncommitted data|❌ Prevented|❌ Prevented|❌ Prevented|
|**Non-Repeatable Read**|Same row, different value|✅ Possible|❌ Prevented|❌ Prevented|
|**Phantom Read**|Different row set|✅ Possible|❌ Prevented*|❌ Prevented|

* PostgreSQL's REPEATABLE READ prevents phantom reads (stronger than SQL standard)

```java

    // Uses READ COMMITTED

@Transactional(
    isolation = Isolation.SERIALIZABLE,
    timeout = 30,  // 30 seconds
    rollbackFor = Exception.class,
    propagation = Propagation.REQUIRED

    // Complex transaction configuration
}
```

### Isolation Levels Enum

```java
public enum Isolation {
    DEFAULT(-1),           // Use database default
    READ_UNCOMMITTED(1),   // PostgreSQL: treated as READ COMMITTED
    READ_COMMITTED(2),     // PostgreSQL default
    REPEATABLE_READ(4),    // Snapshot isolation
    SERIALIZABLE(8);       // Full serialization
    
    private final int value;
}
```

## 8. Optimistic vs Pessimistic Locking

### Optimistic Locking

**Strategy**: Assume conflicts are rare. Check for conflicts at commit time.

```java
@Entity
@Table(name = "products")
public class Product {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;
    private BigDecimal price;
    private Integer quantity;
    
    // Optimistic locking with version
    @Version
    private Long version;  // Automatically managed by JPA
    
    // When updating, JPA checks:
    // UPDATE products 
    // SET name = ?, price = ?, quantity = ?, version = version + 1
    // WHERE id = ? AND version = ?
    //
    // If version doesn't match, throws OptimisticLockException
}

@Service
public class OptimisticLockingService {
    
    @Autowired
    private ProductRepository productRepository;
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void updateProductWithOptimisticLock(Long productId, BigDecimal newPrice) {
        try {
            Product product = productRepository.findById(productId).orElseThrow();
            
            // Version: 1
            product.setPrice(newPrice);
            
            // Save checks version
            // If another transaction updated (version now 2),
            // this will throw OptimisticLockException
            productRepository.save(product);
            
        } catch (OptimisticLockException e) {
            // Handle conflict
            throw new ConcurrentModificationException(
                "Product was modified by another user", e
            );
        }
    }
    
    // Retry on conflict
    @Retryable(
        value = ConcurrentModificationException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 100)
    )
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void updateWithRetry(Long productId, BigDecimal newPrice) {
        // Automatically retries on OptimisticLockException
        Product product = productRepository.findById(productId).orElseThrow();
        product.setPrice(newPrice);
        productRepository.save(product);
    }
}
```

**Pros and Cons:**

```java
// ✅ Pros:
// - No database locks held during transaction
// - Better concurrency (no blocking)
// - Better performance for read-heavy workloads
// - Works well with READ COMMITTED

// ❌ Cons:
// - Conflicts detected only at commit time
// - Work may be wasted if conflict occurs
// - Requires retry logic
// - Not suitable for high-contention scenarios
```

### Pessimistic Locking

**Strategy**: Acquire locks immediately. Block concurrent access.

```java
@Repository
public interface ProductRepository extends JpaRepository<Product, Long> {
    
    // Pessimistic read lock (shared lock)
    @Lock(LockModeType.PESSIMISTIC_READ)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdWithReadLock(@Param("id") Long id);
    
    // Pessimistic write lock (exclusive lock)
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdWithWriteLock(@Param("id") Long id);
    
    // Pessimistic force increment (exclusive lock + version increment)
    @Lock(LockModeType.PESSIMISTIC_FORCE_INCREMENT)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdWithForceIncrementLock(@Param("id") Long id);
}

@Service
public class PessimisticLockingService {
    
    @Autowired
    private ProductRepository productRepository;
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void updateProductWithPessimisticLock(Long productId, BigDecimal newPrice) {
        // Acquire exclusive lock immediately
        // Other transactions will block here until lock is released
        Product product = productRepository.findByIdWithWriteLock(productId)
            .orElseThrow();
        
        // No one else can read or modify this row
        product.setPrice(newPrice);
        
        productRepository.save(product);
        
        // Lock released on commit
    }
    
    // Lock with timeout
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void updateWithTimeout(Long productId, BigDecimal newPrice) {
        try {
            // Set lock timeout
            entityManager.setProperty("javax.persistence.lock.timeout", 5000); // 5 seconds
            
            Product product = productRepository.findByIdWithWriteLock(productId)
                .orElseThrow();
            
            product.setPrice(newPrice);
            productRepository.save(product);
            
        } catch (PessimisticLockException e) {
            throw new LockTimeoutException("Could not acquire lock within timeout");
        }
    }
}
```

**SQL Equivalent:**

```sql
-- Pessimistic read lock (FOR SHARE)
SELECT * FROM products WHERE id = 1 FOR SHARE;
-- Allows other transactions to read with FOR SHARE
-- Blocks transactions trying to acquire FOR UPDATE

-- Pessimistic write lock (FOR UPDATE)
SELECT * FROM products WHERE id = 1 FOR UPDATE;
-- Blocks all other transactions from reading or writing
-- Most restrictive

-- With NOWAIT
SELECT * FROM products WHERE id = 1 FOR UPDATE NOWAIT;
-- Fails immediately if lock cannot be acquired

-- With SKIP LOCKED
SELECT * FROM products WHERE id IN (1, 2, 3) FOR UPDATE SKIP LOCKED;
-- Skips locked rows, returns only unlocked rows
```

**Pros and Cons:**

```java
// ✅ Pros:
// - Conflicts prevented upfront (no wasted work)
// - Guaranteed consistency
// - Suitable for high-contention scenarios
// - Simple logic (no retries needed)

// ❌ Cons:
// - Holds database locks (reduces concurrency)
// - Potential deadlocks
// - Slower for low-contention scenarios
// - Can cause thread blocking
```

### Comparison Table

|Aspect|Optimistic Locking|Pessimistic Locking|
|---|---|---|
|**Lock Acquisition**|At commit time|Immediately|
|**Concurrency**|High|Low|
|**Performance**|Better (low contention)|Worse (high blocking)|
|**Conflicts**|Detected late|Prevented early|
|**Retry Logic**|Required|Not required|
|**Use Cases**|Read-heavy, low contention|Write-heavy, high contention|
|**Deadlock Risk**|Low|High|
|**Implementation**|@Version annotation|@Lock annotation|

### When to Use Each

```java
// Use OPTIMISTIC LOCKING when:
// ✅ Read-heavy workloads (95% reads, 5% writes)
// ✅ Low contention on same records
// ✅ Long-running transactions (user think time)
// ✅ Can tolerate retry logic
// Examples: E-commerce product catalog, blog posts, user profiles

// Use PESSIMISTIC LOCKING when:
// ✅ Write-heavy workloads
// ✅ High contention on same records
// ✅ Short transactions
// ✅ Cannot tolerate conflicts
// Examples: Seat reservation, inventory allocation, ticket sales
```

### Q1: "How would you debug a serialization failure in production?"

**Answer**: Use systematic approach: capture error details, analyze transaction patterns with pg_stat_statements, identify conflicting transactions, review isolation level necessity, add retry logic, and monitor with metrics. PostgreSQL's log_lock_waits helps identify blocking queries.

**Step 1: Capture and Log Serialization Errors**

```java
@Aspect
@Component
@Slf4j
public class SerializationFailureAspect {
    
    @Autowired
    private MeterRegistry meterRegistry;
    
    private final Counter serializationFailures = Counter.builder("db.serialization.failures")
        .description("Count of serialization failures")
        .register(meterRegistry);
    
    @AfterThrowing(
        pointcut = "@annotation(org.springframework.transaction.annotation.Transactional)",
        throwing = "exception"
    )
    public void handleSerializationFailure(JoinPoint joinPoint, Throwable exception) {
        // Check if it's a serialization failure
        if (isSerializationFailure(exception)) {
            serializationFailures.increment();
            
            String methodName = joinPoint.getSignature().toShortString();
            Object[] args = joinPoint.getArgs();
            
            // Log detailed information
            log.error("Serialization failure in method: {}", methodName);
            log.error("Arguments: {}", Arrays.toString(args));
            log.error("Root cause: {}", getRootCause(exception).getMessage());
            log.error("Stack trace: ", exception);
            
            // Capture transaction context
            logTransactionContext(joinPoint);
        }
    }
    
    private boolean isSerializationFailure(Throwable exception) {
        String message = exception.getMessage();
        return message != null && (
            message.contains("could not serialize") ||
            message.contains("serialization failure") ||
            message.contains("deadlock detected")
        );
    }
    
    private Throwable getRootCause(Throwable exception) {
        Throwable cause = exception;
        while (cause.getCause() != null) {
            cause = cause.getCause();
        }
        return cause;
    }
    
    private void logTransactionContext(JoinPoint joinPoint) {
        try {
            // Log isolation level
            Connection conn = DataSourceUtils.getConnection(dataSource);
            int isolationLevel = conn.getTransactionIsolation();
            log.error("Transaction isolation level: {}", 
                     getIsolationLevelName(isolationLevel));
            
            // Log transaction status
            if (TransactionSynchronizationManager.isActualTransactionActive()) {
                log.error("Active transaction detected");
                log.error("Transaction read-only: {}", 
                         TransactionSynchronizationManager.isCurrentTransactionReadOnly());
            }
        } catch (Exception e) {
            log.error("Failed to capture transaction context", e);
        }
    }
    
    private String getIsolationLevelName(int level) {
        return switch (level) {
            case Connection.TRANSACTION_READ_UNCOMMITTED -> "READ_UNCOMMITTED";
            case Connection.TRANSACTION_READ_COMMITTED -> "READ_COMMITTED";
            case Connection.TRANSACTION_REPEATABLE_READ -> "REPEATABLE_READ";
            case Connection.TRANSACTION_SERIALIZABLE -> "SERIALIZABLE";
            default -> "UNKNOWN";
        };
    }
}
```

**Step 4: Review Isolation Level Necessity**

```java
@Component
public class IsolationLevelAnalyzer {
    
    public IsolationRecommendation analyzeMethod(Method method) {
        Transactional annotation = method.getAnnotation(Transactional.class);
        
        if (annotation == null) {
            return IsolationRecommendation.NOT_TRANSACTIONAL;
        }
        
        Isolation isolation = annotation.isolation();
        
        // Check if SERIALIZABLE is really needed
        if (isolation == Isolation.SERIALIZABLE) {
            // Analyze method to see if it can be downgraded
            if (isSimpleCRUD(method)) {
                return IsolationRecommendation.builder()
                    .current(Isolation.SERIALIZABLE)
                    .recommended(Isolation.READ_COMMITTED)
                    .reason("Simple CRUD operation doesn't need SERIALIZABLE")
                    .build();
            }
            
            if (isReadOnly(method)) {
                return IsolationRecommendation.builder()
                    .current(Isolation.SERIALIZABLE)
                    .recommended(Isolation.REPEATABLE_READ)
                    .reason("Read-only operation doesn't need SERIALIZABLE")
                    .build();
            }
        }
        
        // Check if REPEATABLE_READ is really needed
        if (isolation == Isolation.REPEATABLE_READ) {
            if (isSimpleCRUD(method)) {
                return IsolationRecommendation.builder()
                    .current(Isolation.REPEATABLE_READ)
                    .recommended(Isolation.READ_COMMITTED)
                    .reason("Simple CRUD operation doesn't need REPEATABLE_READ")
                    .build();
            }
        }
        
        return IsolationRecommendation.APPROPRIATE;
    }
    
    private boolean isSimpleCRUD(Method method) {
        // Check if method just does save/update/delete
        String methodName = method.getName();
        return methodName.startsWith("save") ||
               methodName.startsWith("update") ||
               methodName.startsWith("create") ||
               methodName.startsWith("delete");
    }
    
    private boolean isReadOnly(Method method) {
        Transactional annotation = method.getAnnotation(Transactional.class);
        return annotation != null && annotation.readOnly();
    }
}

@Data
@Builder
class IsolationRecommendation {
    private Isolation current;
    private Isolation recommended;
    private String reason;
    
    public static final IsolationRecommendation NOT_TRANSACTIONAL = 
        IsolationRecommendation.builder()
            .reason("Method is not transactional")
            .build();
    
    public static final IsolationRecommendation APPROPRIATE = 
        IsolationRecommendation.builder()
            .reason("Current isolation level is appropriate")
            .build();
}
```

```java
        RetryTemplate retryTemplate = new RetryTemplate();
        
        // Retry policy: exponential backoff
        ExponentialBackOffPolicy backOffPolicy = new ExponentialBackOffPolicy();
        backOffPolicy.setInitialInterval(100);  // Start with 100ms
        backOffPolicy.setMultiplier(2.0);       // Double each time
        backOffPolicy.setMaxInterval(2000);     // Cap at 2 seconds
        
        // Retry up to 5 times
        SimpleRetryPolicy retryPolicy = new SimpleRetryPolicy();
        retryPolicy.setMaxAttempts(5);
        
        retryTemplate.setBackOffPolicy(backOffPolicy);
        retryTemplate.setRetryPolicy(retryPolicy);
        
        // Add listeners for monitoring
        retryTemplate.registerListener(new RetryListenerSupport() {
            @Override
            public <T, E extends Throwable> void onError(
                    RetryContext context, 
                    RetryCallback<T, E> callback, 
                    Throwable throwable) {
                
                log.warn("Retry attempt {} failed: {}", 
                        context.getRetryCount(), 
                        throwable.getMessage());
            }
        });
        
        return retryTemplate;
    }
}
```

### Q2: "Explain the difference between snapshot isolation and serializable isolation."

**Answer**: Snapshot isolation (PostgreSQL's REPEATABLE READ) provides consistent view of data as it existed at transaction start, preventing non-repeatable and phantom reads but allowing write skew. Serializable isolation additionally detects write-write conflicts that could violate serializability, using Serializable Snapshot Isolation (SSI) to track read/write dependencies.

**Snapshot Isolation (REPEATABLE READ)**

```java
// Snapshot isolation: Each transaction sees consistent snapshot

@Service
public class SnapshotIsolationExample {
    
    @Autowired
    private AccountRepository accountRepository;
    
    // Transaction 1: Transfer from A to B
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void transaction1() {
        // Snapshot created at transaction start
        
        Account accountA = accountRepository.findById(1L).orElseThrow();
        Account accountB = accountRepository.findById(2L).orElseThrow();
        
        // Read balances from snapshot
        // A = $1000, B = $500
        
        // Transfer $100 from A to B
        accountA.setBalance(accountA.getBalance().subtract(new BigDecimal("100")));
        accountB.setBalance(accountB.getBalance().add(new BigDecimal("100")));
        
        accountRepository.save(accountA);  // A = $900
        accountRepository.save(accountB);  // B = $600
        
        // Commit succeeds (no conflict detected)
    }
    
    // Transaction 2: Transfer from B to A (concurrent)
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void transaction2() {
        // Different snapshot (parallel transaction)
        
        Account accountA = accountRepository.findById(1L).orElseThrow();
        Account accountB = accountRepository.findById(2L).orElseThrow();
        
        // Read balances from its own snapshot
        // A = $1000, B = $500 (same as T1's snapshot)
        
        // Transfer $50 from B to A
        accountB.setBalance(accountB.getBalance().subtract(new BigDecimal("50")));
        accountA.setBalance(accountA.getBalance().add(new BigDecimal("50")));
        
        accountRepository.save(accountB);  // B = $450
        accountRepository.save(accountA);  // A = $1050
        
        // Commit might succeed or fail depending on timing
        // With snapshot isolation: Both commits succeed (write skew!)
        // Final state: A = $1050, B = $450
        // But if serial: A = $1050, B = $550 OR A = $950, B = $550
    }
}
```

**Write Skew Problem**

```java
// Write skew: Both transactions succeed but result is not serializable

@Service
public class WriteSkewExample {

    }
```

**Serializable Isolation**

```java
// Serializable: Detects and prevents write skew

@Service
public class SerializableIsolationExample {
    
    @Autowired
    private DoctorRepository doctorRepository;
    
    // Transaction 1: Doctor Alice goes off call
    @Transactional(isolation = Isolation.SERIALIZABLE)
    @Retryable(maxAttempts = 3)
    public void doctorAliceGoesOffCallSerializable() {
        // PostgreSQL tracks: "T1 read doctors WHERE status=ON_CALL"
        long onCallCount = doctorRepository.countByStatus(Status.ON_CALL);
        
        if (onCallCount > 1) {
            Doctor alice = doctorRepository.findByName("Alice").orElseThrow();
            // PostgreSQL tracks: "T1 wrote Alice.status"
            alice.setStatus(Status.OFF_CALL);
            doctorRepository.save(alice);
        }
        
        // At commit: PostgreSQL checks for conflicts
        // If T2 also read same data and wrote to related data,
        // serialization error is thrown
    }
    
    // Transaction 2: Doctor Bob goes off call (concurrent)
    @Transactional(isolation = Isolation.SERIALIZABLE)
    @Retryable(maxAttempts = 3)
    public void doctorBobGoesOffCallSerializable() {
        // PostgreSQL tracks: "T2 read doctors WHERE status=ON_CALL"
        long onCallCount = doctorRepository.countByStatus(Status.ON_CALL);
        
        if (onCallCount > 1) {
            Doctor bob = doctorRepository.findByName("Bob").orElseThrow();
            // PostgreSQL tracks: "T2 wrote Bob.status"
            bob.setStatus(Status.OFF_CALL);
            doctorRepository.save(bob);
        }
        
        // At commit: PostgreSQL detects conflict
        // T1 and T2 both:
        //   1. Read same data (doctors WHERE status=ON_CALL)
        //   2. Wrote to data that affects that query
        // Serialization error thrown for T2 (or T1)
    }
    
    // Result with SERIALIZABLE:
    // One transaction succeeds, other gets:
    // "ERROR: could not serialize access due to read/write dependencies"
    // Constraint preserved: At least one doctor remains on call
}
```

**How SSI (Serializable Snapshot Isolation) Works**

```java
// PostgreSQL tracks three types of conflicts:

public class SSIExplanation {
    
    public void explainSSI() {
        // SSI tracks read/write dependencies:
        
        // 1. rw-conflicts (read-write)
        // Transaction T1 reads data
        // Transaction T2 writes to same data
        // T1's read is now "dangerous" (based on stale data)
        
        // 2. ww-conflicts (write-write)
        // Transaction T1 writes data
        // Transaction T2 writes to same data
        // Standard conflict (handled by locking)
        
        // 3. wr-conflicts (write-read)
        // Transaction T1 writes data
        // Transaction T2 reads that data
        // T2's read depends on T1
        
        // SSI detects cycles:
        // If T1 → T2 → T3 → T1 (cycle in dependency graph)
        // Then execution is not serializable
        // PostgreSQL aborts one transaction to break cycle
        
        // Example cycle:
        // T1 reads A, writes B
        // T2 reads B, writes C
        // T3 reads C, writes A
        // Cycle: T1 → T2 → T3 → T1
        // One transaction must abort
    }
}
```

|**Phantom reads**|No (PostgreSQL)|No|

|**Read-write conflicts**|Not detected|Detected|
|**Performance**|Fast|Slower (tracking overhead)|
|**Failures**|Rare|More common|
|**Use cases**|Reports, calculations|Critical integrity constraints|

### Q3: "When would you use READ UNCOMMITTED despite PostgreSQL not truly supporting it?"

**Answer**: You wouldn't use READ UNCOMMITTED in PostgreSQL because it doesn't provide any benefit - PostgreSQL automatically upgrades it to READ COMMITTED. However, understanding the reasons for using it in other databases helps with cross-database compatibility and migration scenarios.

**PostgreSQL's Behavior**

```java
@Service

    @Transactional(isolation = Isolation.READ_UNCOMMITTED)
    public List<Product> readUncommitted() {
        // PostgreSQL silently upgrades this to READ_COMMITTED
        // No dirty reads possible
        return productRepository.findAll();
    }
    
    // These are equivalent in PostgreSQL:
    @Transactional(isolation = Isolation.READ_UNCOMMITTED)
    public void method1() { }
    
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void method2() { }
    
    @Transactional  // Default
    public void method3() { }
}
```

**Verify PostgreSQL's Behavior**

```sql
-- Set isolation level to READ UNCOMMITTED
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- Check actual isolation level
SHOW transaction_isolation;
-- Output: "read committed" (not read uncommitted!)

-- PostgreSQL doesn't allow dirty reads
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- Transaction 1 (this session)
UPDATE products SET price = 999.99 WHERE id = 1;
-- Don't commit yet

-- Transaction 2 (different session)
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT price FROM products WHERE id = 1;
-- Returns original price, NOT uncommitted 999.99
-- No dirty read despite READ UNCOMMITTED!

-- Transaction 1
ROLLBACK;
```

**Why PostgreSQL Doesn't Support It**

```java
// PostgreSQL uses MVCC (Multi-Version Concurrency Control)

public class MVCCExplanation {
    
    public void explainMVCC() {
        // MVCC architecture:
        
        // 1. Each transaction gets a transaction ID (xid)
        // 2. Each row version is tagged with:
        //    - xmin: transaction that created it
        //    - xmax: transaction that deleted/updated it
        
        // 3. Visibility rules:
        //    - Transaction can only see rows where:
        //      a) xmin < current transaction's xid (created before)
        //      b) Creating transaction committed
        //      c) xmax is null OR deleting transaction hasn't committed
        
        // 4. Uncommitted changes are invisible:
        //    - Stored in separate tuple versions
        //    - Only creating transaction can see them
        //    - Other transactions see previous committed version
        
        // Result: Dirty reads are architecturally impossible
        //         without significant performance penalty
        
        // To support true READ UNCOMMITTED, PostgreSQL would need to:
        // - Disable MVCC visibility checks (slow)
        // - Add special code paths (complexity)
        // - Break consistency guarantees
        // Not worth it for a feature rarely used correctly
    }
}
```

### Q4: "How do you handle deadlocks with SERIALIZABLE transactions?"

**Answer**: Handle deadlocks through detection, retry logic with exponential backoff, transaction ordering conventions, timeout configuration, and monitoring. Use `@Retryable`, reduce transaction scope, and implement deadlock detection monitoring with pg_stat_activity and pg_locks.

**Understanding Deadlocks in SERIALIZABLE**

```java
// Deadlock scenario: Two transactions

@Service
public class DeadlockScenario {
    
    @Autowired
    private AccountRepository accountRepository;
    
    // Transaction 1: Transfer A → B
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void transferAtoB() {
        Account a = accountRepository.findById(1L).orElseThrow();
        Account b = accountRepository.findById(2L).orElseThrow();
        
        // T1 locks account A
        a.setBalance(a.getBalance().subtract(new BigDecimal("100")));
        accountRepository.save(a);
        
        Thread.sleep(100);  // Simulate processing
        
        // T1 tries to lock account B (might be locked by T2)
        b.setBalance(b.getBalance().add(new BigDecimal("100")));
        accountRepository.save(b);
        
        // Potential deadlock if T2 holds B and wants A
    }
    
    // Transaction 2: Transfer B → A (concurrent)
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void transferBtoA() {
        Account b = accountRepository.findById(2L).orElseThrow();
        Account a = accountRepository.findById(1L).orElseThrow();
        
        // T2 locks account B
        b.setBalance(b.getBalance().subtract(new BigDecimal("50")));
        accountRepository.save(b);
        
        Thread.sleep(100);  // Simulate processing
        
        // T2 tries to lock account A (might be locked by T1)
        a.setBalance(a.getBalance().add(new BigDecimal("50")));
        accountRepository.save(a);
```

**Solution 2: Transaction Ordering Convention**

```java
// Prevent deadlocks by always acquiring locks in same order

@Service
public class OrderedLockingService {
    
    @Autowired
    private AccountRepository accountRepository;
    
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void transferOrdered(Long fromId, Long toId, BigDecimal amount) {
        // CRITICAL: Always lock accounts in ascending ID order
        // This prevents circular wait (deadlock condition)
        
        Long firstId = Math.min(fromId, toId);
        Long secondId = Math.max(fromId, toId);
        
        Account first = accountRepository.findById(firstId).orElseThrow();
        Account second = accountRepository.findById(secondId).orElseThrow();
        
        // Now identify which is from/to
        Account from = (fromId.equals(firstId)) ? first : second;
        Account to = (fromId.equals(firstId)) ? second : first;
        
        // Perform transfer
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
        
        // No deadlock possible because all transactions
        // acquire locks in same order (by ID)
    }
}

@Service

            .sorted()
            .distinct()

        for (Long id : sortedIds) {
            Entity entity = entityRepository.findById(id).orElseThrow();
            // Process entity
            entity.update();
            entityRepository.save(entity);
        }
        
        // No deadlocks because all transactions follow same order
    }
```

**Solution 5: Deadlock Detection and Monitoring**

```java
@Component
public class DeadlockMonitor {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    @Autowired
    private MeterRegistry meterRegistry;
    
    private final Counter deadlockCounter = Counter.builder("db.deadlocks")
        .description("Deadlock occurrences")
        .register(meterRegistry);
    
    @Scheduled(fixedDelay = 30000)  // Every 30 seconds
    public void detectDeadlocks() {
        // Query for deadlock information
        String sql = """
            SELECT
                blocked_locks.pid AS blocked_pid,
                blocked_activity.usename AS blocked_user,
                blocking_locks.pid AS blocking_pid,
                blocking_activity.usename AS blocking_user,
                blocked_activity.query AS blocked_statement,
                blocking_activity.query AS blocking_statement,
                blocked_activity.application_name AS blocked_app
            FROM pg_catalog.pg_locks blocked_locks
            JOIN pg_catalog.pg_stat_activity blocked_activity 
                ON blocked_activity.pid = blocked_locks.pid
            JOIN pg_catalog.pg_locks blocking_locks 
                ON blocking_locks.locktype = blocked_locks.locktype
            JOIN pg_catalog.pg_stat_activity blocking_activity 
                ON blocking_activity.pid = blocking_locks.pid
            WHERE NOT blocked_locks.granted
              AND blocked_locks.pid != blocking_locks.pid
            """;
        
        List<DeadlockInfo> deadlocks = jdbcTemplate.query(sql, 
            (rs, rowNum) -> DeadlockInfo.builder()
                .blockedPid(rs.getInt("blocked_pid"))
                .blockedQuery(rs.getString("blocked_statement"))
                .blockingPid(rs.getInt("blocking_pid"))
                .blockingQuery(rs.getString("blocking_statement"))
                .build()
        );
        
        if (!deadlocks.isEmpty()) {
            deadlockCounter.increment(deadlocks.size());
            
            log.warn("Detected {} potential deadlocks", deadlocks.size());
            deadlocks.forEach(dl -> {
                log.warn("Deadlock: PID {} blocked by PID {}", 
                        dl.getBlockedPid(), dl.getBlockingPid());
                log.warn("  Blocked: {}", dl.getBlockedQuery());
                log.warn("  Blocking: {}", dl.getBlockingQuery());
            });
        }
    }
}

    private int blockedPid;
    private String blockedQuery;
    private int blockingPid;
    private String blockingQuery;
```
```java
}

@Service
public class PessimisticDeadlockPrevention {
    
    @Autowired
    private AccountRepository accountRepository;
    
    @Transactional(isolation = Isolation.REPEATABLE_READ)  // Can use lower isolation
    public void transferSafe(Long fromId, Long toId, BigDecimal amount) {
        // Lock both accounts in ascending order
        List<Long> ids = Arrays.asList(fromId, toId);
        List<Account> accounts = accountRepository.findAndLockByIdsOrdered(ids);
        
        // Find from and to accounts
        Account from = accounts.stream()
            .filter(a -> a.getId().equals(fromId))
            .findFirst()
            .orElseThrow();
        
        Account to = accounts.stream()
            .filter(a -> a.getId().equals(toId))
            .findFirst()
            .orElseThrow();
        
        // Perform transfer (locks already held in order)
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.saveAll(Arrays.asList(from, to));
        
        // No deadlock: locks acquired in consistent order
        // No serialization failures: using pessimistic locks
    }
```

### Q5: "What's the performance impact of using @Version on every entity?"

**Answer**: @Version adds minimal overhead (~2-5% for updates, negligible for reads) but prevents update conflicts. Impact includes: extra column in SELECT/UPDATE, optimistic lock checking, and version increment. Benefits (conflict detection, data integrity) usually outweigh costs. Only skip for read-only or append-only entities.

### Q6: "How would you implement distributed transactions across multiple databases?"

**Answer**: Use Saga pattern with compensation (choreography or orchestration), avoid 2PC due to complexity/blocking, implement idempotency, use outbox pattern for reliable messaging, and handle partial failures with eventual consistency. Spring Boot doesn't natively support distributed transactions well - use Saga frameworks like Axon or manual implementation.

**Why 2PC (Two-Phase Commit) is Problematic**

```java
// Two-Phase Commit (DON'T USE in microservices)

public class TwoPhaseCommitProblems {
    
    public void explainProblems() {
        // Phase 1: Prepare
        // - Coordinator asks all participants: "Can you commit?"
        // - Each participant prepares and responds YES/NO
        // - Participants hold locks during this phase
        
        // Phase 2: Commit
        // - If all YES: Coordinator tells all to COMMIT
        // - If any NO: Coordinator tells all to ROLLBACK
        
        // Problems:
        // 1. Blocking: Participants hold locks until coordinator decides
        // 2. Single point of failure: If coordinator crashes, participants blocked
        // 3. Performance: Network round-trips for every transaction
        // 4. Scalability: Doesn't scale to many services
        // 5. Availability: One slow service blocks entire transaction
        
        // PostgreSQL supports 2PC but NOT recommended for microservices:
        // PREPARE TRANSACTION 'tx_id';
        // COMMIT PREPARED 'tx_id';
        // ROLLBACK PREPARED 'tx_id';
    }
}
```

**Solution 1: Saga Pattern with Orchestration**

```java
// Orchestrator coordinates saga execution

@Service
public class OrderSagaOrchestrator {
    
    @Autowired
    private OrderService orderService;
    
    @Autowired
    private PaymentService paymentService;
    
    @Autowired
    private InventoryService inventoryService;
    
    @Autowired
    private ShippingService shippingService;
    
    @Autowired
    private SagaStateRepository sagaStateRepository;
    
    public void createOrder(OrderRequest request) {
        SagaState saga = SagaState.builder()
            .sagaId(UUID.randomUUID().toString())
            .status(SagaStatus.STARTED)
            .build();
        
        sagaStateRepository.save(saga);
        
        try {
            // Step 1: Create order
            Long orderId = orderService.createOrder(request);
            saga.setOrderId(orderId);
            saga.setStatus(SagaStatus.ORDER_CREATED);
            sagaStateRepository.save(saga);
            
            // Step 2: Process payment
            String paymentId = paymentService.processPayment(
                request.getCustomerId(), 
                request.getAmount()
            );
            saga.setPaymentId(paymentId);
            saga.setStatus(SagaStatus.PAYMENT_PROCESSED);
            sagaStateRepository.save(saga);
            
            // Step 3: Reserve inventory
            inventoryService.reserveInventory(orderId, request.getItems());
            saga.setStatus(SagaStatus.INVENTORY_RESERVED);
            sagaStateRepository.save(saga);
            
            // Step 4: Schedule shipping
            shippingService.scheduleShipping(orderId, request.getAddress());
            saga.setStatus(SagaStatus.COMPLETED);
            sagaStateRepository.save(saga);
            
        } catch (Exception e) {
            // Compensation: Undo completed steps in reverse order
            compensate(saga, e);
            throw new SagaFailedException("Order creation failed", e);
        }
    }
    
    private void compensate(SagaState saga, Exception cause) {
        log.error("Saga {} failed at step {}, compensating...", 
                 saga.getSagaId(), saga.getStatus());
        
        saga.setStatus(SagaStatus.COMPENSATING);
        saga.setFailureReason(cause.getMessage());
        sagaStateRepository.save(saga);
        
        try {
            // Compensate in reverse order
            switch (saga.getStatus()) {
                case INVENTORY_RESERVED:
                    inventoryService.releaseInventory(saga.getOrderId());
                    // Fall through
                case PAYMENT_PROCESSED:
                    paymentService.refundPayment(saga.getPaymentId());
                    // Fall through
                case ORDER_CREATED:
                    orderService.cancelOrder(saga.getOrderId());
                    break;
            }
            
            saga.setStatus(SagaStatus.COMPENSATED);
            sagaStateRepository.save(saga);
            
        } catch (Exception compensationError) {
            saga.setStatus(SagaStatus.COMPENSATION_FAILED);
            saga.setCompensationError(compensationError.getMessage());
            sagaStateRepository.save(saga);
```

### Q7: "Explain how MVCC enables REPEATABLE READ without locking."

**Answer**: MVCC (Multi-Version Concurrency Control) creates snapshot of database at transaction start. Each row version has xmin (creating transaction) and xmax (deleting transaction). Transactions see only versions visible to their snapshot ID, allowing concurrent reads/writes without locks. Old versions kept until no transactions need them (vacuum cleanup).

**MVCC Architecture**

```java
// How PostgreSQL stores row versions

public class MVCCExplanation {
    
    public void explainRowVersions() {
        // Each row has hidden columns:
        
        // xmin: Transaction ID that created this version
        // xmax: Transaction ID that deleted/updated this version (0 if current)
        // ctid: Physical location (page, offset)
        
        // Example: Account balance updates
        
        // Initial state:
        // | id | balance | xmin | xmax | ctid  |
        // | 1  | $1000   | 100  | 0    | (0,1) |
        
        // Transaction 200 updates balance to $900:
        // Old version (marked as deleted):
        // | id | balance | xmin | xmax | ctid  |
        // | 1  | $1000   | 100  | 200  | (0,1) |
        //
        // New version (created):
        // | id | balance | xmin | xmax | ctid  |
        // | 1  | $900    | 200  | 0    | (0,2) |
        
        // Both versions exist simultaneously!
        // Transactions see different versions based on their snapshot
    }
}
```

**Transaction Visibility Rules**

```java
public class VisibilityRules {
    
    public void explainVisibility() {
        // Transaction starts: Gets snapshot ID (e.g., 250)
        // Snapshot contains:
        // - xmin: 250 (current transaction ID)
        // - xmax: highest completed transaction ID
        // - Active transactions: list of ongoing transactions
        
        // Visibility rules:
        // Row version is visible if:
        // 1. xmin < snapshot.xmin (created before snapshot)
        // 2. xmin transaction committed
        // 3. xmax is NULL (not deleted) OR
        //    xmax > snapshot.xmin (deleted after snapshot) OR
        //    xmax transaction not committed
        
        // Example:
        // Transaction 250 starts (REPEATABLE READ)
        // Snapshot: xmin=250, active=[240, 245]
        
        // Row version 1:
        // xmin=100, xmax=0
        // Visible? YES (created before snapshot, not deleted)
        
        // Row version 2:
        // xmin=240, xmax=0
        // Visible? NO (240 is active in snapshot)
        
        // Row version 3:
        // xmin=200, xmax=260
        // Visible? YES (created before snapshot, deleted after snapshot)
    }
}
```

**REPEATABLE READ Example**

```java
@Service
public class MVCCDemonstration {
    
    @Autowired
    private AccountRepository accountRepository;
    
    // Transaction 1: REPEATABLE READ
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void transaction1() {
        // T1 starts, gets snapshot (e.g., xid=100)
        
        // Read 1: Account balance
        Account account = accountRepository.findById(1L).orElseThrow();
        System.out.println("T1 Read 1: " + account.getBalance());  // $1000
        // Sees row version: xmin=50, xmax=0
        
        // Wait... (T2 updates balance in parallel)
        Thread.sleep(5000);
        
        // Read 2: Same account
        entityManager.refresh(account);  // Force reload
        System.out.println("T1 Read 2: " + account.getBalance());  // Still $1000!
        // Still sees same row version: xmin=50, xmax=0
        // Even though T2 created new version: xmin=150, xmax=0
        // T1's snapshot (xid=100) doesn't see T2's changes (xid=150)
        
        // No locks! T1 and T2 run concurrently
        // T1 reads old version, T2 reads/writes new version
    }
    
    // Transaction 2: Concurrent update
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void transaction2() {
        // T2 starts (e.g., xid=150)
        
        // Update balance
        Account account = accountRepository.findById(1L).orElseThrow();
        account.setBalance(new BigDecimal("900"));
        accountRepository.save(account);
        
        // PostgreSQL creates new row version:
        // Old version: xmin=50, xmax=150 (marked as deleted by T2)
        // New version: xmin=150, xmax=0 (created by T2)
        
        // T2 commits
        // New version is now visible to new snapshots
        // But T1's snapshot still sees old version (MVCC magic!)
    }
}
```

**Vacuum Process**

```java
public class VacuumExplanation {
    
    public void explainVacuum() {
        // Problem: Old row versions accumulate
        // Example:
        // - Account updated 1000 times
        // - 1000 row versions exist (999 are old)
        // - Wastes storage space
        
        // Solution: VACUUM
        // - Removes old row versions
        // - Only removes versions no transaction can see
        
        // VACUUM rules:
        // 1. Check xmax of old version
        // 2. If all active transactions have xid > xmax, version is "dead"
        // 3. Dead versions can be removed
        
        // Example:
        // Row version: xmin=100, xmax=200
        // Active transactions: 250, 260, 270
        // All have xid > 200, so version is dead
        // VACUUM removes it
        
        // Automatic VACUUM:
        // - Runs in background
        // - Triggered by autovacuum_vacuum_threshold
        // - Default: 50 + 20% of table size
    }
}
```

### Q8: "What are the trade-offs between application-level and database-level concurrency control?"

**Answer**: Database-level (pessimistic/SERIALIZABLE) provides stronger guarantees but lower concurrency and potential blocking. Application-level (optimistic/@Version) offers better performance and scalability but requires conflict handling and retry logic. Choose based on contention level, consistency requirements, and system architecture.

**Database-Level Concurrency Control**

```java
// Using database features (locks, isolation levels)

@Service
public class DatabaseLevelControl {
    
    // Pessimistic locking
    @Transactional
    public void transferWithPessimisticLock(Long fromId, Long toId, BigDecimal amount) {
        // Database acquires locks immediately
        Account from = accountRepository.findByIdWithWriteLock(fromId).orElseThrow();
        Account to = accountRepository.findByIdWithWriteLock(toId).orElseThrow();
        
        // No other transaction can access these rows
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.saveAll(Arrays.asList(from, to));
        
        // Locks released on commit
    }
    
    // SERIALIZABLE isolation
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void transferWithSerializable(Long fromId, Long toId, BigDecimal amount) {
        // Database ensures serializable execution
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();
        
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.saveAll(Arrays.asList(from, to));
        
        // Database detects conflicts automatically
    }
}
```

```java
// - Database handles everything

// ✅ Immediate conflict detection
```

```java
            accountRepository.saveAll(Arrays.asList(from, to));

        // Application handles concurrency

    @Transactional
    public void transferWithMerge(Long fromId, Long toId, BigDecimal amount) {
        try {
            // Try normal update
            transferWithOptimistic(fromId, toId, amount);
            
        } catch (OptimisticLockException e) {
            // Custom merge strategy
            // Reload entities
            Account from = accountRepository.findById(fromId).orElseThrow();
            Account to = accountRepository.findById(toId).orElseThrow();
            
            // Check if transfer is still valid

                // Retry with fresh data
                from.setBalance(from.getBalance().subtract(amount));
                to.setBalance(to.getBalance().add(amount));
                accountRepository.saveAll(Arrays.asList(from, to));
            } else {
                throw new InsufficientFundsException();
            }
        }
```

```java
        seat.setReserved(true);
        seat.setUserId(userId);
        seatRepository.save(seat);
        
        // Lock prevents double-booking
    }
    
    // Non-critical path: Application-level (optimistic)
    @Transactional
    @Retryable(maxAttempts = 3)
    public void updateUserProfile(Long userId, ProfileUpdate update) {
        // Low contention, can retry
        UserProfile profile = userRepository.findById(userId).orElseThrow();
        // Uses @Version for optimistic locking
        
        profile.apply(update);
        userRepository.save(profile);
        
        // Retries on OptimisticLockException
    }
}
```

**Best Practices**

```java
// ✅ DO: Choose based on contention level
// High contention → Database-level (pessimistic)
// Low contention → Application-level (optimistic)

// ✅ DO: Use hybrid approach
// Critical data → Database-level
// Non-critical data → Application-level

// ✅ DO: Monitor contention
// Track OptimisticLockException frequency
// If > 5% failure rate, consider pessimistic

// ✅ DO: Implement proper retry logic
// Exponential backoff
// Maximum attempts
// Alert on excessive retries

// ✅ DO: Keep transactions short
// Minimize lock hold time
// Reduce wasted work

// ❌ DON'T: Use pessimistic locks with long transactions
// Blocks other users unnecessarily

// ❌ DON'T: Use optimistic locking for high-contention data
// Too many retries, poor UX

// ❌ DON'T: Mix approaches carelessly
// Can lead to deadlocks or starvation

// ❌ DON'T: Ignore performance metrics
// Monitor lock wait times
// Track optimistic lock failure rates
```
