# Handling Database Schema Evolution in Production

## Deep Dive Interview Guide

This guide covers database schema evolution strategies for production systems with Spring Boot and PostgreSQL, including zero-downtime deployments, backward compatibility, multi-phase migrations, and safe rollback procedures.

**Interview Tip**: Schema evolution questions test understanding of production deployments, backward compatibility, risk mitigation, and operational excellence.

---

## Q6: Handling database schema evolution in production

**Short Answer**: Zero-downtime requires backward-compatible changes: add columns as nullable first, migrate data, then add constraints in separate deployments. Multi-phase approach: (1) Add nullable column, (2) Backfill data + dual writes, (3) Add NOT NULL constraint, (4) Remove old column. Blue-green needs schema-compatible with both versions. Always test migrations on production-like data. Rollback: reverse migrations with DOWN scripts, or forward-fix for data migrations.

## 1. Zero-Downtime Deployment Strategies

### Understanding Downtime Causes

```sql
-- ❌ Operations that cause downtime:

-- 1. Adding NOT NULL column without default (locks table)
ALTER TABLE orders ADD COLUMN priority VARCHAR(20) NOT NULL;
-- Lock duration: O(n) where n = table size
-- For 10M rows: ~30-60 seconds of exclusive lock
-- All writes blocked during this time

-- 2. Dropping column with data (locks table, rewrites)
ALTER TABLE orders DROP COLUMN old_column;
-- Lock duration: O(n)
-- Rewrites entire table

-- 3. Adding constraint with validation (locks table)
ALTER TABLE orders ADD CONSTRAINT check_total_positive CHECK (total > 0);
-- Lock duration: O(n) - validates all existing rows

-- 4. Changing column type (rewrites table)
ALTER TABLE orders ALTER COLUMN total TYPE DECIMAL(12,2);
-- Lock duration: O(n)
-- Creates new table, copies data, swaps

-- 5. VACUUM FULL (exclusive lock)
VACUUM FULL orders;
-- Lock duration: O(n)
-- Blocks all operations
```

### Zero-Downtime Patterns

```sql
-- ✅ Safe operations (minimal locking):

-- 1. Add nullable column (fast, no data modification)
ALTER TABLE orders ADD COLUMN priority VARCHAR(20);
-- Lock duration: O(1) - just updates catalog
-- < 100ms even for billion-row tables

-- 2. Add column with default (PostgreSQL 11+, fast)
ALTER TABLE orders ADD COLUMN priority VARCHAR(20) DEFAULT 'NORMAL';
-- Lock duration: O(1) in PostgreSQL 11+
-- Default stored in catalog, not written to all rows

-- 3. Create index CONCURRENTLY (no exclusive lock)
CREATE INDEX CONCURRENTLY idx_orders_priority ON orders(priority);
-- Lock duration: None (uses MVCC)
-- Can take minutes, but doesn't block operations

-- 4. Drop constraint (fast)
ALTER TABLE orders DROP CONSTRAINT check_total_positive;
-- Lock duration: O(1)

-- 5. Add constraint NOT VALID (fast)
ALTER TABLE orders ADD CONSTRAINT check_total_positive 
CHECK (total > 0) NOT VALID;
-- Lock duration: O(1)
-- Doesn't validate existing rows

-- Then validate separately (doesn't block writes)
ALTER TABLE orders VALIDATE CONSTRAINT check_total_positive;
-- Uses ShareUpdateExclusiveLock (allows reads and writes)
```

### Expand-Contract Pattern

```java
// Pattern for zero-downtime schema changes

// Phase 1: EXPAND - Add new schema elements (backward compatible)
// Phase 2: MIGRATE - Dual-write to old and new schema
// Phase 3: CONTRACT - Remove old schema elements

@Service
public class ExpandContractMigration {
    
    // Example: Rename column from 'status' to 'order_status'
    
    // === PHASE 1: EXPAND (Deploy 1) ===
    
    // Migration V1: Add new column
    @Sql("""
        -- Add new column (nullable, fast)
        ALTER TABLE orders ADD COLUMN order_status VARCHAR(20);
        
        -- Create index concurrently (doesn't block)
        CREATE INDEX CONCURRENTLY idx_orders_order_status 
        ON orders(order_status);
        """)
    public void expandAddColumn() {
        // Application code still uses old column
    }
    
    // === PHASE 2: MIGRATE (Deploy 2) ===
    
    // Migration V2: Backfill data + setup dual writes
    @Sql("""
        -- Backfill existing data (in batches to avoid long locks)
        UPDATE orders 
        SET order_status = status 
        WHERE order_status IS NULL
        LIMIT 10000;
        -- Repeat until all rows updated
        
        -- Create trigger for dual writes (temporary)
        CREATE OR REPLACE FUNCTION sync_order_status()
        RETURNS TRIGGER AS $$
        BEGIN
            IF TG_OP = 'INSERT' OR TG_OP = 'UPDATE' THEN
                NEW.order_status := NEW.status;
            END IF;
            RETURN NEW;
        END;
        $$ LANGUAGE plpgsql;
        
        CREATE TRIGGER sync_order_status_trigger
        BEFORE INSERT OR UPDATE ON orders
        FOR EACH ROW
        EXECUTE FUNCTION sync_order_status();
        """)
    public void migrateBackfillAndDualWrite() {
        // Application code updated to write both columns
    }
    
    @Entity
    public class Order {
        @Column(name = "status")  // Old column
        private String status;
        
        @Column(name = "order_status")  // New column
        private String orderStatus;
        
        @PrePersist
        @PreUpdate
        public void syncColumns() {
            // Dual write in application code
            this.orderStatus = this.status;
        }
    }
    
    // === PHASE 3: CONTRACT (Deploy 3) ===
    
    // Migration V3: Switch reads to new column
    @Entity
    public class Order {
        @Column(name = "order_status")
        private String orderStatus;
        
        // Old column removed from entity
    }
    
    // === PHASE 4: CLEANUP (Deploy 4) ===
    
    // Migration V4: Drop old column
    @Sql("""
        -- Drop trigger first
        DROP TRIGGER IF EXISTS sync_order_status_trigger ON orders;
        DROP FUNCTION IF EXISTS sync_order_status();
        
        -- Drop old column (fast in PostgreSQL)
        ALTER TABLE orders DROP COLUMN status;
        """)
    public void contractRemoveOldColumn() {
        // Old column completely removed
    }
}
```

## 2. Backward Compatible Changes

### Safe vs Unsafe Changes

```sql
-- ✅ SAFE (Backward Compatible):

-- 1. Adding nullable column
ALTER TABLE users ADD COLUMN middle_name VARCHAR(50);
-- Old code: Ignores new column
-- New code: Can use new column

-- 2. Adding table
CREATE TABLE user_preferences (
    user_id BIGINT REFERENCES users(id),
    preference_key VARCHAR(50),
    preference_value TEXT
);
-- Old code: Doesn't know about table
-- New code: Can use table

-- 3. Adding index
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
-- Old code: Works fine (slightly faster)
-- New code: Works fine

-- 4. Dropping unused index
DROP INDEX idx_old_unused;
-- Old code: Might be slightly slower if using index
-- New code: Works fine

-- 5. Adding column with default (PostgreSQL 11+)
ALTER TABLE users ADD COLUMN subscription_tier VARCHAR(20) DEFAULT 'FREE';
-- Old code: NULL handling works, gets default on read
-- New code: Gets default value

-- 6. Renaming index
ALTER INDEX idx_old_name RENAME TO idx_new_name;
-- Old code: Postgres auto-uses any matching index
-- New code: Works fine

-- ❌ UNSAFE (Breaking Changes):

-- 1. Dropping column
ALTER TABLE users DROP COLUMN phone_number;
-- Old code: ERROR - column doesn't exist
-- New code: Works

-- 2. Renaming column
ALTER TABLE users RENAME COLUMN email TO email_address;
-- Old code: ERROR - column doesn't exist
-- New code: Uses new name

-- 3. Adding NOT NULL constraint
ALTER TABLE users ALTER COLUMN email SET NOT NULL;
-- Old code: May fail if inserting without email
-- New code: Must provide email

-- 4. Changing column type (incompatible)
ALTER TABLE users ALTER COLUMN age TYPE VARCHAR(10);
-- Old code: May fail (expecting integer)
-- New code: Uses string

-- 5. Dropping table
DROP TABLE old_audit_logs;
-- Old code: ERROR - table doesn't exist
-- New code: Works

-- 6. Adding UNIQUE constraint
ALTER TABLE users ADD CONSTRAINT uk_users_email UNIQUE (email);
-- Old code: May fail if inserting duplicate email
-- New code: Enforces uniqueness
```

### Making Unsafe Changes Safe

```java
@Service
public class SafeMigrationStrategy {

    }

    @Sql("ALTER TABLE users ALTER COLUMN email SET NOT NULL")

    }

    // Phase 1: Add nullable column (Deploy 1)

    // Phase 2: Backfill data + update code to write email (Deploy 2)
    @Sql("""
        UPDATE users SET email = username || '@legacy.com' 
        WHERE email IS NULL

        private String email;

    @Sql("ALTER TABLE users ALTER COLUMN email SET NOT NULL")
    public void phase3AddConstraint() {
        // All rows have email, code always provides email
    }
    
    // === UNSAFE: Rename column ===
    
    // ✅ Use expand-contract pattern (see previous section)
    
    // === UNSAFE: Change column type ===
    
    // Phase 1: Add new column with new type (Deploy 1)
    @Sql("""
        ALTER TABLE products ADD COLUMN price_decimal DECIMAL(10,2);
        UPDATE products SET price_decimal = price::DECIMAL(10,2);
        """)
    public void phase1AddNewType() {}
    
    // Phase 2: Dual write (Deploy 2)
    @Entity
    public class Product {
        @Column(name = "price")
        private Integer priceOld;  // Old INT column
        
        @Column(name = "price_decimal")
        private BigDecimal price;  // New DECIMAL column
        
        @PrePersist
        @PreUpdate
        public void syncPrice() {
            this.priceOld = this.price.intValue();
        }
    }
    
    // Phase 3: Switch reads to new column (Deploy 3)
    @Entity
    public class Product {
        @Column(name = "price_decimal")
        private BigDecimal price;
    }
    
    // Phase 4: Drop old column (Deploy 4)
    @Sql("ALTER TABLE products DROP COLUMN price")
```

### Backward Compatibility Checklist

```java
public class BackwardCompatibilityChecker {
    
    public boolean isBackwardCompatible(Migration migration) {
        // Check for unsafe operations
        
        if (migration.dropsColumn()) {
            return false;  // ❌ Old code will break
        }
        
        if (migration.renamesColumn()) {
            return false;  // ❌ Old code will break
        }
        
        if (migration.addsNotNullWithoutDefault()) {
            return false;  // ❌ Old code may fail inserts
        }
        
        if (migration.changesColumnTypeIncompatibly()) {
            return false;  // ❌ Old code may fail
        }
        
        if (migration.addsUniqueConstraint()) {
            return false;  // ❌ Old code may insert duplicates
        }
        
        if (migration.dropsTable()) {
            return false;  // ❌ Old code will break
        }
        
        // Safe operations
        if (migration.addsNullableColumn()) {
            return true;  // ✅ Old code ignores it
        }
        
        if (migration.addsTable()) {
            return true;  // ✅ Old code doesn't use it
        }
        
        if (migration.addsIndex()) {
            return true;  // ✅ Transparent to code
        }
        
        if (migration.dropsUnusedIndex()) {
            return true;  // ✅ Only affects performance
        }
        
        return true;  // Default: assume compatible
    }
}
```

## 3. Multi-Phase Migrations

### The Standard Pattern

```java
// Standard multi-phase migration for adding NOT NULL column

@Configuration
public class MultiPhaseMigration {
    
    // === PHASE 1: Add Column (Nullable) ===
    // File: V1__add_email_column.sql
    
    @Sql("""
        -- Add column as nullable (fast, no data modification)
        ALTER TABLE users ADD COLUMN email VARCHAR(255);
        
        -- Add index concurrently (doesn't block)
        CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
        
        -- Estimated time: <1 second
        -- Downtime: None
        -- Rollback: Drop column (easy)
        """)
    public void phase1AddColumn() {
        log.info("Phase 1: Added email column (nullable)");
    }
    
    // Deploy application version 1.1
    // - Code can read email (may be NULL)
    // - Code does NOT write email yet
    // - Wait 24 hours to ensure stability
    
    // === PHASE 2: Backfill Data ===
    // File: V2__backfill_email.sql
    
    @Sql("""
        -- Backfill in batches to avoid long locks
        DO $$
        DECLARE
            batch_size INT := 10000;
            rows_updated INT;
        BEGIN
            LOOP
                UPDATE users
                SET email = username || '@migrated.com'
                WHERE email IS NULL
                  AND id IN (
                      SELECT id FROM users 
                      WHERE email IS NULL 
                      LIMIT batch_size
                  );
                
                GET DIAGNOSTICS rows_updated = ROW_COUNT;
                EXIT WHEN rows_updated = 0;
                
                -- Small delay to avoid overload
                PERFORM pg_sleep(0.1);
            END LOOP;
        END $$;
        
        -- Verify backfill
        DO $$
        BEGIN
            IF EXISTS (SELECT 1 FROM users WHERE email IS NULL) THEN
                RAISE EXCEPTION 'Backfill incomplete: NULL emails still exist';
            END IF;
        END $$;
        
        -- Estimated time: 10-30 minutes for 1M rows
        -- Downtime: None (batched updates, small locks)
        -- Rollback: Set email = NULL (reversible)
        """)
    public void phase2BackfillData() {
        log.info("Phase 2: Backfilled email data");
    }
    
    // Deploy application version 1.2
    // - Code writes email on INSERT/UPDATE
    // - Code reads email (never NULL for new rows)
    // - Wait 24-48 hours to ensure dual-write works
    
    @Entity
    public class User {
        @Column(name = "email")  // Nullable in DB, but required in code
        @NotNull  // JPA validation
        private String email;
    }
    
    // === PHASE 3: Add NOT NULL Constraint ===
    // File: V3__add_email_not_null.sql
    
    @Sql("""
        -- Add NOT NULL constraint
        -- This is now safe because:
        -- 1. All existing rows have email (backfilled)
        -- 2. Application always provides email (enforced by JPA)
        
        ALTER TABLE users ALTER COLUMN email SET NOT NULL;
        
        -- Estimated time: <1 second (just catalog update in PostgreSQL)
        -- Downtime: None
        -- Rollback: Remove constraint (easy)
        """)
    public void phase3AddNotNull() {
        log.info("Phase 3: Added NOT NULL constraint on email");
    }
    
    // === PHASE 4: Optional - Add Additional Constraints ===
    // File: V4__add_email_unique.sql
    
    @Sql("""
        -- Add unique constraint (now that data is clean)
        ALTER TABLE users ADD CONSTRAINT uk_users_email UNIQUE (email);
        
        -- Or add check constraint
        ALTER TABLE users ADD CONSTRAINT check_email_format 
        CHECK (email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$');
        
        -- Estimated time: <1 second for catalog changes
        -- For UNIQUE: creates index automatically
        -- Downtime: None (constraint added with NOT VALID, then validated)
        """)
    public void phase4AddConstraints() {
        log.info("Phase 4: Added additional constraints");
    }
}
```

### Complex Example: Splitting a Column

```java
// Split 'full_name' into 'first_name' and 'last_name'

@Service
public class SplitColumnMigration {
    
    // === PHASE 1: Add New Columns ===
    
    @Sql("""
        ALTER TABLE users ADD COLUMN first_name VARCHAR(100);
        ALTER TABLE users ADD COLUMN last_name VARCHAR(100);
        
        CREATE INDEX CONCURRENTLY idx_users_first_name ON users(first_name);
        CREATE INDEX CONCURRENTLY idx_users_last_name ON users(last_name);
        """)
    public void phase1AddColumns() {}
    
    // === PHASE 2: Backfill + Dual Write ===
    
    @Sql("""
        -- Backfill: Split existing data
        UPDATE users
        SET 
            first_name = SPLIT_PART(full_name, ' ', 1),
            last_name = CASE 
                WHEN full_name LIKE '% %' 
                THEN SUBSTRING(full_name FROM POSITION(' ' IN full_name) + 1)
                ELSE ''
            END
        WHERE first_name IS NULL OR last_name IS NULL;
        """)
    public void phase2Backfill() {}
    
    @Entity
    public class User {
        @Column(name = "full_name")
        private String fullName;  // Old column
        
        @Column(name = "first_name")
        private String firstName;  // New column
        
        @Column(name = "last_name")
        private String lastName;  // New column
        
        @PrePersist
        @PreUpdate
        public void syncNames() {
            // Dual write: maintain backward compatibility
            if (firstName != null && lastName != null) {
                this.fullName = firstName + " " + lastName;
            }
        }
    }
    
    // === PHASE 3: Switch Reads ===
    
    @Entity
    public class User {
        @Column(name = "first_name")
        private String firstName;
        
        @Column(name = "last_name")
        private String lastName;
        
        // Computed property for backward compatibility
        @Transient
        public String getFullName() {
            return firstName + " " + lastName;
        }
    }
    
    // === PHASE 4: Add Constraints ===
    
    @Sql("""
        ALTER TABLE users ALTER COLUMN first_name SET NOT NULL;
        ALTER TABLE users ALTER COLUMN last_name SET NOT NULL;
        """)
    public void phase4AddConstraints() {}
    
    // === PHASE 5: Drop Old Column ===
    
    @Sql("ALTER TABLE users DROP COLUMN full_name")
    public void phase5DropOld() {}
}
```

### Timing Guidelines

```java
public class MigrationTimingGuide {
    
    public Duration calculatePhaseWaitTime(PhaseType phase, RiskLevel risk) {
        switch (phase) {
            case ADD_COLUMN:
                // Wait to ensure no errors from new column
                return Duration.ofHours(24);
                
            case BACKFILL_DATA:
                // Wait to ensure backfill is correct and dual-write works
                return risk == RiskLevel.HIGH 
                    ? Duration.ofDays(7)   // 1 week for critical tables
                    : Duration.ofDays(2);  // 2 days for normal tables
                
            case ADD_CONSTRAINT:
                // Wait to ensure constraint doesn't cause issues
                return Duration.ofHours(48);
                
            case DROP_COLUMN:
                // Wait to ensure no code references old column
                return risk == RiskLevel.HIGH
                    ? Duration.ofDays(30)   // 1 month for critical tables
                    : Duration.ofDays(14);  // 2 weeks for normal tables

                return Duration.ofHours(24);

        Week 8: Phase 4 (Drop old column)
        
        Total: 2 months for high-risk migration
        */
```

## 4. Blue-Green Deployments with Schema Changes

### Blue-Green Schema Compatibility

```java
// Blue-Green requirement: Both versions must work with same schema

@Service
public class BlueGreenSchemaStrategy {
    
    // ❌ BAD: Schema change breaks old version
    
    // Deploy 1: Add NOT NULL column
    @Sql("ALTER TABLE users ADD COLUMN email VARCHAR(255) NOT NULL")
    public void badMigration() {
        // Blue (old code): INSERT fails - doesn't provide email
        // Green (new code): INSERT works - provides email
        // Problem: Can't run both versions simultaneously
    }
    
    // ✅ GOOD: Schema compatible with both versions
    
    // Deploy 1: Add nullable column
    @Sql("ALTER TABLE users ADD COLUMN email VARCHAR(255)")
    public void goodMigration() {
        // Blue (old code): INSERT works - ignores email column
        // Green (new code): INSERT works - provides email
        // Compatible: Both versions work!
    }
    
    // Strategy: Make schema changes BEFORE deploying new code
    
    // Timeline:
    // Day 1: Deploy schema change (add nullable email column)
    // Day 2: Blue-Green switch to new code (now uses email column)
    // Day 3: Backfill missing emails
    // Day 7: Add NOT NULL constraint (safe now)
}
```

## 5. Rolling Back Migrations Safely

### Rollback Strategies

```java
// Strategy 1: Reversible Migrations (Best)

@Configuration
public class ReversibleMigration {
    
    // UP migration
    @Sql("""
        -- V1__add_email_column.sql
        ALTER TABLE users ADD COLUMN email VARCHAR(255);
        CREATE INDEX idx_users_email ON users(email);
        """)
    public void up() {}
    
    // DOWN migration (rollback)
    @Sql("""
        -- V1__add_email_column_rollback.sql
        DROP INDEX IF EXISTS idx_users_email;
        ALTER TABLE users DROP COLUMN IF EXISTS email;
        """)
    public void down() {
        // Safe to rollback: no data loss
    }
}

// Strategy 2: Forward-Only Migrations (For Data Changes)

@Configuration
public class ForwardOnlyMigration {
    
    // Example: Data migration that can't be reversed
    
    @Sql("""
        -- V2__migrate_user_roles.sql
        -- Convert string roles to enum
        UPDATE users SET role_id = 1 WHERE role = 'ADMIN';
        UPDATE users SET role_id = 2 WHERE role = 'USER';
        UPDATE users SET role_id = 3 WHERE role = 'GUEST';
        
        -- Drop old column (CAN'T ROLLBACK - data lost!)
        ALTER TABLE users DROP COLUMN role;
        """)
    public void forwardOnlyUp() {}
    
    // Can't rollback: original string data is lost
    // Solution: Keep old column during transition period
    
    @Sql("""
        -- Better approach: Keep old column
        UPDATE users SET role_id = 1 WHERE role = 'ADMIN';
        UPDATE users SET role_id = 2 WHERE role = 'USER';
        UPDATE users SET role_id = 3 WHERE role = 'GUEST';
        
        -- Don't drop yet - wait 30 days
        -- (Allows rollback if needed)
        """)
    public void saferApproach() {}
}
```

### Rollback Decision Matrix

```java
public class RollbackDecisionMaker {
    
    public boolean canSafelyRollback(Migration migration, Duration timeSinceDeployment) {
        
        // Check 1: Is migration reversible?
        if (!migration.isReversible()) {
            log.error("Migration is not reversible: {}", migration.getVersion());
            return false;
        }
        
        // Check 2: Has data been modified?
        if (migration.hasDataMigration()) {
            if (timeSinceDeployment.toHours() > 24) {
                log.warn("Data migration deployed > 24h ago, rollback may lose data");
                return false;  // Too much new data created
            }
        }
        
        // Check 3: Are constraints added?
        if (migration.addsConstraints()) {
            // Check if constraint has been violated
            long violations = checkConstraintViolations(migration);
            if (violations > 0) {
                log.error("Rollback would create {} constraint violations", violations);
                return false;
            }
        }
        
        // Check 4: Are columns dropped?
        if (migration.dropsColumns()) {
            log.error("Cannot rollback column drop - data lost");
            return false;
        }
        
        return true;
    }
    
    public RollbackPlan createRollbackPlan(Migration migration) {
        RollbackPlan plan = new RollbackPlan();
        
        // Step 1: Stop application
        plan.addStep("Stop application", () -> {
            // Prevents new data from being created
            applicationController.stop();
        });
        
        // Step 2: Backup database
        plan.addStep("Backup database", () -> {
            backupService.createBackup("pre_rollback_" + System.currentTimeMillis());
        });
        
        // Step 3: Execute rollback
        plan.addStep("Execute rollback", () -> {
            migrationRunner.rollback(migration);
        });
        
        // Step 4: Verify rollback
        plan.addStep("Verify rollback", () -> {
            verifySchema(migration.getPreviousVersion());
        });
        
        // Step 5: Restart application
        plan.addStep("Restart application", () -> {
            applicationController.start();
        });
        
        return plan;
    }
}
```

### Safe Rollback Patterns

```sql
-- Pattern 1: Add column with default (Easily reversible)

-- UP
ALTER TABLE users ADD COLUMN subscription_tier VARCHAR(20) DEFAULT 'FREE';

-- DOWN (Safe)
ALTER TABLE users DROP COLUMN subscription_tier;
-- Safe: No application code relies on this yet (if rolled back quickly)


-- Pattern 2: Add NOT NULL with multi-phase (Reversible)

-- UP - Phase 1: Add nullable
ALTER TABLE users ADD COLUMN email VARCHAR(255);

-- UP - Phase 2: Backfill
UPDATE users SET email = username || '@example.com' WHERE email IS NULL;

-- UP - Phase 3: Add NOT NULL
ALTER TABLE users ALTER COLUMN email SET NOT NULL;

-- DOWN (Safe at each phase)
-- Phase 3 rollback:
ALTER TABLE users ALTER COLUMN email DROP NOT NULL;

-- Phase 2 rollback:
UPDATE users SET email = NULL WHERE email LIKE '%@example.com';

-- Phase 1 rollback:
ALTER TABLE users DROP COLUMN email;


-- Pattern 3: Rename column (Requires dual-write, complex rollback)

-- UP - Phase 1: Add new column
ALTER TABLE users ADD COLUMN email_address VARCHAR(255);

-- UP - Phase 2: Sync data
UPDATE users SET email_address = email;

-- UP - Phase 3: Drop old column
ALTER TABLE users DROP COLUMN email;

-- DOWN - Phase 3: Recreate old column
ALTER TABLE users ADD COLUMN email VARCHAR(255);
UPDATE users SET email = email_address;

-- DOWN - Phase 2: No action needed

-- DOWN - Phase 1: Drop new column
ALTER TABLE users DROP COLUMN email_address;


-- Pattern 4: Drop column (NOT reversible without backup)

-- UP
ALTER TABLE users DROP COLUMN old_field;

-- DOWN (IMPOSSIBLE without backup)
-- Cannot restore dropped column data
-- This is why we keep columns for 30+ days before dropping
```

## Interview Follow-Up Questions - Detailed Answers

### Q1: "How would you add a UNIQUE constraint to an existing column with millions of rows?"

**Answer**: Use 4-phase approach: (1) Find and fix duplicates, (2) Create unique index CONCURRENTLY (non-blocking), (3) Add constraint using existing index, (4) Verify. Never add constraint directly - it locks table. Total time: 10-30 minutes for 10M rows, zero downtime.

**Step-by-Step Process**

```java
@Service
public class UniqueConstraintMigration {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    // === Phase 1: Identify and Fix Duplicates ===
    
    public void phase1FindDuplicates() {
        // Find duplicate emails
        String findDuplicatesSql = """
            SELECT email, COUNT(*) as count
            FROM users
            GROUP BY email
            HAVING COUNT(*) > 1
            ORDER BY count DESC
            """;
        
        List<DuplicateEmail> duplicates = jdbcTemplate.query(findDuplicatesSql,
            (rs, rowNum) -> new DuplicateEmail(
                rs.getString("email"),
                rs.getInt("count")
            )
        );
        
        log.info("Found {} duplicate emails", duplicates.size());
        
        // Strategy options for handling duplicates:
        // Option A: Keep oldest, delete newer
        // Option B: Keep newest, delete older
        // Option C: Append suffix to make unique
        // Option D: Manual review (export to CSV)
        
        if (duplicates.size() < 100) {
            // Option D: Manual review for small number
            exportDuplicatesForReview(duplicates);
        } else {
            // Option C: Automated fix with suffix
            fixDuplicatesWithSuffix();
        }
    }
    
    private void fixDuplicatesWithSuffix() {
        String fixSql = """
            -- Add suffix to duplicates (keep first occurrence unchanged)
            WITH ranked_users AS (
                SELECT 
                    id,
                    email,
                    ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) as rn
                FROM users
            )
            UPDATE users
            SET email = ranked_users.email || '_' || ranked_users.rn
            FROM ranked_users
            WHERE users.id = ranked_users.id
              AND ranked_users.rn > 1
            """;
        
        int updated = jdbcTemplate.update(fixSql);
        log.info("Fixed {} duplicate emails", updated);
    }
    
    // Alternative: Keep oldest, soft-delete newer
    private void keepOldestDeleteNewer() {
        String deleteSql = """
            -- Soft delete newer duplicates
            WITH ranked_users AS (
                SELECT 
                    id,
                    email,
                    ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at) as rn
                FROM users
            )
            UPDATE users
            SET deleted_at = NOW()
            FROM ranked_users
            WHERE users.id = ranked_users.id
              AND ranked_users.rn > 1
            """;
        
        int deleted = jdbcTemplate.update(deleteSql);
        log.info("Soft-deleted {} duplicate users", deleted);
    }
    
    // === Phase 2: Create Unique Index CONCURRENTLY ===
    
    @Sql("""
        -- Create unique index without blocking (PostgreSQL 9.2+)
        CREATE UNIQUE INDEX CONCURRENTLY idx_users_email_unique 
        ON users(email);
        
        -- For 10M rows: ~10-20 minutes
        -- Zero downtime: reads and writes continue
        -- Uses MVCC to build index incrementally
        """)
    public void phase2CreateIndex() {
        log.info("Creating unique index concurrently...");
        
        // Monitor progress
        monitorIndexCreation("idx_users_email_unique");
        
        log.info("Unique index created successfully");
    }
    
    private void monitorIndexCreation(String indexName) {
        // Query to check index creation progress
        String progressSql = """
            SELECT 
                phase,
                tuples_done,
                tuples_total,
                ROUND(100.0 * tuples_done / NULLIF(tuples_total, 0), 2) as percent_done
            FROM pg_stat_progress_create_index
            WHERE relid = 'users'::regclass
            """;
        
        // Poll every 30 seconds
        while (true) {
            try {
                Map<String, Object> progress = jdbcTemplate.queryForMap(progressSql);
                log.info("Index creation progress: {}% ({}/{})",
                    progress.get("percent_done"),
                    progress.get("tuples_done"),
                    progress.get("tuples_total"));
                
                Thread.sleep(30000);
            } catch (EmptyResultDataAccessException e) {
                // Index creation complete
                break;
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
    }
    
    // === Phase 3: Add Constraint Using Existing Index ===
    
    @Sql("""
        -- Add unique constraint using existing index (fast)
        ALTER TABLE users 
        ADD CONSTRAINT uk_users_email 
        UNIQUE USING INDEX idx_users_email_unique;
        
        -- Takes <1 second (just catalog update)
        -- No table scan needed (index already validates uniqueness)
        """)
    public void phase3AddConstraint() {
        log.info("Adding unique constraint using existing index...");
        
        // Verify constraint
        String verifySql = """
            SELECT constraint_name, constraint_type
            FROM information_schema.table_constraints
            WHERE table_name = 'users'
              AND constraint_name = 'uk_users_email'
            """;
        
        String constraintType = jdbcTemplate.queryForObject(
            verifySql,
            String.class
        );
        
        assertEquals("UNIQUE", constraintType);
        log.info("Unique constraint added successfully");
    }
    
    // === Phase 4: Verify and Monitor ===
    
    public void phase4Verify() {
        // Test constraint is working
        try {
            jdbcTemplate.update(
                "INSERT INTO users (email) VALUES (?)",
                "duplicate@example.com"
            );
            jdbcTemplate.update(
                "INSERT INTO users (email) VALUES (?)",
                "duplicate@example.com"  // Should fail
            );
            fail("Unique constraint not enforced!");
        } catch (DataIntegrityViolationException e) {
            // Expected - constraint is working
            log.info("Unique constraint verified: {}", e.getMessage());
        }
        
        // Monitor for violations (application bugs)
        String violationsSql = """
            SELECT COUNT(*) 
            FROM pg_stat_database_conflicts
            WHERE datname = current_database()
              AND confl_lock > 0
            """;
        
        Long violations = jdbcTemplate.queryForObject(violationsSql, Long.class);
        log.info("Constraint violations detected: {}", violations);
    }
}
```

### Q2: "Explain the difference between forward-only and reversible migrations."

**Answer**: Reversible migrations can be rolled back safely (adding nullable columns, creating indexes) - use for schema changes. Forward-only migrations can't be reversed without data loss (dropping columns, data transformations) - use when rollback is impossible. Best practice: Keep old schema alongside new for 30 days before dropping (allows rollback).

**Comparison and Examples**

```java
// === REVERSIBLE MIGRATIONS ===
```

**Decision Matrix**

```java
public class MigrationTypeDecider {
    
    public MigrationType decideMigrationType(Migration migration) {
        
        // Reversible migrations (can rollback safely)
        if (migration.isAddColumn() && migration.isNullable()) {
            return MigrationType.REVERSIBLE;
        }
        
        if (migration.isAddTable()) {
            return MigrationType.REVERSIBLE_WITH_DATA_LOSS;
            // Reversible, but loses data if rolled back after use
        }
        
        if (migration.isAddIndex() || migration.isAddConstraint()) {
            return MigrationType.REVERSIBLE;
        }
        
        if (migration.isRenameColumn()) {
            return MigrationType.REVERSIBLE;
            // Can undo rename without data loss
        }
        
        // Forward-only migrations (cannot rollback)
        if (migration.isDropColumn()) {
            return MigrationType.FORWARD_ONLY;
            // Data lost when column dropped
        }
        
        if (migration.isDataTransformation()) {
            return MigrationType.FORWARD_ONLY;
            // Original data modified/lost
        }
        
        if (migration.isDropTable()) {
            return MigrationType.FORWARD_ONLY;
            // All table data lost
        }
        
        if (migration.isChangeColumnType() && !migration.isConversionLossless()) {
            return MigrationType.FORWARD_ONLY;
            // Data precision/format lost
        }
        
        return MigrationType.UNKNOWN;
    }
}

enum MigrationType {
    REVERSIBLE,                  // Can rollback with zero data loss
    REVERSIBLE_WITH_DATA_LOSS,   // Can rollback, but loses data created after migration
    FORWARD_ONLY                 // Cannot rollback without data loss
}
```

### Q3: "How do you handle data migrations that take hours to complete?"

**Answer**: Use batched approach: process 10K rows at a time with LIMIT/OFFSET, add pg_sleep() to avoid overload, track progress in migration_status table, make resumable (WHERE id > last_processed_id). For multi-hour migrations: run in background job (not in deployment), provide progress monitoring, allow graceful stop/resume. Example: 100M rows in 1K batches = 100K iterations × 2s = 55 hours, spread over days.

**Batched Migration Implementation**

```java
@Service
public class LongRunningDataMigration {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    // === Strategy 1: Batch Processing with Progress Tracking ===
    
    public void migrateDataInBatches() {
        int batchSize = 10_000;
        long lastProcessedId = getLastProcessedId();
        long totalRows = getTotalRows();
        
        log.info("Starting data migration from ID {}", lastProcessedId);
        log.info("Total rows to migrate: {}", totalRows - lastProcessedId);
        
        while (true) {
            long start = System.currentTimeMillis();
            
            // Process one batch
            int processedCount = processBatch(lastProcessedId, batchSize);
            
            if (processedCount == 0) {
                log.info("Migration complete!");
                break;
            }
            
            // Update progress
            lastProcessedId += batchSize;
            updateProgress(lastProcessedId, totalRows);
            
            long duration = System.currentTimeMillis() - start;
            log.info("Processed batch of {} rows in {}ms", processedCount, duration);
            
            // Throttle to avoid overload (adjust based on system load)
            try {
                Thread.sleep(100);  // 100ms delay between batches
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                log.warn("Migration interrupted, saving progress...");
                saveProgress(lastProcessedId);
                return;
            }
        }
        
        // Mark migration as complete
        markMigrationComplete();
    }
    
    private int processBatch(long lastProcessedId, int batchSize) {
        String sql = """
            UPDATE users
            SET email = username || '@migrated.com'
            WHERE id > ?
              AND id <= ?
              AND email IS NULL
            """;
        
        return jdbcTemplate.update(sql, lastProcessedId, lastProcessedId + batchSize);
    }
    
    private long getLastProcessedId() {
        String sql = """
            SELECT COALESCE(last_processed_id, 0)
            FROM migration_progress
            WHERE migration_name = 'backfill_email_v1'
            """;
        
        try {
            return jdbcTemplate.queryForObject(sql, Long.class);
        } catch (EmptyResultDataAccessException e) {
            // First run - initialize progress tracking
            initializeProgress();
            return 0;
        }
    }
    
    private void updateProgress(long lastProcessedId, long totalRows) {
        String sql = """
            UPDATE migration_progress
            SET last_processed_id = ?,
                updated_at = NOW(),
                progress_pct = ROUND(100.0 * ? / ?, 2)
            WHERE migration_name = 'backfill_email_v1'
            """;
        
        jdbcTemplate.update(sql, lastProcessedId, lastProcessedId, totalRows);
    }
}
```

**Resumable Migration Pattern**

```sql
-- Resumable migration using WHERE clause

-- Instead of this (not resumable):
UPDATE users SET email = username || '@example.com' WHERE email IS NULL;

-- Do this (resumable):
DO $$
DECLARE
    batch_size INT := 10000;
    rows_updated INT;
    last_id BIGINT := 0;
BEGIN
    -- Get last processed ID from previous run
    SELECT COALESCE(last_processed_id, 0) INTO last_id
    FROM migration_progress
    WHERE migration_name = 'backfill_email_v1';
    
    LOOP
        -- Update one batch
        UPDATE users
        SET email = username || '@example.com'
        WHERE id > last_id
          AND id <= last_id + batch_size
          AND email IS NULL;
        
        GET DIAGNOSTICS rows_updated = ROW_COUNT;
        
        -- Exit if no more rows
        EXIT WHEN rows_updated = 0;
        
        -- Update progress
        last_id := last_id + batch_size;
        UPDATE migration_progress
        SET last_processed_id = last_id,
            updated_at = NOW()
        WHERE migration_name = 'backfill_email_v1';
        
        -- Small delay to avoid overload
        PERFORM pg_sleep(0.1);
        
        -- Log progress every 100 batches
        IF last_id % (batch_size * 100) = 0 THEN
            RAISE NOTICE 'Processed up to ID: %', last_id;
        END IF;
    END LOOP;
    
    -- Mark complete
    UPDATE migration_progress
    SET status = 'COMPLETED',
        completed_at = NOW()
    WHERE migration_name = 'backfill_email_v1';
END $$;
```

### Q4: "What's your strategy for testing schema changes with production data?"

**Answer**: Use 5-step approach: (1) Take production snapshot with pg_dump, (2) Restore to staging with anonymization, (3) Run migration on staging, (4) Verify data integrity (row counts, constraints, indexes), (5) Performance test with production load. Automate with nightly pipeline. Never test on production first - always staging with real data volumes.

```java
        for (String table : preState.getTableCounts().keySet()) {

            long postCount = postState.getTableCounts().get(table);

                    table, preCount, postCount

                conname,
                conrelid::regclass AS table_name,

            WHERE connamespace = 'public'::regnamespace

                validateConstraint(constraint);
            } catch (Exception e) {

        if (!errors.isEmpty()) {

            errors.forEach(log::error);
            throw new RuntimeException("Migration verification failed");
        } else {
            log.info("Migration verification passed all checks");
        }
    }
```

### Q5: "How would you migrate from one database to another (e.g., MySQL to PostgreSQL) with zero downtime?"

### Q7: "What's the difference between REINDEX CONCURRENTLY and regular REINDEX during schema migrations?"

**Answer**: REINDEX CONCURRENTLY doesn't lock table (allows reads/writes), but takes 2-3x longer and needs 2x disk space. Regular REINDEX locks table (blocks writes), faster, but causes downtime. For production: always use CONCURRENTLY. Example: 10GB index = 20 minutes CONCURRENTLY (zero downtime) vs 8 minutes regular (8 minutes downtime).

**Detailed Comparison**

```sql
-- Regular REINDEX (BLOCKS WRITES)

REINDEX INDEX idx_users_email;

-- Behavior:
-- - Takes ACCESS EXCLUSIVE lock (blocks all operations)
-- - Builds new index
-- - Swaps with old index
-- - Drops old index
-- Duration: 100% of rebuild time
-- Downtime: 100% of rebuild time
-- Disk space: 1x index size during operation

-- Example: 10GB index, 1M rows
-- Duration: 8 minutes
-- Downtime: 8 minutes (ALL writes blocked)
-- Disk space: 10GB temporarily


-- REINDEX CONCURRENTLY (NO BLOCKING)

REINDEX INDEX CONCURRENTLY idx_users_email;

-- Behavior:
-- - Takes SHARE UPDATE EXCLUSIVE lock (allows reads AND writes)
-- - Builds new index alongside old one
-- - Validates new index
-- - Swaps indexes (brief lock, ~100ms)
-- - Drops old index
-- Duration: 200-300% of rebuild time
-- Downtime: ~100ms (brief swap)
-- Disk space: 2x index size during operation

-- Example: 10GB index, 1M rows
-- Duration: 20 minutes (2.5x slower)
-- Downtime: 100ms (just for swap)
-- Disk space: 20GB temporarily (needs 2x space)
```

**When to Use Each**

```java
public class ReindexStrategy {
    
    public void chooseReindexMethod(Index index) {
        long indexSize = index.getSize();
        boolean isProduction = environment.equals("production");
        boolean hasMaintenanceWindow = hasScheduledMaintenance();
        
        if (isProduction && !hasMaintenanceWindow) {
            // Production, no maintenance window
            // MUST use CONCURRENTLY
            reindexConcurrently(index);
        } else if (hasMaintenanceWindow && indexSize > 100_000_000_000L) {
            // Very large index (>100GB) + maintenance window
            // Regular REINDEX is 3x faster
            reindexRegular(index);
        } else if (isProduction) {
            // Production with maintenance window
            // Still use CONCURRENTLY (safer)
            reindexConcurrently(index);
        } else {
            // Development/staging
            // Use regular (faster)
            reindexRegular(index);
        }
    }
}
```

**Performance Comparison**

```

Regular REINDEX:
- Duration: 8 minutes
- Downtime: 8 minutes
- Disk space: 10GB peak
- Writes blocked: Yes (8 minutes)
- Safe for production: NO

REINDEX CONCURRENTLY:
- Duration: 20 minutes
- Downtime: 100ms
- Disk space: 20GB peak
- Writes blocked: No (100ms swap)
- Safe for production: YES
```

### Q8: "How do you handle schema changes in a microservices architecture where multiple services share a database?"

**Answer**: DON'T share databases between microservices (violates bounded context). If unavoidable: (1) Create database views per service (encapsulation), (2) Version schema changes (backward compatible), (3) Coordinate deployments (deploy schema → service A → service B), (4) Use database-per-service pattern when possible. Sharing databases creates tight coupling and deployment hell.

**Handling Shared Database (Anti-pattern)**

```java
// PROBLEM: Multiple microservices share same database

// Service A (Order Service)
@Entity
@Table(name = "orders")
public class Order {
    @Id private Long id;
    @Column private String status;
    @Column private BigDecimal total;
}

// Service B (Shipping Service) - READS SAME TABLE
@Entity
@Table(name = "orders")
public class OrderReadModel {
    @Id private Long id;
    @Column private String status;  // Only needs status
}

// ISSUE: Service A wants to rename "status" to "order_status"
// This breaks Service B!

// === SOLUTION 1: Database Views (Isolation) ===

-- Create view for each service

-- View for Service A (full access)
CREATE VIEW order_service.orders AS
SELECT * FROM public.orders;

-- View for Service B (limited access)
CREATE VIEW shipping_service.orders AS
SELECT id, status, shipping_address FROM public.orders;

-- Now Service A can change underlying table without breaking Service B
ALTER TABLE public.orders RENAME COLUMN status TO order_status;

-- Update Service A's view
CREATE OR REPLACE VIEW order_service.orders AS
SELECT 
    id,
    order_status AS status,  -- Map back for compatibility
    total,
    ...
FROM public.orders;

-- Service B's view still works (abstraction layer)
```

**Versioned Schema Pattern**

```java
@Service
public class VersionedSchemaService {
    
    // Service A uses v2 schema
    @Entity
    @Table(name = "orders", schema = "orders_v2")
    public class OrderV2 {
        @Column private String orderStatus;  // New column name
    }
    
    // Service B uses v1 schema (compatibility view)
    @Entity
    @Table(name = "orders", schema = "orders_v1")
    public class OrderV1 {
        @Column private String status;  // Old column name
    }
    
    // Database has both schemas:
    // orders_v1.orders -> view with old column names
    // orders_v2.orders -> view with new column names
    // public.orders -> actual table
}
```

**Coordinated Deployment Strategy**

```
Step 1: Deploy schema change (backward compatible)
  ALTER TABLE orders ADD COLUMN order_status VARCHAR(20);
  UPDATE orders SET order_status = status;
  
Step 2: Deploy Service A (uses new column)
  - Dual-write to both columns
  - Reads from new column
  
Step 3: Wait 1 week (ensure Service A stable)

Step 4: Deploy Service B (uses new column)
  - Switch to new column
  
Step 5: Drop old column (after both services migrated)
  ALTER TABLE orders DROP COLUMN status;
```

**Better Solution: Database-Per-Service**

```java
// RECOMMENDED: Each service has its own database

// Order Service
@Entity
@Table(name = "orders")
public class Order {
    @Id private Long id;
    private String status;
    private BigDecimal total;
}

// Shipping Service (separate database)
@Entity
@Table(name = "shipments")
public class Shipment {
    @Id private Long id;
    private Long orderId;  // Reference, not FK
    private String address;
    private String status;
}

// Communication via events, not shared database
@Service
public class OrderService {
    
    @Transactional
    public Order createOrder(Order order) {
        Order saved = orderRepository.save(order);
        
        // Publish event instead of writing to shared DB
        eventPublisher.publish(new OrderCreatedEvent(saved));
        
        return saved;
    }
}

// Shipping Service listens to events
@EventListener
public void onOrderCreated(OrderCreatedEvent event) {
    Shipment shipment = new Shipment();
    shipment.setOrderId(event.getOrderId());
    shipmentRepository.save(shipment);
}
```
