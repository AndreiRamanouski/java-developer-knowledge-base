## Q2: MySQL-specific optimizations

**Short Answer**: InnoDB buffer pool should be 70-80% of RAM (innodb_buffer_pool_size). Query cache deprecated in 8.0 (use application caching). Index hints: FORCE INDEX, USE INDEX in native queries for optimizer control. FULLTEXT indexes for full-text search (MATCH AGAINST). Partitioning: RANGE for time-series, LIST for categories, HASH for even distribution. Covering indexes include all SELECT columns to avoid table access.

## 1. InnoDB Configuration

### innodb_buffer_pool_size (Most Critical)

```sql
-- Check current buffer pool size
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- Default: 128MB (way too small for production!)

-- Optimal setting: 70-80% of available RAM
-- For 16GB RAM server: 12GB
-- For 32GB RAM server: 24GB
-- For 64GB RAM server: 48GB

-- Set in my.cnf (Linux) or my.ini (Windows)
[mysqld]
innodb_buffer_pool_size = 12G

-- Or set dynamically (MySQL 5.7+)
SET GLOBAL innodb_buffer_pool_size = 12884901888;  -- 12GB in bytes

-- Monitor buffer pool usage
SHOW STATUS LIKE 'Innodb_buffer_pool%';

-- Key metrics:
-- Innodb_buffer_pool_pages_data: Pages containing data
-- Innodb_buffer_pool_pages_free: Free pages
-- Innodb_buffer_pool_read_requests: Read requests from cache
-- Innodb_buffer_pool_reads: Reads from disk (should be low)

-- Calculate cache hit ratio
SELECT 
    ROUND(100 - (
        (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests) * 100
    ), 2) AS cache_hit_ratio
FROM (
    SELECT 
        VARIABLE_VALUE AS Innodb_buffer_pool_reads
    FROM information_schema.GLOBAL_STATUS
    WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads'
) AS reads,
(
    SELECT 
        VARIABLE_VALUE AS Innodb_buffer_pool_read_requests
    FROM information_schema.GLOBAL_STATUS
    WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests'
) AS read_requests;

-- Target: > 99% cache hit ratio
```

## 2. Query Cache (Deprecated in MySQL 8.0)

### Understanding Query Cache Deprecation

```sql
-- MySQL 5.7 and earlier: Query cache available

-- Check query cache status
SHOW VARIABLES LIKE 'query_cache%';
-- query_cache_type: ON/OFF/DEMAND
-- query_cache_size: Size in bytes
-- query_cache_limit: Max result size to cache

-- Configuration (my.cnf)
[mysqld]
query_cache_type = 1                    # 0=OFF, 1=ON, 2=DEMAND
query_cache_size = 256M                 # Total cache size
query_cache_limit = 2M                  # Max per-query result size
query_cache_min_res_unit = 4K          # Allocation block size

-- Monitor query cache
SHOW STATUS LIKE 'Qcache%';
-- Qcache_hits: Queries served from cache
-- Qcache_inserts: Queries added to cache
-- Qcache_not_cached: Queries not cached
-- Qcache_lowmem_prunes: Queries evicted due to low memory

-- Calculate cache hit ratio
SELECT 
    ROUND(100 * Qcache_hits / (Qcache_hits + Com_select), 2) AS hit_ratio
FROM 
    (SELECT VARIABLE_VALUE AS Qcache_hits 
     FROM information_schema.GLOBAL_STATUS 
     WHERE VARIABLE_NAME = 'Qcache_hits') AS hits,
    (SELECT VARIABLE_VALUE AS Com_select 
     FROM information_schema.GLOBAL_STATUS 
     WHERE VARIABLE_NAME = 'Com_select') AS selects;

-- MySQL 8.0+: Query cache REMOVED
-- Reason: Lock contention, limited scalability, modern alternatives better
```

### Why Query Cache Was Deprecated

```
Problems with MySQL Query Cache:
1. Single mutex: All queries contend for one lock
2. Invalidation on ANY write: UPDATE invalidates entire table's cache
3. Limited scalability: Becomes bottleneck at high concurrency
4. False positives: Similar queries with different results
5. Memory fragmentation: Over time, cache becomes inefficient

Example scenario:
- Query: SELECT * FROM products WHERE category = 'electronics'
- Cached result: 1000 rows
- Any INSERT/UPDATE/DELETE on products table → Entire cache invalidated
- High write workload → Cache constantly invalidated → More overhead than benefit
```

### Modern Alternative: Application-Level Caching

```java
// === Spring Boot Cache Configuration ===

@Configuration
@EnableCaching
public class CacheConfig {
    
    @Bean
    public CacheManager cacheManager() {
        // Caffeine cache (in-memory, local to each instance)
        CaffeineCacheManager cacheManager = new CaffeineCacheManager("users", "products");
        cacheManager.setCaffeine(Caffeine.newBuilder()
            .maximumSize(10000)
            .expireAfterWrite(Duration.ofMinutes(10))
            .recordStats());
        
        return cacheManager;
    }
}

// === Using Cache Annotations ===

@Service
public class ProductService {
    
    @Autowired
    private ProductRepository productRepository;
    
    // Cache method result
    @Cacheable(value = "products", key = "#id")
    public Product findById(Long id) {
        log.info("Fetching product from database: {}", id);
        return productRepository.findById(id).orElseThrow();
    }
    
    // Cache with condition
    @Cacheable(value = "products", key = "#category", condition = "#category.length() < 50")
    public List<Product> findByCategory(String category) {
        return productRepository.findByCategory(category);
    }
    
    // Evict cache on update
    @CacheEvict(value = "products", key = "#product.id")
    public Product update(Product product) {
        return productRepository.save(product);
    }
    
    // Evict entire cache
    @CacheEvict(value = "products", allEntries = true)
    public void clearCache() {
        log.info("Clearing product cache");
    }
    
    // Update cache
    @CachePut(value = "products", key = "#product.id")
    public Product create(Product product) {
        return productRepository.save(product);
    }
}
```

```java
// === Cache-Aside Pattern (Manual Control) ===

@Service
public class ProductServiceWithRedis {
    
    @Autowired
    private ProductRepository productRepository;
    
    @Autowired
    private RedisTemplate<String, Product> redisTemplate;
    
    public Product findById(Long id) {
        String cacheKey = "product:" + id;
        
        // Try cache first
        Product cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            log.info("Cache hit for product: {}", id);
            return cached;
        }
        
        // Cache miss - fetch from database
        log.info("Cache miss for product: {}", id);
        Product product = productRepository.findById(id).orElseThrow();
        
        // Store in cache
        redisTemplate.opsForValue().set(cacheKey, product, Duration.ofMinutes(10));
        
        return product;
    }
    
    public Product update(Product product) {
        Product updated = productRepository.save(product);
        
        // Invalidate cache
        String cacheKey = "product:" + product.getId();
        redisTemplate.delete(cacheKey);
        
        return updated;
    }
}
```

## 3. Index Hints in Native Queries

### When to Use Index Hints

```sql
-- MySQL query optimizer usually chooses best index
-- But sometimes it makes wrong decisions

-- Scenario: Table with multiple indexes
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    customer_id BIGINT,
    status VARCHAR(20),
    created_at DATETIME,
    INDEX idx_customer (customer_id),
    INDEX idx_status (status),
    INDEX idx_created (created_at),
    INDEX idx_composite (status, created_at)
);

-- Query: Find recent orders by status
SELECT * FROM orders 
WHERE status = 'PENDING' 
  AND created_at > '2024-01-01'
ORDER BY created_at DESC
LIMIT 100;

-- Optimizer chooses idx_status (wrong!)
-- Scans 100,000 PENDING orders, then filters by date
-- Time: 500ms

-- We know idx_composite is better
-- Filters by status AND date, already sorted
-- Time: 50ms

-- Solution: FORCE INDEX
SELECT * FROM orders 
FORCE INDEX (idx_composite)
WHERE status = 'PENDING' 
  AND created_at > '2024-01-01'
ORDER BY created_at DESC
LIMIT 100;
```

### Index Hint Types

```sql
-- === USE INDEX ===
-- Suggests index to optimizer (may be ignored)
SELECT * FROM orders 
USE INDEX (idx_composite)
WHERE status = 'PENDING';

-- === FORCE INDEX ===
-- Forces optimizer to use specific index
SELECT * FROM orders 
FORCE INDEX (idx_composite)
WHERE status = 'PENDING';

-- === IGNORE INDEX ===
-- Tells optimizer to NOT use specific index
SELECT * FROM orders 
IGNORE INDEX (idx_status)
WHERE status = 'PENDING';

-- === Multiple indexes ===
SELECT * FROM orders 
USE INDEX (idx_status, idx_created)
WHERE status = 'PENDING' AND created_at > '2024-01-01';

-- === FOR JOIN ===
SELECT o.*, c.name
FROM orders o
FORCE INDEX FOR JOIN (idx_customer)
JOIN customers c ON o.customer_id = c.id;

-- === FOR ORDER BY ===
SELECT * FROM orders
FORCE INDEX FOR ORDER BY (idx_created)
ORDER BY created_at DESC
LIMIT 100;

-- === FOR GROUP BY ===
SELECT status, COUNT(*)
FROM orders
FORCE INDEX FOR GROUP BY (idx_status)
GROUP BY status;
```

### When Index Hints Are Needed

```java
@Service
public class IndexHintDecisionService {
    
    public boolean shouldUseIndexHint(QueryAnalysis analysis) {
        
        // Reason 1: Optimizer consistently chooses wrong index
        if (analysis.getEstimatedRows() > analysis.getActualRows() * 10) {
            log.warn("Optimizer overestimating rows: {} vs {}", 
                    analysis.getEstimatedRows(), analysis.getActualRows());
            return true;  // Force correct index
        }
        
        // Reason 2: Statistics are stale
        if (analysis.getStatisticsAge() > 7) {  // > 7 days old
            log.warn("Table statistics are {} days old", analysis.getStatisticsAge());
            // Update statistics first: ANALYZE TABLE orders;
            return true;  // May need hint until stats updated
        }
        
        // Reason 3: Query needs specific index for ORDER BY
        if (analysis.hasOrderBy() && analysis.usesFilesort()) {
            log.warn("Query using filesort, force index for ORDER BY");
            return true;  // Force index that matches ORDER BY
        }
        
        // Reason 4: Covering index available but not used
        if (analysis.hasCoveringIndex() && !analysis.usesCoveringIndex()) {
            log.warn("Covering index available but not used");
            return true;  // Force covering index
        }
        
        return false;  // Let optimizer decide
    }
}
```

## 4. FULLTEXT Indexes for Search

### Creating FULLTEXT Indexes

```sql
-- FULLTEXT index for text search (MyISAM or InnoDB 5.6+)

CREATE TABLE articles (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(255),
    content TEXT,
    author VARCHAR(100),
    created_at DATETIME,
    FULLTEXT INDEX ft_title_content (title, content)
) ENGINE=InnoDB;

-- Add FULLTEXT index to existing table
ALTER TABLE articles ADD FULLTEXT INDEX ft_content (content);

-- Create with multiple columns (combined search)
CREATE FULLTEXT INDEX ft_all ON articles(title, content, author);

-- Drop FULLTEXT index
DROP INDEX ft_title_content ON articles;
```

### FULLTEXT Search Modes

```sql
-- === 1. NATURAL LANGUAGE MODE (Default) ===
-- Searches for words, ranks by relevance

SELECT *, MATCH(title, content) AGAINST('spring boot mysql') AS relevance
FROM articles
WHERE MATCH(title, content) AGAINST('spring boot mysql')
ORDER BY relevance DESC
LIMIT 10;

-- How it works:
-- - Splits query into words: "spring", "boot", "mysql"
-- - Finds articles containing these words
-- - Ranks by: word frequency, word rarity (IDF), document length
-- - Higher score = more relevant


-- === 2. BOOLEAN MODE ===
-- Advanced search with operators

-- AND operator (+): Must contain
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('+spring +boot' IN BOOLEAN MODE);
-- Must contain both "spring" AND "boot"

-- OR operator: Any word
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('spring boot' IN BOOLEAN MODE);
-- Contains "spring" OR "boot"

-- NOT operator (-): Exclude
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('+spring -hibernate' IN BOOLEAN MODE);
-- Contains "spring" but NOT "hibernate"

-- Phrase search ("..."): Exact phrase
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('"spring boot"' IN BOOLEAN MODE);
-- Must contain exact phrase "spring boot"

-- Wildcard (*): Prefix match
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('spring*' IN BOOLEAN MODE);
-- Matches: spring, springs, springing, etc.

-- Relevance modifier (>): Increase importance
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('>spring <boot' IN BOOLEAN MODE);
-- "spring" more important than "boot"

-- Combined example
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST(
    '+spring +boot -hibernate "dependency injection"' IN BOOLEAN MODE
);
-- Must have "spring" and "boot"
-- Must not have "hibernate"
-- Bonus for exact phrase "dependency injection"


-- === 3. QUERY EXPANSION MODE ===
-- Automatic query expansion (finds related terms)

SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('mysql' WITH QUERY EXPANSION);

-- How it works:
-- 1. First pass: Find articles matching "mysql"
-- 2. Analyze top results for common words
-- 3. Second pass: Search for original + related words
-- Example: "mysql" → expands to "mysql database sql mariadb"
```

### Full-Text Search Service

```java
@Service
public class FullTextSearchService {
    
    @Autowired
    private ArticleRepository articleRepository;
    
    // Simple search
    public List<Article> search(String query) {
        return articleRepository.searchFullText(query);
    }
    
    // Advanced search with boolean operators
    public List<Article> advancedSearch(SearchRequest request) {
        StringBuilder query = new StringBuilder();
        
        // Must have words
        if (request.getMustHave() != null && !request.getMustHave().isEmpty()) {
            request.getMustHave().forEach(word -> 
                query.append("+").append(word).append(" ")
            );
        }
        
        // Must not have words
        if (request.getMustNotHave() != null && !request.getMustNotHave().isEmpty()) {
            request.getMustNotHave().forEach(word -> 
                query.append("-").append(word).append(" ")
            );
        }
        
        // Exact phrases
        if (request.getExactPhrases() != null && !request.getExactPhrases().isEmpty()) {
            request.getExactPhrases().forEach(phrase -> 
                query.append("\"").append(phrase).append("\" ")
            );
        }
        
        return articleRepository.searchFullTextBoolean(query.toString().trim());
    }
    
    // Search with highlighting
    public List<ArticleSearchResult> searchWithHighlight(String query) {
        List<Article> articles = articleRepository.searchFullText(query);
        
        return articles.stream()
            .map(article -> {
                ArticleSearchResult result = new ArticleSearchResult();
                result.setArticle(article);
                result.setHighlightedTitle(highlightText(article.getTitle(), query));
                result.setHighlightedSnippet(extractSnippet(article.getContent(), query));
                return result;
            })
            .collect(Collectors.toList());
    }
    
    private String highlightText(String text, String query) {
        String[] words = query.split("\\s+");
        String highlighted = text;
        
        for (String word : words) {
            highlighted = highlighted.replaceAll(
                "(?i)" + Pattern.quote(word),
                "<mark>$0</mark>"
            );
        }
        
        return highlighted;
    }
    
    private String extractSnippet(String content, String query) {
        String[] words = query.split("\\s+");
        
        // Find first occurrence of any query word
        int position = -1;
        for (String word : words) {
            int pos = content.toLowerCase().indexOf(word.toLowerCase());
            if (pos != -1 && (position == -1 || pos < position)) {
                position = pos;
            }
        }
        
        if (position == -1) {
            // No match, return beginning
            return content.substring(0, Math.min(200, content.length())) + "...";
        }
        
        // Extract snippet around match
        int start = Math.max(0, position - 100);
        int end = Math.min(content.length(), position + 100);
        
        String snippet = content.substring(start, end);
        if (start > 0) snippet = "..." + snippet;
        if (end < content.length()) snippet = snippet + "...";
        
        return highlightText(snippet, query);
    }
}

    private List<String> exactPhrases;
```

## 5. Partitioning Strategies

### Understanding Table Partitioning

```sql
-- Partitioning splits large table into smaller physical pieces
-- Each partition is stored separately but queried as single table

-- Benefits:
-- 1. Faster queries (partition pruning - scans only relevant partitions)
-- 2. Faster deletes (DROP PARTITION vs DELETE millions of rows)
-- 3. Better maintenance (backup/restore individual partitions)
-- 4. Parallel query execution

-- Check if partitioning is enabled
SHOW PLUGINS;
-- Look for "partition" plugin (enabled by default in MySQL 5.6+)
```

### RANGE Partitioning (Time-Series Data)

```sql
-- === RANGE Partitioning: Split by value ranges ===
-- Best for: Time-series data, sequential data

-- Example: Orders table partitioned by month
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT,
    customer_id BIGINT,
    order_date DATE,
    total DECIMAL(10,2),
    status VARCHAR(20),
    PRIMARY KEY (id, order_date),  -- Partition key must be in PK
    INDEX idx_customer (customer_id),
    INDEX idx_status (status)
)
PARTITION BY RANGE (YEAR(order_date) * 100 + MONTH(order_date)) (
    PARTITION p202401 VALUES LESS THAN (202402),  -- Jan 2024
    PARTITION p202402 VALUES LESS THAN (202403),  -- Feb 2024
    PARTITION p202403 VALUES LESS THAN (202404),  -- Mar 2024
    PARTITION p202404 VALUES LESS THAN (202405),  -- Apr 2024
    PARTITION p202405 VALUES LESS THAN (202406),  -- May 2024
    PARTITION p202406 VALUES LESS THAN (202407),  -- Jun 2024
    PARTITION p_future VALUES LESS THAN MAXVALUE   -- Future data
);

-- Query with partition pruning
EXPLAIN PARTITIONS
SELECT * FROM orders 
WHERE order_date BETWEEN '2024-03-01' AND '2024-03-31';

-- Result:
-- partitions: p202403  (only scans March partition!)
-- rows: 100,000 instead of 1,200,000 (12x less data scanned)

-- Add new partition for new month
ALTER TABLE orders 
ADD PARTITION (
    PARTITION p202407 VALUES LESS THAN (202408)
);

-- Drop old partition (instant delete of old data)
ALTER TABLE orders DROP PARTITION p202401;
-- Much faster than: DELETE FROM orders WHERE order_date < '2024-02-01'

-- Reorganize future partition
ALTER TABLE orders 
REORGANIZE PARTITION p_future INTO (
    PARTITION p202407 VALUES LESS THAN (202408),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

### LIST Partitioning (Categorical Data)

```sql
-- === LIST Partitioning: Split by discrete values ===
-- Best for: Categories, regions, status codes

-- Example: Users table partitioned by region
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT,
    name VARCHAR(100),
    email VARCHAR(255),
    region VARCHAR(20),
    created_at DATETIME,
    PRIMARY KEY (id, region),  -- Region must be in PK
    INDEX idx_email (email)
)
PARTITION BY LIST COLUMNS (region) (
    PARTITION p_us VALUES IN ('US', 'USA', 'UNITED_STATES'),
    PARTITION p_eu VALUES IN ('UK', 'DE', 'FR', 'IT', 'ES'),
    PARTITION p_asia VALUES IN ('JP', 'CN', 'IN', 'KR'),
    PARTITION p_other VALUES IN ('AU', 'BR', 'CA', 'MX')
);

-- Query with partition pruning
SELECT * FROM users WHERE region = 'US';
-- Only scans p_us partition

-- Multi-region query
SELECT * FROM users WHERE region IN ('US', 'UK');
-- Scans p_us and p_eu partitions only

-- Add value to partition
ALTER TABLE users 
REORGANIZE PARTITION p_other INTO (
    PARTITION p_latam VALUES IN ('BR', 'MX', 'AR', 'CL'),
    PARTITION p_other VALUES IN ('AU', 'CA', 'ZA')
);
```

### HASH Partitioning (Even Distribution)

```sql
-- === HASH Partitioning: Distribute data evenly ===
-- Best for: Even distribution, no natural partition key

-- Example: Sessions table with HASH on user_id
CREATE TABLE sessions (
    id BIGINT AUTO_INCREMENT,
    user_id BIGINT,
    session_token VARCHAR(255),
    created_at DATETIME,
    expires_at DATETIME,
    PRIMARY KEY (id, user_id),  -- user_id must be in PK
    INDEX idx_token (session_token)
)
PARTITION BY HASH (user_id)
PARTITIONS 8;  -- 8 partitions (power of 2 recommended)

-- Data is distributed evenly:
-- user_id 1 → partition 1 (1 % 8 = 1)
-- user_id 2 → partition 2 (2 % 8 = 2)
-- user_id 9 → partition 1 (9 % 8 = 1)
-- Each partition has ~12.5% of data

-- Query (no partition pruning with HASH)
SELECT * FROM sessions WHERE user_id = 123;
-- Scans 1 partition (MySQL knows which one from hash)

-- Add partitions (redistributes data)
ALTER TABLE sessions ADD PARTITION PARTITIONS 4;  -- Now 12 partitions

-- LINEAR HASH (faster partition addition, less balanced)
CREATE TABLE sessions_linear (
    id BIGINT AUTO_INCREMENT,
    user_id BIGINT,
    PRIMARY KEY (id, user_id)
)
PARTITION BY LINEAR HASH (user_id)
PARTITIONS 8;
```

### KEY Partitioning (MySQL's Hash Function)

```sql
-- === KEY Partitioning: Like HASH but uses MySQL's hash function ===
-- Simpler than HASH, good default choice

CREATE TABLE logs (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT,
    action VARCHAR(50),
    created_at DATETIME
)
PARTITION BY KEY (id)
PARTITIONS 10;

-- Or partition by multiple columns
PARTITION BY KEY (user_id, created_at)
PARTITIONS 10;
```

```java
@Service
public class PartitionManagementService {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    // Add new month partition
    @Scheduled(cron = "0 0 1 * * *")  // 1st of each month
    public void addNewMonthPartition() {
        LocalDate nextMonth = LocalDate.now().plusMonths(1);
        int yearMonth = nextMonth.getYear() * 100 + nextMonth.getMonthValue();
        String partitionName = String.format("p%d", yearMonth);
        
        String sql = String.format("""
            ALTER TABLE orders
            REORGANIZE PARTITION p_future INTO (
                PARTITION %s VALUES LESS THAN (%d),
                PARTITION p_future VALUES LESS THAN MAXVALUE
            )
            """, partitionName, yearMonth + 1);
        
        try {
            jdbcTemplate.execute(sql);
            log.info("Created partition: {}", partitionName);
        } catch (Exception e) {
            log.error("Failed to create partition", e);
        }
    }
    
    // Drop old partitions (data retention)
    @Scheduled(cron = "0 0 2 1 * *")  // 2 AM on 1st of month
    public void dropOldPartitions() {
        LocalDate cutoff = LocalDate.now().minusMonths(12);  // Keep 12 months
        int yearMonth = cutoff.getYear() * 100 + cutoff.getMonthValue();
        
        // Get list of partitions
        String listSql = """
            SELECT PARTITION_NAME, PARTITION_DESCRIPTION
            FROM information_schema.PARTITIONS
            WHERE TABLE_NAME = 'orders'
              AND TABLE_SCHEMA = DATABASE()
              AND PARTITION_NAME != 'p_future'
            ORDER BY PARTITION_DESCRIPTION
            """;
        
        List<Map<String, Object>> partitions = jdbcTemplate.queryForList(listSql);
        
        for (Map<String, Object> partition : partitions) {
            String partitionName = (String) partition.get("PARTITION_NAME");
            int partitionValue = Integer.parseInt(
                (String) partition.get("PARTITION_DESCRIPTION")
            );
            
            if (partitionValue < yearMonth) {
                String dropSql = String.format(
                    "ALTER TABLE orders DROP PARTITION %s", 
                    partitionName
                );
                
                try {
                    jdbcTemplate.execute(dropSql);
                    log.info("Dropped old partition: {}", partitionName);
                } catch (Exception e) {
                    log.error("Failed to drop partition: {}", partitionName, e);
                }
            }
        }
    }
    
    // Analyze partition sizes
    public Map<String, Long> getPartitionSizes() {
        String sql = """
            SELECT 
                PARTITION_NAME,
                TABLE_ROWS,
                DATA_LENGTH,
                INDEX_LENGTH
            FROM information_schema.PARTITIONS
            WHERE TABLE_NAME = 'orders'
              AND TABLE_SCHEMA = DATABASE()
            ORDER BY PARTITION_ORDINAL_POSITION
            """;
        
        Map<String, Long> sizes = new HashMap<>();
        
        jdbcTemplate.query(sql, rs -> {
            String name = rs.getString("PARTITION_NAME");
            long rows = rs.getLong("TABLE_ROWS");
            long dataSize = rs.getLong("DATA_LENGTH");
            long indexSize = rs.getLong("INDEX_LENGTH");
            long totalSize = dataSize + indexSize;
            
            sizes.put(name, totalSize);
            
            log.info("Partition {}: {} rows, {} bytes", 
                    name, rows, totalSize);
        });
        
        return sizes;
    }
}
```

### Partitioning Best Practices

```sql
-- === Best Practices ===

-- 1. Partition key must be in PRIMARY KEY or UNIQUE key
-- WRONG:
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    order_date DATE
) PARTITION BY RANGE (YEAR(order_date));
-- ERROR: Partition key not in primary key

-- CORRECT:
CREATE TABLE orders (
    id BIGINT,
    order_date DATE,
    PRIMARY KEY (id, order_date)  -- Composite key
) PARTITION BY RANGE (YEAR(order_date));


-- 2. Limit number of partitions (< 1000)
-- Too many partitions = overhead
-- Recommended: 10-100 partitions


-- 3. Use RANGE for time-series
-- Easy to add/drop partitions
-- Natural partition pruning


-- 4. Don't partition small tables (< 1GB)
-- Overhead > benefit


-- 5. Partition pruning only works with partition key in WHERE
SELECT * FROM orders WHERE order_date = '2024-03-15';  -- ✅ Pruning works
SELECT * FROM orders WHERE customer_id = 123;          -- ❌ No pruning (scans all)


-- 6. Test queries with EXPLAIN PARTITIONS
EXPLAIN PARTITIONS SELECT * FROM orders WHERE order_date = '2024-03-15';
-- Shows which partitions are scanned
```

## 6. Covering Indexes

### Understanding Covering Indexes

```sql
-- Covering index: Index contains ALL columns needed by query
-- Result: Index-only scan (no table access needed)

-- Example table
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255),
    name VARCHAR(100),
    age INT,
    city VARCHAR(50),
    created_at DATETIME
);

-- Query: Get name by email
SELECT name FROM users WHERE email = 'user@example.com';

-- Index 1: Regular index (non-covering)
CREATE INDEX idx_email ON users(email);
-- Query execution:
-- 1. Scan idx_email to find rows with email = 'user@example.com'
-- 2. Access table to get 'name' column
-- 3. Return result
-- Extra: Using where

-- Index 2: Covering index
CREATE INDEX idx_email_name ON users(email, name);
-- Query execution:
-- 1. Scan idx_email_name to find email = 'user@example.com'
-- 2. Return 'name' from index (no table access!)
-- Extra: Using index

-- Performance difference:
-- Non-covering: 1.5ms (index scan + table access)
-- Covering: 0.5ms (index-only scan) - 3x faster
```

### Creating Covering Indexes

```sql
-- === Strategy 1: Include frequently queried columns ===

-- Query: Get user info by email
SELECT id, email, name, city 
FROM users 
WHERE email = 'user@example.com';

-- Covering index
CREATE INDEX idx_email_covering ON users(email, name, city);
-- Index contains: email (WHERE), name (SELECT), city (SELECT)
-- id automatically included (primary key)

-- === Strategy 2: ORDER BY columns ===

-- Query: Paginated list
SELECT id, name FROM users 
ORDER BY created_at DESC 
LIMIT 20 OFFSET 0;

-- Covering index (includes ORDER BY column)
CREATE INDEX idx_created_name ON users(created_at DESC, name);
-- No filesort needed + covering

-- === Strategy 3: JOIN columns ===

-- Query: User with order count
SELECT u.id, u.name, COUNT(o.id) as order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- Covering indexes
CREATE INDEX idx_user_id_name ON users(id, name);  -- Users side
CREATE INDEX idx_order_user ON orders(user_id);    -- Orders side
-- Both sides covered

-- === Strategy 4: Composite queries ===

-- Query: Search with multiple conditions
SELECT id, name, email 
FROM users 
WHERE city = 'New York' 
  AND age > 25
ORDER BY created_at DESC
LIMIT 10;

-- Covering index (all columns needed)
CREATE INDEX idx_city_age_created_name_email 
ON users(city, age, created_at DESC, name, email);
-- Column order: WHERE conditions → ORDER BY → SELECT
```

### Covering Index Trade-offs

```java
@Service
public class CoveringIndexAnalysis {
    
    public IndexRecommendation analyzeCoveringIndex(Query query, Index proposedIndex) {
        
        // Calculate benefit
        double benefit = calculateBenefit(query, proposedIndex);
        
        // Calculate cost
        double cost = calculateCost(proposedIndex);
        
        // Decision
        if (benefit > cost * 2) {
            return IndexRecommendation.CREATE;
        } else if (benefit > cost) {
            return IndexRecommendation.CONSIDER;
        } else {
            return IndexRecommendation.SKIP;
        }
    }
    
    private double calculateBenefit(Query query, Index index) {
        // Factors:
        // 1. Query frequency (queries per second)
        // 2. Table access time saved (usually 50-70% faster)
        // 3. Number of rows processed
        
        double queriesPerSec = query.getFrequency();
        double timeSavedPerQuery = 1.0;  // ms saved by avoiding table access
        
        return queriesPerSec * timeSavedPerQuery * 86400;  // Daily time saved (seconds)
    }
    
    private double calculateCost(Index index) {
        // Factors:
        // 1. Index size (storage cost)
        // 2. Write overhead (updates must update index)
        // 3. Memory consumption (in buffer pool)
        
        int columnCount = index.getColumns().size();
        long avgRowSize = calculateAvgRowSize(index.getColumns());
        long tableRows = index.getTable().getRowCount();
        
        // Index size (bytes)
        long indexSize = avgRowSize * tableRows;
        
        // Write overhead (% of write time)
        double writeOverhead = columnCount * 0.05;  // 5% per column
        
        // Normalize cost (arbitrary units for comparison)
        return (indexSize / 1_000_000) + (writeOverhead * 100);
    }
}

// Example decision:
/*
Query: SELECT id, name, email FROM users WHERE city = ?
Frequency: 1000 queries/sec
Current time: 2ms/query
With covering index: 0.8ms/query (1.2ms saved)

Benefit: 1000 * 1.2ms * 86400s = 103,680 seconds/day saved

Proposed index: idx_city_name_email (3 columns)
Index size: 500MB
Write overhead: 15% (3 columns * 5%)

Cost: 500 (size) + 15 (writes) = 515

Decision: 103,680 / 515 = 201x benefit
Recommendation: CREATE (high ROI)
*/
```

### Best Practices for Covering Indexes

```sql
-- === Best Practices ===

-- 1. Don't create covering index for every query
-- Only for frequent, performance-critical queries

-- 2. Column order matters
-- Correct: WHERE columns → ORDER BY columns → SELECT columns
CREATE INDEX idx_covering ON users(city, age, created_at, name, email);

-- Wrong: Random order
CREATE INDEX idx_covering_bad ON users(name, city, email, age, created_at);

-- 3. Consider index size
-- Large indexes = more memory, slower writes
-- Balance coverage vs size

-- Good: 3-4 columns (20-30 bytes each)
CREATE INDEX idx_reasonable ON users(city, age, name);

-- Bad: 10+ columns (100+ bytes total)
CREATE INDEX idx_too_large ON users(col1, col2, col3, ... col10);

-- 4. Use INCLUDE for non-filtering columns (PostgreSQL)
-- MySQL doesn't have INCLUDE, but similar concept with composite

-- 5. Monitor index usage
SELECT 
    TABLE_NAME,
    INDEX_NAME,
    SEQ_IN_INDEX,
    COLUMN_NAME,
    CARDINALITY
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'mydb'
  AND INDEX_NAME = 'idx_covering';

-- 6. Drop unused covering indexes
-- They cost storage and write performance
SELECT 
    object_schema,
    object_name,
    index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
  AND count_star = 0  -- Never used
  AND object_schema = 'mydb';
```
