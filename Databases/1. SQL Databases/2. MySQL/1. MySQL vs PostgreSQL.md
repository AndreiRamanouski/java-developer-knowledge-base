This section covers MySQL-specific topics with Spring Boot, starting with MySQL vs PostgreSQL comparisons.

## Q1: MySQL vs PostgreSQL - Spring Boot Considerations

**Short Answer**: MySQL uses MyISAM/InnoDB engines with table-level locking (MyISAM) vs row-level (InnoDB). PostgreSQL is single-engine, MVCC-based. Spring Boot dialect: MySQL5Dialect/MySQL8Dialect vs PostgreSQL95Dialect. Data types: MySQL JSON vs PostgreSQL JSONB (binary, faster), TEXT vs VARCHAR (no length limit in PG). Transactions: MySQL REPEATABLE READ (default) with gap locks vs PostgreSQL READ COMMITTED (default). Choose MySQL: read-heavy, simpler replication, web apps. PostgreSQL: complex queries, ACID compliance, data integrity.

### Auto-increment vs Sequences

```java
// === MySQL: AUTO_INCREMENT ===

@Entity
@Table(name = "users")
public class UserMySQL {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    // Generated DDL:
    // CREATE TABLE users (
    //     id BIGINT AUTO_INCREMENT PRIMARY KEY,
    //     ...
    // )
}

// === PostgreSQL: SEQUENCES ===

@Entity
@Table(name = "users")
public class UserPostgreSQL {
    
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
    @SequenceGenerator(name = "user_seq", sequenceName = "user_id_seq", allocationSize = 1)
    private Long id;
    
    // Or use IDENTITY (PostgreSQL 10+)
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    // Generated DDL:
    // CREATE SEQUENCE user_id_seq;
    // CREATE TABLE users (
    //     id BIGINT DEFAULT nextval('user_id_seq') PRIMARY KEY,
    //     ...
    // )
}

// Performance difference:
// - MySQL: Single query for INSERT (gets ID immediately)
// - PostgreSQL with SEQUENCE: Two queries (nextval + INSERT)
// - PostgreSQL with IDENTITY: Single query (same as MySQL)
```

## 2. Data Type Mappings

### JSON vs JSONB

```java
// === MySQL: JSON Type ===

@Entity
public class DocumentMySQL {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @Column(columnDefinition = "JSON")
    private String metadata;  // Stored as text, validated as JSON
    
    // Querying JSON in MySQL
    @Query(value = """
        SELECT * FROM documents 
        WHERE JSON_EXTRACT(metadata, '$.status') = ?1
        """, nativeQuery = true)
    List<DocumentMySQL> findByMetadataStatus(String status);
    
    // JSON functions available in MySQL 5.7+:
    // - JSON_EXTRACT: Get value from JSON
    // - JSON_CONTAINS: Check if JSON contains value
    // - JSON_SEARCH: Search for value in JSON
    // - JSON_SET: Update JSON value
    // - JSON_ARRAY: Create JSON array
    // - JSON_OBJECT: Create JSON object
}

// === PostgreSQL: JSONB Type ===

@Entity
public class DocumentPostgreSQL {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @Type(type = "jsonb")  // Hibernate JSONB type
    @Column(columnDefinition = "JSONB")
    private String metadata;  // Stored as binary, indexed efficiently
    
    // Querying JSONB in PostgreSQL (much faster)
    @Query(value = """
        SELECT * FROM documents 
        WHERE metadata->>'status' = ?1
        """, nativeQuery = true)
    List<DocumentPostgreSQL> findByMetadataStatus(String status);
    
    // Or with GIN index for fast lookups:
    // CREATE INDEX idx_documents_metadata ON documents USING GIN (metadata);
    
    // JSONB operators:
    // - ->  : Get JSON object field (returns JSONB)
    // - ->> : Get JSON object field (returns TEXT)
    // - @>  : Contains (left contains right)
    // - <@  : Contained by (left contained in right)
    // - ?   : Key exists
    // - ?|  : Any key exists
    // - ?&  : All keys exist
}

// Performance comparison:
@Test
public void compareJsonPerformance() {
    // Setup: 1M documents with JSON metadata
    
    // MySQL JSON query:
    // SELECT * FROM documents WHERE JSON_EXTRACT(metadata, '$.status') = 'active'
    // Time: 2,500ms (full table scan, no index)
    
    // PostgreSQL JSONB query (without index):
    // SELECT * FROM documents WHERE metadata->>'status' = 'active'
    // Time: 1,800ms (still full scan, but binary format faster)
    
    // PostgreSQL JSONB with GIN index:
    // Time: 50ms (index scan)
    
    // Conclusion: PostgreSQL JSONB is 50x faster with proper indexing
}
```

### Using JSON with JPA Converter

```java
// Cross-database JSON mapping using JPA converter

@Converter(autoApply = true)
public class JsonConverter implements AttributeConverter<Map<String, Object>, String> {
    
    private final ObjectMapper objectMapper = new ObjectMapper();
    
    @Override
    public String convertToDatabaseColumn(Map<String, Object> attribute) {
        try {
            return objectMapper.writeValueAsString(attribute);
        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException("Error converting map to JSON", e);
        }
    }
    
    @Override
    public Map<String, Object> convertToEntityAttribute(String dbData) {
        try {
            return objectMapper.readValue(dbData, new TypeReference<>() {});
        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException("Error converting JSON to map", e);
        }
    }
}

@Entity
public class Document {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @Convert(converter = JsonConverter.class)
    @Column(columnDefinition = "JSON")  // MySQL
    // OR @Column(columnDefinition = "JSONB")  // PostgreSQL
    private Map<String, Object> metadata;
    
    // Works with both databases!
    // But queries will be database-specific
}
```

### TEXT vs VARCHAR

```sql
-- MySQL: VARCHAR has max length, TEXT types for larger content

-- VARCHAR: Max 65,535 bytes (depends on character set)
CREATE TABLE posts_mysql (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(255),          -- 255 chars max
    summary VARCHAR(1000),       -- 1000 chars max
    content TEXT,                -- Up to 65,535 bytes
    long_content MEDIUMTEXT,     -- Up to 16MB
    huge_content LONGTEXT        -- Up to 4GB
);

-- PostgreSQL: TEXT has no length limit, VARCHAR is TEXT internally

CREATE TABLE posts_postgresql (
    id BIGSERIAL PRIMARY KEY,
    title VARCHAR(255),          -- Enforces max length in app
    summary TEXT,                -- No length limit
    content TEXT,                -- No length limit
    long_content TEXT,           -- Same as content (no distinction)
    huge_content TEXT            -- Same as content
);

-- Storage difference:
-- MySQL: TEXT types stored separately, pointer in row (can be slower)
-- PostgreSQL: TEXT stored inline if < ~2KB, else TOAST (transparent)

-- Performance:
-- MySQL: VARCHAR(255) faster than TEXT for short strings
-- PostgreSQL: TEXT and VARCHAR(255) same performance
```

## 3. Transaction Behavior Differences

### Default Isolation Levels

```java
// === MySQL Default: REPEATABLE READ ===

@Service
@Transactional  // Uses REPEATABLE READ by default
public class MySQLTransactionService {
    
    public void demonstrateRepeatableRead() {
        // Transaction 1 starts
        User user1 = userRepository.findById(1L).get();
        System.out.println("First read: " + user1.getName());  // "Alice"
        
        // Meanwhile, Transaction 2 updates the user
        // UPDATE users SET name = 'Bob' WHERE id = 1
        
        // Transaction 1 reads again
        User user2 = userRepository.findById(1L).get();
        System.out.println("Second read: " + user2.getName());  // Still "Alice"!
        
        // MySQL uses gap locks to prevent phantom reads
        // Even new rows won't appear if they fall in the "gap"
    }
}

// === PostgreSQL Default: READ COMMITTED ===

@Service
@Transactional  // Uses READ COMMITTED by default
public class PostgreSQLTransactionService {
    
    public void demonstrateReadCommitted() {
        // Transaction 1 starts
        User user1 = userRepository.findById(1L).get();
        System.out.println("First read: " + user1.getName());  // "Alice"
        
        // Meanwhile, Transaction 2 updates and commits
        // UPDATE users SET name = 'Bob' WHERE id = 1
        
        // Transaction 1 reads again
        User user2 = userRepository.findById(1L).get();
        System.out.println("Second read: " + user2.getName());  // "Bob" (changed!)
        
        // PostgreSQL sees committed changes immediately
        // Non-repeatable reads allowed by default
    }
}
```

### Locking Behavior

```java
// === MySQL: Gap Locks (REPEATABLE READ) ===

@Transactional
public void mysqlGapLocking() {
    // Find users with age > 20
    List<User> users = userRepository.findByAgeGreaterThan(20);
    // MySQL locks: rows + gaps between rows + gap after last row
    
    // Another transaction tries to insert user with age = 25
    // INSERT INTO users (age) VALUES (25)
    // This will BLOCK until first transaction commits
    // Because it falls in the "gap" that's locked
}

// === PostgreSQL: No Gap Locks ===

@Transactional(isolation = Isolation.REPEATABLE_READ)
public void postgresqlNoGapLocking() {
    // Find users with age > 20
    List<User> users = userRepository.findByAgeGreaterThan(20);
    // PostgreSQL locks: only actual rows (no gaps)
    
    // Another transaction inserts user with age = 25
    // INSERT INTO users (age) VALUES (25)
    // This will SUCCEED immediately (no blocking)
    
    // But: Phantom reads prevented through MVCC snapshot isolation
    // New row won't appear in subsequent queries in this transaction
}
```

### Pessimistic Locking

```java
// === MySQL: FOR UPDATE with Gap Locks ===

@Repository
public interface UserRepositoryMySQL extends JpaRepository<User, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT u FROM User u WHERE u.status = ?1")
    List<User> findByStatusWithLock(String status);
    
    // Generated SQL:
    // SELECT * FROM users WHERE status = ? FOR UPDATE
    
    // Locks:
    // - All matching rows
    // - Gaps between rows (prevents inserts)
    // - Next-key locking (row + gap before it)
}

// === PostgreSQL: FOR UPDATE (Row-Level Only) ===

@Repository
public interface UserRepositoryPostgreSQL extends JpaRepository<User, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT u FROM User u WHERE u.status = ?1")
    List<User> findByStatusWithLock(String status);
    
    // Generated SQL:
    // SELECT * FROM users WHERE status = ? FOR UPDATE
    
    // Locks:
    // - Only matching rows (no gaps)
    // - Other transactions can insert between locked rows
}

// Additional PostgreSQL lock options:
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query(value = """
    SELECT * FROM users WHERE status = ?1 
    FOR UPDATE SKIP LOCKED
    """, nativeQuery = true)
List<User> findAvailableForProcessing(String status);
// SKIP LOCKED: Skip rows that are already locked (useful for job queues)

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query(value = """
    SELECT * FROM users WHERE status = ?1 
    FOR UPDATE NOWAIT
    """, nativeQuery = true)
List<User> findWithImmediateLock(String status);
// NOWAIT: Fail immediately if rows are locked (no waiting)
```

```java
public class ReadPerformanceComparison {

        // PostgreSQL (with proper indexes):

            SELECT 
                u.name,
                COUNT(o.id) as order_count,
                SUM(o.total) as total_spent
            FROM users u
            LEFT JOIN orders o ON u.id = o.user_id
            WHERE u.created_at > ?
            GROUP BY u.id, u.name
            HAVING COUNT(o.id) > 10
            ORDER BY total_spent DESC
            LIMIT 100
            """;
        
        // MySQL:
        // - Time: 450ms
        // - Uses temporary tables for GROUP BY
        // - Good for simple aggregations
        
        // PostgreSQL:
        // - Time: 380ms
        // - Better query optimizer for complex queries
        // - More efficient parallel processing
        
        // Conclusion: PostgreSQL ~15% faster for complex queries
    }
    
    @Test
    public void compareFullTextSearch() {
        // Test: Full-text search across large text columns
        
        // MySQL (with FULLTEXT index):

            SELECT * FROM articles

            """;
        // Time: 120ms
        // Good for simple full-text search
        
        // PostgreSQL (with tsvector and GIN index):
        String pgQuery = """
            SELECT * FROM articles
            WHERE search_vector @@ to_tsquery(?)
            """;

        // Better ranking, more features (stemming, dictionaries)

    }
```

```java
    // - Secondary index lookup: 1.2ms
    // - Direct pointer to tuple
    // - One index access usually sufficient
    
    // Conclusion: PostgreSQL ~20% faster for indexed lookups
}
```

## 5. Feature Availability

### Common Table Expressions (CTEs)

```sql
-- MySQL 8.0+: Supports CTEs
WITH RECURSIVE subordinates AS (
    SELECT id, name, manager_id
    FROM employees
    WHERE id = 1
    
    UNION ALL
    
    SELECT e.id, e.name, e.manager_id
    FROM employees e
    INNER JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates;

-- MySQL <8.0: No CTE support
-- Must use derived tables or temporary tables

-- PostgreSQL: Full CTE support (all versions)
WITH recent_orders AS (
    SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days'
),
order_stats AS (
    SELECT 
        user_id,
        COUNT(*) as order_count,
        SUM(total) as total_spent
    FROM recent_orders
    GROUP BY user_id
)
SELECT u.*, os.*
FROM users u
JOIN order_stats os ON u.id = os.user_id;
```

```java
// Spring Data JPA doesn't directly support CTEs
// Must use native queries

@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query(value = """

            SELECT * FROM orders WHERE created_at > DATE_SUB(NOW(), INTERVAL 7 DAY)
        )
        SELECT u.* FROM users u
        JOIN recent_orders ro ON u.id = ro.user_id
        GROUP BY u.id
        HAVING COUNT(ro.id) > 5
        """, nativeQuery = true)
    List<User> findActiveUsersMySql8();
    
    // PostgreSQL with CTE
    @Query(value = """
        WITH recent_orders AS (
            SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days'
        )
        SELECT u.* FROM users u
        JOIN recent_orders ro ON u.id = ro.user_id
        GROUP BY u.id
        HAVING COUNT(ro.id) > 5
        """, nativeQuery = true)
    List<User> findActiveUsersPostgreSQL();
}
```

## 6. When to Choose MySQL vs PostgreSQL

### Decision Matrix

```java
public class DatabaseSelectionGuide {
    
    public DatabaseType selectDatabase(ApplicationProfile profile) {
        
        // === Choose MySQL if: ===
        
        if (profile.isReadHeavy() && profile.hasSimpleQueries()) {
            // MySQL: 20% faster for simple reads
            // Good for: Blogs, content sites, read-heavy web apps
            return DatabaseType.MYSQL;
        }
        
        if (profile.requiresSimpleReplication()) {
            // MySQL: Master-slave replication is simpler
            // Built-in binary log replication
            return DatabaseType.MYSQL;
        }
        
        if (profile.hasHighWriteThroughput() && profile.hasSingleThreadWrites()) {
            // MySQL: Faster for single-threaded writes
            // Good for: Sequential logging, simple CRUD
            return DatabaseType.MYSQL;
        }
        
        if (profile.requiresMyISAM()) {
            // MySQL: Only database with MyISAM engine
            // Good for: Full-text search (pre-5.7), read-only data
            return DatabaseType.MYSQL;
        }
        
        // === Choose PostgreSQL if: ===
        
        if (profile.hasComplexQueries()) {
            // PostgreSQL: Better query optimizer
            // Full CTE, window functions, lateral joins
            return DatabaseType.POSTGRESQL;
        }
        
        if (profile.requiresACIDCompliance()) {
            // PostgreSQL: Stricter ACID compliance
            // Better data integrity guarantees
            return DatabaseType.POSTGRESQL;
        }
        
        if (profile.hasHighConcurrency()) {
            // PostgreSQL: MVCC = better concurrent write performance
            // Readers don't block writers
            return DatabaseType.POSTGRESQL;
        }
        
        if (profile.requiresAdvancedDataTypes()) {
            // PostgreSQL: Arrays, JSONB, UUID, HSTORE, etc.
            // Better for complex data models
            return DatabaseType.POSTGRESQL;
        }
        
        if (profile.requiresGeospatialData()) {
            // PostgreSQL: PostGIS extension
            // Industry standard for GIS
            return DatabaseType.POSTGRESQL;
        }
        
        if (profile.requiresFullTextSearch()) {
            // PostgreSQL: Better full-text search (tsvector, GIN)
            // More features than MySQL FULLTEXT
            return DatabaseType.POSTGRESQL;
        }
        
        return DatabaseType.POSTGRESQL;  // Default recommendation
    }
}

enum DatabaseType {
    MYSQL, POSTGRESQL
}

class ApplicationProfile {
    private boolean readHeavy;
    private boolean simpleQueries;
    private boolean complexQueries;
    private boolean highConcurrency;
    private boolean requiresACIDCompliance;
    // ... getters
}
```

### Use Case Examples

```
=== MySQL is Better For: ===

1. WordPress, Drupal, Joomla (CMS):
   - Simple queries (get post by ID)
   - Read-heavy (95% reads)
   - Master-slave replication
   
2. E-commerce (simple):
   - Product catalog (mostly reads)
   - Simple relationships
   - Proven ecosystem (Magento, WooCommerce)
   
3. Web applications:
   - CRUD operations
   - Session storage
   - User authentication
   
4. Logging (with MyISAM):
   - Write-only tables
   - No updates/deletes
   - Fast inserts

5. Small to medium businesses:
   - Simpler to set up and manage
   - Lower learning curve
   - More hosting options


=== PostgreSQL is Better For: ===

1. Financial systems:
   - Strict ACID compliance
   - Complex transactions
   - Data integrity critical
   
2. Analytics platforms:
   - Complex queries with CTEs
   - Window functions
   - Aggregations over large datasets
   
3. Geospatial applications:
   - PostGIS extension
   - Location-based services
   - Mapping applications
   
4. Data warehousing:
   - Large-scale data processing
   - Complex joins and aggregations
   - Parallel query execution
   
5. Scientific/research applications:
   - Complex data types (arrays, JSON, custom types)
   - Advanced indexing (GIN, GIST)
   - Extensibility (custom functions, operators)
   
6. Microservices with complex domains:
   - Each service needs complex queries
   - High concurrency
   - Strong consistency requirements
```
