# MySQL Locking Mechanisms with Spring Boot

## Deep Dive Interview Guide

This guide covers MySQL locking mechanisms for production Spring Boot applications, including row locks, table locks, gap locks, deadlock handling, and Spring Data JPA @Lock annotation usage.

**Interview Tip**: Locking questions test understanding of concurrency, transaction isolation, race conditions, performance optimization, and production debugging skills.

---

## Q5: MySQL Locking Mechanisms

**Short Answer**: Table locks block entire table, row locks (InnoDB default) lock specific rows. SELECT FOR UPDATE acquires exclusive lock (write), FOR SHARE acquires shared lock (read). Gap locks prevent phantom reads in REPEATABLE READ (lock gaps between rows). Next-key locks combine row + gap before it. Deadlocks detected by timeout or algorithm; resolve with retry logic. Use @Lock(LockModeType.PESSIMISTIC_WRITE) for SELECT FOR UPDATE, @Lock(LockModeType.PESSIMISTIC_READ) for FOR SHARE in JPA.

## 1. Table Locks vs Row Locks

### Table-Level Locking (MyISAM, MEMORY engines)

```sql
-- === Table Locks (MyISAM) ===
-- Locks entire table - blocks ALL concurrent access

CREATE TABLE counters (
    name VARCHAR(50) PRIMARY KEY,
    value BIGINT
) ENGINE=MyISAM;

-- Session 1: Acquire write lock
LOCK TABLES counters WRITE;
UPDATE counters SET value = value + 1 WHERE name = 'visitors';
-- Table is locked - no other session can read or write

-- Session 2: Try to read (blocks until Session 1 releases lock)
SELECT * FROM counters WHERE name = 'visitors';
-- BLOCKED! Waiting for table lock...

-- Session 1: Release lock
UNLOCK TABLES;
-- Session 2: Now proceeds


-- Read lock (shared)
-- Session 1:
LOCK TABLES counters READ;
SELECT * FROM counters;  -- ✅ Can read
UPDATE counters SET value = 0;  -- ❌ ERROR: Table is read-locked

-- Session 2:
SELECT * FROM counters;  -- ✅ Can read (multiple readers OK)
UPDATE counters SET value = 1;  -- ❌ BLOCKED (waiting for write)

-- Performance characteristics:
-- Pros: Simple, no deadlocks
-- Cons: Poor concurrency, entire table blocked
-- Use case: Rare - legacy applications, batch operations
```

### Row-Level Locking (InnoDB)

```sql
-- === Row Locks (InnoDB) ===
-- Locks only specific rows - better concurrency

CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    balance DECIMAL(10,2),
    INDEX idx_user (user_id)
) ENGINE=InnoDB;

-- Session 1: Lock specific row
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- Only row with id=1 is locked

-- Session 2: Different row - no blocking
START TRANSACTION;
SELECT * FROM accounts WHERE id = 2 FOR UPDATE;
-- ✅ Proceeds immediately (different row)

-- Session 3: Same row - blocks
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- ❌ BLOCKED! Waiting for Session 1 to commit/rollback

-- Session 1: Commit
COMMIT;
-- Session 3: Now proceeds

-- Performance characteristics:
-- Pros: High concurrency, parallel operations
-- Cons: More complex, potential deadlocks
-- Use case: Default for InnoDB, production applications
```

### Lock Escalation and Lock Types

```sql
-- InnoDB lock types:

-- 1. Record Lock: Locks specific index record
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- Locks: id=1 index record

-- 2. Gap Lock: Locks gap between index records
SELECT * FROM accounts WHERE id > 5 AND id < 10 FOR UPDATE;
-- Locks: gap between 5 and 10 (prevents inserts)

-- 3. Next-Key Lock: Record lock + gap before it (default in REPEATABLE READ)
SELECT * FROM accounts WHERE id >= 5 FOR UPDATE;
-- Locks: id=5, 6, 7... + gaps before each

-- 4. Insert Intention Lock: Special gap lock for INSERT
INSERT INTO accounts VALUES (8, 123, 100.00);
-- Waits if gap is locked by another transaction

-- Show current locks
SELECT * FROM performance_schema.data_locks;

-- Example output:
-- OBJECT_NAME | LOCK_TYPE | LOCK_MODE | LOCK_STATUS | LOCK_DATA
-- accounts    | RECORD    | X         | GRANTED     | 1
-- accounts    | RECORD    | X         | WAITING     | 2
```

### Spring Boot Comparison

```java
// === Table Lock Example (avoid in production) ===

@Service
public class TableLockService {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    @Transactional
    public void performBatchUpdate() {
        // Lock entire table
        jdbcTemplate.execute("LOCK TABLES products WRITE");
        
        try {
            // Perform batch operations
            jdbcTemplate.update("UPDATE products SET price = price * 1.1");
            jdbcTemplate.update("UPDATE products SET updated_at = NOW()");
        } finally {
            jdbcTemplate.execute("UNLOCK TABLES");
        }
        
        // WARNING: This blocks ALL access to products table
        // Even SELECT queries from other users are blocked!
    }
}

// === Row Lock Example (recommended) ===

@Service
public class RowLockService {
    
    @Autowired
    private AccountRepository accountRepository;
    
    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        // Lock only specific rows
        Account from = accountRepository.findByIdWithLock(fromId);
        Account to = accountRepository.findByIdWithLock(toId);
        
        // Operations on locked rows
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
        
        // Locks released on commit
        // Other accounts can be accessed concurrently ✅
    }
}

@Repository
public interface AccountRepository extends JpaRepository<Account, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = ?1")
    Account findByIdWithLock(Long id);
}
```

## 2. SELECT ... FOR UPDATE

### Understanding FOR UPDATE

```sql
-- SELECT FOR UPDATE: Acquires exclusive (write) lock
-- Blocks other SELECT FOR UPDATE and UPDATE/DELETE
-- Allows regular SELECT (unless SERIALIZABLE isolation)

CREATE TABLE inventory (
    product_id BIGINT PRIMARY KEY,
    quantity INT,
    reserved INT
) ENGINE=InnoDB;

INSERT INTO inventory VALUES (1, 100, 0);

-- === Basic Usage ===

-- Session 1: Lock row for update
START TRANSACTION;
SELECT * FROM inventory WHERE product_id = 1 FOR UPDATE;
-- Acquires exclusive lock on product_id=1

-- Session 2: Try to lock same row
START TRANSACTION;
SELECT * FROM inventory WHERE product_id = 1 FOR UPDATE;
-- ❌ BLOCKED! Waiting for Session 1...

-- Session 3: Regular read (no lock)
SELECT * FROM inventory WHERE product_id = 1;
-- ✅ Proceeds immediately (reads don't block in READ COMMITTED)

-- Session 1: Update and commit
UPDATE inventory SET quantity = 95, reserved = 5 WHERE product_id = 1;
COMMIT;

-- Session 2: Now acquires lock and sees updated data
-- Returns: product_id=1, quantity=95, reserved=5


-- === FOR UPDATE NOWAIT (MySQL 8.0+) ===
-- Fail immediately if row is locked

SELECT * FROM inventory WHERE product_id = 1 FOR UPDATE NOWAIT;
-- If locked: ERROR 3572 (HY000): Statement aborted because lock(s) could not be acquired


-- === FOR UPDATE SKIP LOCKED (MySQL 8.0+) ===
-- Skip locked rows (useful for job queues)

-- Queue table
CREATE TABLE jobs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    status VARCHAR(20),
    payload TEXT
) ENGINE=InnoDB;

INSERT INTO jobs (status, payload) VALUES 
('PENDING', 'job1'),
('PENDING', 'job2'),
('PENDING', 'job3');

-- Worker 1:
START TRANSACTION;
SELECT * FROM jobs 
WHERE status = 'PENDING' 
ORDER BY id 
LIMIT 1 
FOR UPDATE SKIP LOCKED;
-- Returns: id=1 (and locks it)

-- Worker 2 (concurrent):
START TRANSACTION;
SELECT * FROM jobs 
WHERE status = 'PENDING' 
ORDER BY id 
LIMIT 1 
FOR UPDATE SKIP LOCKED;
-- Returns: id=2 (skips id=1 because it's locked) ✅

-- Worker 3 (concurrent):
START TRANSACTION;
SELECT * FROM jobs 
WHERE status = 'PENDING' 
ORDER BY id 
LIMIT 1 
FOR UPDATE SKIP LOCKED;
-- Returns: id=3 ✅

-- All three workers process different jobs concurrently!
```

### Spring Data JPA with FOR UPDATE

```java
@Entity
@Table(name = "inventory")
public class Inventory {
    
    @Id
    private Long productId;
    
    private Integer quantity;
    private Integer reserved;
    
    // Getters and setters
}

@Repository
public interface InventoryRepository extends JpaRepository<Inventory, Long> {
    
    // SELECT ... FOR UPDATE
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT i FROM Inventory i WHERE i.productId = ?1")
    Optional<Inventory> findByIdWithLock(Long productId);
    
    // FOR UPDATE NOWAIT (native query)
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "javax.persistence.lock.timeout", value = "0"))
    @Query("SELECT i FROM Inventory i WHERE i.productId = ?1")
    Optional<Inventory> findByIdWithLockNoWait(Long productId);
    
    // FOR UPDATE SKIP LOCKED (native query)
    @Query(value = """
        SELECT * FROM inventory 
        WHERE product_id = ?1 
        FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
    Optional<Inventory> findByIdSkipLocked(Long productId);
}

@Service
public class InventoryService {
    
    @Autowired
    private InventoryRepository inventoryRepository;
    
    // Reserve inventory (prevents overselling)
    @Transactional
    public void reserveInventory(Long productId, int quantity) {
        // Lock row to prevent concurrent reservations
        Inventory inventory = inventoryRepository
            .findByIdWithLock(productId)
            .orElseThrow(() -> new ProductNotFoundException(productId));
        
        if (inventory.getQuantity() < quantity) {
            throw new InsufficientInventoryException();
        }
        
        // Update inventory
        inventory.setQuantity(inventory.getQuantity() - quantity);
        inventory.setReserved(inventory.getReserved() + quantity);
        
        inventoryRepository.save(inventory);
        
        // Lock released on commit
    }
    
    // Non-blocking reserve attempt
    @Transactional
    public boolean tryReserveInventory(Long productId, int quantity) {
        try {
            // Try to acquire lock immediately
            Optional<Inventory> inventoryOpt = 
                inventoryRepository.findByIdWithLockNoWait(productId);
            
            if (inventoryOpt.isEmpty()) {
                return false;  // Product not found
            }
            
            Inventory inventory = inventoryOpt.get();
            
            if (inventory.getQuantity() < quantity) {
                return false;  // Not enough inventory
            }
            
            inventory.setQuantity(inventory.getQuantity() - quantity);
            inventory.setReserved(inventory.getReserved() + quantity);
            inventoryRepository.save(inventory);
            
            return true;
            
        } catch (PessimisticLockingFailureException e) {
            // Lock not available immediately
            log.debug("Product {} is locked, skipping", productId);
            return false;
        }
    }
}
```

### Job Queue Implementation

```java
@Entity
@Table(name = "jobs")
public class Job {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @Enumerated(EnumType.STRING)
    private JobStatus status;
    
    private String payload;
    
    private LocalDateTime createdAt;
    private LocalDateTime startedAt;
    private LocalDateTime completedAt;
}

enum JobStatus {
    PENDING, PROCESSING, COMPLETED, FAILED
}

@Repository
public interface JobRepository extends JpaRepository<Job, Long> {
    
    // Get next available job (skip locked)
    @Query(value = """
        SELECT * FROM jobs 
        WHERE status = 'PENDING' 
        ORDER BY id 
        LIMIT 1 
        FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
    Optional<Job> findNextAvailableJob();
}

@Service
public class JobProcessorService {
    
    @Autowired
    private JobRepository jobRepository;
    
    @Scheduled(fixedDelay = 1000)
    @Transactional
    public void processJobs() {
        Optional<Job> jobOpt = jobRepository.findNextAvailableJob();
        
        if (jobOpt.isEmpty()) {
            log.debug("No jobs available");
            return;
        }
        
        Job job = jobOpt.get();
        
        try {
            // Mark as processing
            job.setStatus(JobStatus.PROCESSING);
            job.setStartedAt(LocalDateTime.now());
            jobRepository.save(job);
            
            // Process job
            processJobPayload(job.getPayload());
            
            // Mark as completed
            job.setStatus(JobStatus.COMPLETED);
            job.setCompletedAt(LocalDateTime.now());
            jobRepository.save(job);
            
        } catch (Exception e) {
            log.error("Job {} failed", job.getId(), e);
            job.setStatus(JobStatus.FAILED);
            jobRepository.save(job);
        }
    }
    
    private void processJobPayload(String payload) {
        // Actual job processing logic
        log.info("Processing: {}", payload);
        // Simulate work
        try {
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

// Multiple instances can run concurrently:
// Instance 1: Processes job id=1
// Instance 2: Processes job id=2 (skips id=1)
// Instance 3: Processes job id=3 (skips id=1, id=2)
// No conflicts! Each instance gets different job ✅
```

## 3. LOCK IN SHARE MODE (FOR SHARE)

### Understanding Shared Locks

```sql
-- LOCK IN SHARE MODE (MySQL < 8.0)
-- FOR SHARE (MySQL 8.0+, preferred syntax)

-- Shared lock: Multiple readers allowed, no writers

CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    price DECIMAL(10,2),
    version INT
) ENGINE=InnoDB;

-- === Shared Lock Example ===

-- Session 1: Acquire shared lock
START TRANSACTION;
SELECT * FROM products WHERE id = 1 LOCK IN SHARE MODE;
-- or: SELECT * FROM products WHERE id = 1 FOR SHARE;

-- Session 2: Also acquire shared lock (allowed)
START TRANSACTION;
SELECT * FROM products WHERE id = 1 LOCK IN SHARE MODE;
-- ✅ Proceeds! Multiple readers allowed

-- Session 3: Try to update (blocked)
START TRANSACTION;
UPDATE products SET price = 99.99 WHERE id = 1;
-- ❌ BLOCKED! Waiting for shared locks to release

-- Session 1: Commit
COMMIT;

-- Session 2: Still holding shared lock
-- Session 3: Still blocked

-- Session 2: Commit
COMMIT;

-- Session 3: Now proceeds with update


-- === FOR SHARE vs FOR UPDATE ===

-- FOR SHARE:
-- - Allows multiple concurrent readers
-- - Blocks writers (UPDATE/DELETE)
-- - Use case: Read data, prevent modifications until you're done

-- FOR UPDATE:
-- - Allows only one reader/writer
-- - Blocks all other FOR UPDATE and FOR SHARE
-- - Use case: Read data, planning to modify it
```

### Use Case: Preventing Lost Updates

```sql
-- Problem: Lost update without locking

-- Initial state: product price = 100

-- Transaction 1:
START TRANSACTION;
SELECT price FROM products WHERE id = 1;  -- Reads: 100
-- Calculate new price: 100 + 10 = 110

-- Transaction 2 (concurrent):
START TRANSACTION;
SELECT price FROM products WHERE id = 1;  -- Reads: 100
-- Calculate new price: 100 + 20 = 120

-- Transaction 1:
UPDATE products SET price = 110 WHERE id = 1;
COMMIT;

-- Transaction 2:
UPDATE products SET price = 120 WHERE id = 1;
COMMIT;

-- Final price: 120
-- Lost Transaction 1's update! Should be 130 (100 + 10 + 20)


-- Solution: Use FOR SHARE or FOR UPDATE

-- Transaction 1:
START TRANSACTION;
SELECT price FROM products WHERE id = 1 FOR SHARE;  -- Reads: 100, locks
-- Calculate: 100 + 10 = 110

-- Transaction 2 (concurrent):
START TRANSACTION;
SELECT price FROM products WHERE id = 1 FOR SHARE;  -- Reads: 100, locks
-- Calculate: 100 + 20 = 120

-- Transaction 1:
UPDATE products SET price = 110 WHERE id = 1;
-- Tries to upgrade shared lock to exclusive
-- ❌ DEADLOCK! Both transactions holding shared locks, both want exclusive

-- Better solution: Use FOR UPDATE from the start

-- Transaction 1:
START TRANSACTION;
SELECT price FROM products WHERE id = 1 FOR UPDATE;  -- Exclusive lock
-- Calculate: 100 + 10 = 110
UPDATE products SET price = 110 WHERE id = 1;
COMMIT;

-- Transaction 2:
START TRANSACTION;
SELECT price FROM products WHERE id = 1 FOR UPDATE;  -- Waits for Transaction 1
-- Reads: 110 (sees Transaction 1's update)
-- Calculate: 110 + 20 = 130 ✅
UPDATE products SET price = 130 WHERE id = 1;
COMMIT;

-- Final price: 130 ✅ Correct!
```

### Spring Data JPA with FOR SHARE

```java
@Repository
public interface ProductRepository extends JpaRepository<Product, Long> {
    
    // FOR SHARE (read lock)
    @Lock(LockModeType.PESSIMISTIC_READ)
    @Query("SELECT p FROM Product p WHERE p.id = ?1")
    Optional<Product> findByIdWithReadLock(Long id);
    
    // FOR UPDATE (write lock)
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = ?1")
    Optional<Product> findByIdWithWriteLock(Long id);
}

@Service
public class ProductPriceService {
    
    @Autowired
    private ProductRepository productRepository;
    
    // Read-only operation (use shared lock)
    @Transactional
    public ProductDTO getProductForDisplay(Long productId) {
        // Acquire shared lock (allows concurrent reads)
        Product product = productRepository
            .findByIdWithReadLock(productId)
            .orElseThrow();
        
        // Return DTO (no modifications)
        return new ProductDTO(product);
    }
    
    // Write operation (use exclusive lock)
    @Transactional
    public void updatePrice(Long productId, BigDecimal newPrice) {
        // Acquire exclusive lock
        Product product = productRepository
            .findByIdWithWriteLock(productId)
            .orElseThrow();
        
        // Update
        product.setPrice(newPrice);
        productRepository.save(product);
    }
    
    // Increment price (prevent lost updates)
    @Transactional
    public void incrementPrice(Long productId, BigDecimal increment) {
        // Use exclusive lock from the start
        Product product = productRepository
            .findByIdWithWriteLock(productId)
            .orElseThrow();
        
        // Read current price and update
        BigDecimal currentPrice = product.getPrice();
        product.setPrice(currentPrice.add(increment));
        productRepository.save(product);
        
        // No lost updates! ✅
    }
}
```

### Optimistic Locking Alternative

```java
// Alternative: Optimistic locking with @Version

@Entity
public class Product {
    
    @Id
    private Long id;
    
    private String name;
    private BigDecimal price;
    
    @Version  // Optimistic locking
    private Integer version;
}

@Service
public class OptimisticProductService {
    
    @Autowired
    private ProductRepository productRepository;
    
    @Transactional
    public void incrementPriceOptimistic(Long productId, BigDecimal increment) {
        Product product = productRepository.findById(productId).orElseThrow();
        
        // Read and update
        product.setPrice(product.getPrice().add(increment));
        
        // Save with version check
        try {
            productRepository.save(product);
            // SQL: UPDATE products SET price = ?, version = version + 1 
            //      WHERE id = ? AND version = ?
        } catch (OptimisticLockingFailureException e) {
            // Version mismatch - retry
            throw new ConcurrentModificationException("Product was modified");
        }
    }
}

// Comparison:
// Pessimistic (FOR UPDATE): Locks row immediately, blocks others
// Optimistic (@Version): No lock, fails on conflict, retry required

// Use pessimistic when: High contention expected
// Use optimistic when: Low contention, want to avoid locks
```

## 4. Gap Locks and Next-Key Locks

### Understanding Gap Locks

```sql
-- Gap locks: Lock the gap between index records
-- Purpose: Prevent phantom reads in REPEATABLE READ isolation

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    customer_id BIGINT,
    status VARCHAR(20),
    created_at DATETIME,
    INDEX idx_status (status)
) ENGINE=InnoDB;

INSERT INTO orders VALUES 
(1, 100, 'PENDING', NOW()),
(5, 101, 'PENDING', NOW()),
(10, 102, 'SHIPPED', NOW());

-- === Gap Lock Example ===

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Session 1: Lock range
START TRANSACTION;
SELECT * FROM orders WHERE id > 1 AND id < 10 FOR UPDATE;
-- Locks:
-- - Row: id=5
-- - Gap: (1, 5) - between 1 and 5
-- - Gap: (5, 10) - between 5 and 10

-- Session 2: Try to insert into gap
START TRANSACTION;
INSERT INTO orders VALUES (3, 103, 'PENDING', NOW());
-- ❌ BLOCKED! id=3 falls in gap (1, 5)

INSERT INTO orders VALUES (7, 104, 'PENDING', NOW());
-- ❌ BLOCKED! id=7 falls in gap (5, 10)

INSERT INTO orders VALUES (11, 105, 'PENDING', NOW());
-- ✅ Proceeds! id=11 not in locked range

-- Session 1: Commit
COMMIT;

-- Session 2: Now proceeds with inserts


-- === Gap Lock Prevention (READ COMMITTED) ===

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Session 1:
START TRANSACTION;
SELECT * FROM orders WHERE id > 1 AND id < 10 FOR UPDATE;
-- Locks only existing rows: id=5
-- NO gap locks in READ COMMITTED

-- Session 2:
START TRANSACTION;
INSERT INTO orders VALUES (3, 103, 'PENDING', NOW());
-- ✅ Proceeds immediately! No gap lock

-- But now phantom reads are possible:
-- Session 1:
SELECT * FROM orders WHERE id > 1 AND id < 10;
-- Returns: id=3, id=5 (sees new row!)
```

### Next-Key Locks

```sql
-- Next-Key Lock = Record Lock + Gap Lock before it
-- Default locking in REPEATABLE READ

CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    age INT,
    INDEX idx_age (age)
) ENGINE=InnoDB;

INSERT INTO users VALUES 
(1, 'alice', 20),
(2, 'bob', 25),
(3, 'charlie', 30),
(4, 'david', 35);

-- === Next-Key Lock Example ===

-- Session 1: Range query
START TRANSACTION;
SELECT * FROM users WHERE age >= 25 AND age < 35 FOR UPDATE;

-- Locks (using idx_age):
-- Next-key lock on age=25: (20, 25] (gap + record)
-- Next-key lock on age=30: (25, 30] (gap + record)
-- Gap lock: (30, 35)

-- Session 2: Try various operations
START TRANSACTION;

-- Insert age=22 (in gap (20, 25))
INSERT INTO users VALUES (5, 'eve', 22);
-- ❌ BLOCKED!

-- Insert age=27 (in gap (25, 30))
INSERT INTO users VALUES (6, 'frank', 27);
-- ❌ BLOCKED!

-- Insert age=32 (in gap (30, 35))
INSERT INTO users VALUES (7, 'grace', 32);
-- ❌ BLOCKED!

-- Insert age=18 (before gap)
INSERT INTO users VALUES (8, 'henry', 18);
-- ✅ Proceeds!

-- Insert age=40 (after gap)
INSERT INTO users VALUES (9, 'iris', 40);
-- ✅ Proceeds!

-- Update locked row
UPDATE users SET username = 'robert' WHERE age = 25;
-- ❌ BLOCKED!


-- === Visualization ===

-- age values: 20, 25, 30, 35
-- Gaps: (-∞, 20), (20, 25), (25, 30), (30, 35), (35, +∞)

-- Query: WHERE age >= 25 AND age < 35
-- Locks:
-- Next-key (20, 25]: Prevents INSERT age=21-25
-- Next-key (25, 30]: Prevents INSERT age=26-30
-- Gap (30, 35):      Prevents INSERT age=31-34
```

### Gap Lock Behavior with Different Indexes

```sql
-- Gap locks behavior depends on index used

CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    category VARCHAR(50),
    price DECIMAL(10,2),
    INDEX idx_category (category),
    INDEX idx_price (price)
) ENGINE=InnoDB;

INSERT INTO products VALUES 
(1, 'electronics', 100),
(2, 'electronics', 200),
(3, 'books', 15),
(4, 'books', 25);

-- === Using Primary Key (no gap locks between values) ===
SELECT * FROM products WHERE id BETWEEN 1 AND 3 FOR UPDATE;
-- Locks: id=1, id=2, id=3 (records only)
-- Gap locks only at boundaries

-- === Using Secondary Index (gap locks between same category) ===
SELECT * FROM products WHERE category = 'electronics' FOR UPDATE;
-- Locks:
-- - Records: id=1, id=2
-- - Gap between category 'electronics' entries
-- - Prevents: INSERT INTO products VALUES (5, 'electronics', 150)


-- === Avoiding Gap Locks ===

-- Method 1: Use READ COMMITTED isolation
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- No gap locks, but phantom reads possible

-- Method 2: Use unique index lookup
SELECT * FROM products WHERE id = 1 FOR UPDATE;
-- Only locks id=1, no gaps (unique lookup)

-- Method 3: Use FOR UPDATE SKIP LOCKED
SELECT * FROM products WHERE category = 'electronics' 
FOR UPDATE SKIP LOCKED;
-- Skips locked gaps
```

### Spring Boot Gap Lock Handling

```java
@Service
public class OrderProcessingService {
    
    @Autowired
    private OrderRepository orderRepository;
    
    // Gap locks can cause blocking
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public List<Order> getPendingOrders() {
        // This creates gap locks
        return orderRepository.findByStatusWithLock("PENDING");
        
        // Locks all PENDING orders + gaps
        // Blocks concurrent INSERT of new PENDING orders
    }
    
    // Avoid gap locks with READ COMMITTED
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public List<Order> getPendingOrdersNoGapLock() {
        return orderRepository.findByStatusWithLock("PENDING");
        
        // Locks only existing PENDING orders
        // Allows concurrent INSERT of new PENDING orders ✅
        // But: May see new rows in subsequent queries (phantom reads)
    }
    
    // Alternative: Process one order at a time
    @Transactional
    public void processNextOrder() {
        // Use SKIP LOCKED to avoid gap lock contention
        Optional<Order> orderOpt = orderRepository.findNextPendingOrder();
        
        if (orderOpt.isEmpty()) {
            return;
        }
        
        Order order = orderOpt.get();
        processOrder(order);
    }
}

@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT o FROM Order o WHERE o.status = ?1")
    List<Order> findByStatusWithLock(String status);
    
    @Query(value = """
        SELECT * FROM orders 
        WHERE status = 'PENDING' 
        ORDER BY id 
        LIMIT 1 
        FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
    Optional<Order> findNextPendingOrder();
}
```

## 5. Deadlock Detection and Resolution

### Understanding Deadlocks

```sql
-- Deadlock: Two transactions waiting for each other

CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(10,2)
) ENGINE=InnoDB;

INSERT INTO accounts VALUES (1, 1000), (2, 1000);

-- === Classic Deadlock ===
```

### Common Deadlock Scenarios

```sql
-- Scenario 1: Different lock order

-- Transaction 1: Lock A then B
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- Lock A
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- Lock B
COMMIT;

-- Transaction 2: Lock B then A (DEADLOCK!)
START TRANSACTION;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- Lock B
UPDATE accounts SET balance = balance + 50 WHERE id = 1;   -- Lock A
COMMIT;

-- Solution: Always lock in same order (e.g., by ID ascending)


-- Scenario 2: Gap lock + insert

-- Transaction 1:
START TRANSACTION;
SELECT * FROM orders WHERE id > 5 AND id < 15 FOR UPDATE;
-- Gap locks: (5, 15)

-- Transaction 2:
START TRANSACTION;
SELECT * FROM orders WHERE id > 10 AND id < 20 FOR UPDATE;
-- Gap locks: (10, 20) - overlaps with Transaction 1!

-- Transaction 1:
INSERT INTO orders VALUES (12, ...);  -- Waits for gap (10, 20)

-- Transaction 2:
INSERT INTO orders VALUES (8, ...);   -- Waits for gap (5, 15)

-- DEADLOCK!


-- Scenario 3: Shared lock upgrade

-- Transaction 1:
START TRANSACTION;
SELECT * FROM products WHERE id = 1 LOCK IN SHARE MODE;

-- Transaction 2:
START TRANSACTION;
SELECT * FROM products WHERE id = 1 LOCK IN SHARE MODE;

-- Both hold shared locks

-- Transaction 1:
UPDATE products SET price = 100 WHERE id = 1;
-- Tries to upgrade to exclusive lock - waits for Transaction 2

-- Transaction 2:
UPDATE products SET price = 200 WHERE id = 1;
-- Tries to upgrade to exclusive lock - waits for Transaction 1

-- DEADLOCK!

-- Solution: Use FOR UPDATE from the start
```

### Deadlock Prevention Strategies

```java
@Service
public class DeadlockPreventionService {
    
    @Autowired
    private AccountRepository accountRepository;
    
    // ❌ BAD: Can cause deadlock
    @Transactional
    public void transferBad(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findByIdWithLock(fromId);
        Account to = accountRepository.findByIdWithLock(toId);
        
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
        
        // Problem: Lock order depends on method arguments
        // transfer(1, 2) locks: 1, 2
        // transfer(2, 1) locks: 2, 1 - DIFFERENT ORDER!
    }
    
    // ✅ GOOD: Lock in consistent order
    @Transactional
    public void transferGood(Long fromId, Long toId, BigDecimal amount) {
        // Always lock in ascending ID order
        Long firstId = Math.min(fromId, toId);
        Long secondId = Math.max(fromId, toId);
        
        Account first = accountRepository.findByIdWithLock(firstId);
        Account second = accountRepository.findByIdWithLock(secondId);
        
        // Determine which is from/to
        Account from = (fromId.equals(firstId)) ? first : second;
        Account to = (fromId.equals(firstId)) ? second : first;
        
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
        
        // Now: All transfers lock in same order (ascending ID) ✅
    }
    
    // Alternative: Single query
    @Transactional
    public void transferSingleQuery(Long fromId, Long toId, BigDecimal amount) {
        // Use single UPDATE to avoid multiple locks
        accountRepository.updateBalance(fromId, amount.negate());
        accountRepository.updateBalance(toId, amount);
        
        // Still need to validate balances first
    }
}
```

### Deadlock Retry Logic

```java
@Service
public class TransactionRetryService {
    
    private static final int MAX_RETRIES = 3;
    
    @Autowired
    private AccountRepository accountRepository;
    
    public void transferWithRetry(Long fromId, Long toId, BigDecimal amount) {
        int attempt = 0;
        
        while (attempt < MAX_RETRIES) {
            try {
                attemptTransfer(fromId, toId, amount);
                return;  // Success!
                
            } catch (PessimisticLockingFailureException e) {
                // Deadlock or lock timeout
                attempt++;
                
                if (attempt >= MAX_RETRIES) {
                    throw new RuntimeException("Transfer failed after " + MAX_RETRIES + " attempts", e);
                }
                
                log.warn("Deadlock detected on attempt {}, retrying...", attempt);
                
                // Exponential backoff
                try {
                    Thread.sleep((long) Math.pow(2, attempt) * 100);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("Interrupted during retry", ie);
                }
            }
        }
    }
    
    @Transactional
    private void attemptTransfer(Long fromId, Long toId, BigDecimal amount) {
        // Lock in consistent order
        Long firstId = Math.min(fromId, toId);
        Long secondId = Math.max(fromId, toId);
        
        Account first = accountRepository.findByIdWithLock(firstId);
        Account second = accountRepository.findByIdWithLock(secondId);
        
        Account from = (fromId.equals(firstId)) ? first : second;
        Account to = (fromId.equals(firstId)) ? second : first;
        
        // Validate
        if (from.getBalance().compareTo(amount) < 0) {
            throw new InsufficientFundsException();
        }
        
        // Transfer
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
        
        accountRepository.save(from);
        accountRepository.save(to);
    }
}
```

```java
        try {
            // Get deadlock info from SHOW ENGINE INNODB STATUS
            String deadlockInfo = jdbcTemplate.queryForObject(
                "SHOW ENGINE INNODB STATUS",
                String.class

            // Parse and log relevant parts
            String[] lines = deadlockInfo.split("\n");

            for (String line : lines) {

                    inDeadlockSection = true;
                }
                
                if (inDeadlockSection) {
                    deadlockDetails.append(line).append("\n");
                    
                    if (line.contains("WE ROLL BACK")) {
                        break;
                    }
                }

            log.error("Deadlock details:\n{}", deadlockDetails);

            log.error("Failed to retrieve deadlock info", ex);
```

### Lock Modes Overview

```java
// LockModeType enumeration

public enum LockModeType {
    
    // No lock
    NONE,
    
    // Optimistic locks (use @Version)
    OPTIMISTIC,              // Read version, check on commit
    OPTIMISTIC_FORCE_INCREMENT,  // Increment version even on read
    
    // Pessimistic locks (database locks)
    PESSIMISTIC_READ,        // SELECT ... FOR SHARE (shared lock)
    PESSIMISTIC_WRITE,       // SELECT ... FOR UPDATE (exclusive lock)
    PESSIMISTIC_FORCE_INCREMENT,  // FOR UPDATE + increment version
    
    // JPA provider specific
    READ,   // Synonym for OPTIMISTIC
    WRITE   // Synonym for OPTIMISTIC_FORCE_INCREMENT
}
```

### Complete Lock Examples

```java
@Repository
public interface ProductRepository extends JpaRepository<Product, Long> {
    
    // === No Lock (default) ===
    Optional<Product> findById(Long id);
    // SELECT * FROM products WHERE id = ?
    
    // === Pessimistic Write Lock (FOR UPDATE) ===
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = ?1")
    Optional<Product> findByIdForUpdate(Long id);
    // SELECT * FROM products WHERE id = ? FOR UPDATE
    
    // === Pessimistic Read Lock (FOR SHARE) ===
    @Lock(LockModeType.PESSIMISTIC_READ)
    @Query("SELECT p FROM Product p WHERE p.id = ?1")
    Optional<Product> findByIdForShare(Long id);
    // SELECT * FROM products WHERE id = ? FOR SHARE
    
    // === Optimistic Lock ===
    @Lock(LockModeType.OPTIMISTIC)
    Optional<Product> findByIdOptimistic(Long id);
    // SELECT * FROM products WHERE id = ?
    // Version checked on update
    
    // === Lock with Query Methods ===
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    List<Product> findByCategory(String category);
    // SELECT * FROM products WHERE category = ? FOR UPDATE
    
    // === Lock with Native Query ===
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query(value = "SELECT * FROM products WHERE price > ?1", nativeQuery = true)
    List<Product> findExpensiveProducts(BigDecimal minPrice);
    // Lock may not work with native queries in all JPA providers
    // Better to add FOR UPDATE explicitly in SQL
    
    @Query(value = "SELECT * FROM products WHERE price > ?1 FOR UPDATE", nativeQuery = true)
    List<Product> findExpensiveProductsExplicit(BigDecimal minPrice);
    
    // === Lock Timeout ===
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({
        @QueryHint(name = "javax.persistence.lock.timeout", value = "5000")  // 5 seconds
    })
    Optional<Product> findByIdWithTimeout(Long id);
    // Wait up to 5 seconds for lock
    
    // === NOWAIT ===
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({
        @QueryHint(name = "javax.persistence.lock.timeout", value = "0")
    })
    Optional<Product> findByIdNoWait(Long id);
    // Fail immediately if locked
}
```

### Service Layer Lock Usage

```java
@Service
public class ProductService {
    
    @Autowired
    private ProductRepository productRepository;
    
    // === Read-only with shared lock ===
    @Transactional(readOnly = true)
    public ProductDTO getProductDetails(Long id) {
        Product product = productRepository
            .findByIdForShare(id)
            .orElseThrow();
        
        // Shared lock allows concurrent reads
        // Blocks concurrent updates
        return new ProductDTO(product);
    }
    
    // === Update with exclusive lock ===
    @Transactional
    public void updateStock(Long productId, int quantitySold) {
        Product product = productRepository
            .findByIdForUpdate(productId)
            .orElseThrow();
        
        // Exclusive lock - no concurrent reads or writes
        int currentStock = product.getStock();
        
        if (currentStock < quantitySold) {
            throw new InsufficientStockException();
        }
        
        product.setStock(currentStock - quantitySold);
        productRepository.save(product);
    }
    
    // === Optimistic locking ===
    @Transactional
    public void updatePriceOptimistic(Long productId, BigDecimal newPrice) {
        Product product = productRepository
            .findByIdOptimistic(productId)
            .orElseThrow();
        
        product.setPrice(newPrice);
        
        try {
            productRepository.save(product);
        } catch (OptimisticLockingFailureException e) {
            // Version mismatch - product was modified concurrently
            throw new ConcurrentModificationException(
                "Product was modified by another user"
            );
        }
    }
    
    // === Try lock with timeout ===
    @Transactional
    public boolean tryUpdateStock(Long productId, int quantity) {
        try {
            Product product = productRepository
                .findByIdNoWait(productId)
                .orElseThrow();
            
            if (product.getStock() >= quantity) {
                product.setStock(product.getStock() - quantity);
                productRepository.save(product);
                return true;
            }
            
            return false;
            
        } catch (PessimisticLockingFailureException e) {
            // Product is locked by another transaction
            log.debug("Product {} is currently locked", productId);
            return false;
        }
    }
}
```

```java
@Service
public class DirectLockingService {
    
    @PersistenceContext
    private EntityManager entityManager;
    
    // Lock existing entity
    @Transactional
    public void lockExistingEntity(Product product) {
        // Acquire pessimistic write lock on already-loaded entity
        entityManager.lock(product, LockModeType.PESSIMISTIC_WRITE);
        
        // Now can safely modify
        product.setPrice(product.getPrice().multiply(BigDecimal.valueOf(1.1)));
    }
    
    // Find with lock
    @Transactional
    public Product findWithLock(Long id) {
        // Find and lock in one operation
        return entityManager.find(
            Product.class, 
            id, 
            LockModeType.PESSIMISTIC_WRITE
        );
    }
    
    // Lock with properties
    @Transactional
    public Product findWithLockTimeout(Long id) {
        Map<String, Object> properties = new HashMap<>();
        properties.put("javax.persistence.lock.timeout", 5000);  // 5 seconds
        
        return entityManager.find(
            Product.class,
            id,
            LockModeType.PESSIMISTIC_WRITE,
            properties
        );
    }
    
    // Refresh with lock
    @Transactional
    public void refreshWithLock(Product product) {
        // Refresh entity from database and acquire lock
        entityManager.refresh(product, LockModeType.PESSIMISTIC_WRITE);
    }
```

## Best Practices Summary

```
✅ DO:
- Use row locks (InnoDB) for production applications
- Lock in consistent order to prevent deadlocks (e.g., by ID)
- Use FOR UPDATE when planning to modify data
- Use FOR SHARE for read-only checks that block writes
- Implement retry logic for deadlocks (3 attempts with backoff)
- Use SKIP LOCKED for job queues
- Consider READ COMMITTED to avoid gap locks
- Monitor deadlock frequency
- Use short transactions to minimize lock duration
- Use optimistic locking for low-contention scenarios

❌ DON'T:
- Use table locks (blocks entire table)
- Lock in different orders (causes deadlocks)
- Hold locks for long periods (impacts concurrency)
- Upgrade shared locks to exclusive (can deadlock)
- Ignore deadlock exceptions (they indicate design issues)
- Use pessimistic locks for everything (hurts performance)
- Forget to handle PessimisticLockingFailureException
- Use FOR UPDATE on large ranges (creates many gap locks)
```
