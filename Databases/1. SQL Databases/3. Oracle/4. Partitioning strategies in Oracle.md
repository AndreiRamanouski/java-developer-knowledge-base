# Oracle Partitioning Strategies in Spring Boot

## Overview

Partitioning is a critical database design technique for managing large tables in Oracle. It divides tables and indexes into smaller, more manageable pieces while maintaining logical integrity. Understanding partitioning is essential for building high-performance enterprise applications.

**Key Concept**: Partitioning improves performance through partition pruning (scanning only relevant partitions), enables better data management (archive old partitions), and enhances availability (operations on individual partitions).

---

## 1. Range Partitioning

Range partitioning divides data based on ranges of values, typically used for date/time or numeric columns.

### Basic Range Partitioning

**Oracle DDL:**

```sql
-- Partition orders by order date (monthly)
CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    order_date DATE NOT NULL,
    customer_id NUMBER NOT NULL,
    total_amount NUMBER(10,2),
    status VARCHAR2(20)
)
PARTITION BY RANGE (order_date) (
    PARTITION orders_2024_01 VALUES LESS THAN (DATE '2024-02-01'),
    PARTITION orders_2024_02 VALUES LESS THAN (DATE '2024-03-01'),
    PARTITION orders_2024_03 VALUES LESS THAN (DATE '2024-04-01'),
    PARTITION orders_2024_04 VALUES LESS THAN (DATE '2024-05-01'),
    PARTITION orders_2024_05 VALUES LESS THAN (DATE '2024-06-01'),
    PARTITION orders_2024_06 VALUES LESS THAN (DATE '2024-07-01'),
    PARTITION orders_2024_07 VALUES LESS THAN (DATE '2024-08-01'),
    PARTITION orders_2024_08 VALUES LESS THAN (DATE '2024-09-01'),
    PARTITION orders_2024_09 VALUES LESS THAN (DATE '2024-10-01'),
    PARTITION orders_2024_10 VALUES LESS THAN (DATE '2024-11-01'),
    PARTITION orders_2024_11 VALUES LESS THAN (DATE '2024-12-01'),
    PARTITION orders_2024_12 VALUES LESS THAN (DATE '2025-01-01'),
    PARTITION orders_future VALUES LESS THAN (MAXVALUE)
);

-- Create local indexes (partitioned along with table)
CREATE INDEX idx_orders_customer ON orders(customer_id) LOCAL;
CREATE INDEX idx_orders_status ON orders(status) LOCAL;
```

**Spring Boot Entity:**

```java
@Entity
@Table(name = "orders")
@Data
@NoArgsConstructor
@AllArgsConstructor
public class Order {
    
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
    @SequenceGenerator(name = "order_seq", sequenceName = "ORDER_SEQ", allocationSize = 1)
    @Column(name = "order_id")
    private Long orderId;
    
    @Column(name = "order_date", nullable = false)
    private LocalDate orderDate;  // Partition key
    
    @Column(name = "customer_id", nullable = false)
    private Long customerId;
    
    @Column(name = "total_amount")
    private BigDecimal totalAmount;
    
    @Column(name = "status", length = 20)
    @Enumerated(EnumType.STRING)
    private OrderStatus status;
}

enum OrderStatus {
    PENDING, PROCESSING, SHIPPED, DELIVERED, CANCELLED
}
```

**JPA Repository with Partition-Aware Queries:**

```java
@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    
    // ✅ Partition pruning: Query includes partition key
    @Query("SELECT o FROM Order o WHERE o.orderDate BETWEEN :startDate AND :endDate")
    List<Order> findOrdersByDateRange(
        @Param("startDate") LocalDate startDate,
        @Param("endDate") LocalDate endDate
    );
    
    // ✅ Partition pruning: Single partition accessed
    @Query("SELECT o FROM Order o WHERE o.orderDate = :date AND o.status = :status")
    List<Order> findOrdersByDateAndStatus(
        @Param("date") LocalDate date,
        @Param("status") OrderStatus status
    );
    
    // ❌ Full table scan: No partition key in WHERE clause
    List<Order> findByCustomerId(Long customerId);
    
    // ✅ Better: Include partition key hint
    @Query("SELECT o FROM Order o WHERE o.customerId = :customerId " +
           "AND o.orderDate >= :fromDate")
    List<Order> findByCustomerIdSinceDate(
        @Param("customerId") Long customerId,
        @Param("fromDate") LocalDate fromDate
    );
}
```

### Automatic Partition Management with INTERVAL

**Oracle DDL:**

```sql
-- Automatically create monthly partitions as needed
CREATE TABLE sales (
    sale_id NUMBER PRIMARY KEY,
    sale_date DATE NOT NULL,
    product_id NUMBER,
    quantity NUMBER,
    amount NUMBER(10,2)
)
PARTITION BY RANGE (sale_date)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))  -- Auto-create monthly partitions
(
    PARTITION sales_initial VALUES LESS THAN (DATE '2024-01-01')
);

-- Oracle automatically creates partitions as data arrives:
-- INSERT for 2024-02-15 -> Creates partition for Feb 2024
-- INSERT for 2024-03-20 -> Creates partition for Mar 2024
```

**Service Layer:**

```java
@Service
@Slf4j
public class SalesService {
    
    @Autowired
    private SalesRepository salesRepository;
    
    @PersistenceContext
    private EntityManager entityManager;
    
    /**
     * Efficient query - uses partition pruning
     */
    public List<Sale> getMonthlySales(int year, int month) {
        LocalDate startDate = LocalDate.of(year, month, 1);
        LocalDate endDate = startDate.plusMonths(1);
        
        // Oracle scans only the relevant partition
        return salesRepository.findBySaleDateBetween(startDate, endDate);
    }
    
    /**
     * Check partition information
     */
    public List<PartitionInfo> getPartitionInfo() {
        String sql = """
            SELECT partition_name, high_value, num_rows, blocks
            FROM user_tab_partitions
            WHERE table_name = 'SALES'
            ORDER BY partition_position
        """;
        
        @SuppressWarnings("unchecked")
        List<Object[]> results = entityManager.createNativeQuery(sql).getResultList();
        
        return results.stream()
            .map(row -> new PartitionInfo(
                (String) row[0],  // partition_name
                (String) row[1],  // high_value
                ((Number) row[2]).longValue(),  // num_rows
                ((Number) row[3]).longValue()   // blocks
            ))
            .collect(Collectors.toList());
    }
}

@Data
@AllArgsConstructor
class PartitionInfo {
    private String partitionName;
    private String highValue;
    private Long numRows;
    private Long blocks;
}
```

## 2. List Partitioning

List partitioning divides data based on discrete values, ideal for categorizing by region, status, or type.

### Basic List Partitioning

**Oracle DDL:**

```sql
-- Partition customers by region
CREATE TABLE customers (
    customer_id NUMBER PRIMARY KEY,
    customer_name VARCHAR2(100),
    region VARCHAR2(20) NOT NULL,
    email VARCHAR2(100),
    created_date DATE
)
PARTITION BY LIST (region) (
    PARTITION cust_north_america VALUES ('USA', 'CANADA', 'MEXICO'),
    PARTITION cust_europe VALUES ('UK', 'GERMANY', 'FRANCE', 'ITALY', 'SPAIN'),
    PARTITION cust_asia VALUES ('CHINA', 'JAPAN', 'INDIA', 'SINGAPORE'),
    PARTITION cust_other VALUES (DEFAULT)  -- Catch-all for other regions
);

-- Local indexes
CREATE INDEX idx_customers_email ON customers(email) LOCAL;
```

**Spring Boot Entity:**

```java
@Entity
@Table(name = "customers")
@Data
public class Customer {
    
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "cust_seq")
    @SequenceGenerator(name = "cust_seq", sequenceName = "CUSTOMER_SEQ")
    @Column(name = "customer_id")
    private Long customerId;
    
    @Column(name = "customer_name", length = 100)
    private String customerName;
    
    @Column(name = "region", length = 20, nullable = false)
    private String region;  // Partition key
    
    @Column(name = "email", length = 100)
    private String email;
    
    @Column(name = "created_date")
    private LocalDate createdDate;
}
```

**Repository with Region-Based Queries:**

```java
@Repository
public interface CustomerRepository extends JpaRepository<Customer, Long> {
    
    // ✅ Partition pruning: Scans single partition
    List<Customer> findByRegion(String region);
    
    // ✅ Partition pruning: Scans specific partitions
    @Query("SELECT c FROM Customer c WHERE c.region IN :regions")
    List<Customer> findByRegions(@Param("regions") List<String> regions);
    
    // ✅ Efficient: Partition key in WHERE
    @Query("SELECT c FROM Customer c WHERE c.region = :region " +
           "AND c.createdDate >= :sinceDate")
    List<Customer> findByRegionSinceDate(
        @Param("region") String region,
        @Param("sinceDate") LocalDate sinceDate
    );
}
```

**Service with Region-Specific Logic:**

```java
@Service
public class CustomerService {
    
    @Autowired
    private CustomerRepository customerRepository;
    
    /**
     * Get customers by region - efficient partition access
     */
    public List<Customer> getCustomersByRegion(String region) {
        // Oracle accesses only the relevant partition
        return customerRepository.findByRegion(region);
    }
    
    /**
     * Get customers from multiple regions
     */
    public List<Customer> getCustomersByRegions(List<String> regions) {
        // Oracle accesses only specified partitions
        return customerRepository.findByRegions(regions);
    }
    
    /**
     * Get European customers (demonstrates partition pruning)
     */
    public List<Customer> getEuropeanCustomers() {
        // Scans only cust_europe partition
        List<String> europeanCountries = Arrays.asList(
            "UK", "GERMANY", "FRANCE", "ITALY", "SPAIN"
        );
        return customerRepository.findByRegions(europeanCountries);
    }
}
```

## 3. Hash Partitioning

Hash partitioning evenly distributes data across partitions using a hash function. Best for load balancing when no natural partitioning key exists.

### Basic Hash Partitioning

**Oracle DDL:**

```sql
-- Partition sessions by session_id (hash)
CREATE TABLE user_sessions (
    session_id VARCHAR2(100) PRIMARY KEY,
    user_id NUMBER NOT NULL,
    ip_address VARCHAR2(45),
    created_at TIMESTAMP,
    last_activity TIMESTAMP,
    session_data CLOB
)
PARTITION BY HASH (session_id)
PARTITIONS 8;  -- Creates 8 partitions with even distribution

-- Oracle names them: SYS_P1, SYS_P2, ..., SYS_P8
-- You can specify custom names:
CREATE TABLE user_sessions_named (
    session_id VARCHAR2(100) PRIMARY KEY,
    user_id NUMBER NOT NULL,
    ip_address VARCHAR2(45),
    created_at TIMESTAMP
)
PARTITION BY HASH (session_id) (
    PARTITION sess_p1,
    PARTITION sess_p2,
    PARTITION sess_p3,
    PARTITION sess_p4,
    PARTITION sess_p5,
    PARTITION sess_p6,
    PARTITION sess_p7,
    PARTITION sess_p8
);
```

**Spring Boot Entity:**

```java
@Entity
@Table(name = "user_sessions")
@Data
public class UserSession {
    
    @Id
    @Column(name = "session_id", length = 100)
    private String sessionId;  // Partition key (hash)
    
    @Column(name = "user_id", nullable = false)
    private Long userId;
    
    @Column(name = "ip_address", length = 45)
    private String ipAddress;
    
    @Column(name = "created_at")
    private Instant createdAt;
    
    @Column(name = "last_activity")
    private Instant lastActivity;
    
    @Lob
    @Column(name = "session_data")
    private String sessionData;
}
```

**Repository:**

```java
@Repository
public interface UserSessionRepository extends JpaRepository<UserSession, String> {
    
    // ✅ Partition pruning: Specific session_id -> single partition
    Optional<UserSession> findBySessionId(String sessionId);
    
    // ❌ Full table scan: user_id is not partition key
    List<UserSession> findByUserId(Long userId);
    
    // Cleanup old sessions
    @Modifying
    @Query("DELETE FROM UserSession s WHERE s.lastActivity < :cutoffTime")
    int deleteInactiveSessions(@Param("cutoffTime") Instant cutoffTime);
}
```

**Service:**

```java
@Service
public class SessionService {
    
    @Autowired
    private UserSessionRepository sessionRepository;
    
    /**
     * Find session by ID - efficient (single partition access)
     */
    public Optional<UserSession> getSession(String sessionId) {
        // Oracle uses hash(session_id) to determine partition
        // Scans only 1 of 8 partitions
        return sessionRepository.findBySessionId(sessionId);
    }
    
    /**
     * Create new session
     */
    @Transactional
    public UserSession createSession(Long userId, String ipAddress) {
        UserSession session = new UserSession();
        session.setSessionId(UUID.randomUUID().toString());
        session.setUserId(userId);
        session.setIpAddress(ipAddress);
        session.setCreatedAt(Instant.now());
        session.setLastActivity(Instant.now());
        
        // Oracle automatically determines partition based on hash
        return sessionRepository.save(session);
    }
    
    /**
     * Cleanup old sessions (affects all partitions)
     */
    @Transactional
    public int cleanupInactiveSessions(Duration inactivePeriod) {
        Instant cutoff = Instant.now().minus(inactivePeriod);
        // Scans all partitions (no partition pruning possible)
        return sessionRepository.deleteInactiveSessions(cutoff);
    }
}
```

## 4. Composite Partitioning

Composite partitioning combines two partitioning strategies: range-list, range-hash, list-hash, etc.

### Range-Hash Composite Partitioning

**Oracle DDL:**

```sql
-- Partition by order date (range), then by customer_id (hash)
CREATE TABLE order_items (
    order_item_id NUMBER PRIMARY KEY,
    order_id NUMBER NOT NULL,
    order_date DATE NOT NULL,
    customer_id NUMBER NOT NULL,
    product_id NUMBER,
    quantity NUMBER,
    unit_price NUMBER(10,2)
)
PARTITION BY RANGE (order_date)
SUBPARTITION BY HASH (customer_id)
SUBPARTITIONS 4 (
    PARTITION items_2024_q1 VALUES LESS THAN (DATE '2024-04-01'),
    PARTITION items_2024_q2 VALUES LESS THAN (DATE '2024-07-01'),
    PARTITION items_2024_q3 VALUES LESS THAN (DATE '2024-10-01'),
    PARTITION items_2024_q4 VALUES LESS THAN (DATE '2025-01-01'),
    PARTITION items_future VALUES LESS THAN (MAXVALUE)
);

-- Results in: 5 partitions × 4 subpartitions = 20 total partitions
-- items_2024_q1 -> 4 subpartitions (hash on customer_id)
-- items_2024_q2 -> 4 subpartitions (hash on customer_id)
-- etc.
```

**Spring Boot Entity:**

```java
@Entity
@Table(name = "order_items")
@Data
public class OrderItem {
    
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "item_seq")
    @SequenceGenerator(name = "item_seq", sequenceName = "ORDER_ITEM_SEQ")
    @Column(name = "order_item_id")
    private Long orderItemId;
    
    @Column(name = "order_id", nullable = false)
    private Long orderId;
    
    @Column(name = "order_date", nullable = false)
    private LocalDate orderDate;  // Range partition key
    
    @Column(name = "customer_id", nullable = false)
    private Long customerId;  // Hash subpartition key
    
    @Column(name = "product_id")
    private Long productId;
    
    @Column(name = "quantity")
    private Integer quantity;
    
    @Column(name = "unit_price")
    private BigDecimal unitPrice;
}
```

**Repository:**

```java
@Repository
public interface OrderItemRepository extends JpaRepository<OrderItem, Long> {
    
    // ✅ Best: Both partition keys -> single subpartition
    @Query("SELECT oi FROM OrderItem oi " +
           "WHERE oi.orderDate BETWEEN :startDate AND :endDate " +
           "AND oi.customerId = :customerId")
    List<OrderItem> findByDateRangeAndCustomer(
        @Param("startDate") LocalDate startDate,
        @Param("endDate") LocalDate endDate,
        @Param("customerId") Long customerId
    );
    
    // ✅ Good: Range partition key -> limits to specific partitions
    @Query("SELECT oi FROM OrderItem oi " +
           "WHERE oi.orderDate BETWEEN :startDate AND :endDate")
    List<OrderItem> findByDateRange(
        @Param("startDate") LocalDate startDate,
        @Param("endDate") LocalDate endDate
    );
    
    // ⚠️ Moderate: Only hash key -> scans all date partitions
    List<OrderItem> findByCustomerId(Long customerId);
    
    // ❌ Worst: No partition keys -> full table scan
    List<OrderItem> findByProductId(Long productId);
}
```

### Range-List Composite Partitioning

**Oracle DDL:**

```sql
-- Partition by date (range), then by region (list)
CREATE TABLE sales_transactions (
    transaction_id NUMBER PRIMARY KEY,
    transaction_date DATE NOT NULL,
    region VARCHAR2(20) NOT NULL,
    amount NUMBER(10,2),
    product_id NUMBER
)
PARTITION BY RANGE (transaction_date)
SUBPARTITION BY LIST (region) (
    PARTITION sales_2024_q1 VALUES LESS THAN (DATE '2024-04-01') (
        SUBPARTITION sales_2024_q1_na VALUES ('USA', 'CANADA'),
        SUBPARTITION sales_2024_q1_eu VALUES ('UK', 'GERMANY', 'FRANCE'),
        SUBPARTITION sales_2024_q1_asia VALUES ('CHINA', 'JAPAN', 'INDIA')
    ),
    PARTITION sales_2024_q2 VALUES LESS THAN (DATE '2024-07-01') (
        SUBPARTITION sales_2024_q2_na VALUES ('USA', 'CANADA'),
        SUBPARTITION sales_2024_q2_eu VALUES ('UK', 'GERMANY', 'FRANCE'),
        SUBPARTITION sales_2024_q2_asia VALUES ('CHINA', 'JAPAN', 'INDIA')
    )
    -- Additional quarters...
);
```

**Service with Composite Query:**

```java
@Service
public class SalesAnalyticsService {
    
    @Autowired
    private SalesTransactionRepository salesRepository;
    
    /**
     * Most efficient: Both partition keys specified
     */
    public BigDecimal getQuarterlySalesByRegion(int year, int quarter, String region) {
        LocalDate startDate = getQuarterStart(year, quarter);
        LocalDate endDate = startDate.plusMonths(3);
        
        // Oracle accesses single subpartition
        // Example: Q1 2024 + USA -> sales_2024_q1_na subpartition only
        List<SalesTransaction> sales = salesRepository
            .findByDateRangeAndRegion(startDate, endDate, region);
        
        return sales.stream()
            .map(SalesTransaction::getAmount)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
    
    /**
     * Less efficient: Only date range
     */
    public Map<String, BigDecimal> getQuarterlySalesByAllRegions(int year, int quarter) {
        LocalDate startDate = getQuarterStart(year, quarter);
        LocalDate endDate = startDate.plusMonths(3);
        
        // Oracle accesses all subpartitions within date range
        List<SalesTransaction> sales = salesRepository
            .findByDateRangeBetween(startDate, endDate);
        
        return sales.stream()
            .collect(Collectors.groupingBy(
                SalesTransaction::getRegion,
                Collectors.reducing(
                    BigDecimal.ZERO,
                    SalesTransaction::getAmount,
                    BigDecimal::add
                )
            ));
    }
    
    private LocalDate getQuarterStart(int year, int quarter) {
        return LocalDate.of(year, (quarter - 1) * 3 + 1, 1);
    }
}
```

## 5. Partition Pruning in Queries

Partition pruning is Oracle's optimization that eliminates scanning irrelevant partitions.

### Understanding Partition Pruning

**Explain Plan Analysis:**

```java
@Service
public class PartitionPruningAnalysisService {
    
    @PersistenceContext
    private EntityManager entityManager;
    
    /**
     * Analyze partition access for a query
     */
    public void analyzePartitionAccess(String query) {
        // Get execution plan
        String explainQuery = "EXPLAIN PLAN FOR " + query;
        entityManager.createNativeQuery(explainQuery).executeUpdate();
        
        // Retrieve plan
        String planQuery = """
            SELECT operation, options, object_name, partition_start, partition_stop
            FROM plan_table
            WHERE plan_id = (SELECT MAX(plan_id) FROM plan_table)
            ORDER BY id
        """;
        
        @SuppressWarnings("unchecked")
        List<Object[]> results = entityManager.createNativeQuery(planQuery).getResultList();
        
        results.forEach(row -> {
            log.info("Operation: {}, Options: {}, Object: {}, Partitions: {}-{}",
                row[0], row[1], row[2], row[3], row[4]);
        });
    }
}
```

### Partition Pruning Examples

**Example 1: Static Pruning (Compile-Time)**

```java
// Query with constant values
@Query(value = """
    SELECT * FROM orders 
    WHERE order_date >= DATE '2024-06-01' 
    AND order_date < DATE '2024-07-01'
    """, nativeQuery = true)
List<Order> findJuneOrders();

// Execution plan shows:
// PARTITION RANGE SINGLE (Partition: 6, 6)
// Only partition 6 (June 2024) is scanned
```

**Example 2: Dynamic Pruning (Runtime)**

```java
// Query with bind variables
@Query("SELECT o FROM Order o WHERE o.orderDate BETWEEN :start AND :end")
List<Order> findOrdersByDateRange(
    @Param("start") LocalDate start,
    @Param("end") LocalDate end
);

// Execution plan shows:
// PARTITION RANGE ITERATOR (Partition: KEY, KEY)
// Partition determined at runtime based on bind values
```

**Example 3: No Pruning (Full Scan)**

```java
// Query without partition key
@Query("SELECT o FROM Order o WHERE o.customerId = :customerId")
List<Order> findOrdersByCustomer(@Param("customerId") Long customerId);

// Execution plan shows:
// PARTITION RANGE ALL (Partition: 1, N)
// All partitions scanned - inefficient!
```

### Optimizing for Partition Pruning

**❌ Bad: Missing Partition Key**

```java
@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    
    // Scans ALL partitions
    List<Order> findByStatus(OrderStatus status);
    
    // Scans ALL partitions
    @Query("SELECT o FROM Order o WHERE o.totalAmount > :amount")
    List<Order> findExpensiveOrders(@Param("amount") BigDecimal amount);
}
```

**✅ Good: Include Partition Key**

```java
@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    
    // Scans only relevant partitions
    @Query("SELECT o FROM Order o " +
           "WHERE o.orderDate >= :fromDate " +
           "AND o.status = :status")
    List<Order> findByDateAndStatus(
        @Param("fromDate") LocalDate fromDate,
        @Param("status") OrderStatus status
    );
    
    // Scans specific date range partitions
    @Query("SELECT o FROM Order o " +
           "WHERE o.orderDate BETWEEN :start AND :end " +
           "AND o.totalAmount > :amount")
    List<Order> findExpensiveOrdersInRange(
        @Param("start") LocalDate start,
        @Param("end") LocalDate end,
        @Param("amount") BigDecimal amount
    );
}
```

### Partition-Wise Joins

When joining partitioned tables, Oracle can perform partition-wise joins for better performance:

```java
/**
 * Both tables partitioned on the same key
 */
@Query(value = """
    SELECT o.*, oi.*
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.order_date BETWEEN :start AND :end
    """, nativeQuery = true)
List<Object[]> findOrdersWithItems(
    @Param("start") LocalDate start,
    @Param("end") LocalDate end
);

// Oracle performs partition-wise join:
// - Join orders partition 1 with order_items partition 1
// - Join orders partition 2 with order_items partition 2
// - etc.
// More efficient than full table joins
```

## 6. JPA Considerations with Partitioned Tables

### Transparency to Application

**Good News**: Partitioning is mostly transparent to JPA:

```java
@Entity
@Table(name = "orders")
public class Order {
    // No special JPA annotations needed for partitioned tables
    // JPA doesn't know or care that table is partitioned
    
    @Id
    private Long orderId;
    
    private LocalDate orderDate;  // Partition key (just a regular field)
    
    // Rest of entity...
}
```

### Best Practices for JPA with Partitioned Tables

**1. Always Include Partition Key in Queries**

```java
@Service
public class OrderQueryService {
    
    @Autowired
    private OrderRepository orderRepository;
    
    // ❌ Bad: No partition key
    public List<Order> getCustomerOrders(Long customerId) {
        return orderRepository.findByCustomerId(customerId);  // Full scan!
    }
    
    // ✅ Good: Include date range
    public List<Order> getRecentCustomerOrders(Long customerId, int days) {
        LocalDate fromDate = LocalDate.now().minusDays(days);
        return orderRepository.findByCustomerIdAndOrderDateAfter(customerId, fromDate);
    }
}
```

**2. Batch Operations with Partition Awareness**

```java
@Service
public class OrderBatchService {
    
    @PersistenceContext
    private EntityManager entityManager;
    
    /**
     * Efficient bulk delete using partition key
     */
    @Transactional
    public int archiveOldOrders(LocalDate cutoffDate) {
        // Oracle can drop entire partitions (very fast)
        // or delete with partition pruning
        String jpql = "DELETE FROM Order o WHERE o.orderDate < :cutoffDate";
        
        return entityManager.createQuery(jpql)
            .setParameter("cutoffDate", cutoffDate)
            .executeUpdate();
    }
    
    /**
     * Partition-aware batch insert
     */
    @Transactional
    public void importOrders(List<Order> orders) {
        // Group by partition (order_date month)
        Map<YearMonth, List<Order>> partitionedOrders = orders.stream()
            .collect(Collectors.groupingBy(
                order -> YearMonth.from(order.getOrderDate())
            ));
        
        // Insert partition by partition
        partitionedOrders.forEach((month, monthOrders) -> {
            log.info("Inserting {} orders for {}", monthOrders.size(), month);
            
            monthOrders.forEach(order -> {
                entityManager.persist(order);
            });
            
            entityManager.flush();
            entityManager.clear();
        });
    }
}
```

```java
@Service
public class PartitionMaintenanceService {
    
    @PersistenceContext
    private EntityManager entityManager;
    
    /**
     * Add new partition manually (if not using INTERVAL)
     */
    @Transactional
    public void addMonthlyPartition(int year, int month) {

        LocalDate highValue = LocalDate.of(year, month, 1).plusMonths(1);
        
        String ddl = String.format("""
            ALTER TABLE orders ADD PARTITION %s
            VALUES LESS THAN (DATE '%s')
            """, partitionName, highValue);
        
        entityManager.createNativeQuery(ddl).executeUpdate();
        
        log.info("Added partition: {}", partitionName);
    }

     * Drop old partition (archive strategy)
     */
    @Transactional
    public void dropOldPartition(String partitionName) {
        String ddl = String.format("""
            ALTER TABLE orders DROP PARTITION %s
            """, partitionName);
        
        entityManager.createNativeQuery(ddl).executeUpdate();
        
        log.info("Dropped partition: {}", partitionName);
    }
    
    /**
     * Truncate partition (fast delete)
     */
    @Transactional
    public void truncatePartition(String partitionName) {
        String ddl = String.format("""
            ALTER TABLE orders TRUNCATE PARTITION %s
            """, partitionName);
        
        entityManager.createNativeQuery(ddl).executeUpdate();
        
        log.info("Truncated partition: {}", partitionName);
    }
    
    /**
     * Get partition statistics
     */
    public List<PartitionStats> getPartitionStatistics(String tableName) {
        String sql = """
            SELECT 
                partition_name,
                partition_position,
                high_value,
                num_rows,
                blocks,
                ROUND(num_rows * avg_row_len / 1024 / 1024, 2) as size_mb
            FROM user_tab_partitions
            WHERE table_name = UPPER(:tableName)
            ORDER BY partition_position
            """;
        
        @SuppressWarnings("unchecked")
        List<Object[]> results = entityManager.createNativeQuery(sql)
            .setParameter("tableName", tableName)
            .getResultList();
        
        return results.stream()
            .map(row -> new PartitionStats(
                (String) row[0],
                ((Number) row[1]).intValue(),
                (String) row[2],
                ((Number) row[3]).longValue(),
                ((Number) row[4]).longValue(),
                ((Number) row[5]).doubleValue()
            ))
            .collect(Collectors.toList());
    }
}
```

## Best Practices Summary

### ✅ DO:

1. **Choose the right partitioning strategy** based on data access patterns
2. **Always include partition key** in WHERE clauses when possible
3. **Use composite partitioning** for multi-dimensional data access
4. **Monitor partition sizes** and rebalance if needed
5. **Use local indexes** on partitioned tables
6. **Archive old partitions** instead of deleting rows
7. **Test partition pruning** with EXPLAIN PLAN

### ❌ DON'T:

1. **Don't over-partition** (too many partitions adds overhead)
2. **Don't use partitioning** on small tables (<10 million rows)
3. **Don't forget partition keys** in queries (defeats the purpose)
4. **Don't use global indexes** unless absolutely necessary
5. **Don't partition on low-cardinality columns** (except list partitioning)

## Interview Questions

**Q1: What's the difference between range and list partitioning?**

Range partitioning divides data based on value ranges (dates, numbers), while list partitioning divides based on discrete values (regions, statuses). Range is best for continuous data, list for categorical data.

**Q2: How does partition pruning work?**

Oracle analyzes the WHERE clause and determines which partitions contain relevant data, scanning only those partitions. This can be static (compile-time) or dynamic (runtime based on bind variables).

**Q3: When should you use hash partitioning?**

Use hash partitioning when there's no natural partition key, you need even data distribution, or want to enable parallel DML operations. Common for session tables, event logs, or high-volume transaction tables.

**Q4: What are the JPA implications of partitioned tables?**

JPA is mostly transparent to partitioning, but developers must ensure queries include partition keys for efficient pruning. Batch operations should be partition-aware for optimal performance.

**Q5: How do you maintain partitions in production?**

Use ALTER TABLE ADD/DROP PARTITION for manual management, or INTERVAL partitioning for automatic creation. Use partition exchange for bulk loading and truncate partitions instead of deleting rows.
