# MongoDB Document Modeling Patterns

## Overview

Document modeling in MongoDB differs fundamentally from relational database design. MongoDB's flexible schema allows embedding related data within documents or referencing between documents. The right choice depends on data access patterns, relationships, and update frequency.

**Key Concept**: Design your schema based on how your application queries and updates data, not based on normalized relational principles. MongoDB rewards denormalization - duplicate data when it improves query performance and fits your access patterns.

---

## 1. Embedded Documents vs References

### Understanding the Trade-offs

**Embedded Documents (Denormalized):**

```
Document: {
  _id: ObjectId("..."),
  name: "John Doe",
  address: {              // ← Embedded document
    street: "123 Main St",
    city: "New York",
    zip: "10001"
  }
}

Pros:
✅ Single query retrieves all data
✅ Atomic updates (entire document)
✅ Better read performance
✅ Data locality (disk/memory)

Cons:
❌ Document size limit (16MB)
❌ Data duplication if reused
❌ Harder to query embedded data independently
❌ Updates affect multiple documents
```

**References (Normalized):**

```
User Document: {
  _id: ObjectId("..."),
  name: "John Doe",
  address_id: ObjectId("...")  // ← Reference
}

Address Document: {
  _id: ObjectId("..."),
  street: "123 Main St",
  city: "New York",
  zip: "10001"
}

Pros:
✅ No duplication
✅ Easy to update once
✅ Smaller document size
✅ Can query addresses independently

Cons:
❌ Multiple queries needed
❌ No joins (application-level)
❌ Slower reads
❌ No atomic updates across documents
```

### Embedded Document Example

**Entity Classes:**

```java
@Document(collection = "users")
@Data
@NoArgsConstructor
@AllArgsConstructor
public class User {
    
    @Id
    private String id;
    
    private String name;
    private String email;
    
    // Embedded document
    private Address address;
    
    // Array of embedded documents
    private List<PhoneNumber> phoneNumbers;
    
    // Embedded metadata
    private UserMetadata metadata;
    
    private LocalDateTime createdAt;
}

// Not a separate collection - embedded only
@Data
@NoArgsConstructor
@AllArgsConstructor
public class Address {
    private String street;
    private String city;
    private String state;
    private String zipCode;
    private String country;
}

@Data
@NoArgsConstructor
@AllArgsConstructor
public class PhoneNumber {
    private String type;  // HOME, WORK, MOBILE
    private String number;
    private boolean primary;
}

@Data
public class UserMetadata {
    private LocalDateTime lastLogin;
    private int loginCount;
    private List<String> recentSearches;
}
```

**Repository and Service:**

```java
@Repository
public interface UserRepository extends MongoRepository<User, String> {
    
    // Query embedded document fields using dot notation
    List<User> findByAddressCity(String city);
    
    List<User> findByAddressCityAndAddressState(String city, String state);
    
    // Query array of embedded documents
    List<User> findByPhoneNumbersType(String type);
    
    @Query("{ 'phoneNumbers.number': ?0 }")
    User findByPhoneNumber(String phoneNumber);
    
    // Query embedded metadata
    @Query("{ 'metadata.loginCount': { $gte: ?0 } }")
    List<User> findActiveUsers(int minLoginCount);
}

@Service
@RequiredArgsConstructor
public class UserService {
    
    private final UserRepository userRepository;
    
    public User createUser(String name, String email, Address address) {
        User user = new User();
        user.setName(name);
        user.setEmail(email);
        user.setAddress(address);
        user.setPhoneNumbers(new ArrayList<>());
        user.setMetadata(new UserMetadata());
        user.setCreatedAt(LocalDateTime.now());
        
        return userRepository.save(user);
    }
    
    public User updateAddress(String userId, Address newAddress) {
        User user = userRepository.findById(userId)
            .orElseThrow(() -> new UserNotFoundException(userId));
        
        // Update embedded document - single atomic operation
        user.setAddress(newAddress);
        return userRepository.save(user);
    }
    
    public User addPhoneNumber(String userId, PhoneNumber phoneNumber) {
        User user = userRepository.findById(userId)
            .orElseThrow(() -> new UserNotFoundException(userId));
        
        user.getPhoneNumbers().add(phoneNumber);
        return userRepository.save(user);
    }
}
```

### Reference Example

**Entity Classes with References:**

```java
@Document(collection = "users")
@Data
public class User {
    
    @Id
    private String id;
    
    private String name;
    private String email;
    
    // Reference to separate Address document
    @DBRef
    private Address address;
    
    // Reference to multiple Order documents
    @DBRef
    private List<Order> orders;
    
    private LocalDateTime createdAt;
}

@Document(collection = "addresses")
@Data
public class Address {
    
    @Id
    private String id;
    
    private String street;
    private String city;
    private String state;
    private String zipCode;
    
    // Can be shared by multiple users
    private LocalDateTime createdAt;
}

@Document(collection = "orders")
@Data
public class Order {
    
    @Id
    private String id;
    
    private String orderNumber;
    
    @DBRef
    private User user;  // Back reference
    
    private BigDecimal totalAmount;
    private String status;
    private LocalDateTime orderDate;
}
```

**MongoDB Document Structure:**

```json
// User document
{

  "name": "John Doe",
  "email": "john@example.com",
  "address": {
    "$ref": "addresses",
    "$id": ObjectId("507f1f77bcf86cd799439012")
  },
  "orders": [
    {
      "$ref": "orders",
      "$id": ObjectId("507f1f77bcf86cd799439013")
    },
    {
      "$ref": "orders",
      "$id": ObjectId("507f1f77bcf86cd799439014")
    }
  ],
  "createdAt": ISODate("2023-01-01T00:00:00Z")
}

// Address document (separate collection)
{
  "_id": ObjectId("507f1f77bcf86cd799439012"),
  "street": "123 Main St",
  "city": "New York",
  "state": "NY",
  "zipCode": "10001",
  "createdAt": ISODate("2023-01-01T00:00:00Z")
}

// Order document (separate collection)
{
  "_id": ObjectId("507f1f77bcf86cd799439013"),
  "orderNumber": "ORD-2024-001",
  "user": {
    "$ref": "users",
    "$id": ObjectId("507f1f77bcf86cd799439011")

  "totalAmount": 99.99,
  "status": "SHIPPED",
  "orderDate": ISODate("2024-01-15T10:30:00Z")
}
```

**Service with References:**

```java
@Service
@RequiredArgsConstructor
public class UserReferenceService {
    
    private final UserRepository userRepository;
    private final AddressRepository addressRepository;
    private final OrderRepository orderRepository;
    
    /**
     * Create user with referenced address
     */
    public User createUserWithAddress(String name, String email, Address address) {
        // Save address first
        Address savedAddress = addressRepository.save(address);
        
        // Create user with reference
        User user = new User();
        user.setName(name);
        user.setEmail(email);
        user.setAddress(savedAddress);  // DBRef automatically handled
        user.setCreatedAt(LocalDateTime.now());
        
        return userRepository.save(user);
    }
    
    /**
     * Get user with address (requires 2 queries)
     */
    public UserDTO getUserWithAddress(String userId) {
        // Query 1: Get user
        User user = userRepository.findById(userId)
            .orElseThrow(() -> new UserNotFoundException(userId));
        
        // Query 2: Get address (if @DBRef lazy loaded)
        // Spring Data MongoDB automatically resolves @DBRef
        Address address = user.getAddress();
        
        return new UserDTO(user, address);
    }
    
    /**
     * Update shared address affects all users
     */
    public void updateAddress(String addressId, Address updatedAddress) {
        Address address = addressRepository.findById(addressId)
            .orElseThrow(() -> new AddressNotFoundException(addressId));
        
        address.setStreet(updatedAddress.getStreet());
        address.setCity(updatedAddress.getCity());
        address.setState(updatedAddress.getState());
        address.setZipCode(updatedAddress.getZipCode());
        
        addressRepository.save(address);
        
        // All users with this address reference see the update
    }
}
```

### Decision Matrix: Embed vs Reference

|Factor|Embed|Reference|
|---|---|---|
|**Relationship**|One-to-one, one-to-few|One-to-many, many-to-many|
|**Data Size**|Small, bounded|Large, unbounded|
|**Update Frequency**|Updated together|Updated independently|
|**Data Duplication**|Acceptable|Not acceptable|
|**Query Pattern**|Always accessed together|Sometimes accessed separately|
|**Read Performance**|⭐⭐⭐⭐⭐ Single query|⭐⭐⭐ Multiple queries|
|**Write Performance**|⭐⭐⭐ Update entire doc|⭐⭐⭐⭐⭐ Update only changed|
|**Consistency**|⭐⭐⭐⭐⭐ Atomic|⭐⭐⭐ No atomic guarantee|

## 2. One-to-Many Relationships

### Pattern 1: Embed Child Array (One-to-Few)

**Use When:**

- Small number of children (< 100)
- Children always accessed with parent
- Children don't change often
- Children don't need independent querying

**Example: User with Orders**

```java
@Document(collection = "users")
@Data
public class User {
    
    @Id
    private String id;
    
    private String name;
    private String email;
    
    // Embedded array of orders (one-to-few)
    private List<Order> orders = new ArrayList<>();
    
    // Embedded array of addresses (one-to-few)
    private List<Address> addresses = new ArrayList<>();
}

@Data
public class Order {
    // Not a separate document
    private String orderNumber;
    private BigDecimal totalAmount;
    private String status;
    private LocalDateTime orderDate;
    private List<OrderItem> items;
}

@Data
public class OrderItem {
    private String productId;
    private String productName;
    private int quantity;
    private BigDecimal price;
}
```

**MongoDB Document:**

```json
  "orders": [
    {
      "orderNumber": "ORD-001",

          "productId": "PROD-123",
```

```java
@Service
@RequiredArgsConstructor
public class UserOrderService {
    
    private final MongoTemplate mongoTemplate;
    
    public User addOrder(String userId, Order order) {
        Query query = new Query(Criteria.where("_id").is(userId));
        Update update = new Update().push("orders", order);
        
        FindAndModifyOptions options = new FindAndModifyOptions()
            .returnNew(true);
        
        return mongoTemplate.findAndModify(query, update, options, User.class);
    }
    
    public User updateOrderStatus(String userId, String orderNumber, String status) {
        Query query = new Query(
            Criteria.where("_id").is(userId)
                .and("orders.orderNumber").is(orderNumber)
        );
        
        Update update = new Update()
            .set("orders.$.status", status);
        
        return mongoTemplate.findAndModify(
            query, update, 
            new FindAndModifyOptions().returnNew(true), 
            User.class
        );
    }
    
    public List<User> findUsersWithPendingOrders() {
        Query query = new Query(
            Criteria.where("orders.status").is("PENDING")
        );
        
        return mongoTemplate.find(query, User.class);
    }
}
```

### Pattern 3: Parent Reference (One-to-Squillions)

**Use When:**

- Massive number of children (millions+)
- Can't store array in parent (16MB limit)
- Children are primary access pattern

**Example: Product with Reviews**

```java
@Document(collection = "products")
@Data
public class Product {
    
    @Id
    private String id;
    
    private String name;
    private String description;
    private BigDecimal price;
    
    // Statistics (not all reviews)
    private ReviewStatistics reviewStats;
}

@Data
public class ReviewStatistics {
    private long totalReviews;
    private double averageRating;
    private Map<Integer, Long> ratingDistribution;  // Rating -> Count
}

@Document(collection = "reviews")
@Data
@CompoundIndex(def = "{'productId': 1, 'createdAt': -1}")
public class Review {
    
    @Id
    private String id;
    
    // Parent reference
    @Indexed
    private String productId;
    
    private String userId;
    private String userName;
    
    private int rating;  // 1-5
    private String title;
    private String comment;
    
    private LocalDateTime createdAt;
    private int helpfulCount;
}
```

**Service with Aggregation:**

```java
@Service
@RequiredArgsConstructor
public class ProductReviewService {
    
    private final ProductRepository productRepository;
    private final ReviewRepository reviewRepository;
    private final MongoTemplate mongoTemplate;
    
    public Review addReview(String productId, Review review) {
        review.setProductId(productId);
        review.setCreatedAt(LocalDateTime.now());
        
        Review savedReview = reviewRepository.save(review);
        
        // Update product statistics
        updateProductStats(productId);
        
        return savedReview;
    }
    
    private void updateProductStats(String productId) {
        // Aggregate review statistics
        Aggregation aggregation = Aggregation.newAggregation(
            Aggregation.match(Criteria.where("productId").is(productId)),
            Aggregation.group("productId")
                .count().as("totalReviews")
                .avg("rating").as("averageRating")
        );
        
        AggregationResults<ReviewStats> results = mongoTemplate.aggregate(
            aggregation, "reviews", ReviewStats.class
        );
        
        ReviewStats stats = results.getUniqueMappedResult();
        
        if (stats != null) {
            // Update product with aggregated stats
            Query query = new Query(Criteria.where("_id").is(productId));
            Update update = new Update()
                .set("reviewStats.totalReviews", stats.getTotalReviews())
                .set("reviewStats.averageRating", stats.getAverageRating());
            
            mongoTemplate.updateFirst(query, update, Product.class);
        }
    }
    
    public Page<Review> getProductReviews(String productId, int page, int size) {
        Pageable pageable = PageRequest.of(
            page, size,
            Sort.by(Sort.Direction.DESC, "helpfulCount", "createdAt")
        );
        
        return reviewRepository.findByProductId(productId, pageable);
    }
}

@Data
class ReviewStats {
    private long totalReviews;
    private double averageRating;
}
```

## 3. Many-to-Many Relationships

### Pattern 1: Array of References with @DBRef

**Use When:**

- Moderate number of relationships
- Need to access entities independently
- Relationships change frequently

**Example: Students and Courses**

```java
@Document(collection = "students")
@Data
public class Student {
    
    @Id
    private String id;
    
    private String name;
    private String email;
    
    // Array of course references
    @DBRef
    private List<Course> courses = new ArrayList<>();
    
    private LocalDateTime enrolledDate;
}

@Document(collection = "courses")
@Data
public class Course {
    
    @Id
    private String id;
    
    private String code;
    private String name;
    private String instructor;
    private int maxStudents;
    
    // Back references (optional)
    @DBRef
    private List<Student> students = new ArrayList<>();
}
```

**MongoDB Documents:**

```json
// Student document

  "_id": ObjectId("507f1f77bcf86cd799439011"),

      "$id": ObjectId("507f1f77bcf86cd799439021")
    },
    {
      "$ref": "courses",
      "$id": ObjectId("507f1f77bcf86cd799439022")
```

**Service:**

```java
@Service
@RequiredArgsConstructor
public class EnrollmentService {
    
    private final StudentRepository studentRepository;
    private final CourseRepository courseRepository;
    
    @Transactional
    public void enrollStudent(String studentId, String courseId) {
        Student student = studentRepository.findById(studentId)
            .orElseThrow(() -> new StudentNotFoundException(studentId));
        
        Course course = courseRepository.findById(courseId)
            .orElseThrow(() -> new CourseNotFoundException(courseId));
        
        // Check capacity
        if (course.getStudents().size() >= course.getMaxStudents()) {
            throw new CourseFullException(courseId);
        }
        
        // Add course to student
        if (!student.getCourses().contains(course)) {
            student.getCourses().add(course);
            studentRepository.save(student);
        }
        
        // Add student to course
        if (!course.getStudents().contains(student)) {
            course.getStudents().add(student);
            courseRepository.save(course);
        }
    }
    
    @Transactional
    public void unenrollStudent(String studentId, String courseId) {
        Student student = studentRepository.findById(studentId)
            .orElseThrow(() -> new StudentNotFoundException(studentId));
        
        Course course = courseRepository.findById(courseId)
            .orElseThrow(() -> new CourseNotFoundException(courseId));
        
        student.getCourses().removeIf(c -> c.getId().equals(courseId));
        studentRepository.save(student);
        
        course.getStudents().removeIf(s -> s.getId().equals(studentId));
        courseRepository.save(course);
    }
}
```

### Pattern 2: Junction Collection (Recommended)

**Use When:**

- Need to store relationship metadata
- Large number of relationships
- Better query performance needed

**Example: Users and Groups with Roles**

```java
@Document(collection = "users")
@Data
public class User {
    @Id
    private String id;
    private String name;
    private String email;
    
    // No direct reference to groups
}

@Document(collection = "groups")
@Data
public class Group {
    @Id
    private String id;
    private String name;
    private String description;
    
    // No direct reference to users
}

@Document(collection = "user_groups")
@Data
@CompoundIndex(def = "{'userId': 1, 'groupId': 1}", unique = true)
public class UserGroup {
    
    @Id
    private String id;
    
    @Indexed
    private String userId;
    
    @Indexed
    private String groupId;
    
    // Relationship metadata
    private String role;  // OWNER, ADMIN, MEMBER
    private LocalDateTime joinedAt;
    private LocalDateTime lastActiveAt;
    private boolean isActive;
}
```

**MongoDB Documents:**

```json
// User document
{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "John Doe",
  "email": "john@example.com"
}

// Group document
{
  "_id": ObjectId("507f1f77bcf86cd799439021"),
  "name": "Spring Developers",
  "description": "Community for Spring Framework developers"
}

// UserGroup junction document
{
  "_id": ObjectId("507f1f77bcf86cd799439031"),
  "userId": "507f1f77bcf86cd799439011",
  "groupId": "507f1f77bcf86cd799439021",
  "role": "ADMIN",
  "joinedAt": ISODate("2024-01-15T10:30:00Z"),
  "lastActiveAt": ISODate("2024-01-20T14:20:00Z"),

```

**Repository and Service:**

```java
@Repository
public interface UserGroupRepository extends MongoRepository<UserGroup, String> {
    
    List<UserGroup> findByUserId(String userId);
    
    List<UserGroup> findByGroupId(String groupId);
    
    Optional<UserGroup> findByUserIdAndGroupId(String userId, String groupId);
    
    List<UserGroup> findByUserIdAndIsActive(String userId, boolean isActive);
    
    List<UserGroup> findByGroupIdAndRole(String groupId, String role);
    
    long countByGroupIdAndIsActive(String groupId, boolean isActive);
    
    void deleteByUserIdAndGroupId(String userId, String groupId);
}

@Service
@RequiredArgsConstructor
public class UserGroupService {
    
    private final UserGroupRepository userGroupRepository;
    private final UserRepository userRepository;
    private final GroupRepository groupRepository;
    
    public UserGroup addUserToGroup(String userId, String groupId, String role) {
        // Validate user and group exist
        userRepository.findById(userId)
            .orElseThrow(() -> new UserNotFoundException(userId));
        
        groupRepository.findById(groupId)
            .orElseThrow(() -> new GroupNotFoundException(groupId));
        
        // Check if relationship already exists
        Optional<UserGroup> existing = userGroupRepository
            .findByUserIdAndGroupId(userId, groupId);
        
        if (existing.isPresent()) {
            throw new UserAlreadyInGroupException(userId, groupId);
        }
        
        // Create relationship
        UserGroup userGroup = new UserGroup();
        userGroup.setUserId(userId);
        userGroup.setGroupId(groupId);
        userGroup.setRole(role);
        userGroup.setJoinedAt(LocalDateTime.now());
        userGroup.setActive(true);
        
        return userGroupRepository.save(userGroup);
    }
    
    public List<GroupWithRole> getUserGroups(String userId) {
        List<UserGroup> userGroups = userGroupRepository.findByUserId(userId);
        
        // Join with groups (application-level)
        return userGroups.stream()
            .map(ug -> {
                Group group = groupRepository.findById(ug.getGroupId())
                    .orElse(null);
                
                return new GroupWithRole(group, ug.getRole(), ug.getJoinedAt());
            })
            .filter(g -> g.getGroup() != null)
            .collect(Collectors.toList());
    }
    
    public List<UserWithRole> getGroupMembers(String groupId) {
        List<UserGroup> userGroups = userGroupRepository.findByGroupId(groupId);
        
        return userGroups.stream()
            .map(ug -> {
                User user = userRepository.findById(ug.getUserId())
                    .orElse(null);
                
                return new UserWithRole(user, ug.getRole(), ug.getJoinedAt());
            })
            .filter(u -> u.getUser() != null)
            .collect(Collectors.toList());
    }
    
    public void removeUserFromGroup(String userId, String groupId) {
        userGroupRepository.deleteByUserIdAndGroupId(userId, groupId);
    }
    
    public long getActiveGroupMemberCount(String groupId) {
        return userGroupRepository.countByGroupIdAndIsActive(groupId, true);
    }
}

@Data

class GroupWithRole {
    private Group group;
    private String role;
    private LocalDateTime joinedAt;
}

@Data
@AllArgsConstructor
class UserWithRole {
    private User user;
    private String role;
    private LocalDateTime joinedAt;
```

## 5. Schema Design Best Practices

### Rule 1: Design for Access Patterns

**Example: Blog Application**

**Anti-Pattern (Normalized Thinking):**

```java
// Separate collections for everything
@Document(collection = "posts")
class Post {
    @Id String id;
    String title;
    String content;
    String authorId;  // Reference
    List<String> tagIds;  // References
}

@Document(collection = "authors")
class Author {
    @Id String id;
    String name;
}

@Document(collection = "tags")
class Tag {
    @Id String id;
    String name;
}
// Result: 3+ queries to display a post
```

**Better Pattern (Denormalized for Reads):**


## Best Practices Summary

### ✅ DO:

1. **Design for your query patterns** - not normalized forms
2. **Embed when data accessed together** - improves read performance
3. **Reference when data grows large** - avoid 16MB limit
4. **Denormalize frequently accessed data** - reduce joins
5. **Use junction collections** for many-to-many with metadata
6. **Index embedded fields** - enable fast queries
7. **Store aggregates** - pre-compute expensive calculations
8. **Snapshot data** when history matters (orders, invoices)
9. **Use subset pattern** for large arrays
10. **Test with realistic data volumes** - 100 vs 1M records different

### ❌ DON'T:

1. **Don't normalize like relational DBs** - MongoDB isn't SQL
2. **Don't embed unbounded arrays** - 16MB limit
3. **Don't use @DBRef everywhere** - performance cost
4. **Don't ignore access patterns** - design drives schema
5. **Don't skip indexes** - especially on referenced fields
6. **Don't update denormalized data inconsistently** - use transactions
7. **Don't over-denormalize** - balance reads vs consistency
8. **Don't forget document size** - monitor growth
9. **Don't use deep nesting** - 3-4 levels maximum
10. **Don't skip testing queries** - verify index usage

## Interview Questions

**Q1: When should you embed documents vs use references in MongoDB?**

Embed when: (1) data accessed together (address in user), (2) one-to-few relationships, (3) data doesn't change independently, (4) want atomic updates. Reference when: (1) data accessed separately, (2) one-to-many or many-to-many, (3) data shared/reused, (4) large/unbounded data, (5) independent updates needed.

**Q2: How do you model one-to-many relationships in MongoDB?**

Three patterns: (1) Embed array for one-to-few (user with 2-3 addresses), (2) Parent reference for one-to-many (order with userId), (3) Child reference array when moderate (user with 10-20 order IDs). Choose based on array size, access patterns, and update frequency.

**Q3: What's the best way to handle many-to-many relationships in MongoDB?**

Use junction collection pattern: create separate collection storing both IDs plus relationship metadata (user_groups with userId, groupId, role, joinedAt). Better than @DBRef arrays because: (1) stores relationship data, (2) easier queries, (3) better performance, (4) avoids circular references.

**Q4: Explain polymorphic modeling in MongoDB with an example.**

Store different types in single collection using discriminator field (_class or type). Example: PaymentMethod base class with CreditCard, BankAccount, PayPal subclasses. Use @TypeAlias for type discrimination. Allows querying all payment methods together while preserving type-specific fields. Good for similar entities with variations.

**Q5: What are key MongoDB schema design principles?**

(1) Design for access patterns not normalization, (2) embed data accessed together, (3) respect 16MB document limit, (4) denormalize for read-heavy workloads, (5) consider read/write ratio, (6) snapshot data when history matters, (7) pre-compute aggregates, (8) use subset pattern for large arrays, (9) index embedded fields, (10) test with realistic data volumes.

## Summary

MongoDB document modeling patterns:

- ✅ **Embed vs Reference** - Based on access patterns, data size, update frequency
- ✅ **One-to-Many** - Embed array (few), parent reference (many), child array (moderate)
- ✅ **Many-to-Many** - Junction collection with metadata (recommended)
- ✅ **Polymorphic** - Single collection with discriminator, preserves type safety
- ✅ **Design Principles** - Query patterns drive schema, not normalization
- ✅ **Denormalization** - Duplicate for reads, aggregate summaries, subset pattern

**Key Takeaway**: MongoDB schema design is fundamentally different from relational databases. Embrace denormalization and data duplication when it improves query performance. Design your schema around how your application accesses data, not around normalized forms. The right choice between embedding and referencing depends on your specific access patterns, data size, and update frequency.
