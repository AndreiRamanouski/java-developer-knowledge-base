# Liquibase Changelog Organization

## Overview

Properly organizing Liquibase changelogs is crucial for maintaining database migrations in production systems. Good organization enables team collaboration, supports multiple environments, and scales from monoliths to microservices.

**Key Concept**: Changelog organization should reflect your development workflow, release strategy, and deployment model. Well-structured changelogs are easy to navigate, review, and maintain across the software lifecycle.

---

## 1. Master Changelog Pattern

The master changelog is the entry point that references all other changelog files. It acts as a table of contents for your database migrations.

### Basic Master Changelog

**db/changelog/db.changelog-master.yaml:**

```yaml
databaseChangeLog:
  # Include version-specific changelogs in order
  - include:
      file: db/changelog/v1.0/db.changelog-v1.0.yaml
  - include:
      file: db/changelog/v1.1/db.changelog-v1.1.yaml
  - include:
      file: db/changelog/v2.0/db.changelog-v2.0.yaml
  - include:
      file: db/changelog/v2.1/db.changelog-v2.1.yaml
```

**Directory Structure:**

```
src/main/resources/
└── db/
    └── changelog/
        ├── db.changelog-master.yaml          # Master file
        ├── v1.0/
        │   ├── db.changelog-v1.0.yaml        # Version master
        │   ├── 001-create-users-table.yaml
        │   ├── 002-create-roles-table.yaml
        │   └── 003-add-indexes.yaml
        ├── v1.1/
        │   ├── db.changelog-v1.1.yaml
        │   ├── 004-add-email-verification.yaml
        │   └── 005-add-user-preferences.yaml
        └── v2.0/
            ├── db.changelog-v2.0.yaml
            ├── 006-create-orders-table.yaml
            └── 007-add-payment-integration.yaml
```

**Version Master (db.changelog-v1.0.yaml):**

```yaml
databaseChangeLog:
  - include:
      file: db/changelog/v1.0/001-create-users-table.yaml
  - include:
      file: db/changelog/v1.0/002-create-roles-table.yaml
  - include:
      file: db/changelog/v1.0/003-add-indexes.yaml
```

### Advanced Master Changelog with Metadata

**db/changelog/db.changelog-master.yaml:**

```yaml
databaseChangeLog:
  # Schema initialization (always runs first)
  - include:
      file: db/changelog/init/db.changelog-init.yaml
  
  # Core tables (v1.0 - Initial Release)
  - include:
      file: db/changelog/releases/v1.0/db.changelog-v1.0.yaml
      context: all
      labels: release-1.0
  
  # Authentication features (v1.1)
  - include:
      file: db/changelog/releases/v1.1/db.changelog-v1.1.yaml
      context: all
      labels: release-1.1,feature-auth
  
  # Payment integration (v2.0)
  - include:
      file: db/changelog/releases/v2.0/db.changelog-v2.0.yaml
      context: all
      labels: release-2.0,feature-payment
  
  # Performance optimizations (v2.1)
  - include:
      file: db/changelog/releases/v2.1/db.changelog-v2.1.yaml
      context: all
      labels: release-2.1,optimization
  
  # Test data (dev/test environments only)
  - include:
      file: db/changelog/test-data/db.changelog-test-data.yaml
      context: dev,test
      labels: test-data
  
  # Production-specific optimizations
  - include:
      file: db/changelog/production/db.changelog-prod-indexes.yaml
      context: prod
      labels: production-only
```

### Master Changelog with Include All

**db/changelog/db.changelog-master.yaml:**

```yaml
databaseChangeLog:
  # Include all files in a directory (alphabetical order)
  - includeAll:
      path: db/changelog/migrations/
      relativeToChangelogFile: true
      errorIfMissingOrEmpty: true
      
  # Include with filtering
  - includeAll:
      path: db/changelog/views/
      relativeToChangelogFile: true
      filter: "*.sql"  # Only SQL files
      
  # Include with specific order using minDepth/maxDepth
  - includeAll:
      path: db/changelog/releases/
      relativeToChangelogFile: true
      minDepth: 1
      maxDepth: 2
```

**Warning**: `includeAll` processes files in alphabetical order, so use numbered prefixes:

```
migrations/
├── 001-create-users-table.yaml
├── 002-create-orders-table.yaml
├── 003-create-products-table.yaml
└── 004-add-foreign-keys.yaml
```

## 2. Organizing by Feature vs by Version

### Version-Based Organization (Recommended for Most Projects)

Organizes changelogs by release version or sprint.

**Structure:**

```
db/changelog/
├── db.changelog-master.yaml
├── v1.0/
│   ├── db.changelog-v1.0.yaml
│   ├── 001-create-users-schema.yaml
│   ├── 002-create-orders-schema.yaml
│   └── 003-baseline-indexes.yaml
├── v1.1/
│   ├── db.changelog-v1.1.yaml
│   ├── 004-add-email-verification.yaml
│   └── 005-add-user-metadata.yaml
├── v2.0/
│   ├── db.changelog-v2.0.yaml
│   ├── 006-payments-schema.yaml
│   ├── 007-notifications-schema.yaml
│   └── 008-refactor-user-roles.yaml
└── v2.1/
    ├── db.changelog-v2.1.yaml
    ├── 009-add-analytics-tables.yaml
    └── 010-optimize-queries.yaml
```

**Master Changelog:**

```yaml
databaseChangeLog:
  - include:
      file: db/changelog/v1.0/db.changelog-v1.0.yaml
  - changeSet:
      id: tag-v1.0
      author: system
      changes:
        - tagDatabase:
            tag: v1.0
            
  - include:
      file: db/changelog/v1.1/db.changelog-v1.1.yaml
  - changeSet:
      id: tag-v1.1
      author: system
      changes:
        - tagDatabase:
            tag: v1.1
            
  - include:
      file: db/changelog/v2.0/db.changelog-v2.0.yaml
  - changeSet:
      id: tag-v2.0
      author: system
      changes:
        - tagDatabase:
            tag: v2.0
```

**Pros:**

- ✅ Clear release boundaries
- ✅ Easy rollback to specific version
- ✅ Aligns with version control tags
- ✅ Simple for audit and compliance

**Cons:**

- ❌ Large versions can have many files
- ❌ Features spanning versions are split

### Feature-Based Organization

Organizes changelogs by feature or domain.

**Structure:**

```
db/changelog/
├── db.changelog-master.yaml
├── features/
│   ├── authentication/
│   │   ├── db.changelog-auth.yaml
│   │   ├── 001-create-users-table.yaml
│   │   ├── 002-create-roles-table.yaml
│   │   └── 003-create-permissions-table.yaml
│   ├── orders/
│   │   ├── db.changelog-orders.yaml
│   │   ├── 004-create-orders-table.yaml
│   │   ├── 005-create-order-items-table.yaml
│   │   └── 006-create-shipping-table.yaml
│   ├── payments/
│   │   ├── db.changelog-payments.yaml
│   │   ├── 007-create-payments-table.yaml
│   │   └── 008-create-payment-methods-table.yaml
│   └── notifications/
│       ├── db.changelog-notifications.yaml
│       ├── 009-create-notifications-table.yaml
│       └── 010-create-email-templates-table.yaml
```

**Master Changelog:**

```yaml
databaseChangeLog:
  # Core authentication feature
  - include:
      file: db/changelog/features/authentication/db.changelog-auth.yaml
      labels: feature-auth
      
  # Orders management
  - include:
      file: db/changelog/features/orders/db.changelog-orders.yaml
      labels: feature-orders
      
  # Payment processing
  - include:
      file: db/changelog/features/payments/db.changelog-payments.yaml
      labels: feature-payments
      
  # Notification system
  - include:
      file: db/changelog/features/notifications/db.changelog-notifications.yaml
      labels: feature-notifications
```

**Pros:**

- ✅ Logical grouping by domain
- ✅ Easy to find feature-related changes
- ✅ Good for microservices
- ✅ Clear ownership per team

**Cons:**

- ❌ Harder to track release versions
- ❌ Need careful numbering across features
- ❌ Complex dependencies between features

### Hybrid Approach (Best of Both Worlds)

Combine version and feature organization.

**Structure:**


## 3. Including Changelogs (include, includeAll)

### Include Single File

**Basic Include:**

```yaml
databaseChangeLog:
  # Absolute path from classpath
  - include:
      file: db/changelog/changes/001-create-users.yaml
  
  # Relative to master changelog
  - include:
      file: changes/002-create-orders.yaml
      relativeToChangelogFile: true
  
  # With context
  - include:
      file: db/changelog/test-data/seed-data.yaml
      context: dev,test
  
  # With labels
  - include:
      file: db/changelog/features/payments.yaml
      labels: feature-payments,release-2.0
  
  # Ignore if missing (optional changelog)
  - include:
      file: db/changelog/custom/custom-changes.yaml
      ignore: true
```

### Include All Files

**Basic IncludeAll:**

```yaml
databaseChangeLog:
  # Include all files in directory
  - includeAll:
      path: db/changelog/migrations/
  
  # Relative path
  - includeAll:
      path: migrations/
      relativeToChangelogFile: true
  
  # With filter
  - includeAll:
      path: db/changelog/sql-scripts/
      filter: "*.sql"  # Only SQL files
  
  # With context
  - includeAll:
      path: db/changelog/test-data/
      context: dev,test
  
  # Error if directory is empty
  - includeAll:
      path: db/changelog/critical/
      errorIfMissingOrEmpty: true
  
  # Control directory depth
  - includeAll:
      path: db/changelog/releases/
      minDepth: 1    # Skip files in releases/ itself
      maxDepth: 2    # Include up to 2 levels deep
  
  # Resource comparator for custom ordering
  - includeAll:
      path: db/changelog/migrations/
      resourceComparator: "org.liquibase.resource.ClassLoaderResourceAccessor"
```

### Advanced Include Patterns

**Conditional Includes:**

```yaml
databaseChangeLog:
  # Include based on environment
  - include:
      file: db/changelog/dev/dev-optimizations.yaml
      context: dev
  
  - include:
      file: db/changelog/prod/prod-optimizations.yaml
      context: prod
  
  # Include based on database type
  - include:
      file: db/changelog/oracle/oracle-specific.yaml
      dbms: oracle
  
  - include:
      file: db/changelog/postgresql/postgresql-specific.yaml
      dbms: postgresql
```

**Organized IncludeAll:**

```yaml
databaseChangeLog:
  # Schema creation (runs first)
  - includeAll:
      path: db/changelog/01-schema/
      relativeToChangelogFile: true
      context: all
  
  # Tables creation
  - includeAll:
      path: db/changelog/02-tables/
      relativeToChangelogFile: true
      context: all
  
  # Indexes and constraints
  - includeAll:
      path: db/changelog/03-indexes/
      relativeToChangelogFile: true
      context: all
  
  # Views and stored procedures
  - includeAll:
      path: db/changelog/04-views/
      relativeToChangelogFile: true
      context: all
  
  # Reference data
  - includeAll:
      path: db/changelog/05-reference-data/
      relativeToChangelogFile: true
      context: all
  
  # Test data (dev/test only)
  - includeAll:
      path: db/changelog/06-test-data/
      relativeToChangelogFile: true
      context: dev,test
```

## 4. Contexts and Labels for Environment-Specific Changes

### Contexts (Environment-Based Filtering)

Contexts control which changesets run in which environments.

**Defining Contexts in ChangeSets:**

```yaml
databaseChangeLog:
  # Runs in all environments
  - changeSet:
      id: 001-create-users
      author: john.doe
      context: all
      changes:
        - createTable:
            tableName: users
  
  # Only in development
  - changeSet:
      id: 002-insert-dev-users
      author: john.doe
      context: dev
      changes:
        - insert:
            tableName: users
            columns:
              - column:
                  name: username
                  value: dev_user
  
  # Dev and Test only
  - changeSet:
      id: 003-insert-test-data
      author: john.doe
      context: dev,test
      changes:
        - loadData:
            file: db/test-data/users.csv
            tableName: users
  
  # Production only
  - changeSet:
      id: 004-create-prod-indexes
      author: john.doe
      context: prod
      changes:
        - createIndex:
            indexName: idx_users_email_prod
            tableName: users
  
  # Multiple contexts with OR logic
  - changeSet:
      id: 005-staging-or-prod
      author: john.doe
      context: staging,prod
      changes:
        - addColumn:
            tableName: users
            columns:
              - column:
                  name: verified_at
                  type: TIMESTAMP
```

**Configuring Contexts in Spring Boot:**

**application-dev.yml:**

```yaml
spring:
  liquibase:
    contexts: dev
    change-log: classpath:db/changelog/db.changelog-master.yaml
```

**application-test.yml:**

```yaml
spring:
  liquibase:
    contexts: test
```

**application-prod.yml:**

```yaml
spring:
  liquibase:
    contexts: prod
```

**Runtime Context Selection:**

```java
@Configuration
public class LiquibaseContextConfiguration {
    
    @Bean
    public SpringLiquibase liquibase(
            DataSource dataSource,
            @Value("${spring.profiles.active:dev}") String activeProfile) {
        
        SpringLiquibase liquibase = new SpringLiquibase();
        liquibase.setDataSource(dataSource);
        liquibase.setChangeLog("classpath:db/changelog/db.changelog-master.yaml");
        
        // Map profile to context
        String context = switch (activeProfile) {
            case "prod" -> "prod";
            case "staging" -> "staging";
            case "test" -> "test";
            default -> "dev";
        };
        
        liquibase.setContexts(context);
        
        return liquibase;
    }
}
```

### Labels (Feature-Based Filtering)

Labels enable feature-based or tag-based filtering.

**Defining Labels:**

```yaml
databaseChangeLog:
  # Authentication feature
  - changeSet:
      id: 001-create-users
      author: john.doe
      labels: feature-auth,release-1.0
      changes:
        - createTable:
            tableName: users
  
  - changeSet:
      id: 002-create-roles
      author: john.doe
      labels: feature-auth,release-1.0
      changes:
        - createTable:
            tableName: roles
  
  # Payment feature
  - changeSet:
      id: 003-create-payments
      author: jane.doe
      labels: feature-payment,release-2.0
      changes:
        - createTable:
            tableName: payments
  
  # Bug fix
  - changeSet:
      id: 004-fix-user-constraint
      author: john.doe
      labels: bugfix,hotfix-1.0.1
      changes:
        - dropNotNullConstraint:
            tableName: users
            columnName: middle_name
  
  # Multiple labels
  - changeSet:
      id: 005-analytics-tables
      author: jane.doe
      labels: feature-analytics,release-2.0,optional
      changes:
        - createTable:
            tableName: analytics_events
```

**Configuring Labels:**

**application.yml:**

```yaml
spring:
  liquibase:
    labels: release-1.0,feature-auth
```

**Programmatic Label Selection:**

```java
@Configuration
public class LiquibaseLabelConfiguration {
    
    @Bean
    public SpringLiquibase liquibase(
            DataSource dataSource,
            @Value("${app.release.version}") String releaseVersion) {
        
        SpringLiquibase liquibase = new SpringLiquibase();
        liquibase.setDataSource(dataSource);
        liquibase.setChangeLog("classpath:db/changelog/db.changelog-master.yaml");
        
        // Run only changesets for current release
        liquibase.setLabels("release-" + releaseVersion);
        
        return liquibase;
    }
}
```

### Combining Contexts and Labels

```yaml
databaseChangeLog:
  # Production feature, specific release
  - changeSet:
      id: 001-payment-gateway
      author: john.doe
      context: prod
      labels: feature-payment,release-2.0
      changes:
        - createTable:
            tableName: payment_gateway_config
  
  # Development data for authentication feature
  - changeSet:
      id: 002-dev-auth-data
      author: john.doe
      context: dev,test
      labels: feature-auth,test-data
      changes:
        - loadData:
            file: db/test-data/auth-users.csv
            tableName: users
  
  # Performance optimization for production in specific release
  - changeSet:
      id: 003-prod-indexes
      author: jane.doe
      context: prod
      labels: release-2.1,optimization
      changes:
        - createIndex:
            indexName: idx_orders_performance
            tableName: orders
```

**Running with Specific Context and Labels:**

```bash
# Run only production changesets for release 2.0
mvn liquibase:update \
  -Dliquibase.contexts=prod \
  -Dliquibase.labels=release-2.0

# Run dev changesets for authentication feature
mvn liquibase:update \
  -Dliquibase.contexts=dev \
  -Dliquibase.labels=feature-auth
```

### Advanced Context/Label Expressions

**Complex Label Expressions:**

```yaml
spring:
  liquibase:
    # Run changesets with label1 AND label2
    labels: label1 AND label2
    
    # Run changesets with label1 OR label2
    labels: label1 OR label2
    
    # Run changesets with label1 but NOT label2
    labels: label1 AND !label2
    
    # Complex expression
    labels: (feature-auth OR feature-payment) AND release-2.0 AND !deprecated
```

## 5. Modular Changelog Structure for Microservices

### Microservices Architecture with Shared Database

**Structure:**

```
microservices/
├── user-service/
│   └── src/main/resources/db/changelog/
│       ├── db.changelog-master.yaml
│       └── migrations/
│           ├── 001-create-users-table.yaml
│           └── 002-create-user-profiles.yaml
├── order-service/
│   └── src/main/resources/db/changelog/
│       ├── db.changelog-master.yaml
│       └── migrations/
│           ├── 001-create-orders-table.yaml
│           └── 002-create-order-items.yaml
├── payment-service/
│   └── src/main/resources/db/changelog/
│       ├── db.changelog-master.yaml
│       └── migrations/
│           ├── 001-create-payments-table.yaml
│           └── 002-create-transactions.yaml
└── shared/
    └── db/changelog/
        ├── db.changelog-shared.yaml
        └── migrations/
            └── 001-create-common-types.yaml
```

**Service-Specific Master Changelog:**

**user-service/db.changelog-master.yaml:**

```yaml
databaseChangeLog:
  # Include shared changes first
  - include:
      file: classpath:db/changelog/shared/db.changelog-shared.yaml
      context: all
  
  # Service-specific schema
  - changeSet:
      id: user-service-schema
      author: system
      changes:
        - createSchema:
            schemaName: user_service
  
  # Service-specific migrations
  - includeAll:
      path: db/changelog/migrations/
      relativeToChangelogFile: true
      context: all
```

**order-service/db.changelog-master.yaml:**

```yaml
databaseChangeLog:
  # Include shared changes
  - include:
      file: classpath:db/changelog/shared/db.changelog-shared.yaml
      context: all
  
  # Service-specific schema
  - changeSet:
      id: order-service-schema
      author: system
      changes:
        - createSchema:
            schemaName: order_service
  
  # Service-specific migrations
  - includeAll:
      path: db/changelog/migrations/
      relativeToChangelogFile: true
      context: all
```

### Database-Per-Service Pattern

Each microservice has its own database.

**user-service configuration:**

```yaml
spring:
  datasource:
    url: jdbc:oracle:thin:@localhost:1521:USER_DB
    username: user_service
    password: ${USER_SERVICE_DB_PASSWORD}
  
  liquibase:
    change-log: classpath:db/changelog/db.changelog-master.yaml
    default-schema: user_service
```

````
- Format: `{sequence}-{description}.yaml`
- Example: `001-create-users-table.yaml`

2. Update version master changelog to include new file
3. Test locally: `mvn liquibase:update`
4. Test rollback: `mvn liquibase:rollback -Dliquibase.rollbackCount=1`
5. Create pull request

- `staging`: Staging environment
- `prod`: Production environment
````

## Best Practices Summary

### ✅ DO:

1. **Use master changelog pattern** for organization
2. **Choose appropriate organization** (version-based for most projects)
3. **Use contexts** for environment-specific changes
4. **Use labels** for feature/release tracking
5. **Create modular structure** for microservices
6. **Version control all changelogs** with meaningful commits
7. **Use date-based IDs** to avoid conflicts
8. **Tag releases** in both Git and Liquibase
9. **Document changelog structure** in README

### ❌ DON'T:

1. **Don't use includeAll** without numbered prefixes
2. **Don't hardcode environments** in changesets
3. **Don't commit executed changesets** without new IDs
4. **Don't skip version control** for database changes
5. **Don't create cross-service dependencies** in microservices
6. **Don't ignore merge conflicts** in changelogs
7. **Don't forget to test** rollbacks
8. **Don't mix concerns** in single changeset

## Interview Questions

**Q1: What's the difference between include and includeAll?**

`include` adds a single changelog file explicitly, while `includeAll` automatically includes all files in a directory (in alphabetical order). Use `include` for explicit control, `includeAll` for convention-based organization with numbered prefixes.

**Q2: When should you use contexts vs labels?**

**Contexts** are for environment-based filtering (dev, test, prod). **Labels** are for feature-based or release-based filtering (feature-auth, release-2.0). Contexts answer "where should this run?", labels answer "what feature/release is this?".

**Q3: How do you handle database migrations in microservices?**

Each microservice should have its own database and changelog. For shared structures, create a shared library. Avoid cross-service foreign keys; maintain referential integrity in application code or use materialized references.

**Q4: What's the best way to organize changelogs for a long-lived project?**

Use version-based organization with feature subdirectories (hybrid approach). Tag each release, use contexts for environments, labels for features. Structure: `releases/v1.0/feature-name/001-changeset.yaml`.

**Q5: How do you prevent changelog conflicts in team development?**

Use date-based changeset IDs (`20240601-001`), maintain changelog in version control, use feature branches for new migrations, and have code review process for all database changes.
