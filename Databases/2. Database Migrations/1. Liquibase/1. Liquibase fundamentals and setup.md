# Liquibase with Spring Boot - Database Migrations

## Overview

Liquibase is a database schema change management tool that tracks, versions, and deploys database changes. It's essential for maintaining database consistency across environments and enabling continuous deployment.

**Key Concept**: Liquibase treats database schemas like source code - versioned, reviewed, and deployed systematically. Each change is tracked in changesets, ensuring repeatable, predictable deployments.

---

## 1. Liquibase Fundamentals and Setup

### What is Liquibase?

Liquibase is a database-independent library for tracking, managing, and applying database schema changes. It:

- **Tracks** every database change in version control
- **Prevents** duplicate execution of changes
- **Supports** multiple database platforms (Oracle, MySQL, PostgreSQL, etc.)
- **Enables** rollback of changes
- **Provides** audit trail of all database modifications

### Architecture Overview

## 2. Spring Boot Auto-Configuration

Spring Boot automatically configures Liquibase when `liquibase-core` is on the classpath.

### Basic Configuration

**application.yml:**

```yaml
spring:
  datasource:
    url: jdbc:oracle:thin:@localhost:1521:ORCL
    username: myuser
    password: mypassword
    driver-class-name: oracle.jdbc.OracleDriver
  
  liquibase:
    # Enable/disable Liquibase
    enabled: true
    
    # Location of changelog file (default: db/changelog/db.changelog-master.yaml)
    change-log: classpath:db/changelog/db.changelog-master.yaml
    
    # Default schema for Liquibase tables
    default-schema: myschema
    
    # Schema for DATABASECHANGELOG tables
    liquibase-schema: myschema
    
    # Database schema to use
    database-change-log-table: DATABASECHANGELOG
    database-change-log-lock-table: DATABASECHANGELOGLOCK
    
    # Contexts to use (comma-separated)
    contexts: dev,test
    
    # Labels to use
    labels: feature-1,release-1.0
    
    # Drop first (WARNING: Dangerous in production!)
    drop-first: false
    
    # Rollback file location
    rollback-file: target/rollback.sql
    
    # Tag for rollback
    tag: version-1.0
    
    # Parameters to pass to changesets
    parameters:
      table-prefix: APP_
      schema-name: myschema
```

**application.properties:**

```properties
# Enable Liquibase
spring.liquibase.enabled=true

# Changelog location
spring.liquibase.change-log=classpath:db/changelog/db.changelog-master.xml

# Schema settings
spring.liquibase.default-schema=myschema
spring.liquibase.liquibase-schema=myschema

# Contexts and labels
spring.liquibase.contexts=dev,test
spring.liquibase.labels=feature-1

# Parameters
spring.liquibase.parameters.table-prefix=APP_
spring.liquibase.parameters.schema-name=myschema
```

### Programmatic Configuration

**Custom Liquibase Configuration:**

```java
@Configuration
public class LiquibaseConfiguration {
    
    @Bean
    public SpringLiquibase liquibase(DataSource dataSource) {
        SpringLiquibase liquibase = new SpringLiquibase();
        liquibase.setDataSource(dataSource);
        liquibase.setChangeLog("classpath:db/changelog/db.changelog-master.yaml");
        liquibase.setContexts("dev,test");
        liquibase.setLabels("feature-1");
        liquibase.setDropFirst(false);
        liquibase.setShouldRun(true);
        
        // Custom parameters
        Map<String, String> parameters = new HashMap<>();
        parameters.put("schema.name", "myschema");
        parameters.put("table.prefix", "APP_");
        liquibase.setChangeLogParameters(parameters);
        
        return liquibase;
    }
}
```

**Conditional Liquibase Configuration:**

```java
@Configuration
public class ConditionalLiquibaseConfiguration {
    
    @Bean
    @ConditionalOnProperty(
        name = "spring.liquibase.enabled",
        havingValue = "true",
        matchIfMissing = true
    )
    public SpringLiquibase liquibase(
            DataSource dataSource,
            @Value("${spring.profiles.active:dev}") String activeProfile) {
        
        SpringLiquibase liquibase = new SpringLiquibase();
        liquibase.setDataSource(dataSource);
        liquibase.setChangeLog("classpath:db/changelog/db.changelog-master.yaml");
        
        // Different contexts based on profile
        if ("prod".equals(activeProfile)) {
            liquibase.setContexts("prod");
            liquibase.setShouldRun(false);  // Run manually in prod
        } else {
            liquibase.setContexts("dev,test");
            liquibase.setShouldRun(true);
        }
        
        return liquibase;
    }
}
```

### Multiple DataSources with Liquibase

```java
@Configuration
public class MultiDataSourceLiquibaseConfiguration {
    
    @Bean
    @ConfigurationProperties("spring.datasource.primary")
    public DataSourceProperties primaryDataSourceProperties() {
        return new DataSourceProperties();
    }
    
    @Bean
    @Primary
    public DataSource primaryDataSource() {
        return primaryDataSourceProperties()
            .initializeDataSourceBuilder()
            .build();
    }
    
    @Bean
    public SpringLiquibase primaryLiquibase(
            @Qualifier("primaryDataSource") DataSource dataSource) {
        return createLiquibase(
            dataSource, 
            "classpath:db/changelog/primary/db.changelog-master.yaml"
        );
    }
    
    @Bean
    @ConfigurationProperties("spring.datasource.secondary")
    public DataSourceProperties secondaryDataSourceProperties() {
        return new DataSourceProperties();
    }
    
    @Bean
    public DataSource secondaryDataSource() {
        return secondaryDataSourceProperties()
            .initializeDataSourceBuilder()
            .build();
    }
    
    @Bean
    public SpringLiquibase secondaryLiquibase(
            @Qualifier("secondaryDataSource") DataSource dataSource) {
        return createLiquibase(
            dataSource, 
            "classpath:db/changelog/secondary/db.changelog-master.yaml"
        );
    }
    
    private SpringLiquibase createLiquibase(DataSource dataSource, String changeLog) {
        SpringLiquibase liquibase = new SpringLiquibase();
        liquibase.setDataSource(dataSource);
        liquibase.setChangeLog(changeLog);
        liquibase.setContexts("dev,test");
        liquibase.setShouldRun(true);
        return liquibase;
    }
}
```

## 3. Changelog File Formats

Liquibase supports four formats: XML, YAML, JSON, and SQL. Each has pros and cons.

### XML Format (Most Feature-Rich)

**db/changelog/db.changelog-master.xml:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<databaseChangeLog
    xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xmlns:ext="http://www.liquibase.org/xml/ns/dbchangelog-ext"
    xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
        http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-latest.xsd
        http://www.liquibase.org/xml/ns/dbchangelog-ext
        http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-ext.xsd">

    <!-- Include other changelog files -->
    <include file="db/changelog/changes/001-create-users-table.xml"/>
    <include file="db/changelog/changes/002-create-orders-table.xml"/>
    <include file="db/changelog/changes/003-add-indexes.xml"/>
    
    <!-- Or include by relative path -->
    <include file="changes/004-add-audit-columns.xml" relativeToChangelogFile="true"/>
    
    <!-- Include directory (all files in order) -->
    <includeAll path="db/changelog/changes/v1.0/" relativeToChangelogFile="true"/>
</databaseChangeLog>
```

**db/changelog/changes/001-create-users-table.xml:**

### SQL Format (Database-Specific)

**db/changelog/db.changelog-master.sql:**

```sql
--liquibase formatted sql

--changeset john.doe:001-create-users-table
--comment: Create users table with basic columns
CREATE TABLE users (
    user_id NUMBER(19) PRIMARY KEY,
    username VARCHAR2(50) NOT NULL UNIQUE,
    email VARCHAR2(100) NOT NULL UNIQUE,
    password_hash VARCHAR2(255) NOT NULL,
    first_name VARCHAR2(50),
    last_name VARCHAR2(50),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at TIMESTAMP,
    is_active NUMBER(1) DEFAULT 1 NOT NULL
);
--rollback DROP TABLE users;

--changeset john.doe:001-create-users-sequence
--comment: Create sequence for users table
CREATE SEQUENCE users_seq START WITH 1 INCREMENT BY 1;
--rollback DROP SEQUENCE users_seq;

--changeset john.doe:002-create-orders-table
--comment: Create orders table
CREATE TABLE orders (
    order_id NUMBER(19) PRIMARY KEY,
    user_id NUMBER(19) NOT NULL,
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    total_amount NUMBER(10,2),
    status VARCHAR2(20) DEFAULT 'PENDING',
    CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(user_id)
);
--rollback DROP TABLE orders;
```

### Format Comparison

|Feature|XML|YAML|JSON|SQL|
|---|---|---|---|---|
|**Readability**|⭐⭐|⭐⭐⭐⭐|⭐⭐⭐|⭐⭐⭐⭐|
|**Database Independence**|✅|✅|✅|❌|
|**IDE Support**|✅✅|✅|✅|✅✅|
|**Validation**|✅✅|✅|✅|⭐|
|**Complex Changes**|✅✅|✅✅|✅|✅✅|
|**Learning Curve**|Medium|Low|Medium|Low|
|**Best For**|Complex schemas|General use|API teams|SQL experts|

**Recommendation**: Use **YAML** for most projects (best balance of readability and features), **SQL** for database-specific optimizations or when migrating existing SQL scripts.

## 4. ChangeSet Structure and Best Practices

### ChangeSet Anatomy

```yaml
databaseChangeLog:
  - changeSet:
      # Unique identifier (required)
      id: 001-create-users-table
      
      # Author name (required)
      author: john.doe
      
      # Human-readable description
      comment: Create users table with authentication columns
      
      # Context(s) when this runs
      context: dev,test,prod
      
      # Labels for filtering
      labels: feature-auth,release-1.0
      
      # Database platforms to run on
      dbms: oracle,postgresql
      
      # Run always (even if already executed)
      runAlways: false
      
      # Run on every change (useful for views)
      runOnChange: false
      
      # Fail on error
      failOnError: true
      
      # Preconditions
      preConditions:
        - onFail: MARK_RAN
        - not:
            - tableExists:
                tableName: users
      
      # Actual changes
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: user_id
                  type: NUMBER(19)
                  constraints:
                    primaryKey: true
                    nullable: false
      
      # Rollback strategy
      rollback:
        - dropTable:
            tableName: users
```

### Best Practices for ChangeSets

#### 1. Naming Convention

```yaml
# ✅ Good: Sequential numbering with descriptive name
001-create-users-table
002-add-email-index
003-add-user-roles-table

# ✅ Good: Date-based with feature
20240601-001-create-users-table
20240601-002-add-email-index

# ✅ Good: Version-based
v1.0-001-create-users-table
v1.0-002-add-email-index
v1.1-001-add-audit-columns

# ❌ Bad: No sequence
create-users
add-index
update-table

# ❌ Bad: Not descriptive
changeset-1
changeset-2
update-1
```

#### 2. One Logical Change Per ChangeSet

```yaml
# ✅ Good: Single logical change
databaseChangeLog:
  - changeSet:
      id: 001-create-users-table
      author: john.doe
      changes:
        - createTable:
            tableName: users
            # ...
  
  - changeSet:
      id: 002-create-users-index
      author: john.doe
      changes:
        - createIndex:
            indexName: idx_users_email
            tableName: users
            columns:
              - column:
                  name: email

# ❌ Bad: Multiple unrelated changes
databaseChangeLog:
  - changeSet:
      id: 001-multiple-changes
      author: john.doe
      changes:
        - createTable:
            tableName: users
        - createTable:
            tableName: orders
        - createTable:
            tableName: products
        # Too many changes in one changeset!
```

#### 3. Never Modify Executed ChangeSets

```yaml
# ❌ NEVER DO THIS: Modifying already-executed changeset
# Original (already executed)
databaseChangeLog:
  - changeSet:
      id: 001-create-users-table
      author: john.doe
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: user_id
                  type: NUMBER(19)

# ❌ Bad: Changing executed changeset
databaseChangeLog:
  - changeSet:
      id: 001-create-users-table
      author: john.doe
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: user_id
                  type: NUMBER(19)
              - column:
                  name: email  # NEW COLUMN - DON'T DO THIS!
                  type: VARCHAR2(100)

# ✅ Good: Create new changeset
databaseChangeLog:
  - changeSet:
      id: 001-create-users-table
      author: john.doe
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: user_id
                  type: NUMBER(19)
  
  - changeSet:
      id: 005-add-email-to-users
      author: john.doe
      changes:
        - addColumn:
            tableName: users
            columns:
              - column:
                  name: email
                  type: VARCHAR2(100)
```

#### 4. Use Contexts and Labels

```yaml
# Context-specific changes
databaseChangeLog:
  # Always runs
  - changeSet:
      id: 001-create-users-table
      author: john.doe
      context: all
      changes:
        - createTable:
            tableName: users
  
  # Only in dev/test
  - changeSet:
      id: 002-insert-test-data
      author: john.doe
      context: dev,test
      changes:
        - insert:
            tableName: users
            columns:
              - column:
                  name: username
                  value: testuser
  
  # Only in production
  - changeSet:
      id: 003-add-production-indexes
      author: john.doe
      context: prod
      changes:
        - createIndex:
            indexName: idx_users_performance
            tableName: users

# Label-based filtering
databaseChangeLog:
  - changeSet:
      id: 004-feature-payment
      author: jane.doe
      labels: feature-payment,release-2.0
      changes:
        - createTable:
            tableName: payments
```

#### 5. Database-Agnostic vs Database-Specific

```yaml
# ✅ Good: Database-agnostic (preferred)
databaseChangeLog:
  - changeSet:
      id: 001-create-users-table
      author: john.doe
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: user_id
                  type: BIGINT
                  autoIncrement: true

# Database-specific when needed
databaseChangeLog:
  # Oracle-specific
  - changeSet:
      id: 002-create-oracle-sequence
      author: john.doe
      dbms: oracle
      changes:
        - sql:
            sql: |
              CREATE SEQUENCE users_seq START WITH 1 INCREMENT BY 1
  
  # PostgreSQL-specific
  - changeSet:
      id: 002-create-postgres-sequence
      author: john.doe
      dbms: postgresql
      changes:
        - sql:
            sql: |
              CREATE SEQUENCE users_seq START 1 INCREMENT 1
```

## 5. Preconditions and Rollback Strategies

### Preconditions

Preconditions check database state before executing a changeset.

**Types of Preconditions:**

```yaml
databaseChangeLog:
  # Table exists check
  - changeSet:
      id: 001-add-email-index
      author: john.doe
      preConditions:
        - onFail: MARK_RAN  # Skip if condition fails
        - tableExists:
            tableName: users
      changes:
        - createIndex:
            indexName: idx_users_email
            tableName: users
  
  # Table NOT exists
  - changeSet:
      id: 002-create-orders-table
      author: john.doe
      preConditions:
        - onFail: HALT  # Stop execution if condition fails
        - not:
            - tableExists:
                tableName: orders
      changes:
        - createTable:
            tableName: orders
  
  # Column exists
  - changeSet:
      id: 003-modify-email-column
      author: john.doe
      preConditions:
        - onFail: WARN  # Warn but continue
        - columnExists:
            tableName: users
            columnName: email
      changes:
        - modifyDataType:
            tableName: users
            columnName: email
            newDataType: VARCHAR2(200)
  
  # Custom SQL precondition
  - changeSet:
      id: 004-add-premium-features
      author: john.doe
      preConditions:
        - onFail: MARK_RAN
        - sqlCheck:
            expectedResult: 0
            sql: |
              SELECT COUNT(*) FROM users WHERE account_type = 'PREMIUM'
      changes:
        - createTable:
            tableName: premium_features
  
  # Multiple preconditions (AND logic)
  - changeSet:
      id: 005-complex-migration
      author: john.doe
      preConditions:
        - and:
            - tableExists:
                tableName: users
            - columnExists:
                tableName: users
                columnName: email
            - not:
                - indexExists:
                    indexName: idx_users_email
      changes:
        - createIndex:
            indexName: idx_users_email
  
  # OR logic
  - changeSet:
      id: 006-conditional-change
      author: john.doe
      preConditions:
        - or:
            - dbms:
                type: oracle
            - dbms:
                type: postgresql
      changes:
        - sql:
            sql: -- Database-specific SQL
```

**Precondition Actions:**

|onFail Value|Description|Use Case|
|---|---|---|
|**HALT**|Stop execution|Critical changes that require specific state|
|**WARN**|Log warning, continue|Optional optimizations|
|**MARK_RAN**|Mark as ran, skip execution|Idempotent changes|
|**CONTINUE**|Ignore and continue|Best-effort changes|

### Rollback Strategies

#### 1. Automatic Rollback

Many Liquibase changes have automatic rollback:

```yaml
databaseChangeLog:
  # createTable -> automatic rollback (dropTable)
  - changeSet:
      id: 001-create-users
      author: john.doe
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: user_id
                  type: BIGINT
      # No explicit rollback needed - Liquibase knows how to reverse
  
  # addColumn -> automatic rollback (dropColumn)
  - changeSet:
      id: 002-add-email
      author: john.doe
      changes:
        - addColumn:
            tableName: users
            columns:
              - column:
                  name: email
                  type: VARCHAR(100)
  
  # createIndex -> automatic rollback (dropIndex)
  - changeSet:
      id: 003-add-index
      author: john.doe
      changes:
        - createIndex:
            indexName: idx_users_email
            tableName: users
            columns:
              - column:
                  name: email
```

#### 2. Explicit Rollback

For complex changes or SQL:

```yaml
databaseChangeLog:
  # Explicit rollback for custom SQL
  - changeSet:
      id: 004-update-user-status
      author: john.doe
      changes:
        - sql:
            sql: |
              UPDATE users 
              SET status = 'ACTIVE' 
              WHERE created_at < SYSDATE - 30
      rollback:
        - sql:
            sql: |
              UPDATE users 
              SET status = 'PENDING' 
              WHERE created_at < SYSDATE - 30
  
  # Rollback with multiple steps
  - changeSet:
      id: 005-complex-migration
      author: john.doe
      changes:
        - sql:
            sql: |
              -- Complex data migration
              INSERT INTO new_table 
              SELECT * FROM old_table;
        - dropTable:
            tableName: old_table
      rollback:
        - createTable:
            tableName: old_table
            columns:
              - column:
                  name: id
                  type: BIGINT
        - sql:
            sql: |
              INSERT INTO old_table 
              SELECT * FROM new_table;
```

#### 3. Empty Rollback (Not Reversible)

```yaml
databaseChangeLog:
  # Data changes that can't be rolled back
  - changeSet:
      id: 006-delete-old-data
      author: john.doe
      changes:
        - delete:
            tableName: audit_logs
            where: created_at < SYSDATE - 365
      rollback:
        - empty  # Cannot restore deleted data
```

#### 4. Rollback to Tag

```yaml
# Tag a specific point
databaseChangeLog:
  - changeSet:
      id: 001-create-users
      author: john.doe
      changes:
        - createTable:
            tableName: users
  
  - changeSet:
      id: tag-version-1.0
      author: john.doe
      changes:
        - tagDatabase:
            tag: version-1.0
  
  - changeSet:
      id: 002-add-orders
      author: john.doe
      changes:
        - createTable:
            tableName: orders
```

**Rollback Command:**

```bash
# Rollback to tag
liquibase rollback version-1.0

# Rollback last N changesets
liquibase rollback-count 3

# Rollback to date
liquibase rollback-to-date 2024-06-01
```

## 6. DATABASECHANGELOG and DATABASECHANGELOGLOCK Tables

### DATABASECHANGELOG Table

Liquibase automatically creates this table to track executed changesets.

**Structure:**

```sql
CREATE TABLE DATABASECHANGELOG (
    ID VARCHAR2(255) NOT NULL,           -- ChangeSet ID
    AUTHOR VARCHAR2(255) NOT NULL,       -- Author name
    FILENAME VARCHAR2(255) NOT NULL,     -- Changelog file name
    DATEEXECUTED TIMESTAMP NOT NULL,     -- When executed
    ORDEREXECUTED NUMBER NOT NULL,       -- Execution order
    EXECTYPE VARCHAR2(10) NOT NULL,      -- EXECUTED, FAILED, SKIPPED, RERAN, MARK_RAN
    MD5SUM VARCHAR2(35),                 -- Checksum of changeset
    DESCRIPTION VARCHAR2(255),           -- Description
    COMMENTS VARCHAR2(255),              -- Comments
    TAG VARCHAR2(255),                   -- Tag if any
    LIQUIBASE VARCHAR2(20),              -- Liquibase version
    CONTEXTS VARCHAR2(255),              -- Contexts used
    LABELS VARCHAR2(255),                -- Labels used
    DEPLOYMENT_ID VARCHAR2(10)           -- Deployment identifier
);
```

**Query Examples:**

```java
@Service
public class LiquibaseMetadataService {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    /**
     * Get all executed changesets
     */
    public List<ChangeSetInfo> getExecutedChangeSets() {
        String sql = """
            SELECT id, author, filename, dateexecuted, exectype, comments
            FROM DATABASECHANGELOG
            ORDER BY orderexecuted
            """;
        
        return jdbcTemplate.query(sql, (rs, rowNum) -> 
            new ChangeSetInfo(
                rs.getString("id"),
                rs.getString("author"),
                rs.getString("filename"),
                rs.getTimestamp("dateexecuted").toInstant(),
                rs.getString("exectype"),
                rs.getString("comments")
            )
        );
    }
    
    /**
     * Get recently executed changesets
     */
    public List<ChangeSetInfo> getRecentChangeSets(int days) {
        String sql = """
            SELECT id, author, filename, dateexecuted, exectype
            FROM DATABASECHANGELOG
            WHERE dateexecuted >= SYSDATE - :days
            ORDER BY dateexecuted DESC
            """;
        
        return jdbcTemplate.query(sql, 
            Map.of("days", days),
            (rs, rowNum) -> new ChangeSetInfo(
                rs.getString("id"),
                rs.getString("author"),
                rs.getString("filename"),
                rs.getTimestamp("dateexecuted").toInstant(),
                rs.getString("exectype"),
                null
            )
        );
    }
    
    /**
     * Check if specific changeset was executed
     */
    public boolean isChangeSetExecuted(String id, String author) {
        String sql = """
            SELECT COUNT(*)
            FROM DATABASECHANGELOG
            WHERE id = ? AND author = ?
            """;
        
        Integer count = jdbcTemplate.queryForObject(sql, Integer.class, id, author);
        return count != null && count > 0;
    }
}

@Data
@AllArgsConstructor
class ChangeSetInfo {
    private String id;
    private String author;
    private String filename;
    private Instant dateExecuted;
    private String execType;
    private String comments;
}
```

### DATABASECHANGELOGLOCK Table

Prevents concurrent Liquibase execution.

**Structure:**

```sql
CREATE TABLE DATABASECHANGELOGLOCK (
    ID NUMBER NOT NULL,              -- Lock ID (always 1)
    LOCKED NUMBER(1) NOT NULL,       -- 1 = locked, 0 = unlocked
    LOCKGRANTED TIMESTAMP,           -- When lock was acquired
    LOCKEDBY VARCHAR2(255),          -- Who/what holds the lock
    CONSTRAINT PK_DATABASECHANGELOGLOCK PRIMARY KEY (ID)
);
```

**Handling Lock Issues:**

```java
@Service
public class LiquibaseLockService {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    /**
     * Check if database is locked
     */
    public boolean isDatabaseLocked() {
        String sql = "SELECT locked FROM DATABASECHANGELOGLOCK WHERE id = 1";
        Integer locked = jdbcTemplate.queryForObject(sql, Integer.class);
        return locked != null && locked == 1;
    }
    
    /**
     * Force release lock (USE WITH CAUTION!)
     */
    @Transactional
    public void forceReleaseLock() {
        String sql = """
            UPDATE DATABASECHANGELOGLOCK 
            SET locked = 0, 
                lockgranted = NULL, 
                lockedby = NULL 
            WHERE id = 1
            """;
        
        int updated = jdbcTemplate.update(sql);
        
        if (updated > 0) {
            log.warn("Liquibase lock forcefully released!");
        }
    }
    
    /**
     * Get lock information
     */
    public LockInfo getLockInfo() {
        String sql = """
            SELECT locked, lockgranted, lockedby
            FROM DATABASECHANGELOGLOCK
            WHERE id = 1
            """;
        
        return jdbcTemplate.queryForObject(sql, (rs, rowNum) -> 
            new LockInfo(
                rs.getInt("locked") == 1,
                rs.getTimestamp("lockgranted") != null 
                    ? rs.getTimestamp("lockgranted").toInstant() 
                    : null,
                rs.getString("lockedby")
            )
        );
    }
}

@Data
@AllArgsConstructor
class LockInfo {
    private boolean locked;
    private Instant lockGranted;
    private String lockedBy;
}
```

**Common Lock Issues:**

```bash

# If locked by crashed process, release manually:
```

## 7. Running Liquibase on Startup vs Manually

### Running on Startup (Default)

**Configuration:**

```yaml
spring:
  liquibase:
    enabled: true  # Runs on application startup
    change-log: classpath:db/changelog/db.changelog-master.yaml
```

**Pros:**

- ✅ Automatic database updates
- ✅ Simple configuration
- ✅ Good for development and testing
- ✅ Ensures database is always in sync

**Cons:**

- ❌ Startup delays in production
- ❌ No control over timing
- ❌ Risky for large migrations
- ❌ Difficult to rollback

### Running Manually (Production Best Practice)

**Disable on Startup:**

```yaml
spring:
  liquibase:
    enabled: false  # Don't run automatically
```

**Manual Execution Options:**

#### Option 3: Custom Spring Bean

```java
@Configuration
public class ManualLiquibaseConfiguration {
    
    @Value("${liquibase.run.manual:false}")
    private boolean runManually;
    
    @Bean
    @ConditionalOnProperty(name = "liquibase.run.manual", havingValue = "true")
    public CommandLineRunner liquibaseRunner(DataSource dataSource) {
        return args -> {
            if (runManually && Arrays.asList(args).contains("--migrate")) {
                runLiquibase(dataSource);
            }
        };
    }
    
    private void runLiquibase(DataSource dataSource) throws Exception {
        Connection connection = dataSource.getConnection();
        Database database = DatabaseFactory.getInstance()
            .findCorrectDatabaseImplementation(new JdbcConnection(connection));
        
        Liquibase liquibase = new Liquibase(
            "db/changelog/db.changelog-master.yaml",
            new ClassLoaderResourceAccessor(),
            database
        );
        
        log.info("Running Liquibase migrations...");
        liquibase.update(new Contexts(), new LabelExpression());
        log.info("Liquibase migrations completed!");
        
        connection.close();
    }
}
```

#### Option 4: Dedicated Migration Service

```java
@Service
public class DatabaseMigrationService {
    
    @Autowired
    private DataSource dataSource;
    
    @Value("${spring.liquibase.change-log}")
    private String changeLog;
    
    /**
     * Run migrations programmatically
     */
    public void migrate() throws LiquibaseException, SQLException {
        Connection connection = dataSource.getConnection();
        Database database = DatabaseFactory.getInstance()
            .findCorrectDatabaseImplementation(new JdbcConnection(connection));
        
        Liquibase liquibase = new Liquibase(
            changeLog,
            new ClassLoaderResourceAccessor(),
            database
        );
        
        // Get pending changesets
        List<ChangeSet> pendingChangeSets = liquibase.listUnrunChangeSets(
            new Contexts(), 
            new LabelExpression()
        );
        
        log.info("Pending changesets: {}", pendingChangeSets.size());
        
        // Update database
        liquibase.update(new Contexts(), new LabelExpression());
        
        connection.close();
        
        log.info("Migration completed successfully!");
    }
    
    /**
     * Generate SQL for review
     */
    public String generateMigrationSQL() throws Exception {
        Connection connection = dataSource.getConnection();
        Database database = DatabaseFactory.getInstance()
            .findCorrectDatabaseImplementation(new JdbcConnection(connection));
        
        Liquibase liquibase = new Liquibase(
            changeLog,
            new ClassLoaderResourceAccessor(),
            database
        );
        
        StringWriter stringWriter = new StringWriter();
        liquibase.update(new Contexts(), new LabelExpression(), stringWriter);
        
        connection.close();
        
        return stringWriter.toString();
    }
    
    /**
     * Validate changelog
     */
    public void validateChangelog() throws Exception {
        Connection connection = dataSource.getConnection();
        Database database = DatabaseFactory.getInstance()
            .findCorrectDatabaseImplementation(new JdbcConnection(connection));
        
        Liquibase liquibase = new Liquibase(
            changeLog,
            new ClassLoaderResourceAccessor(),
            database
        );
        
        liquibase.validate();
        
        connection.close();
        
        log.info("Changelog validation successful!");
    }
}
```

**REST Endpoint for Manual Migration (Secured!):**

```java
@RestController
@RequestMapping("/api/admin/database")

            return ResponseEntity.ok(sql);
        } catch (Exception e) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body("Error: " + e.getMessage());
        }
    }
    
    @PostMapping("/validate")
    @PreAuthorize("hasRole('ADMIN')")
    public ResponseEntity<MigrationResponse> validate() {
        try {
            migrationService.validateChangelog();
            return ResponseEntity.ok(new MigrationResponse(
                true, 
                "Validation successful"
            ));
        } catch (Exception e) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new MigrationResponse(false, e.getMessage()));
        }
    }
}

}
```

## Best Practices Summary

### ✅ DO:

1. **Use meaningful changeset IDs** with sequential numbering
2. **One logical change per changeset** for easier rollback
3. **Never modify executed changesets** - create new ones instead
4. **Always include rollback** strategies
5. **Use preconditions** for idempotency
6. **Test migrations** in lower environments first
7. **Version control** all changelog files
8. **Use contexts** for environment-specific changes
9. **Run manually in production** with DBA review

### ❌ DON'T:

1. **Don't modify executed changesets** in DATABASECHANGELOG
2. **Don't skip rollback testing** before production
3. **Don't run large migrations on startup** in production
4. **Don't hardcode environment-specific values**
5. **Don't use `drop-first: true`** in production
6. **Don't ignore lock issues** - investigate and fix properly

## Interview Questions

**Q1: How does Liquibase prevent duplicate execution of changesets?**

Liquibase tracks executed changesets in the DATABASECHANGELOG table using a combination of ID, AUTHOR, and FILENAME. Before executing a changeset, it checks if an entry exists in this table. If found, it skips execution.

**Q2: What's the difference between runAlways and runOnChange?**

- `runAlways`: Executes every time Liquibase runs, regardless of whether it was previously executed
- `runOnChange`: Executes only if the changeset content has changed (checksum differs)

Both are useful for views, stored procedures, or triggers that need redeployment.

**Q3: How do you handle database-specific SQL in Liquibase?**

Use the `dbms` attribute to specify which database platforms should execute a changeset:

```yaml
- changeSet:
    id: 001-oracle-specific
    author: john.doe
    dbms: oracle
    changes:
      - sql:
          sql: CREATE SEQUENCE...
```

**Q4: What happens if Liquibase execution fails mid-migration?**

Liquibase marks failed changesets with `EXECTYPE='FAILED'` in DATABASECHANGELOG. The lock is released. On next run, it attempts to re-execute the failed changeset. Some databases support automatic rollback within the changeset transaction.

**Q5: How do you handle Liquibase in a microservices environment?**

Each microservice should have its own changelog and database schema. Use service-specific prefixes for tables, different database users/schemas, or separate databases entirely. Coordinate cross-service schema changes carefully.
