# Flyway Fundamentals and Setup

## Overview

Flyway is a database migration tool that follows a simple, SQL-based approach to version control for databases. It uses numbered SQL scripts with strict naming conventions to track and apply schema changes in a predictable, repeatable manner.

**Key Concept**: Flyway takes a script-first approach - migrations are simple SQL files with version numbers. This makes Flyway intuitive for developers who prefer SQL over declarative formats like Liquibase's XML/YAML.

### Auto-Configuration in Action

Spring Boot automatically configures Flyway when it's on the classpath:

**FlywayAutoConfiguration:**

```java
@Configuration
@ConditionalOnClass(Flyway.class)
@ConditionalOnBean(DataSource.class)
@ConditionalOnProperty(prefix = "spring.flyway", name = "enabled", matchIfMissing = true)
@AutoConfigureAfter({ DataSourceAutoConfiguration.class, JdbcTemplateAutoConfiguration.class })
public class FlywayAutoConfiguration {
    
    @Bean
    @ConfigurationProperties(prefix = "spring.flyway")
    public FlywayProperties flywayProperties() {
        return new FlywayProperties();
    }
    
    @Bean
    public Flyway flyway(DataSource dataSource, FlywayProperties properties) {
        FluentConfiguration configuration = Flyway.configure()
            .dataSource(dataSource)
            .locations(properties.getLocations())
            .baselineOnMigrate(properties.isBaselineOnMigrate())
            .baselineVersion(properties.getBaselineVersion());
        
        Flyway flyway = configuration.load();
        flyway.migrate();
        return flyway;
    }
}
```

**What Happens Automatically:**

1. ✅ Flyway is created and configured
2. ✅ Migration scripts are discovered from `classpath:db/migration`
3. ✅ `flyway_schema_history` table is created
4. ✅ Pending migrations are executed on startup
5. ✅ Application starts only if migrations succeed

### Manual Configuration

```java
@Configuration
public class FlywayConfig {
    
    @Bean
    public Flyway flyway(DataSource dataSource) {
        FluentConfiguration configuration = Flyway.configure()
            .dataSource(dataSource)
            .locations("classpath:db/migration", "filesystem:/opt/sql")
            .baselineOnMigrate(true)
            .baselineVersion("0")
            .validateOnMigrate(true)
            .outOfOrder(false)
            .cleanDisabled(true); // Safety: prevent accidental clean
        
        Flyway flyway = configuration.load();
        flyway.migrate();
        
        return flyway;
    }
}
```

```java
            .schemas("secondary_schema");
        
        Flyway flyway = configuration.load();
        flyway.migrate();
        
        return flyway;
    }
}
```

## 2. Migration File Naming Conventions

### Versioned Migrations Format

**Naming Pattern:**

```
V{version}__{description}.sql

V → Prefix (required)
{version} → Version number (1, 1.1, 2, 2.1, etc.)
__ → Double underscore separator (required)
{description} → Human-readable description (underscores for spaces)
.sql → File extension
```

**Examples:**

```
V1__create_users_table.sql
V2__create_orders_table.sql
V3__add_email_column_to_users.sql
V4__create_indexes.sql
V5__insert_reference_data.sql
V6__add_foreign_keys.sql
V10__create_products_table.sql
V11__migrate_legacy_data.sql
```

**Version Number Formats:**

```
# Integer versioning (recommended for most projects)
V1__initial_schema.sql
V2__add_users.sql
V3__add_orders.sql

# Decimal versioning (for parallel development)
V1.0__initial_schema.sql
V1.1__add_indexes.sql
V2.0__add_users.sql
V2.1__add_user_preferences.sql

# Timestamp versioning (avoids conflicts)
V20240601000000__initial_schema.sql
V20240601120000__add_users.sql
V20240602093000__add_orders.sql

# Semantic versioning
V1.0.0__initial_schema.sql
V1.1.0__add_users.sql
V1.1.1__fix_user_constraints.sql
V2.0.0__breaking_changes.sql
```

### File Naming Rules

**Valid Names:**

```
V1__create_schema.sql                    ✅
V2__add_users_table.sql                  ✅
V3__insert_reference_data.sql            ✅
V10__major_refactor.sql                  ✅
V1.1__add_index.sql                      ✅
V20240601120000__migration.sql           ✅
```

**Invalid Names:**

```
V1_create_schema.sql                     ❌ (single underscore)
v1__create_schema.sql                    ❌ (lowercase v)
V1create_schema.sql                      ❌ (missing separator)
V1__.sql                                 ❌ (missing description)
V__create_schema.sql                     ❌ (missing version)
1__create_schema.sql                     ❌ (missing V prefix)
V1__create schema.sql                    ❌ (space in filename)
```

### Description Best Practices

**Good Descriptions:**

```
V1__create_users_table.sql
V2__add_email_verification_to_users.sql
V3__create_orders_and_order_items_tables.sql
V4__add_indexes_for_performance.sql
V5__migrate_legacy_customer_data.sql
V6__add_audit_columns_to_all_tables.sql
```

**Poor Descriptions:**

```
V1__changes.sql                          ❌ Too vague
V2__update.sql                           ❌ Not descriptive
V3__stuff.sql                            ❌ Unprofessional
V4__temp.sql                             ❌ Suggests temporary
V5__fix.sql                              ❌ What was fixed?
```

### Ordering Rules

Flyway executes migrations in version order, not filename order:

```
File Order:              Execution Order:
V1__users.sql            V1__users.sql
V10__products.sql        V2__orders.sql
V2__orders.sql           V3__indexes.sql
V3__indexes.sql          V10__products.sql
V20__cleanup.sql         V20__cleanup.sql
```

**Version Comparison:**

```
1 < 1.1 < 1.2 < 2 < 2.1 < 10 < 20
```

## 3. Versioned vs Repeatable Migrations

### Versioned Migrations

**Purpose**: One-time, sequential schema changes

**Naming**: `V{version}__{description}.sql`

**Characteristics:**

- ✅ Executed exactly once
- ✅ Run in version order
- ✅ Checksum validated (changes not allowed)
- ✅ Recorded in `flyway_schema_history`
- ✅ Cannot be modified after execution

**Use Cases:**

```sql
-- V1__create_schema.sql
-- Creating new tables (one-time)
CREATE TABLE users (...);

-- V2__add_column.sql
-- Adding columns (one-time)
ALTER TABLE users ADD COLUMN phone_number VARCHAR(20);

-- V3__migrate_data.sql
-- Data migrations (one-time)
UPDATE users SET status = 'ACTIVE' WHERE status IS NULL;

-- V4__add_constraint.sql
-- Adding constraints (one-time)
ALTER TABLE users ADD CONSTRAINT uk_email UNIQUE (email);
```

**Versioned Migration Flow:**

```
1. Flyway scans db/migration/
2. Finds V5__new_migration.sql
3. Checks flyway_schema_history
4. V5 not found → executes migration
5. Records V5 in history with checksum
6. Next startup: V5 found in history → skips
```

### Repeatable Migrations

**Purpose**: Idempotent operations that may change

**Naming**: `R__{description}.sql`

**Characteristics:**

- ✅ Executed every time checksum changes
- ✅ Run AFTER all versioned migrations
- ✅ Run in alphabetical order (by description)
- ✅ Must be idempotent
- ✅ Can be modified and re-executed

**Use Cases:**

**R__create_user_summary_view.sql:**

```sql
-- Repeatable migration for view
-- Executed every time this file changes

-- Drop and recreate view
DROP VIEW IF EXISTS v_user_summary;

CREATE VIEW v_user_summary AS
SELECT 
    u.user_id,
    u.username,
    u.email,
    COUNT(o.order_id) as total_orders,
    COALESCE(SUM(o.total_amount), 0) as total_spent,
    MAX(o.order_date) as last_order_date
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
GROUP BY u.user_id, u.username, u.email;
```

**R__create_stored_procedures.sql:**

```sql
-- Repeatable migration for stored procedures
-- Can be modified and will re-execute

CREATE OR REPLACE FUNCTION calculate_user_loyalty_points(p_user_id BIGINT)
RETURNS INTEGER AS $$
DECLARE
    total_points INTEGER;
BEGIN
    SELECT COALESCE(SUM(points), 0)
    INTO total_points
    FROM orders
    WHERE user_id = p_user_id
    AND status = 'COMPLETED';
    
    RETURN total_points;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE FUNCTION get_active_users()
RETURNS TABLE(user_id BIGINT, username VARCHAR, email VARCHAR) AS $$
BEGIN
    RETURN QUERY
    SELECT u.user_id, u.username, u.email
    FROM users u
    WHERE u.is_active = TRUE
    ORDER BY u.created_at DESC;
END;
$$ LANGUAGE plpgsql;
```

**R__refresh_materialized_views.sql:**

```sql
-- Refresh materialized views
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_user_statistics;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_product_rankings;
```

### Execution Order

```
Startup Flow:
1. Execute pending versioned migrations (V1, V2, V3...)
2. Execute repeatable migrations (R__a, R__b, R__c...)
   - Only if checksum changed
   - In alphabetical order by description
```

**Example Directory:**

```
db/migration/
├── V1__create_users.sql              (Run once)
├── V2__create_orders.sql             (Run once)
├── V3__add_indexes.sql               (Run once)
├── R__create_views.sql               (Run when changed, alphabetically first)
└── R__create_procedures.sql          (Run when changed, alphabetically second)
```

**Execution Order:**

```
First Startup:
1. V1__create_users.sql
2. V2__create_orders.sql
3. V3__add_indexes.sql
4. R__create_views.sql
5. R__create_procedures.sql

Second Startup (R__create_views.sql modified):
1. R__create_views.sql (checksum changed)
2. R__create_procedures.sql (runs because repeatable, even if unchanged)

Third Startup (new V4 added, R__create_views.sql modified):
1. V4__add_column.sql
2. R__create_views.sql
3. R__create_procedures.sql
```

### Idempotency Requirements

**Repeatable migrations MUST be idempotent:**

**✅ Good - Idempotent:**

```sql
-- Use CREATE OR REPLACE
CREATE OR REPLACE VIEW v_summary AS ...

-- Use DROP IF EXISTS
DROP VIEW IF EXISTS v_summary;
CREATE VIEW v_summary AS ...

-- Use conditional logic
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_proc WHERE proname = 'my_function') THEN
        CREATE FUNCTION my_function() ...
    END IF;
END $$;
```

**❌ Bad - Not Idempotent:**

```sql
-- Will fail on second run
CREATE VIEW v_summary AS ...

-- Will fail if already exists
CREATE FUNCTION my_function() ...

-- Unpredictable results
INSERT INTO settings VALUES (1, 'value');
```

### Comparison Table

|Aspect|Versioned (V)|Repeatable (R)|
|---|---|---|
|**Prefix**|V|R|
|**Execution**|Once|Every checksum change|
|**Order**|Version number|Alphabetical|
|**Modification**|❌ Not allowed|✅ Allowed|
|**Use Case**|Schema changes|Views, procedures|
|**Idempotency**|Not required|Required|
|**Rollback**|Can be undone|Must handle manually|

## 4. Undo Migrations (Paid Feature)

### Flyway Teams Edition

**Undo migrations are a PAID feature** (Flyway Teams edition):

```xml
<!-- Flyway Teams dependency -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
    <version>9.22.0</version>
</dependency>

<!-- Teams license required -->
<dependency>
    <groupId>org.flywaydb.enterprise</groupId>
    <artifactId>flyway-enterprise</artifactId>
    <version>9.22.0</version>
</dependency>
```

**License Configuration:**

```yaml
spring:
  flyway:
    license-key: ${FLYWAY_LICENSE_KEY}
```

### Undo Migration Format

**Naming Convention:**

```
U{version}__{description}.sql

U → Undo prefix
{version} → Must match corresponding V migration
{description} → Should match or describe undo operation
```

**Example Pair:**

**V1__create_users_table.sql (Forward):**

```sql
CREATE TABLE users (
    user_id BIGSERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL
);

CREATE INDEX idx_users_email ON users(email);
```

**U1__create_users_table.sql (Undo):**

```sql
DROP INDEX IF EXISTS idx_users_email;
DROP TABLE IF EXISTS users;
```

### Directory Structure with Undo

```
src/main/resources/
└── db/
    └── migration/
        ├── V1__create_users_table.sql
        ├── U1__create_users_table.sql
        ├── V2__create_orders_table.sql
        ├── U2__create_orders_table.sql
        ├── V3__add_email_to_users.sql
        └── U3__add_email_to_users.sql
```

### Undo Command

```bash
# Undo last migration
flyway undo

# Undo to specific version
flyway undo -target=2

# Undo with info
flyway undo -outOfOrder=true
```

**With Spring Boot:**

```java
@Configuration
public class FlywayConfig {
    
    @Bean
    public Flyway flyway(DataSource dataSource) {
        Flyway flyway = Flyway.configure()
            .dataSource(dataSource)
            .locations("classpath:db/migration")
            .load();
        
        // Normal migration
        flyway.migrate();
        
        // To undo (requires Teams license)
        // flyway.undo();
        
        return flyway;
    }
}
```

### Limitations and Considerations

**⚠️ Important Notes:**

1. **Paid Feature Only**

```
Community Edition: No undo support
Teams Edition: Full undo support
Enterprise Edition: Full undo support
```

2. **Not a Time Machine**

```sql
-- Forward migration
INSERT INTO users VALUES (1, 'john', 'john@example.com');

-- Undo migration
DELETE FROM users WHERE user_id = 1;

-- Problem: If user was modified after creation,
-- undo loses those changes
```

3. **Production Risk**

```
Undo in production is risky:
- Data loss potential
- Referential integrity issues
- Application compatibility problems
```

### Alternative: Manual Rollback Migrations

**Community Edition Alternative:**

Instead of undo migrations, create new forward migrations:

**V1__create_users_table.sql:**

```sql
CREATE TABLE users (
    user_id BIGSERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL
);
```

**V2__add_email_to_users.sql:**

```sql
ALTER TABLE users ADD COLUMN email VARCHAR(100);
```

**V3__rollback_add_email.sql (if V2 needs to be undone):**

```sql
-- Forward migration to undo V2
ALTER TABLE users DROP COLUMN IF EXISTS email;
```

**Benefits:**

- ✅ Works with Community Edition
- ✅ Clear audit trail
- ✅ Explicit rollback decision
- ✅ Version controlled

## 5. flyway_schema_history Table

### Table Structure

**Flyway automatically creates this table:**

```sql
CREATE TABLE flyway_schema_history (
    installed_rank INTEGER NOT NULL,
    version VARCHAR(50),
    description VARCHAR(200) NOT NULL,
    type VARCHAR(20) NOT NULL,
    script VARCHAR(1000) NOT NULL,
    checksum INTEGER,
    installed_by VARCHAR(100) NOT NULL,
    installed_on TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    execution_time INTEGER NOT NULL,
    success BOOLEAN NOT NULL,
    CONSTRAINT flyway_schema_history_pk PRIMARY KEY (installed_rank)
);

CREATE INDEX flyway_schema_history_s_idx 
ON flyway_schema_history (success);
```

### Column Descriptions

|Column|Type|Description|
|---|---|---|
|**installed_rank**|INTEGER|Sequential order of execution|
|**version**|VARCHAR(50)|Version number (e.g., "1", "2.1")|
|**description**|VARCHAR(200)|Migration description from filename|
|**type**|VARCHAR(20)|Migration type (SQL, JDBC, BASELINE)|
|**script**|VARCHAR(1000)|Script filename|
|**checksum**|INTEGER|CRC32 checksum of migration content|
|**installed_by**|VARCHAR(100)|Database user who ran migration|
|**installed_on**|TIMESTAMP|When migration was executed|
|**execution_time**|INTEGER|Duration in milliseconds|
|**success**|BOOLEAN|Whether migration succeeded|

### Example Data

```sql
SELECT * FROM flyway_schema_history ORDER BY installed_rank;
```

**Results:**

```
installed_rank | version | description           | type | script                         | checksum    | installed_by | installed_on        | execution_time | success
---------------|---------|----------------------|------|--------------------------------|-------------|--------------|---------------------|----------------|--------
```

### Querying Schema History

**Get Current Version:**

```sql
SELECT version, description
FROM flyway_schema_history
WHERE type = 'SQL'
  AND version IS NOT NULL
ORDER BY installed_rank DESC
LIMIT 1;
```

**Get All Applied Migrations:**

```sql
SELECT 
    installed_rank,
    version,
    description,
    installed_on,
    execution_time,
    success
FROM flyway_schema_history
ORDER BY installed_rank;
```

**Find Failed Migrations:**

```sql
SELECT 
    installed_rank,
    version,
    description,
    script,
    installed_on
FROM flyway_schema_history
WHERE success = FALSE;
```

**Calculate Total Migration Time:**

```sql
SELECT 
    SUM(execution_time) as total_ms,
    SUM(execution_time) / 1000.0 as total_seconds
FROM flyway_schema_history
WHERE success = TRUE;
```

**Get Repeatable Migration History:**

```sql
SELECT 
    installed_rank,
    description,
    checksum,
    installed_on,
    execution_time
FROM flyway_schema_history
WHERE version IS NULL  -- Repeatable migrations have NULL version
ORDER BY installed_rank DESC;
```

### Checksum Validation

**How Checksums Work:**

```java
// Flyway calculates CRC32 checksum of file content
// V1__create_users.sql content → CRC32 → 1234567890

// On startup:
// 1. Calculate checksum of V1__create_users.sql
// 2. Query flyway_schema_history for V1 checksum
// 3. Compare: current checksum vs stored checksum
// 4. If different → ValidationException
```

**Checksum Mismatch Error:**

```
Migration checksum mismatch for migration version 1
-> Applied to database : 1234567890
-> Resolved locally    : 9876543210
Either revert the changes to the migration, or run repair to update the schema history.
```

### Callbacks

**Custom Callback:**

```java
@Component
public class FlywayMigrationCallback implements Callback {
    
    private static final Logger log = LoggerFactory.getLogger(FlywayMigrationCallback.class);
    
    @Override
    public boolean supports(Event event, Context context) {
        return event == Event.BEFORE_MIGRATE || 
               event == Event.AFTER_MIGRATE ||
               event == Event.AFTER_MIGRATE_ERROR;
    }
    
    @Override
    public boolean canHandleInTransaction(Event event, Context context) {
        return true;
    }
    
    @Override
    public void handle(Event event, Context context) {
        if (event == Event.BEFORE_MIGRATE) {
            log.info("Starting Flyway migration...");
            log.info("Current schema version: {}", 
                context.getConnection().getCurrentSchemaVersion());
        } else if (event == Event.AFTER_MIGRATE) {
            log.info("Flyway migration completed successfully");
            log.info("New schema version: {}", 
                context.getConnection().getCurrentSchemaVersion());
        } else if (event == Event.AFTER_MIGRATE_ERROR) {
            log.error("Flyway migration failed!");
        }
    }
    
    @Override
    public String getCallbackName() {
        return "MigrationLogger";
    }
}
```

## Best Practices Summary

### ✅ DO:

1. **Use clear version numbers** (1, 2, 3 or timestamps)
2. **Write descriptive filenames** (V1__create_users_table.sql)
3. **Use repeatable migrations** for views and procedures
4. **Enable validation** in production
5. **Disable clean** in production (clean-disabled: true)
6. **Baseline existing databases** before first migration
7. **Test migrations** in non-production first
8. **Keep migrations small** and focused
9. **Use placeholders** for environment-specific values
10. **Monitor flyway_schema_history** for audit trail

### ❌ DON'T:

1. **Don't modify executed migrations** (checksum will fail)
2. **Don't use clean** in production (deletes all data!)
3. **Don't skip version numbers** unnecessarily
4. **Don't use vague descriptions** (V1__changes.sql)
5. **Don't mix unrelated changes** in one migration
6. **Don't forget rollback strategy** (undo or forward fix)
7. **Don't ignore checksum errors** (investigate first)
8. **Don't run migrations manually** in production without testing
9. **Don't enable auto-migration** in production
10. **Don't delete from schema history** unless absolutely necessary

## Interview Questions

**Q1: What's the difference between versioned and repeatable migrations in Flyway?**

Versioned migrations (V prefix) run exactly once and cannot be modified after execution. They're used for one-time schema changes. Repeatable migrations (R prefix) run every time their checksum changes and must be idempotent. They're used for views, stored procedures, and functions that may need updates.

**Q2: How does Flyway detect if a migration has already been executed?**

Flyway maintains a `flyway_schema_history` table that records all executed migrations with their version, checksum, and execution details. On startup, Flyway compares migration files against this table - if a version exists in the table, it's skipped; if not, it's executed.

**Q3: What happens if you modify an already-executed migration file?**

Flyway calculates a checksum of each migration file. If you modify an executed migration, the checksum changes. On next startup, Flyway detects the mismatch and throws a ValidationException. You must either revert the change or run `flyway repair` to update the stored checksum.

**Q4: Explain Flyway's naming convention for migration files.**

Versioned migrations use `V{version}__{description}.sql` where V is required prefix, version is a number (1, 1.1, 2), double underscore separates version from description, and description uses underscores for spaces. Repeatable migrations use `R__{description}.sql` with no version number.

**Q5: What's the purpose of baseline-on-migrate?**

`baseline-on-migrate` allows Flyway to work with existing databases. When enabled, Flyway creates a baseline entry in the schema history table instead of trying to create all objects. Migrations with versions higher than the baseline version will execute; those equal to or below are ignored.

## Summary

Flyway fundamentals enable database version control:

- ✅ **Auto-configuration** with Spring Boot
- ✅ **Simple naming** with V and R prefixes
- ✅ **Versioned migrations** for one-time changes
- ✅ **Repeatable migrations** for views/procedures
- ✅ **Schema history tracking** in flyway_schema_history
- ✅ **Flexible configuration** with Spring properties

**Key Takeaway**: Flyway takes a script-first, SQL-based approach to migrations. Use versioned migrations (V) for schema changes, repeatable migrations (R) for idempotent objects, and always validate checksums. The flyway_schema_history table provides complete audit trail of all database changes.
