# Flyway Production Strategies

## Overview

Running database migrations in production requires careful planning, thorough testing, and robust safety mechanisms. Flyway provides multiple deployment strategies and features to ensure safe, reliable schema evolution in production environments.

**Key Concept**: Production migrations are high-risk operations. Success requires pre-deployment validation, controlled execution, comprehensive monitoring, and clear rollback procedures. Never run untested migrations directly in production.

---

## 1. Running Flyway on Application Startup vs Separate Process

### Application Startup Migration

**Default Spring Boot Behavior:**

```yaml
# application.yml
spring:
  flyway:
    enabled: true  # Migrations run on startup
    locations: classpath:db/migration
```

**What Happens:**

```
1. Application starts
2. DataSource bean created
3. Flyway auto-configuration triggered
4. Flyway scans migration files
5. Pending migrations executed
6. Application continues startup (or fails if migrations fail)
```

**Advantages:**

- ✅ Simple configuration
- ✅ Guaranteed schema version matches application
- ✅ No separate deployment step
- ✅ Works well in development/staging

**Disadvantages:**

- ❌ Application won't start if migration fails
- ❌ All instances try to migrate simultaneously (clustering issues)
- ❌ No control over timing
- ❌ Difficult to monitor progress
- ❌ Can't review migration before execution

**When to Use:**

- Development environments
- Staging/QA environments
- Small applications with single instance
- Non-critical applications

### Separate Process Migration

**Disable Auto-Migration:**

```yaml
# application-prod.yml
spring:
  flyway:
    enabled: false  # Don't run on startup
```

**Manual Migration Options:**

**Option 1: Maven Plugin**

```bash
# Run migration separately before deployment
mvn flyway:migrate \
  -Dflyway.url=jdbc:postgresql://prod-db:5432/proddb \
  -Dflyway.user=flyway_user \
  -Dflyway.password=${FLYWAY_PASSWORD}
```

**Option 2: Flyway CLI**

```bash
# Using Flyway command-line tool
flyway \
  -url=jdbc:postgresql://prod-db:5432/proddb \
  -user=flyway_user \
  -password=${FLYWAY_PASSWORD} \
  -locations=filesystem:/opt/sql/migrations \
  migrate
```

**Option 3: Custom Migration Application**

```java
@SpringBootApplication

            SpringApplication.run(MigrationApplication.class, args);

            log.info("Starting database migration...");

        } catch (Exception e) {
            log.error("Migration failed", e);
            System.exit(1);
        }
    }
```

### Production Deployment Script

```bash
#!/bin/bash
set -e

ENVIRONMENT="production"
VERSION="2.0.0"
DB_URL="jdbc:postgresql://prod-db:5432/proddb"
DB_USER="flyway_user"
DB_PASSWORD="${FLYWAY_PASSWORD}"

echo "=== Production Migration Deployment ==="
echo "Environment: ${ENVIRONMENT}"
echo "Version: ${VERSION}"
echo "Timestamp: $(date)"

# 1. Backup database
echo "Step 1: Creating database backup..."
pg_dump -h prod-db -U postgres proddb > backup_$(date +%Y%m%d_%H%M%S).sql
echo "✓ Backup created"

# 2. Validate migrations
echo "Step 2: Validating migrations..."
flyway \
  -url=${DB_URL} \
  -user=${DB_USER} \
  -password=${DB_PASSWORD} \
  -locations=filesystem:./migrations \
  validate

if [ $? -ne 0 ]; then
    echo "✗ Validation failed!"
    exit 1
fi
echo "✓ Validation passed"

# 3. Check pending migrations
echo "Step 3: Checking pending migrations..."
PENDING=$(flyway \
  -url=${DB_URL} \
  -user=${DB_USER} \
  -password=${DB_PASSWORD} \
  -locations=filesystem:./migrations \
  info | grep -c "Pending" || echo "0")

echo "Pending migrations: ${PENDING}"

if [ "${PENDING}" -eq "0" ]; then
    echo "No pending migrations. Skipping migration step."
    exit 0
fi

# 4. Generate migration SQL for review (Teams edition)
echo "Step 4: Generating migration SQL..."
# flyway -configFiles=flyway.conf -dryRunOutput=migration.sql migrate
# Review migration.sql manually

# 5. Execute migration
echo "Step 5: Executing migrations..."
START_TIME=$(date +%s)

flyway \
  -url=${DB_URL} \
  -user=${DB_USER} \
  -password=${DB_PASSWORD} \
  -locations=filesystem:./migrations \
  migrate

MIGRATION_EXIT_CODE=$?
END_TIME=$(date +%s)
DURATION=$((END_TIME - START_TIME))

if [ ${MIGRATION_EXIT_CODE} -ne 0 ]; then
    echo "✗ Migration failed after ${DURATION} seconds!"
    echo "Check logs and consider rollback."
    exit 1
fi

echo "✓ Migration completed successfully in ${DURATION} seconds"

# 6. Verify schema
echo "Step 6: Verifying schema..."
flyway \
  -url=${DB_URL} \
  -user=${DB_USER} \
  -password=${DB_PASSWORD} \
  -locations=filesystem:./migrations \
  validate

echo "✓ Schema verification passed"

# 7. Log migration completion
echo "Step 7: Logging migration completion..."
psql -h prod-db -U ${DB_USER} -d proddb << EOF
INSERT INTO migration_audit_log (
    environment,
    version,
    executed_by,
    duration_seconds,
    status
) VALUES (
    '${ENVIRONMENT}',
    '${VERSION}',
    '$(whoami)',
    ${DURATION},
    'SUCCESS'
);
EOF

echo "=== Migration Deployment Complete ==="
```

## 2. Handling Large Data Migrations

### Batch Processing Pattern

**Problem:**

```sql
-- ❌ DON'T: Process millions of rows in single transaction
UPDATE users SET status = 'ACTIVE' WHERE status IS NULL;
-- Locks entire table, runs forever, fills transaction log
```

**Solution:**

```sql
-- V2.0__migrate_user_status_batched.sql
-- ✅ DO: Process in batches

DO $$
DECLARE
    batch_size INTEGER := 10000;
    total_rows INTEGER;
    processed_rows INTEGER := 0;
    affected_rows INTEGER;
BEGIN
    -- Count total rows
    SELECT COUNT(*) INTO total_rows
    FROM users
    WHERE status IS NULL;
    
    RAISE NOTICE 'Total rows to process: %', total_rows;
    
    LOOP
        -- Update batch
        WITH batch AS (
            SELECT user_id
            FROM users
            WHERE status IS NULL
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        )
        UPDATE users
        SET status = 'ACTIVE'
        WHERE user_id IN (SELECT user_id FROM batch);
        
        GET DIAGNOSTICS affected_rows = ROW_COUNT;
        
        EXIT WHEN affected_rows = 0;
        
        processed_rows := processed_rows + affected_rows;
        
        RAISE NOTICE 'Processed % / % rows (%.2f%%)',
            processed_rows,
            total_rows,
            (processed_rows::DECIMAL / total_rows * 100);
        
        -- Commit batch
        COMMIT;
        
        -- Small delay to avoid overwhelming database
        PERFORM pg_sleep(0.1);
    END LOOP;
    
    RAISE NOTICE 'Migration completed: % rows processed', processed_rows;
END $$;
```

### Java-Based Large Migration

```java
package db.migration;

import org.flywaydb.core.api.migration.BaseJavaMigration;
import org.flywaydb.core.api.migration.Context;
import java.sql.*;

public class V2_0__Migrate_Large_Dataset extends BaseJavaMigration {
    
    private static final int BATCH_SIZE = 10000;
    private static final int REPORT_INTERVAL = 50000;
    
    @Override
    public void migrate(Context context) throws Exception {
        Connection conn = context.getConnection();
        
        // Disable auto-commit for manual transaction control
        conn.setAutoCommit(false);
        
        long totalRows = getTotalRows(conn);
        long processedRows = 0;
        long startTime = System.currentTimeMillis();
        
        System.out.printf("Starting migration of %,d rows%n", totalRows);
        
        try (PreparedStatement select = conn.prepareStatement(
                "SELECT user_id, email, first_name, last_name " +
                "FROM users " +
                "WHERE full_name IS NULL " +
                "ORDER BY user_id " +
                "LIMIT ?");
             PreparedStatement update = conn.prepareStatement(
                "UPDATE users SET full_name = ? WHERE user_id = ?")) {
            
            boolean moreRows = true;
            
            while (moreRows) {
                select.setInt(1, BATCH_SIZE);
                ResultSet rs = select.executeQuery();
                
                int batchCount = 0;
                
                while (rs.next()) {
                    long userId = rs.getLong("user_id");
                    String firstName = rs.getString("first_name");
                    String lastName = rs.getString("last_name");
                    
                    // Transform data
                    String fullName = buildFullName(firstName, lastName);
                    
                    update.setString(1, fullName);
                    update.setLong(2, userId);
                    update.addBatch();
                    
                    batchCount++;
                    processedRows++;
                    
                    if (batchCount >= BATCH_SIZE) {
                        break;
                    }
                }
                
                rs.close();
                
                if (batchCount == 0) {
                    moreRows = false;
                } else {
                    // Execute batch
                    update.executeBatch();
                    
                    // Commit batch
                    conn.commit();
                    
                    // Report progress
                    if (processedRows % REPORT_INTERVAL == 0) {
                        long elapsed = System.currentTimeMillis() - startTime;
                        double rowsPerSecond = processedRows / (elapsed / 1000.0);
                        double percentComplete = (processedRows * 100.0) / totalRows;
                        
                        System.out.printf(
                            "Progress: %,d / %,d rows (%.2f%%) - %.0f rows/sec%n",
                            processedRows, totalRows, percentComplete, rowsPerSecond
                        );
                    }
                    
                    // Small delay to avoid overwhelming database
                    Thread.sleep(100);
                }
            }
            
            long duration = System.currentTimeMillis() - startTime;
            double rowsPerSecond = processedRows / (duration / 1000.0);
            
            System.out.printf(
                "Migration completed: %,d rows in %.2f seconds (%.0f rows/sec)%n",
                processedRows, duration / 1000.0, rowsPerSecond
            );
            
        } catch (Exception e) {
            conn.rollback();
            throw e;
        }
    }
    
    private long getTotalRows(Connection conn) throws SQLException {
        try (Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT COUNT(*) FROM users WHERE full_name IS NULL")) {
            rs.next();
            return rs.getLong(1);
        }
    }
    
    private String buildFullName(String firstName, String lastName) {
        StringBuilder sb = new StringBuilder();
        if (firstName != null && !firstName.isEmpty()) {
            sb.append(firstName);
        }
        if (lastName != null && !lastName.isEmpty()) {
            if (sb.length() > 0) {
                sb.append(" ");
            }
            sb.append(lastName);
        }
        return sb.toString();
    }
}
```

### Parallel Processing for Very Large Tables

```java
package db.migration;

import org.flywaydb.core.api.migration.BaseJavaMigration;
import org.flywaydb.core.api.migration.Context;
import java.sql.*;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.*;

public class V3_0__Parallel_Migration extends BaseJavaMigration {
    
    private static final int BATCH_SIZE = 10000;
    private static final int THREAD_POOL_SIZE = 4;
    
    @Override
    public void migrate(Context context) throws Exception {
        Connection conn = context.getConnection();
        
        // Get ID ranges for parallel processing
        List<IdRange> ranges = getIdRanges(conn, THREAD_POOL_SIZE);
        
        ExecutorService executor = Executors.newFixedThreadPool(THREAD_POOL_SIZE);
        List<Future<MigrationResult>> futures = new ArrayList<>();
        
        System.out.printf("Starting parallel migration with %d threads%n", 
            THREAD_POOL_SIZE);
        
        // Submit migration tasks
        for (IdRange range : ranges) {
            Future<MigrationResult> future = executor.submit(
                () -> migrateRange(conn, range)
            );
            futures.add(future);
        }
        
        // Wait for all tasks to complete
        long totalProcessed = 0;
        for (Future<MigrationResult> future : futures) {
            MigrationResult result = future.get();
            totalProcessed += result.getRowsProcessed();
            System.out.printf("Range %d-%d: %,d rows processed%n",
                result.getStartId(), result.getEndId(), result.getRowsProcessed());
        }
        
        executor.shutdown();
        
        System.out.printf("Parallel migration completed: %,d total rows%n", 
            totalProcessed);
    }
    
    private List<IdRange> getIdRanges(Connection conn, int chunks) 
            throws SQLException {
        List<IdRange> ranges = new ArrayList<>();
        
        // Get min and max IDs
        try (Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT MIN(user_id), MAX(user_id) FROM users")) {
            rs.next();
            long minId = rs.getLong(1);
            long maxId = rs.getLong(2);
            
            long rangeSize = (maxId - minId + 1) / chunks;
            
            for (int i = 0; i < chunks; i++) {
                long startId = minId + (i * rangeSize);
                long endId = (i == chunks - 1) ? maxId : startId + rangeSize - 1;
                ranges.add(new IdRange(startId, endId));
            }
        }
        
        return ranges;
    }
    
    private MigrationResult migrateRange(Connection conn, IdRange range) 
            throws SQLException {
        
        String updateSql = """
            UPDATE users
            SET full_name = first_name || ' ' || last_name
            WHERE user_id >= ? AND user_id <= ?
              AND full_name IS NULL
            """;
        
        try (PreparedStatement update = conn.prepareStatement(updateSql)) {
            update.setLong(1, range.getStartId());
            update.setLong(2, range.getEndId());
            
            int rowsProcessed = update.executeUpdate();
            conn.commit();
            
            return new MigrationResult(
                range.getStartId(),
                range.getEndId(),
                rowsProcessed
            );
        }
    }
    
    private record IdRange(long startId, long endId) {}
    
    private record MigrationResult(long startId, long endId, long rowsProcessed) {}
}
```

**Using Progress Table:**

```sql
-- V2.0__resumable_migration.sql
DO $$
DECLARE
    migration_id VARCHAR(100) := 'migrate_user_status_v2';
    batch_size INTEGER := 10000;
    last_id BIGINT := 0;
    total_rows BIGINT;
    processed_rows BIGINT := 0;
BEGIN
    -- Check if migration already started
    SELECT COALESCE(last_processed_id, 0), COALESCE(processed_rows, 0)
    INTO last_id, processed_rows
    FROM migration_progress
    WHERE migration_id = migration_id;
    
    -- Initialize if new migration
    IF NOT FOUND THEN
        SELECT COUNT(*) INTO total_rows
        FROM users WHERE status IS NULL;
        
        INSERT INTO migration_progress (
            migration_id, total_rows, status
        ) VALUES (
            migration_id, total_rows, 'IN_PROGRESS'
        );
    END IF;
    
    -- Resume from last checkpoint
    LOOP
        WITH batch AS (
            SELECT user_id
            FROM users
            WHERE status IS NULL
              AND user_id > last_id
            ORDER BY user_id
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        )
        UPDATE users
        SET status = 'ACTIVE'
        WHERE user_id IN (SELECT user_id FROM batch)
        RETURNING user_id INTO last_id;
        
        EXIT WHEN NOT FOUND;
        
        processed_rows := processed_rows + 1;
        
        -- Update progress every 1000 rows
        IF processed_rows % 1000 = 0 THEN
            UPDATE migration_progress
            SET processed_rows = processed_rows,
                last_processed_id = last_id,
                updated_at = CURRENT_TIMESTAMP
            WHERE migration_id = migration_id;
            
            COMMIT;
        END IF;
    END LOOP;
    
    -- Mark as completed
    UPDATE migration_progress
    SET status = 'COMPLETED',
        completed_at = CURRENT_TIMESTAMP
    WHERE migration_id = migration_id;
    
    COMMIT;
END $$;
```

## 3. Zero-Downtime Techniques

### Expand-Contract Pattern

**Phase 1: Expand (Backward Compatible)**

```sql
-- V2.0__expand_add_full_name.sql
-- Add new column without removing old columns

ALTER TABLE users ADD COLUMN full_name VARCHAR(200);

-- Create function to sync data
CREATE OR REPLACE FUNCTION sync_full_name()
RETURNS TRIGGER AS $$
BEGIN
    -- Sync from old to new
    IF NEW.full_name IS NULL THEN
        NEW.full_name := COALESCE(NEW.first_name, '') || ' ' || 
                         COALESCE(NEW.last_name, '');
    END IF;
    
    -- Sync from new to old (for backward compatibility)
    IF NEW.first_name IS NULL AND NEW.full_name IS NOT NULL THEN
        -- Parse full_name back to first/last (simple split)
        NEW.first_name := split_part(NEW.full_name, ' ', 1);
        NEW.last_name := split_part(NEW.full_name, ' ', 2);
    END IF;
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Create trigger
CREATE TRIGGER users_sync_full_name
    BEFORE INSERT OR UPDATE ON users
    FOR EACH ROW
    EXECUTE FUNCTION sync_full_name();

-- Backfill existing data in batches
DO $$
DECLARE
    batch_size INTEGER := 10000;
    affected_rows INTEGER;
BEGIN
    LOOP
        UPDATE users
        SET full_name = COALESCE(first_name, '') || ' ' || 
                        COALESCE(last_name, '')
        WHERE user_id IN (
            SELECT user_id
            FROM users
            WHERE full_name IS NULL
            LIMIT batch_size
        );
        
        GET DIAGNOSTICS affected_rows = ROW_COUNT;
        EXIT WHEN affected_rows = 0;
        
        RAISE NOTICE 'Backfilled % rows', affected_rows;
        COMMIT;
        PERFORM pg_sleep(0.1);
    END LOOP;
END $$;
```

### Online Index Creation

**PostgreSQL:**

```sql
-- V2.1__create_index_concurrently.sql
-- Create index without blocking writes

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_users_full_name
ON users(full_name);

-- Verify index is valid
DO $$
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_indexes
        WHERE indexname = 'idx_users_full_name'
        AND indexdef LIKE '%CONCURRENTLY%'
    ) THEN
        RAISE EXCEPTION 'Index creation failed';
    END IF;
END $$;
```

**Note**: CONCURRENTLY cannot run inside transaction block in PostgreSQL. Use separate migration or Java-based migration:

```java
package db.migration;

public class V2_1__Create_Index_Concurrently extends BaseJavaMigration {

            System.out.println("Creating index concurrently...");

        }

}
```

### Blue-Green Database Strategy

```
┌──────────────┐         ┌──────────────┐
│ Blue (Old)   │         │ Green (New)  │
```

## 4. Rollback Strategies (Manual Intervention)

### Understanding Flyway Rollback Limitations

**Community Edition:**

- ❌ No automatic undo migrations
- ❌ No built-in rollback command
- ✅ Must use manual rollback strategies

**Teams Edition:**

- ✅ Undo migrations (U prefix)
- ✅ Flyway undo command
- ❌ Requires commercial license

### Manual Rollback Approach 1: Forward Fix

**Problem Migration:**

```sql
-- V2.0__add_email_verification.sql
ALTER TABLE users ADD COLUMN email_verified BOOLEAN DEFAULT FALSE;
-- Oops! Should have been TRUE
```

**Rollback via Forward Fix:**

```sql
-- V2.1__fix_email_verification_default.sql
-- Don't undo V2.0, fix it forward

-- Update default for future inserts
ALTER TABLE users ALTER COLUMN email_verified SET DEFAULT TRUE;

-- Fix existing rows
UPDATE users SET email_verified = TRUE WHERE email_verified = FALSE;
```

### Manual Rollback Approach 2: Explicit Undo Migration

```sql
-- V2.0__add_user_preferences.sql
CREATE TABLE user_preferences (
    preference_id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    theme VARCHAR(50) DEFAULT 'light',
    notifications_enabled BOOLEAN DEFAULT TRUE,
    CONSTRAINT fk_preferences_user FOREIGN KEY (user_id)
        REFERENCES users(user_id) ON DELETE CASCADE
);

CREATE INDEX idx_preferences_user_id ON user_preferences(user_id);
```

**Explicit Rollback Migration:**

```sql
-- V2.1__rollback_user_preferences.sql
-- Manual rollback of V2.0

-- Drop table and all dependencies
DROP INDEX IF EXISTS idx_preferences_user_id;
DROP TABLE IF EXISTS user_preferences;

-- Remove from Flyway history (optional, not recommended)
-- DELETE FROM flyway_schema_history WHERE version = '2.0';
```

### Rollback Decision Framework

```java
@Service
public class RollbackDecisionService {
    
    public RollbackStrategy determineStrategy(MigrationFailure failure) {
        
        // 1. Data corruption or loss
        if (failure.causedDataLoss()) {
            // Restore from backup immediately
            return RollbackStrategy.RESTORE_FROM_BACKUP;
        }
        
        // 2. Schema change causing application errors
        if (failure.causedApplicationFailure()) {
            if (failure.isReversible() && !failure.hasDataChanges()) {
                // Safe to undo schema
                return RollbackStrategy.MANUAL_UNDO_MIGRATION;
            } else {
                // Has data changes, can't safely undo
                return RollbackStrategy.FORWARD_FIX;
            }
        }
        
        // 3. Performance issues
        if (failure.causedPerformanceIssue()) {
            // Often fixable forward
            return RollbackStrategy.FORWARD_FIX;
        }
        
        // 4. Constraint violation
        if (failure.causedConstraintViolation()) {
            // Fix data then retry
            return RollbackStrategy.FIX_DATA_AND_RETRY;
        }
        
        // 5. Timeout or resource exhaustion
        if (failure.isTransient()) {
            // Retry with optimizations
            return RollbackStrategy.RETRY_WITH_OPTIMIZATION;
        }
        
        // Default: manual intervention
        return RollbackStrategy.MANUAL_INTERVENTION;
    }
}
```

````
### Automated Rollback Script

```bash
#!/bin/bash
set -e

MIGRATION_VERSION=$1
ROLLBACK_TYPE=$2  # undo, forward-fix, restore

if [ -z "$MIGRATION_VERSION" ]; then
    echo "Usage: $0 <version> <rollback-type>"
    exit 1
fi

echo "=== Rollback Migration ${MIGRATION_VERSION} ==="

case ${ROLLBACK_TYPE} in
    undo)
        echo "Performing manual undo..."
        
        # Generate undo SQL
        cat > /tmp/undo_${MIGRATION_VERSION}.sql << EOF
-- Auto-generated undo for version ${MIGRATION_VERSION}
-- Review carefully before execution!

-- Add your undo SQL here
EOF
        
        echo "Undo SQL template created: /tmp/undo_${MIGRATION_VERSION}.sql"
        echo "Edit the file and run: flyway migrate"
        ;;
        
    forward-fix)
        echo "Performing forward fix..."
        
        # Generate forward fix template
        NEXT_VERSION=$(echo "${MIGRATION_VERSION} + 0.1" | bc)
        cat > /tmp/fix_${NEXT_VERSION}.sql << EOF
-- Forward fix for issues in version ${MIGRATION_VERSION}

-- Add your fix SQL here
EOF
        
        echo "Forward fix template created: /tmp/fix_${NEXT_VERSION}.sql"
        echo "Edit the file and run: flyway migrate"
        ;;
        
    restore)
        echo "Restoring from backup..."
        
        # Find most recent backup before migration
        BACKUP_FILE=$(ls -t backup_*.sql | head -1)
        
        if [ -z "$BACKUP_FILE" ]; then
            echo "No backup file found!"
            exit 1
        fi
        
        echo "Found backup: ${BACKUP_FILE}"
        read -p "Restore from this backup? (yes/no): " CONFIRM
        
        if [ "$CONFIRM" = "yes" ]; then
            echo "Restoring database..."
            psql -h ${DB_HOST} -U ${DB_USER} -d ${DB_NAME} < ${BACKUP_FILE}
            echo "Restore complete"
        else
            echo "Restore cancelled"
        fi
        ;;
        
    *)
        echo "Invalid rollback type: ${ROLLBACK_TYPE}"
        echo "Valid types: undo, forward-fix, restore"
        exit 1
        ;;
esac
````

## 5. Lock Handling in Clustered Deployments

### Flyway Locking Mechanism

**Schema History Lock Table:**

```sql
-- Flyway automatically manages this
SELECT * FROM flyway_schema_history_lock;

-- Structure (internal)
installed_rank | locked
---------------+--------
1              | 1  (locked) or 0 (unlocked)
```

**Lock Acquisition Flow:**

```
Instance 1                    Instance 2                    Instance 3
     |                             |                             |
     ├─ Try lock (UPDATE...)       |                             |
     ├─ SUCCESS (rows=1)           |                             |
     ├─ Run migrations            ├─ Try lock                   |
     |                             ├─ FAIL (rows=0)             |
     |                             ├─ Wait...                    |
     |                             |                            ├─ Try lock
     |                             |                            ├─ FAIL (rows=0)
     ├─ Release lock               |                            ├─ Wait...
     |                             ├─ Try lock                   |
     |                             ├─ SUCCESS                    |
     |                             ├─ Run migrations            |
     |                             |                             ├─ Wait...
```

### Kubernetes Init Container Pattern

**Recommended Approach:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3

    spec:

      initContainers:
```

**What Happens:**

```
Pod 1: Init container acquires lock → runs migration → releases lock → main starts
Pod 2: Init container waits for lock → lock released → checks migrations → already done → main starts
Pod 3: Init container waits for lock → lock released → checks migrations → already done → main starts
```

### Custom Lock Timeout Configuration

**Application Configuration:**

**Custom Lock Service:**

```java
@Configuration
public class FlywayLockConfig {
    
    private static final int LOCK_TIMEOUT_MINUTES = 30;
    private static final int POLL_INTERVAL_SECONDS = 10;
    
    @Bean
    public Flyway flyway(DataSource dataSource) {
        // Custom Flyway configuration with timeout handling
        Flyway flyway = Flyway.configure()
            .dataSource(dataSource)
            .locations("classpath:db/migration")
            .load();
        
        // Wrap migration execution with timeout
        executeMigrationWithTimeout(flyway);
        
        return flyway;
    }
    
    private void executeMigrationWithTimeout(Flyway flyway) {
        long startTime = System.currentTimeMillis();
        long maxWaitMillis = LOCK_TIMEOUT_MINUTES * 60 * 1000;
        
        while (true) {
            try {
                log.info("Attempting to acquire migration lock...");
                flyway.migrate();
                log.info("Migration completed successfully");
                return;
                
            } catch (Exception e) {
                if (isLockException(e)) {
                    long elapsed = System.currentTimeMillis() - startTime;
                    
                    if (elapsed >= maxWaitMillis) {
                        log.error("Timeout waiting for migration lock after {} minutes",
                            LOCK_TIMEOUT_MINUTES);
                        throw new RuntimeException(
                            "Migration lock timeout after " + LOCK_TIMEOUT_MINUTES + " minutes", e);
                    }
                    
                    log.info("Migration lock held by another instance, waiting... ({}/{} minutes)",
                        elapsed / 60000, LOCK_TIMEOUT_MINUTES);
                    
                    try {
                        Thread.sleep(POLL_INTERVAL_SECONDS * 1000);
                    } catch (InterruptedException ie) {
                        Thread.currentThread().interrupt();
                        throw new RuntimeException("Interrupted waiting for lock", ie);
                    }
                } else {
                    // Not a lock exception, fail immediately
                    throw e;
                }
            }
        }
    }
    
    private boolean isLockException(Exception e) {
        String message = e.getMessage();
        return message != null && (
            message.contains("locked") ||
            message.contains("lock") ||
            message.contains("Unable to obtain lock")
        );
    }
}
```

### Emergency Lock Release

**Admin Endpoint:**

```java
@RestController
@RequestMapping("/api/admin/flyway")
@PreAuthorize("hasRole('ADMIN')")
public class FlywayLockController {
    
    @Autowired
    private DataSource dataSource;
    
    @GetMapping("/lock-status")
    public ResponseEntity<LockStatus> getLockStatus() {
        try (Connection conn = dataSource.getConnection();
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT * FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 1")) {
            
            if (rs.next()) {
                return ResponseEntity.ok(new LockStatus(
                    false,  // Flyway doesn't expose lock status easily
                    rs.getTimestamp("installed_on").toInstant(),
                    rs.getString("description")
                ));
            }
            
            return ResponseEntity.ok(new LockStatus(false, null, "No migrations"));
            
        } catch (Exception e) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new LockStatus(true, null, "Error checking lock: " + e.getMessage()));
        }
    }
    
    @PostMapping("/force-unlock")
    public ResponseEntity<UnlockResult> forceUnlock() {
        log.warn("Force unlock requested - this is dangerous!");
        
        try (Connection conn = dataSource.getConnection()) {
            // Flyway manages locks internally
            // This is a workaround - use with extreme caution
            
            // Clear any stuck migrations
            try (Statement stmt = conn.createStatement()) {
                int deleted = stmt.executeUpdate(
                    "DELETE FROM flyway_schema_history WHERE success = false"
                );
                
                if (deleted > 0) {
                    log.warn("Cleared {} failed migration records", deleted);
                }
            }
            
            return ResponseEntity.ok(new UnlockResult(
                true,
                "Lock released - retry migration"
            ));
            
        } catch (Exception e) {
            log.error("Failed to force unlock", e);
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new UnlockResult(false, e.getMessage()));
        }
    }
}
```

```java
                log.info("Pending migrations: {}", pending.length);
                for (MigrationInfo info : pending) {
                    log.info("  - Version {}: {}", 
                        info.getVersion(), info.getDescription());
                }
            }
            
        } catch (Exception e) {
            log.error("Migration validation failed", e);
            throw new RuntimeException("Pre-migration validation failed", e);
        }
    }
```

### Custom Dry Run Implementation

```java
@Service
public class DryRunMigrationService {
    
    @Autowired
    private DataSource dataSource;
    
    /**
     * Simulate migration without actually executing
     * Community edition workaround
     */
    public DryRunResult performDryRun(String targetVersion) {
        Flyway flyway = Flyway.configure()
            .dataSource(dataSource)
            .locations("classpath:db/migration")
            .target(targetVersion)
            .load();
        
        List<String> sqlStatements = new ArrayList<>();
        List<String> warnings = new ArrayList<>();
        
        try {
            // Get pending migrations
            MigrationInfo[] pending = flyway.info().pending();
            
            for (MigrationInfo info : pending) {
                // Read migration file
                String sql = readMigrationFile(info);
                sqlStatements.add(sql);
                
                // Analyze SQL for potential issues
                warnings.addAll(analyzeSql(sql));
            }
            
            // Generate report
            return new DryRunResult(
                true,
                sqlStatements,
                warnings,
                "Dry run completed successfully"
            );
            
        } catch (Exception e) {
            return new DryRunResult(
                false,
                sqlStatements,
                List.of("Dry run failed: " + e.getMessage()),
                "Dry run failed"
            );
        }
    }
    
    private String readMigrationFile(MigrationInfo info) {
        // Read migration file content
        try {
            String filename = info.getScript();
            Resource resource = new ClassPathResource("db/migration/" + filename);
            return StreamUtils.copyToString(
                resource.getInputStream(),
                StandardCharsets.UTF_8
            );
        } catch (IOException e) {
            return "-- Error reading file: " + e.getMessage();
        }
    }
    
    private List<String> analyzeSql(String sql) {
        List<String> warnings = new ArrayList<>();
        
        // Check for potentially dangerous operations
        if (sql.toUpperCase().contains("DROP TABLE")) {
            warnings.add("⚠️  DROP TABLE detected - data loss risk");
        }
        
        if (sql.toUpperCase().contains("DROP COLUMN")) {
            warnings.add("⚠️  DROP COLUMN detected - data loss risk");
        }
        
        if (sql.toUpperCase().contains("ALTER TABLE") && 
            sql.toUpperCase().contains("NOT NULL")) {
            warnings.add("⚠️  Adding NOT NULL constraint - may fail on existing data");
        }
        
        if (sql.toUpperCase().contains("CREATE INDEX") && 
            !sql.toUpperCase().contains("CONCURRENTLY")) {
            warnings.add("⚠️  Non-concurrent index creation - will lock table");
        }
        
        // Check for missing transactions
        if (!sql.toUpperCase().contains("BEGIN") && 
            !sql.toUpperCase().contains("COMMIT")) {
            warnings.add("ℹ️  No explicit transaction - using Flyway default");
        }
        
        return warnings;
    }
}

record DryRunResult(
    boolean success,
    List<String> sqlStatements,
    List<String> warnings,
    String message
) {}
```

## Best Practices Summary

### ✅ DO:

1. **Run migrations separately** from application in production
2. **Use Kubernetes init containers** for clustered deployments
3. **Process large migrations** in batches with progress tracking
4. **Use expand-contract** for zero-downtime changes
5. **Plan rollback strategy** before migration (forward fix preferred)
6. **Configure lock timeouts** to prevent indefinite waits
7. **Always validate** before migrating
8. **Test migrations** with production-like data volumes
9. **Monitor migration** progress and duration
10. **Document rollback** procedures in playbook

### ❌ DON'T:

1. **Don't run migrations** on all pods simultaneously
2. **Don't process millions** of rows in single transaction
3. **Don't apply breaking changes** without expand-contract
4. **Don't rely on automatic undo** (Community edition lacks it)
5. **Don't ignore lock timeouts** (causes indefinite hangs)
6. **Don't skip validation** (catches errors early)
7. **Don't test only** with small datasets
8. **Don't forget backup** before production migration
9. **Don't create non-concurrent** indexes on large tables
10. **Don't skip dry run** review for complex migrations

## Interview Questions

**Q1: Should you run Flyway migrations on application startup in production?**

No, run migrations separately in production using init containers, Kubernetes jobs, or dedicated migration processes. This provides better control, monitoring, handles clustering properly, and enables pre-deployment validation. Startup migrations are fine for dev/staging but risky for production.

**Q2: How do you handle a migration that needs to process millions of rows?**

Process in batches (10k-50k rows per transaction), use `FOR UPDATE SKIP LOCKED` to avoid contention, track progress in a separate table for resumability, add small delays between batches, consider parallel processing with ID ranges, and monitor performance throughout.

**Q3: What's the expand-contract pattern and why use it?**

Expand-contract enables zero-downtime schema changes: (1) Expand - add new columns/tables while keeping old ones, deploy dual-write application code, (2) Migrate - deploy app version using new schema, (3) Contract - remove old columns/tables after all instances updated. Prevents downtime and maintains backward compatibility.

**Q4: How do you rollback a failed Flyway migration in Community edition?**

Flyway Community lacks automatic undo. Use forward fixes (preferred) - create new migration fixing the issue, or manual undo migrations - create explicit rollback migration, or restore from backup for data corruption. Document rollback procedures in runbooks and always have backups before migrations.

**Q5: How does Flyway handle locking in clustered environments?**

Flyway uses database-level locking on schema history table. First instance acquires lock and runs migrations, other instances wait. In Kubernetes, use init containers so only first pod runs migrations, others skip. Implement lock timeouts to prevent indefinite waits, and have emergency unlock procedures.

Flyway production strategies enable safe database evolution:

- ✅ **Separate migration process** for control and monitoring
- ✅ **Batch processing** for large data migrations
- ✅ **Zero-downtime** via expand-contract pattern
- ✅ **Manual rollback** strategies (forward fix preferred)
- ✅ **Lock handling** for clustered deployments
- ✅ **Validation and dry runs** before execution

**Key Takeaway**: Production migrations require careful planning and execution. Safe migrations are more important than fast migrations.
