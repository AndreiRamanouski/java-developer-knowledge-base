# Flyway vs Liquibase Comparison

## Overview

Flyway and Liquibase are the two most popular database migration tools in the Java ecosystem. Both enable version-controlled schema evolution, but they differ significantly in philosophy, complexity, and feature sets.

**Key Concept**: Flyway favors simplicity with SQL-first migrations and minimal configuration. Liquibase provides more features with declarative changesets and database abstraction, but with increased complexity. Choose based on your team's needs, not just features.

## 2. When to Choose Flyway vs Liquibase

### Choose Flyway When:

**1. Simplicity is Priority**

```
✅ Team prefers SQL over XML/YAML
✅ Want minimal configuration
✅ Don't need database abstraction
✅ Straightforward migration needs
```

**Example: Startup with Single Database**

```yaml
# application.yml (Flyway)
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration

# That's it! Drop SQL files in db/migration/
```

**2. SQL Expertise**

```
✅ Team has strong SQL skills
✅ DBA-driven migrations
✅ Database-specific optimizations needed
✅ Want full control over SQL
```

**Example: Complex Database Optimization**

```sql
-- V2__optimize_queries.sql (Flyway)
-- Full control over PostgreSQL-specific features
CREATE INDEX CONCURRENTLY idx_users_complex 
ON users USING GIN (to_tsvector('english', full_name));

CREATE MATERIALIZED VIEW user_stats AS
SELECT user_id, COUNT(*) as order_count
FROM orders
GROUP BY user_id;

CREATE INDEX ON user_stats(user_id);
```

**3. Microservices Architecture**

```
✅ Each service owns database
✅ Simple, independent migrations
✅ No cross-database coordination
✅ Minimal dependencies
```

**4. Quick Prototyping**

```
✅ Fast iteration cycles
✅ Minimal overhead
✅ Learning curve minimal
✅ No time for complex tooling
```

### Choose Liquibase When:

**1. Database Portability Required**

```
✅ Support multiple databases (Postgres, MySQL, Oracle)
✅ Customers on different databases
✅ Want database-agnostic migrations
✅ Avoid database-specific SQL
```

**Example: Multi-Database Product**

```xml
<!-- V1__create_users.xml (Liquibase) -->
<!-- Works on PostgreSQL, MySQL, Oracle, SQL Server -->
<changeSet id="1" author="dev">
    <createTable tableName="users">
        <column name="user_id" type="BIGINT" autoIncrement="true">
            <constraints primaryKey="true"/>
        </column>
        <column name="username" type="VARCHAR(50)">
            <constraints nullable="false" unique="true"/>
        </column>
        <column name="email" type="VARCHAR(100)">
            <constraints nullable="false" unique="true"/>
        </column>
    </createTable>
</changeSet>
```

**2. Complex Migration Requirements**

```
✅ Need rollback capabilities
✅ Conditional migrations (preconditions)
✅ Data transformations (loadData)
✅ Schema diffing and generation
```

**Example: Conditional Migration**

```xml
<changeSet id="2" author="dev">
    <preConditions onFail="MARK_RAN">
        <not>
            <columnExists tableName="users" columnName="status"/>
        </not>
    </preConditions>
    
    <addColumn tableName="users">
        <column name="status" type="VARCHAR(20)" defaultValue="ACTIVE"/>
    </addColumn>
</changeSet>
```

**3. Team Prefers Declarative Approach**

```
✅ Developers less SQL-proficient
✅ Want change type abstraction
✅ Prefer structured formats (XML/YAML)
✅ Value IDE assistance
```

**4. Existing Liquibase Investment**

```
✅ Already using Liquibase
✅ Team trained on Liquibase
✅ Existing changelog repository
✅ Migration costs too high
```

**5. Need Advanced Features (Community Edition)**

```
✅ Rollback without paying
✅ Diff and generate from database
✅ Contexts and labels
✅ Preconditions
```

### Real-World Scenario Comparison

**Scenario 1: B2B SaaS (Multi-Tenant)**

```
Decision: Liquibase
Reason:
- Customers use different databases (PostgreSQL, MySQL, SQL Server)
- Need database-agnostic migrations
- Schema generation for new tenants
- Diffing for customer-specific schemas
```

**Scenario 2: Internal Microservices**

```
Decision: Flyway
Reason:
- Single database (PostgreSQL)
- Simple, independent migrations per service
- Team prefers SQL
- Minimal complexity
```

**Scenario 3: Enterprise Monolith**

```
Decision: Depends
- Single database → Flyway (simplicity)
- Multiple databases → Liquibase (portability)
- Strong DBA team → Flyway (SQL control)
- Developer-driven → Liquibase (abstraction)
```

**Scenario 4: Startup MVP**

```
Decision: Flyway
Reason:
- Fast iteration
- Single database
- Minimal learning curve
- No complexity needed
```

## 3. Migration Complexity Handling

### Simple Migration

**Flyway Approach:**

```sql
-- V1__create_users.sql
CREATE TABLE users (
    user_id BIGSERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE
);

CREATE INDEX idx_users_email ON users(email);
```

**Liquibase Approach:**

```xml
<!-- V1__create_users.xml -->
<databaseChangeLog>
    <changeSet id="1" author="dev">
        <createTable tableName="users">
            <column name="user_id" type="BIGINT" autoIncrement="true">
                <constraints primaryKey="true"/>
            </column>
            <column name="username" type="VARCHAR(50)">
                <constraints nullable="false"/>
            </column>
            <column name="email" type="VARCHAR(100)">
                <constraints nullable="false" unique="true"/>
            </column>
        </createTable>
        
        <createIndex tableName="users" indexName="idx_users_email">
            <column name="email"/>
        </createIndex>
    </changeSet>
</databaseChangeLog>
```

**Winner: Flyway** (simpler for basic DDL)

### Complex Data Migration

**Flyway Approach:**

```java
// V2__Migrate_User_Data.java
public class V2__Migrate_User_Data extends BaseJavaMigration {
    
    @Override
    public void migrate(Context context) throws Exception {
        try (PreparedStatement select = context.getConnection().prepareStatement(
                "SELECT user_id, first_name, last_name FROM users");
             PreparedStatement update = context.getConnection().prepareStatement(
                "UPDATE users SET full_name = ? WHERE user_id = ?")) {
            
            ResultSet rs = select.executeQuery();
            
            while (rs.next()) {
                long userId = rs.getLong("user_id");
                String fullName = rs.getString("first_name") + " " + rs.getString("last_name");
                
                update.setString(1, fullName);
                update.setLong(2, userId);
                update.executeUpdate();
            }
        }
    }
}
```

**Liquibase Approach:**

```xml
<changeSet id="2" author="dev">
    <!-- Add new column -->
    <addColumn tableName="users">
        <column name="full_name" type="VARCHAR(200)"/>
    </addColumn>
    
    <!-- Update using SQL -->
    <sql>
        UPDATE users 
        SET full_name = first_name || ' ' || last_name
        WHERE full_name IS NULL
    </sql>
    
    <!-- Or use custom change class for complex logic -->
    <customChange class="com.example.MigrateUserDataChange"/>
</changeSet>
```

**Winner: Tie** (both support complex migrations via code)

### Rollback Scenario

**Flyway Community (Manual):**

```sql
-- V2__add_status_column.sql
ALTER TABLE users ADD COLUMN status VARCHAR(20);

-- To rollback, create new migration:
-- V3__rollback_status_column.sql
ALTER TABLE users DROP COLUMN status;
```

**Flyway Teams (Undo):**

```sql
-- V2__add_status_column.sql
ALTER TABLE users ADD COLUMN status VARCHAR(20);

-- U2__add_status_column.sql (automatic rollback)
ALTER TABLE users DROP COLUMN status;
```

**Liquibase (Built-in):**

```xml
<changeSet id="2" author="dev">
    <addColumn tableName="users">
        <column name="status" type="VARCHAR(20)"/>
    </addColumn>
    
    <rollback>
        <dropColumn tableName="users" columnName="status"/>
    </rollback>
</changeSet>

<!-- Command: liquibase rollback -->
```

**Winner: Liquibase** (built-in rollback in Community edition)

### Database-Specific Features

**Flyway (Full Control):**

```sql
-- V3__postgres_specific.sql
-- Use any PostgreSQL feature directly

-- Full-text search
CREATE INDEX idx_users_fulltext ON users 
USING GIN (to_tsvector('english', full_name));

-- Partitioning
CREATE TABLE orders (
    order_id BIGSERIAL,
    order_date DATE NOT NULL,
    total_amount DECIMAL(10,2)
) PARTITION BY RANGE (order_date);

-- JSONB
ALTER TABLE users ADD COLUMN metadata JSONB;
CREATE INDEX idx_metadata ON users USING GIN (metadata);

-- Materialized views
CREATE MATERIALIZED VIEW user_order_summary AS
SELECT user_id, COUNT(*) as order_count
FROM orders GROUP BY user_id;
```

**Liquibase (Limited Abstraction):**

```xml
<changeSet id="3" author="dev" dbms="postgresql">
    <!-- Must use SQL for database-specific features -->
    <sql>
        CREATE INDEX idx_users_fulltext ON users 
        USING GIN (to_tsvector('english', full_name))
    </sql>
</changeSet>

<!-- OR use database-specific changelog -->
<include file="db/changelog/postgresql-specific.sql" context="postgresql"/>
```

**Winner: Flyway** (easier for database-specific optimizations)

### Multi-Database Support

**Flyway (Separate SQL files):**

```
db/migration/
├── postgresql/
│   ├── V1__create_schema.sql
│   └── V2__add_indexes.sql
├── mysql/
│   ├── V1__create_schema.sql
│   └── V2__add_indexes.sql
└── oracle/
    ├── V1__create_schema.sql
    └── V2__add_indexes.sql

# Configuration per database
spring.flyway.locations=classpath:db/migration/${database.type}
```

**Liquibase (Single Abstracted Changelog):**

```xml
<!-- Works on all databases -->
<changeSet id="1" author="dev">
    <createTable tableName="users">
        <column name="user_id" type="BIGINT" autoIncrement="true">
            <constraints primaryKey="true"/>
        </column>
    </createTable>
</changeSet>

<!-- Database-specific overrides when needed -->
<changeSet id="2" author="dev" dbms="postgresql">
    <sql>CREATE INDEX CONCURRENTLY idx_users_email ON users(email)</sql>
</changeSet>

<changeSet id="2" author="dev" dbms="mysql">
    <sql>CREATE INDEX idx_users_email ON users(email)</sql>
</changeSet>
```

**Winner: Liquibase** (better multi-database abstraction)

## Best Practices Summary

### ✅ Flyway Best Practices:

1. **Use SQL for simple migrations** - leverage database features
2. **Java migrations for complex logic** - when SQL insufficient
3. **Version with timestamps** - avoid conflicts in teams
4. **Manual rollback strategy** - plan before migrating
5. **Keep migrations small** - easier to understand and rollback
6. **Test with Testcontainers** - not just H2
7. **Run separately in production** - init containers or jobs
8. **Document database-specific** features used

### ✅ Liquibase Best Practices:

1. **Use abstracted change types** - when supporting multiple DBs
2. **SQL for database-specific** - don't force abstraction
3. **Always include rollback** - even if not used
4. **Use preconditions** - prevent execution errors
5. **Context/labels for environments** - dev, staging, prod
6. **Master changelog pattern** - organize by version/feature
7. **Validate before deployment** - use updateSQL
8. **Test rollback procedures** - don't assume they work

## Interview Questions

**Q1: What are the main differences between Flyway and Liquibase?**

Flyway is SQL-first with minimal complexity - migrations are simple SQL files with version numbers. Liquibase uses declarative XML/YAML with change type abstraction for database portability. Flyway has easier learning curve, Liquibase has more features (rollback, diff, preconditions) in Community edition but is more complex.

**Q2: When would you choose Flyway over Liquibase?**

Choose Flyway when: (1) single database with no portability needs, (2) team has strong SQL skills and wants full control, (3) simplicity is priority over features, (4) microservices with independent schemas, (5) quick prototyping/MVP. Flyway's SQL-first approach is faster to learn and simpler to maintain.

**Q3: When would you choose Liquibase over Flyway?**

Choose Liquibase when: (1) supporting multiple databases (PostgreSQL, MySQL, Oracle), (2) need rollback in Community edition, (3) need schema diffing and generation, (4) want declarative approach with change type abstraction, (5) team prefers structured formats over SQL, (6) need preconditions and complex conditional logic.

**Q4: How do rollback capabilities differ between Flyway and Liquibase?**

Liquibase has built-in rollback in Community edition using rollback tags - can rollback to tags, specific changesets, or by count. Flyway Community requires manual rollback via forward-fix migrations. Flyway Teams ($950/year) provides undo migrations (U prefix files) similar to Liquibase.

**Q5: What's the learning curve difference between Flyway and Liquibase?**

Flyway: 1-2 days to productivity - just write SQL files with V prefix. Liquibase: 1-2 weeks to productivity - must learn XML/YAML syntax, change types, preconditions, contexts/labels. Flyway is simpler but less featured; Liquibase is more complex but more powerful. Choose based on team skills and requirements.
