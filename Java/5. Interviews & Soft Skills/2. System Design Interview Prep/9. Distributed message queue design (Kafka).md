# Distributed Message Queue Design (Kafka)

> **Applies to:** Java 17+ · Apache Kafka 3.x–4.x · **Last updated:** 2026-11-21

> ⚠️ **About the numbers in this guide:** throughput, latency and sizing figures are back-of-envelope assumptions for an interview discussion, not measured benchmarks. Measure on your own hardware and workload before relying on them — see the [JMH guide](../../2.%20Modern%20Java%20Features/7.%20Performance%20%26%20Optimization/1.%20JMH%20%28Java%20Microbenchmark%20Harness%29.md) for how to benchmark properly.

## Overview

"Design a distributed message queue" (often phrased "design Kafka") is a classic system design question because it touches almost every distributed-systems topic in one problem: partitioning, replication, leader election, durability vs latency, consumer coordination, delivery semantics and storage efficiency.

This walkthrough designs a Kafka-like system — a **partitioned, replicated, append-only log** — and explains *why* each design decision is made, which is what interviewers are really testing.

**Queue vs log — decide this first:**

```text
Traditional queue (RabbitMQ, SQS):
  Message delivered → acked → deleted
  Broker tracks per-message state for every consumer
  Great for task distribution; no replay; fan-out needs one queue per subscriber

Distributed log (Kafka):
  Message appended → retained by time/size, independent of consumption
  Each consumer group tracks ONE number per partition (its offset)
  Fan-out and replay are free; the broker stays simple and fast

This design: a distributed log. Ask the interviewer if they want queue semantics
(per-message acks, deletion on consume) — if so, adjust section 6 accordingly.
```

**What makes a log fast:**

```text
1. Sequential disk I/O     — appends and sequential reads run near disk bandwidth
2. OS page cache           — recent data is read from memory, no application cache
3. Batching everywhere     — producers, brokers and consumers move batches, not messages
4. Zero-copy transfer      — sendfile() moves bytes from page cache to socket directly
5. Dumb broker, smart client — consumers track offsets; broker keeps no per-message state
```

## 1. Requirements Gathering

### 1.1 Clarifying questions

```text
1. "Is this a work queue (each message processed once by one worker) or a
    pub/sub event stream (many independent consumers)?"
   → Event stream: several services consume the same events independently.

2. "Do consumers need to replay old messages?"
   → Yes: new services backfill from history; consumers re-process after bug fixes.

3. "What ordering is required?"
   → Per entity (all events for one order in order). No global ordering needed.

4. "Delivery guarantee — can we lose messages? Can we duplicate them?"
   → No loss once a write is acknowledged. Duplicates acceptable (consumers idempotent);
     exactly-once is a bonus for stream-processing pipelines.

5. "Throughput, message size, retention?"
   → 1M messages/sec peak, ~1 KB average, 7-day retention.

6. "Latency requirements?"
   → End-to-end p99 < 100 ms is fine; throughput matters more than single-digit ms.

7. "Single region or multi-region?"
   → Single region, multi-AZ. Cross-region replication is a follow-up topic.
```

### 1.2 Confirmed requirements

```text
Functional:
  ✓ Producers publish messages to named topics, optionally with a key
  ✓ Consumers subscribe to topics; consumer groups share work
  ✓ Multiple consumer groups each receive every message
  ✓ Per-key ordering
  ✓ Replay from an earlier offset or timestamp
  ✓ Time/size-based retention; optional compaction (latest value per key)

Non-functional:
  ✓ Durability: acknowledged writes survive the loss of any single broker / AZ
  ✓ Availability: 99.95%+; automatic leader failover in seconds
  ✓ Throughput: 1M msg/s peak ingress, several times that in egress (fan-out)
  ✓ Horizontal scalability: add brokers and partitions without downtime
  ✓ Latency: p99 end-to-end < 100 ms

Out of scope (mention, don't design):
  ✗ Schema registry, stream processing, connectors
  ✗ Multi-region active-active replication
  ✗ Per-message TTL, priorities, delayed delivery
```

### 1.3 Scale estimation

```text
Ingress:
  Peak 1M msg/s × 1 KB = ~1 GB/s
  Average (assume 30% of peak) = ~300 MB/s

Replication (factor 3):
  Disk writes cluster-wide = 3 × ingress → ~3 GB/s peak

Egress:
  Assume 4 consumer groups read everything → ~4 GB/s peak reads
  Mostly served from page cache when consumers keep up

Storage (7-day retention, based on the average):
  300 MB/s × 86,400 s × 7 ≈ 181 TB of unique data
  × 3 replicas ≈ 544 TB of disk (+ headroom ≈ 700 TB)
  → Tiered storage (old segments in object storage) becomes attractive

Brokers (assumption: one broker comfortably sustains ~100 MB/s of
ingress including its replication traffic and consumer reads):
  1 GB/s / 100 MB/s ≈ 10 brokers for peak ingress
  Storage: 700 TB / (12 × 8 TB disks ≈ 96 TB per broker) ≈ 8 brokers
  → ~12–15 brokers spread over 3 AZs, with headroom for failures

Partitions:
  Target per-partition throughput ~10 MB/s for producers and consumers
  1 GB/s / 10 MB/s ≈ 100 partitions across busy topics (more for parallelism)
```

## 2. High-Level Architecture

```text
                         ┌────────────────────────────────────────┐
                         │     Controller quorum (KRaft, 3 nodes)  │
                         │  topics, partitions, leaders, ISR, ACLs │
                         └───────────────┬────────────────────────┘
                                         │ metadata log
          ┌──────────────────────────────┼──────────────────────────────┐
          ▼                              ▼                              ▼
   ┌─────────────┐                ┌─────────────┐                ┌─────────────┐
   │  Broker 1   │                │  Broker 2   │                │  Broker 3   │
   │ AZ-a        │                │ AZ-b        │                │ AZ-c        │
   │ orders-0 L  │◄──replicate────│ orders-0 F  │                │ orders-0 F  │
   │ orders-1 F  │────replicate──►│ orders-1 L  │                │ orders-1 F  │
   │ orders-2 F  │                │ orders-2 F  │────replicate──►│ orders-2 L  │
   └─────▲───────┘                └─────▲───────┘                └─────▲───────┘
         │ produce / fetch (to partition leaders)                      │
   ┌─────┴──────────┐                                    ┌─────────────┴────────┐
   │   Producers    │                                    │ Consumer groups      │
   │ (batch, key →  │                                    │ billing: C1, C2      │
   │  partition)    │                                    │ shipping: C3         │
   └────────────────┘                                    └──────────────────────┘

L = leader replica, F = follower replica
```

Core components:

| Component | Responsibility |
|---|---|
| **Producer client** | Chooses the partition (by key hash), batches and compresses records, retries with idempotence |
| **Broker** | Stores partition replicas as segment files; serves produce requests (leaders) and fetch requests; replicates as follower |
| **Controller quorum** | Source of truth for cluster metadata; elects partition leaders; handles broker join/leave |
| **Group coordinator** | A broker role per consumer group: membership, partition assignment, committed offsets |
| **Consumer client** | Pulls batches from partition leaders, processes, commits offsets |

Every partition has exactly one leader at a time; clients fetch metadata to learn which broker leads which partition and talk to it directly — there's no central proxy in the data path.

## 3. Storage: The Partitioned Log

### 3.1 Why partitions

```text
One log per topic would cap throughput at one disk/one broker and serialize
all consumers. Partitioning the topic:
  ✓ spreads writes and reads across brokers (horizontal scale)
  ✓ is the unit of parallelism for consumers (one consumer per partition per group)
  ✓ is the unit of ordering (order guaranteed within a partition only)
  ✓ is the unit of replication and leadership
```

### 3.2 Segments and indexes

A partition is a directory of **segment** files. Only the newest (active) segment is written to; older segments are immutable and are deleted or compacted as a whole.

```text
orders-0/
  00000000000000000000.log        ← records, offsets 0 … 1,048,575
  00000000000000000000.index      ← sparse offset → byte position
  00000000000000000000.timeindex  ← sparse timestamp → offset
  00000000000001048576.log        ← active segment (appends go here)
  00000000000001048576.index
  00000000000001048576.timeindex
```

- The segment file name is its **base offset**.
- The **offset index** is sparse (an entry every few KB): to read offset N, binary-search the segment list by base offset, binary-search the index for the nearest entry ≤ N, then scan forward a few KB.
- The **time index** supports "replay from timestamp T".
- Segments roll at a size (default 1 GiB) or age limit, which keeps deletion cheap: retention deletes whole files instead of rewriting data.

### 3.3 Why it's fast

```text
Write path:  append to the end of the active segment (sequential write)
             → data goes to the OS page cache; the OS flushes to disk asynchronously
             → durability comes from REPLICATION, not from fsync on every write

Read path:   consumers that keep up read data that's still in the page cache
             → sendfile() copies page cache → NIC without going through the JVM heap
             → batches stay compressed end-to-end (broker doesn't decompress)

No per-message bookkeeping on the broker:
  a consumer's state is one offset per partition, stored as a normal record
```

### 3.4 Retention and compaction

| Policy | Mechanism | Use |
|---|---|---|
| Delete (time/size) | Delete whole segments older than `retention.ms` or beyond `retention.bytes` | Event streams |
| Compact | Background cleaner rewrites old segments keeping only the latest record per key; `null` value = tombstone deletes the key | Changelogs, current-state topics, consumer offsets |

### 3.5 Tiered storage

At hundreds of TB, keeping everything on broker disks is expensive and makes broker replacement slow (re-replicating TBs). **Tiered storage** keeps recent segments on local disk and moves older, closed segments to object storage (S3, GCS), while consumers still read them through the broker. Brokers become lighter, recovery faster, and retention can grow cheaply. (Kafka implements this via KIP-405.)

## 4. Producer Path

### 4.1 Choosing the partition

```text
key != null  → partition = murmur2(key) % numPartitions
               → same key, same partition → per-key ordering
key == null  → "sticky" partitioning: fill a batch for one partition, then switch
               → large batches, even spread over time, no ordering guarantee
```

⚠️ Changing `numPartitions` changes the mapping for new records, breaking per-key ordering across the change. Over-provision partitions for keyed topics up front.

### 4.2 Batching and compression

```text
Producer accumulates records per partition into batches:
  batch.size  — max bytes per batch (e.g. 64 KB)
  linger.ms   — max wait to fill a batch (e.g. 5–10 ms)
  compression — lz4 / zstd per batch (JSON often compresses 3–5×)

One produce request carries batches for many partitions led by the same broker.
Trade-off: a few ms of latency for much higher throughput and less I/O.
```

### 4.3 Acknowledgements and durability

| `acks` | Producer waits for | Risk |
|---|---|---|
| `0` | Nothing | Lost on any failure |
| `1` | Leader wrote it | Lost if leader dies before followers copy it |
| `all` | All in-sync replicas | Survives loss of all but one ISR member |

Combined with `min.insync.replicas = 2` and replication factor 3: a write succeeds only when at least 2 replicas have it; with only 1 replica in sync, writes are **rejected** rather than accepted unsafely.

### 4.4 Idempotent producer

Retries after a lost acknowledgement would duplicate records. The broker assigns each producer an ID; the producer numbers batches per partition (sequence numbers). The leader keeps the last few sequence numbers per producer and partition and drops duplicates, which also prevents reordering on retry.

## 5. Replication and Failover

### 5.1 Leader–follower replication

```text
Followers continuously FETCH from the leader (the same protocol consumers use).

Leader tracks for each follower the offset it has fetched up to.
ISR (in-sync replicas) = replicas that have caught up within replica.lag.time.max.ms (30 s default).

High watermark (HW) = highest offset replicated to ALL ISR members.
  - Consumers can only read up to the HW → they never see data that could be lost on failover.
  - acks=all completes when the HW passes the record.
```

```text
Offsets:          0   1   2   3   4   5   6
Leader log:      [x] [x] [x] [x] [x] [x] [x]   LEO = 7
Follower A:      [x] [x] [x] [x] [x]           LEO = 5
Follower B:      [x] [x] [x] [x] [x] [x]       LEO = 6
High watermark = min(LEO of ISR) = 5 → consumers can read offsets 0..4
```

### 5.2 Leader failure

```text
1. Controller detects the broker is gone (missed heartbeats to the controller quorum).
2. For each partition it led, the controller picks a new leader FROM THE ISR.
3. Controller bumps the partition's leader epoch and publishes the change in the metadata log.
4. Clients refresh metadata (they get NOT_LEADER errors) and switch to the new leader.
5. Followers truncate any uncommitted tail that diverges from the new leader,
   using leader epochs to find the divergence point, then re-sync.

Typical failover: a few seconds.
```

**Unclean leader election:** if *no* ISR member is alive, choose between waiting for one (unavailable, no data loss) or electing an out-of-sync replica (available, loses acknowledged data). Kafka defaults to waiting (`unclean.leader.election.enable=false`) — durability over availability.

### 5.3 Rack/AZ awareness

Place the 3 replicas of every partition in 3 different AZs. Losing an entire AZ then leaves 2 in-sync replicas — still writable with `min.insync.replicas=2`. Consumers can be configured to fetch from a follower in their own AZ to save cross-AZ traffic costs.

## 6. Consumer Path

### 6.1 Pull, not push

```text
Pull (Kafka):  consumer asks "give me up to N bytes from offset X"
  ✓ consumers control their own rate → natural back-pressure
  ✓ batch size adapts to how far behind the consumer is
  ✓ replay = fetch from an older offset; no broker-side state
  ✗ needs long polling to avoid busy-waiting (fetch.max.wait.ms)

Push (traditional brokers): broker sends as fast as it can
  ✗ broker must track per-consumer rate and buffers; slow consumers get overwhelmed
```

### 6.2 Consumer groups and assignment

```text
Topic orders: 6 partitions

Group "billing" (3 consumers):   C1 ← P0,P1   C2 ← P2,P3   C3 ← P4,P5
Group "shipping" (1 consumer):   C4 ← P0..P5

Rules:
  - each partition is assigned to exactly one consumer in a group
  - more consumers than partitions → idle consumers
  - groups are independent: every group sees every record
```

The **group coordinator** (the broker leading the internal offsets-topic partition that the group ID hashes to) manages membership via heartbeats and triggers **rebalances** when members join, leave or crash. Rebalance designs:

| Approach | Behaviour |
|---|---|
| Eager (classic) | Everyone gives up all partitions, then gets a new assignment — a short stop-the-world pause |
| Cooperative / incremental | Only partitions that actually move are revoked |
| Broker-driven protocol (Kafka 4.x, KIP-848) | The coordinator computes assignments and reconciles them incrementally; clients stay simple |
| Static membership | A restarting instance with the same `group.instance.id` gets its partitions back without a rebalance |

### 6.3 Offset management

```text
Committed offsets are stored as records in an internal, compacted topic
(__consumer_offsets), keyed by (group, topic, partition).

Commit AFTER processing  → at-least-once (crash → reprocess from last commit)
Commit BEFORE processing → at-most-once  (crash → skip uncommitted work)
```

The offsets topic is itself partitioned and replicated, so committing scales with the cluster and survives failures — no separate database needed.

### 6.4 Consumer lag

`lag = log-end offset − committed offset` per partition. It's the key health metric: growing lag means consumers can't keep up (scale out up to the partition count, or speed up processing).

## 7. Delivery Semantics and Exactly-Once

```text
At-most-once:   commit before processing; acks=0/1 producers
At-least-once:  acks=all + retries; commit after processing          ← default target
Exactly-once (Kafka → Kafka):
  idempotent producer (no duplicates from retries)
  + transactions: output records AND consumer offsets committed atomically
  + consumers use isolation.level=read_committed (skip aborted data)
```

How transactions work at a high level:

```text
1. Producer registers a transactional.id with a transaction coordinator
   (fences off older "zombie" instances with the same id).
2. Producer writes records to several partitions; coordinator logs which partitions are involved.
3. Producer sends the consumer's offsets to the transaction as well.
4. Commit: coordinator writes PREPARE_COMMIT to its log, then COMMIT markers into every
   involved partition. read_committed consumers only see records once the marker lands.
```

Exactly-once stops at the Kafka boundary. Side effects in a database or another API still need idempotent consumers (dedup keys, upserts) or the **transactional outbox** pattern on the producer side.

## 8. Metadata and Coordination

```text
Cluster metadata: topics, partition counts, replica assignments, leaders, ISR,
                  configs, ACLs, broker registrations.

KRaft design (Kafka 3.3+ production, ZooKeeper removed in 4.0):
  - 3 or 5 controller nodes run a Raft quorum
  - metadata changes are records in a replicated metadata log
  - the active controller makes decisions; brokers replay the log to stay in sync
  - controller failover = Raft leader election (fast; state already replicated)

Why not ZooKeeper anymore: a second distributed system to operate, metadata
loading on controller failover was slow at large partition counts, and the
metadata log model scales to millions of partitions.
```

Interview point: the data plane (produce/fetch to partition leaders) is decentralized; only metadata decisions go through the controller.

## 9. Scaling and Bottlenecks

| Problem | Symptom | Solution |
|---|---|---|
| Hot partition | One partition's leader saturates; lag on one partition | Better key (add a suffix / salt for very hot keys, accepting weaker ordering), more partitions, split the topic |
| Too few partitions | Can't add consumers; throughput capped | Create topics with headroom; for keyed topics plan the count up front |
| Too many partitions | Slow failover, high memory and file-handle use | Budget partitions per broker; consolidate tiny topics |
| Broker disk full | Writes fail | Retention limits, tiered storage, add brokers and reassign partitions |
| Unbalanced cluster | Some brokers hot after adding nodes | Partition reassignment / automated rebalancing (e.g. Cruise Control) |
| Slow consumers | Lag grows; reads hit disk instead of page cache | Scale consumers (≤ partitions), batch processing, separate slow side effects |
| Cross-AZ cost | Large network bills | Rack-aware replica placement, follower fetching from local AZ |

**Adding a broker** doesn't move data automatically: new partitions land on it, existing ones must be **reassigned**, which copies replicas in the background (throttled so it doesn't starve production traffic).

| Metric | Alert when |
|---|---|
| Under-replicated partitions | > 0 for minutes (a broker is down or lagging) |
| Offline partitions | > 0 (no leader → data unavailable) |
| Active controller count | ≠ 1 |
| Consumer lag (per group) | Growing steadily, or time lag above the SLO |
| Produce/fetch request latency p99 | Above the latency budget |
| Disk usage | > 75–80% |
| ISR shrink/expand rate | Frequent (flapping replicas) |
| Request handler / network thread idle % | Low (broker saturated) |

## 11. Interview Questions

**Q: Why does Kafka write to the page cache and rely on replication instead of fsync-ing every message?**

A: Calling fsync for every message would make each write wait for the physical disk, limiting a broker to a few thousand writes per second even on SSDs, and batching would only partly hide it. Kafka instead appends to the OS page cache — a memory write — and lets the operating system flush to disk in the background. Durability comes from replication across brokers in different failure domains: with `acks=all`, replication factor 3 and `min.insync.replicas=2`, an acknowledged record exists in the memory or disk of at least two machines in different availability zones. Losing it would require those machines to fail simultaneously before the OS flushes, which is far less likely than a single disk or broker failure. This trade buys sequential, batched I/O at near-disk bandwidth, and it also means recently written data is already in memory for consumers that keep up, so most reads never touch the disk. Teams with extreme durability needs can still configure periodic or per-message flushes per topic, at a large throughput cost.

---

**Q: How does Kafka guarantee that consumers never see data that's later lost on leader failover?**

A: Through the high watermark. The leader tracks how far each in-sync follower has replicated, and the high watermark is the highest offset present on every in-sync replica. Consumers can only fetch up to the high watermark. If the leader dies, the controller elects a new leader from the ISR — and every ISR member, by definition, has all records up to the high watermark — so everything consumers have seen survives. Records above the high watermark on the old leader might not exist on the new one; followers that had them truncate back to the new leader's log, using leader epochs to find exactly where the logs diverged. Producers with `acks=all` were never told those records succeeded, so they retry them, and the idempotent producer prevents duplicates when the retry lands. The design deliberately refuses to elect an out-of-sync replica by default, choosing temporary unavailability over losing acknowledged data.

---

**Q: How do you choose the number of partitions for a topic?**

A: Partitions set the ceiling on parallelism, so start from throughput: estimate the topic's peak bytes per second, divide by what one consumer instance can process per partition (measured, e.g. 5–10 MB/s for a typical service, often much less if each record triggers a database write), and do the same for producer throughput per partition. Take the larger number and add headroom for growth, because increasing partitions later changes the key-to-partition mapping and breaks ordering for keyed topics. Then sanity-check the cost: each partition adds replication traffic, open files, memory and leader-election work, and very high counts slow down failover and rebalancing. Consumer-group size matters too — there's no benefit to 200 partitions if you'll run at most 12 consumers, except as growth headroom. A common outcome is a small multiple of the expected maximum consumer count, for example 12, 24 or 48, chosen so it divides evenly among likely group sizes.

---

**Q: What happens when a consumer in a group crashes, and how do you avoid duplicate processing?**

A: The group coordinator stops receiving the crashed consumer's heartbeats and, after the session timeout, removes it and triggers a rebalance; its partitions are reassigned to the remaining members. They resume from the last committed offsets of those partitions, so any records the crashed consumer processed after its last commit are delivered again — that's at-least-once delivery. Duplicates are therefore expected and must be handled in the consumer: store a processed-message ID in the same database transaction as the side effect, use upserts keyed by business IDs, or ignore events whose version is not newer than what's stored. Committing more often narrows the window but can't close it. When the processing itself only reads and writes Kafka topics, transactions can make it exactly-once by committing the output records and the input offsets atomically. Rebalance-related duplicates can also be reduced with cooperative assignment and static membership, so short restarts don't move partitions at all.

---

**Q: How would you support "replay all events from last Tuesday" for a new service?**

A: Because the log retains data independently of consumption, a new consumer group can start anywhere in the retained history. The time index in each segment maps timestamps to offsets, so the client asks the broker for the offset of the first record at or after Tuesday 00:00 for each partition and starts fetching from there; existing groups are unaffected because offsets are tracked per group. The important prerequisites are design decisions made earlier: retention must cover the period (7 days in this design, or longer with tiered storage), the events must be self-contained enough to rebuild state, and the new service's handlers must be idempotent and tolerate high throughput during catch-up. For state that must be rebuildable indefinitely, a compacted topic keeps the latest record per key forever, so a new service can bootstrap current state from it and then follow the live event stream.

---

**Q: Kafka vs RabbitMQ vs NATS — when would your design be the wrong choice?**

A: A log-based design shines for high-throughput event streams with several independent consumers and replay. It's a poorer fit when the workload is a classic task queue with per-message behaviour: priorities, per-message TTLs, delayed retries, or many consumers sharing one small stream where ordering doesn't matter. Because the unit of parallelism is the partition, scaling a queue of slow jobs to 500 workers needs 500 partitions, and a single slow or poison message blocks its partition. Brokers like RabbitMQ or SQS track each message's state and let any number of workers compete for messages, with dead-lettering built in. Kafka 4.x is adding share groups (queue-like consumption with per-record acknowledgement) to address this, but for many job-queue workloads a traditional broker is simpler. NATS is the better fit at the other end of the spectrum: when the requirement is low-latency service-to-service communication rather than a durable event history. Core NATS offers subject-based pub/sub, queue groups for load balancing and built-in request/reply with sub-millisecond latency, but it's at-most-once — nothing is stored. Its JetStream layer adds replicated streams, durable consumers with acks, replay and publish de-duplication in the same lightweight server, which covers moderate event-streaming and work-queue needs, edge and multi-region setups via leaf nodes, and small operational footprints. I'd still choose this Kafka-style design for very large retained data sets, long retention and the stream-processing and data-integration ecosystem around Kafka.

---

## 12. Key Takeaways

- **Log, not queue**: an append-only, retained log makes fan-out and replay free; the broker tracks one offset per partition per group instead of per-message state
- **Partition = unit of ordering, parallelism, replication**: key by the entity that needs ordering; size partition counts up front for keyed topics
- **Fast by design**: sequential appends, OS page cache, batching + compression end to end, zero-copy reads
- **Durability via replication**: RF 3 across AZs, `acks=all`, `min.insync.replicas=2`; ISR + high watermark ensure consumers only see data that survives failover
- **Failover**: controller elects a new leader from the ISR; leader epochs truncate divergent tails; unclean election off by default (consistency over availability)
- **Pull-based consumers**: natural back-pressure and replay; consumer groups split partitions; offsets stored in a compacted internal topic
- **Delivery semantics**: at-least-once + idempotent consumers in practice; idempotent producer + transactions give exactly-once within Kafka only
- **Metadata via a Raft quorum (KRaft)**: decisions centralized in the controller, data path fully decentralized
- **Scale levers**: more brokers + partition reassignment, tiered storage for long retention, rack-aware placement, watch for hot partitions
- **Health metrics**: under-replicated and offline partitions, consumer lag, request latency, disk usage
