# Distributed Task Queue Design (RabbitMQ)

> **Applies to:** Java 17+ · RabbitMQ 3.13–4.x · **Last updated:** 2026-11-21

> ⚠️ **About the numbers in this guide:** throughput, latency and sizing figures are back-of-envelope assumptions for an interview discussion, not measured benchmarks. Measure on your own hardware and workload before relying on them — see the [JMH guide](../../2.%20Modern%20Java%20Features/7.%20Performance%20%26%20Optimization/1.%20JMH%20%28Java%20Microbenchmark%20Harness%29.md) for how to benchmark properly.

## Overview

"Design a distributed task queue" (or "design a message broker like RabbitMQ", "design a background job system") is the queue-shaped sibling of [designing Kafka](9.%20Distributed%20message%20queue%20design%20%28Kafka%29.md). Instead of a retained log that many readers scan, the core abstraction is a **queue of individual messages**, each delivered to one worker, acknowledged, and then deleted. The interesting problems are per-message: routing, acknowledgements and redelivery, fair distribution, retries with delay, poison messages, priorities and flow control.

This walkthrough designs a RabbitMQ-like broker plus the worker side, and explains the trade-offs interviewers probe.

**Queue vs log — why this design is different from Kafka:**

```text
Distributed log (Kafka):
  Consumer state = one offset per partition → broker is simple, replay is free
  Parallelism = number of partitions; one slow message blocks its partition

Task queue (RabbitMQ):
  Broker tracks EVERY message: ready → unacked → acked (deleted) / requeued / dead-lettered
  Parallelism = number of workers; any idle worker takes the next message
  Per-message features: routing, TTL, priority, delayed retry, dead-lettering
  No replay: an acked message is gone
```

**Typical workloads:** sending emails and push notifications, generating PDFs and thumbnails, video transcoding, payment captures, webhook delivery, data imports — work that must happen once, reliably, by any available worker.

## 1. Requirements Gathering

### 1.1 Clarifying questions

```text
1. "What kinds of tasks? How long does a task take?"
   → Mixed: emails (~100 ms), PDF generation (~2 s), video transcoding (minutes).

2. "Must every task run exactly once? Can we lose tasks?"
   → No loss once enqueue is acknowledged. Duplicates possible but rare;
     task handlers will be idempotent.

3. "Do tasks need ordering?"
   → Mostly no. Some flows (e.g. per-account ledger updates) need per-key order.

4. "Retries? Delays? Scheduling?"
   → Retries with exponential backoff; delayed tasks ("send reminder in 1 hour");
     failed tasks parked for inspection.

5. "Priorities?"
   → Yes: password-reset emails before newsletters.

6. "Who produces tasks, and do consumers need routing rules?"
   → Many services; tasks routed by type and region to dedicated worker pools.

7. "Throughput and backlog?"
   → 50K tasks/sec peak; backlogs of millions during outages must not take the system down.
```

### 1.2 Confirmed requirements

```text
Functional:
  ✓ Enqueue a task with a type, payload, optional priority, optional delay
  ✓ Route tasks to queues by type/region/pattern; several queues may receive a copy
  ✓ Workers pull tasks, acknowledge on success, reject on failure
  ✓ Automatic redelivery if a worker dies mid-task
  ✓ Retries with backoff; dead-letter queue after N failures
  ✓ Priorities within a queue
  ✓ Per-key ordering for selected task types

Non-functional:
  ✓ Durability: an acknowledged enqueue survives the loss of a broker node
  ✓ Availability: 99.95%; queue failover in seconds
  ✓ Throughput: 50K tasks/s peak enqueue and dequeue
  ✓ Latency: p99 enqueue → start of processing < 50 ms when workers are available
  ✓ Graceful degradation under backlog (bounded memory, back-pressure to producers)

Out of scope (mention, don't design):
  ✗ Replay of completed tasks (use an event log for that)
  ✗ Cron-style recurring schedules (separate scheduler that enqueues tasks)
  ✗ Multi-region active-active
```

### 1.3 Scale estimation

```text
Throughput:
  50K tasks/s peak × 2 KB average payload = ~100 MB/s in and out
  Quorum queues replicate to 3 nodes → ~300 MB/s of replicated writes cluster-wide

Backlog (worst case: workers down for 1 hour at peak):
  50K × 3,600 = 180M tasks × 2 KB = ~360 GB
  → backlog must live on DISK, not in RAM; queues must page messages out of memory

Queues:
  ~50 task types × 3 regions + retry/wait/DLQ queues ≈ 500 queues

Nodes (assumption: one node sustains ~15–20K persistent, replicated msg/s):
  50K / 15K ≈ 4 nodes for throughput → 5 nodes (odd number for Raft majorities)
  Spread queue leaders evenly across nodes (a single queue is bound to one leader node)

Workers:
  Little's law: concurrency = arrival rate × processing time
  Emails: 30K/s × 0.1 s = 3,000 concurrent handlers
  PDFs:    2K/s × 2 s   = 4,000 concurrent handlers
  → worker pools sized per task type, autoscaled on queue depth
```

## 2. High-Level Architecture

```text
 Producers (services)
   │  publish(exchange="tasks", routingKey="email.password-reset.eu", props: priority, ttl)
   ▼
┌───────────────────────────────────────────────────────────────────────┐
│                     Broker cluster (5 nodes, 3 AZs)                   │
│                                                                       │
│  Exchange "tasks" (topic)                                             │
│     ├─ "email.*.eu"     ──► queue email.eu      (quorum, R3, leader n1)│
│     ├─ "pdf.*.eu"       ──► queue pdf.eu        (quorum, R3, leader n2)│
│     └─ "video.#"        ──► queue video         (quorum, R3, leader n3)│
│                                                                       │
│  Each queue: DLX → retry/wait queues → back to work queue; DLQ        │
│  Metadata store (Raft): users, vhosts, exchanges, bindings, policies  │
└───────────────────────────────────────────────────────────────────────┘
   │  deliver (prefetch-limited)          ▲ ack / nack / reject
   ▼                                       │
 Worker pools (per task type, autoscaled on queue depth)
```

Core components:

| Component | Responsibility |
|---|---|
| **Producer client** | Publishes to an exchange with a routing key; waits for **publisher confirms** |
| **Exchange** | Stateless router: matches the routing key against bindings and copies the message into matching queues |
| **Queue** | Ordered, durable buffer with per-message state (ready, unacked); replicated via Raft (quorum queue) |
| **Metadata store** | Cluster-wide definitions: exchanges, queues, bindings, users, policies (RabbitMQ 4.x can use Khepri, a Raft-based store that replaces Mnesia) |
| **Consumer/worker** | Holds a channel with a prefetch limit; acks after processing |

Clients connect to any node; if the queue's leader lives on another node, traffic is forwarded inside the cluster. For efficiency, workers for a busy queue should connect to the node hosting its leader (or use a load balancer plus enough nodes that forwarding is cheap).

## 3. Routing: Exchanges and Bindings

Routing is decided by the broker, so producers only know an exchange name and a routing key — not which queues or services exist.

| Exchange type | Matches | Example |
|---|---|---|
| Direct | Exact routing key | `pdf.invoice` → queue `pdf` |
| Topic | Patterns: `*` = one word, `#` = zero or more words | `email.*.eu`, `video.#` |
| Fanout | Every bound queue | Broadcast "cache invalidated" to all services |
| Headers | Message headers (`x-match: all/any`) | Route on `tenant=acme, tier=gold` |

```text
Design choices to call out in an interview:
  - One topic exchange per domain ("tasks", "notifications") with structured keys
    <type>.<subtype>.<region>, so new worker pools can bind without producer changes.
  - Routing happens once per message at publish time: cost grows with the number
    of bindings for topic exchanges (trie-based matching keeps it cheap).
  - Unroutable messages are silently dropped unless the publisher sets "mandatory"
    (message returned) or the exchange has an alternate exchange.
```

## 4. Queue Storage and Message Lifecycle

### 4.1 Per-message state

```text
             publish                deliver                 ack
 (producer) ────────► READY ───────────────► UNACKED ───────────► deleted
                        ▲                        │
                        │  nack(requeue) /       │ reject(no requeue) / TTL expired /
                        │  consumer connection   │ delivery limit exceeded
                        │  lost                  ▼
                        └────────────────── dead-letter exchange → retry or DLQ
```

The broker must persist this state durably and replicate it — that's the main cost compared with a log, where the broker only stores records and consumers store an offset.

### 4.2 Quorum queues (replicated with Raft)

```text
Queue "email.eu": Raft group of 3 members on nodes n1 (leader), n2, n4

Enqueue:   leader appends the command to its Raft log → replicates to followers
           → committed once a MAJORITY (2 of 3) has it → publisher confirm sent
Deliver:   leader assigns ready messages to consumers (state change also logged)
Ack:       logged and replicated; message state becomes "settled"
Snapshots: the log is truncated periodically so it doesn't grow forever

Leader failure: remaining members elect a new leader (Raft); in-flight unacked
messages are returned to READY and redelivered with redelivered=true.
```

Why Raft rather than primary-backup mirroring: a majority quorum gives a clear, safe rule for which writes are committed and which node can become leader, avoiding the split-brain and data-loss modes of the old mirrored queues (removed in RabbitMQ 4.0).

### 4.3 Memory vs disk

```text
Messages are written to the queue's on-disk log; recent ones are also cached in memory
for fast delivery. Under backlog, memory holds only metadata and a small window —
bodies are read back from disk when delivered.

Node-level protection:
  memory high watermark (e.g. 40% of RAM)  → block publishing connections
  disk free limit                           → block publishing connections
  → producers see back-pressure instead of the broker crashing
```

### 4.4 Streams (when you need log semantics too)

RabbitMQ also offers **streams**: replicated, append-only logs with offset-based, non-destructive reads. They give Kafka-like replay and high fan-out inside the same broker — useful for an audit trail of tasks — but the core of this design remains queues.

## 5. Producer Path

```text
1. Producer publishes with deliveryMode=persistent and a unique messageId.
2. Broker routes to queues; each quorum queue commits the message (majority).
3. Broker sends a publisher CONFIRM (ack) once ALL target queues have committed it,
   or a NACK if it couldn't be stored. With "mandatory", unroutable → RETURN.
4. Producer keeps the message until confirmed; on timeout or nack it republishes.
   → at-least-once enqueue; duplicates possible → consumers dedupe on messageId.
```

Confirms are asynchronous and batched: a producer keeps many publishes in flight and processes confirms as they arrive (by delivery tag), so throughput isn't limited by round-trips.

**Enqueue consistent with the database:** a service that writes an order and enqueues "send confirmation email" can't make both atomic. Use a **transactional outbox**: insert the task into an outbox table in the same DB transaction, and a relay publishes it with confirms.

## 6. Consumer Path

### 6.1 Push with prefetch (credit-based flow control)

```text
Worker opens a channel with prefetch = N (basic.qos)
Broker pushes up to N unacked messages to that worker, then waits for acks
Each ack frees one slot → broker pushes the next message

prefetch = 1      → fair dispatch: a slow task never hoards others; lowest throughput
prefetch = 10-50  → good default for short tasks
prefetch = 250+   → high throughput for tiny, fast tasks; risk of uneven load
```

Unlike Kafka's pull model, the broker pushes — but prefetch turns it into credit-based flow control, so fast workers get more work and slow ones get less, automatically.

### 6.2 Acknowledgements and redelivery

| Worker action | Broker result |
|---|---|
| `ack` | Message deleted |
| `nack(requeue=true)` | Back to READY and redelivered (position depends on the queue type) |
| `reject/nack(requeue=false)` | Dead-lettered (if a DLX is set) or dropped |
| Connection/channel closes with unacked messages | All of them return to READY with `redelivered=true` |

AMQP itself has no per-message ack deadline, but RabbitMQ enforces a **consumer timeout** (default 30 minutes): a channel holding a delivery unacked for longer is closed and the message is redelivered. Long-running tasks (video transcoding) need it raised for their queue, or a different design — see section 9.

### 6.3 Competing consumers and autoscaling

All workers of a pool consume from the same queue; any idle worker takes the next message. Scale on **queue depth and age of the oldest message** (e.g. KEDA RabbitMQ scaler). There's no partition limit on consumers, unlike Kafka.

## 7. Retries, Delays and Dead Letters

### 7.1 Retry with exponential backoff

```text
email.eu ──fail (reject)──► DLX "tasks.retry" ──► wait queue "email.eu.wait.10s" (TTL 10s)
    ▲                                                     │ expired
    └──────────────── dead-lettered back to email.eu ─────┘

Attempt count tracked in the x-death header (per queue + reason).
Use one wait queue per delay tier (10s, 1m, 10m): with per-message TTLs, a short
TTL can be stuck behind a long one because only the head of a queue expires.
After N attempts → route to DLQ "email.eu.dlq" (no TTL; alert + manual replay).
```

### 7.2 Poison messages

A message that crashes the worker before it can reject it would be redelivered forever. Quorum queues track a **delivery count** and dead-letter (or drop) a message once it exceeds `delivery-limit` (default 20 in RabbitMQ 4.x) — the broker-side safety net.

### 7.3 Delayed tasks ("send reminder in 1 hour")

```text
Options:
  a) TTL wait queues per delay tier → dead-letter into the work queue
     ✓ built-in, durable   ✗ fixed tiers only
  b) Delayed-message exchange plugin (per-message x-delay)
     ✓ arbitrary delays    ✗ state held on one node; not for very large volumes
  c) External scheduler (DB table with run_at + poller, or Quartz) enqueues at due time
     ✓ arbitrary delays, queryable, cancellable   ✗ extra component
For long delays (hours/days) and cancellable reminders, (c) is usually the right answer.
```

## 8. Ordering and Priorities

### 8.1 Ordering

```text
One queue, one consumer       → FIFO (requeued messages can come back out of order)
One queue, many consumers     → no ordering across tasks
Single active consumer (SAC)  → FIFO with standbys for failover; throughput of one worker
Consistent-hash exchange      → hash(routing key or header) → one of N queues,
                                one consumer per queue → per-key ordering with parallelism
```

Per-account ledger updates: route by `account_id` through a consistent-hash exchange to 16 queues, each with a single active consumer.

### 8.2 Priorities

```text
Classic queues support x-max-priority (e.g. 0–10): higher-priority ready messages
are delivered first. Quorum queues support two priority levels (normal and high).

Caveats:
  - Priority only reorders READY messages; with a large prefetch, low-priority
    messages already sent to workers still run first → keep prefetch small.
  - Often simpler: separate queues and worker pools per priority
    (email.critical vs email.bulk) — isolates capacity, no starvation questions.
```

## 9. Scaling and Bottlenecks

| Problem | Symptom | Solution |
|---|---|---|
| One very hot queue | Its leader node is saturated; others idle | A queue is bound to one leader: shard into N queues (consistent-hash exchange or producer-side sharding) and spread leaders across nodes |
| Huge backlog | Memory/disk alarms block all publishers | Bound queues (`x-max-length` + `reject-publish`), separate workloads into different vhosts/clusters, scale workers |
| Long-running tasks (minutes–hours) | Consumer timeouts, redelivery storms after worker restarts | Raise consumer timeout per queue; better: task holds a **lease** in a DB, queue message only triggers work; checkpoint progress |
| Too many queues/connections | High memory per node | Pool channels, share connections, consolidate queue types |
| Publisher blocked by alarms | Upstream API latency spikes | Separate publish and consume connections; outbox decouples API from broker availability |
| Cross-AZ latency | Slower confirms | Quorum members in 3 AZs is the durability cost; keep payloads small |

**Scaling out:** adding nodes doesn't move existing queues automatically. New queues are placed on the new nodes, and existing quorum queues can grow/shrink members and rebalance leaders (`rabbitmq-queues rebalance quorum`).

## 10. Monitoring

| Metric | Alert when |
|---|---|
| Queue depth (ready) | Growing for N minutes, or above the SLO-derived threshold |
| Age of oldest message | Above the processing SLO (e.g. emails older than 2 minutes) |
| Unacked count | Consistently near `prefetch × workers` with low throughput (stuck workers) |
| DLQ depth | > 0 |
| Redelivery rate | Rising (workers crashing or timing out) |
| Memory / disk alarms | Any alarm (publishers are blocked) |
| Quorum queue members out of sync | Members lagging or missing |
| Publish confirm latency p99 | Above budget |

RabbitMQ's Prometheus plugin exposes per-queue and per-node metrics; scale workers on depth and oldest-message age.

## 11. Interview Questions

**Q: How does a task queue guarantee that a task isn't lost if a worker crashes halfway through?**

A: The broker only deletes a message when the consumer explicitly acknowledges it, and workers ack after the task finishes, not when they receive it. While a message is delivered but unacknowledged, the broker tracks it as "unacked" against that consumer's channel. If the worker process dies, its TCP connection closes, the broker notices the closed channel and moves all of that channel's unacked messages back to the ready state, marked as redelivered, so another worker picks them up. On the enqueue side, publisher confirms make sure a message was durably committed — on a quorum queue that means replicated to a majority of nodes — before the producer considers it sent, and producers republish anything that wasn't confirmed. Together this gives at-least-once execution, which means a crash after the task's side effect but before the ack causes a duplicate run, so tasks must be idempotent, typically by recording the message ID in the same transaction as the side effect.

---

**Q: Why use a prefetch limit, and how do you choose it?**

A: Without a limit, the broker pushes messages to consumers as fast as the network allows, so the first worker to connect can receive a huge chunk of the queue while others sit idle, and a crash returns all of those messages at once. Prefetch caps the number of unacknowledged messages per consumer, turning push delivery into credit-based flow control: each ack lets the broker send one more message. That gives fair distribution across workers and bounds memory on both sides. The right value depends on task duration relative to network round-trip time. For long tasks measured in seconds or minutes, prefetch 1 is best because there's no benefit to holding a second task, and it keeps distribution perfectly fair and priorities effective. For short tasks of a few milliseconds, a prefetch of tens to hundreds hides the round-trip latency and keeps workers busy. I'd start around 10–50 for typical business tasks and tune it while watching worker utilisation and the unacked count.

---

**Q: How would you implement retries with exponential backoff without blocking the queue?**

A: Retrying inside the worker by sleeping holds a worker and a delivery slot for the whole delay, and requeueing immediately just spins the failure. Instead, on failure the worker rejects the message without requeue, so the broker dead-letters it to a retry exchange that routes it into a wait queue with a fixed TTL, say 10 seconds. That wait queue has no consumers; when the message expires, its own dead-letter settings route it back to the original work queue. The broker records each pass in the `x-death` header, so the worker can read the attempt count and choose the next tier — 10 seconds, then 1 minute, then 10 minutes — or, after the maximum, publish it to a dead-letter queue for inspection. I'd use separate wait queues per delay tier because a queue only expires messages at its head, so mixing a 10-second and a 10-minute message in one queue would delay the short one. The quorum-queue delivery limit is a second safety net for messages that crash the worker before it can reject them.

---

**Q: A single queue receives 200K tasks per second and its node is overloaded. What do you do?**

A: In a broker like RabbitMQ a queue is a single ordered structure with one leader process on one node, so it can't be scaled across nodes by itself — the fix is to shard it. I'd create several queues, for example 16, bind them through a consistent-hash exchange or have producers pick a shard by hashing a key, and make sure the quorum-queue leaders are spread evenly across nodes. Worker pools consume from all shards, so total capacity grows with the number of nodes. If ordering per key matters, hashing by that key preserves it per shard, with a single active consumer per shard. I'd also check whether the load is really one workload: separating critical tasks from bulk tasks into their own queues and even their own cluster or vhost avoids one noisy workload's backlog triggering memory alarms that block everyone. And if the requirement is really a high-volume stream with many readers rather than a work queue, that's a sign a partitioned log like Kafka is the better tool.

---

**Q: When would you choose this queue-based design over a Kafka-style log, or over NATS?**

A: The queue design fits work distribution: each task should be done once by any available worker, tasks are independent, and per-message behaviour matters — routing by type and region, priorities, TTLs, delayed retries, dead-lettering — with worker pools that scale freely without being capped by partition counts, and one slow task not blocking others. A Kafka-style log is better when many independent consumers need the same events, when replay and long retention matter, or for very high sustained throughput and stream processing; its per-partition ordering and offset model make it simple and fast but poor at per-message handling. NATS suits low-latency request/reply and fan-out between services with a very small footprint; core NATS stores nothing, and its JetStream layer adds work-queue streams with acks and redelivery that can cover simpler task-queue needs. In practice many companies run a log for domain events and a task queue for background jobs, and the interview answer should tie the choice to requirements rather than to brand names.

## 12. Key Takeaways

- **Queue, not log**: the broker tracks every message (ready → unacked → acked/dead-lettered); parallelism comes from workers, not partitions
- **Routing in the broker**: producers publish to an exchange with a structured routing key; bindings decide which queues get copies
- **Durability**: persistent messages on quorum queues (Raft, majority commit) + publisher confirms + outbox for DB consistency
- **At-least-once execution**: ack after processing, automatic redelivery on worker crash, idempotent tasks with a message-ID dedup
- **Prefetch = flow control**: small for long tasks (fairness), larger for tiny tasks (throughput)
- **Retries without blocking**: reject → DLX → TTL wait queue per delay tier → back to work queue; DLQ after N attempts; delivery limit as a safety net
- **Ordering when needed**: single active consumer, or consistent-hash sharding with one consumer per shard
- **Priorities**: small prefetch, or separate queues/worker pools per priority
- **Scaling**: one queue = one leader node; shard hot queues, spread leaders, isolate noisy workloads; protect the cluster with bounded queues and memory/disk alarms
- **Monitor depth and age**: queue depth, oldest-message age, DLQ depth and redelivery rate drive alerts and autoscaling
