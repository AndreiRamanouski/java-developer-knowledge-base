# Real-Time Messaging System Design (NATS)

> **Applies to:** Java 17+ · NATS Server 2.10+ · **Last updated:** 2026-11-21

> ⚠️ **About the numbers in this guide:** throughput, latency and sizing figures are back-of-envelope assumptions for an interview discussion, not measured benchmarks. Measure on your own hardware and workload before relying on them — see the [JMH guide](../../2.%20Modern%20Java%20Features/7.%20Performance%20%26%20Optimization/1.%20JMH%20%28Java%20Microbenchmark%20Harness%29.md) for how to benchmark properly.

## Overview

"Design a real-time pub/sub system", "design the messaging backbone for microservices and IoT devices" or "design a system like NATS" is the third member of the messaging family, next to the [Kafka log](9.%20Distributed%20message%20queue%20design%20%28Kafka%29.md) and the [RabbitMQ task queue](10.%20Distributed%20task%20queue%20design%20%28RabbitMQ%29.md). The focus here is **connectivity**: routing millions of small messages per second between services and devices with minimal latency, request/reply without service discovery, multiple regions and edge sites, and tenant isolation — with persistence as an *optional* layer rather than the core.

**Three messaging designs, three cores:**

```text
Log (Kafka):         store everything, consumers track offsets      → replay, fan-out, streams
Queue (RabbitMQ):    store each task until one worker acks it       → work distribution, retries
Fabric (NATS):       route each message to current interest, now    → low latency, request/reply,
                     (persistence added per subject when needed)       location transparency, edge
```

**Key design idea:** in the core layer the server stores nothing. It keeps an in-memory index of *who is interested in which subjects* and forwards each message to the matching subscribers immediately. Everything else — clustering, multi-region, edge, multi-tenancy — is about propagating that interest efficiently. Durability (JetStream) is a separate, opt-in subsystem.

## 1. Requirements Gathering

### 1.1 Clarifying questions

```text
1. "What traffic patterns? Events, commands, queries?"
   → Service-to-service request/reply (queries, commands), event fan-out to many
     subscribers, telemetry from devices to the cloud, commands from cloud to devices.

2. "Latency targets?"
   → Request/reply p99 < 5 ms within a region (excluding handler time);
     fan-out delivery p99 < 10 ms.

3. "Is it acceptable to lose a message?"
   → For live telemetry and request/reply (client retries): yes, at-most-once is fine.
     For orders, payments and device commands: no — need durable, at-least-once delivery.

4. "Where are the clients?"
   → Microservices in 3 cloud regions; ~500 edge sites (stores, factories) with
     ~100 devices each and unreliable WAN links.

5. "Multi-tenancy?"
   → Yes: several business units and external partners; strict isolation,
     explicit sharing of selected subjects.

6. "Scale?"
   → ~5K service instances + 50K devices connected; 2M msg/s peak published,
     ~512 B average payload; average fan-out factor 3.
```

### 1.2 Confirmed requirements

```text
Functional:
  ✓ Publish/subscribe on hierarchical subjects with wildcards
  ✓ Load-balanced consumption (queue groups) without broker configuration
  ✓ Request/reply with fast failure when nobody can answer
  ✓ Optional persistence for selected subjects: replay, acks, redelivery, de-duplication
  ✓ Edge sites keep working locally when the WAN link is down
  ✓ Multi-tenant isolation with explicit cross-tenant sharing
  ✓ Small key-value store for configuration and coordination (nice to have)

Non-functional:
  ✓ Latency: sub-millisecond server-side routing; p99 request/reply < 5 ms in-region
  ✓ Throughput: 2M msg/s published, ~6M msg/s delivered
  ✓ Availability: no single point of failure; clients fail over automatically
  ✓ Operational simplicity: small footprint, runs at the edge on modest hardware
  ✓ Security: TLS everywhere, per-client permissions, decentralized credential management

Out of scope (mention, don't design):
  ✗ Long-term retention and analytics (ship to Kafka / a data lake via a bridge)
  ✗ Complex per-message features (priorities, per-message TTL routing)
```

### 1.3 Scale estimation

```text
Messages:
  2M msg/s × 512 B ≈ 1 GB/s ingress
  Fan-out factor 3 → 6M deliveries/s ≈ 3 GB/s egress across all regions

Per region (traffic split roughly evenly over 3 regions):
  ~670K msg/s in, ~2M deliveries/s out ≈ 1 GB/s egress

Servers per region (assumption: one server routes ~1M+ small msg/s and
~0.5–1 GB/s of egress on a modern multi-core VM, CPU and NIC bound):
  1 GB/s egress / ~0.5 GB/s per server → 2–3 servers for throughput
  → 3-5 servers per region for headroom, failure tolerance and JetStream Raft quorums

Connections:
  5K service instances + 50K devices
  Devices connect to their site's leaf node, not to the cloud
  → cloud servers see ~5K service connections + 500 leaf node connections

Persistence (JetStream, only for business-critical subjects, ~5% of traffic):
  100K msg/s × 512 B ≈ 50 MB/s × R3 = 150 MB/s of replicated writes
  7-day retention ≈ 30 TB per region before replication → moderate disks per server
```

## 2. High-Level Architecture

```text
               ┌──────────────────────── Supercluster ─────────────────────────┐
               │                                                               │
   Region EU   │  ┌─────────────┐  gateway  ┌─────────────┐  gateway  ┌─────────────┐
               │  │ Cluster EU  │◄─────────►│ Cluster US  │◄─────────►│ Cluster AP  │
   services ──►│  │ s1 s2 s3    │           │ s1 s2 s3    │           │ s1 s2 s3    │
               │  │ (full mesh) │◄──────────┼─────────────┼──────────►│ (full mesh) │
               │  └──────▲──────┘           └─────────────┘           └─────────────┘
               └─────────┼─────────────────────────────────────────────────────────┘
                         │ leaf node connections (outbound from the edge, over TLS)
          ┌──────────────┼──────────────────┐
          ▼              ▼                  ▼
   ┌────────────┐ ┌────────────┐     ┌────────────┐
   │ Leaf: store│ │ Leaf: store│ ... │ Leaf: plant│   ← one small server per site
   │ 101        │ │ 102        │     │ 7          │
   └─────▲──────┘ └─────▲──────┘     └─────▲──────┘
         │ devices, POS terminals, local services connect locally
```

| Component | Responsibility |
|---|---|
| **Server** | Accepts client connections, maintains subscription interest, routes messages; optionally runs JetStream |
| **Cluster** | 3+ servers in a region connected in a full mesh of *routes*; clients can connect to any |
| **Gateways** | Connect clusters into a **supercluster**; forward only what remote clusters are interested in |
| **Leaf node** | A server at an edge site that connects outbound to a cluster, extends its subject space, and keeps local traffic local |
| **Accounts** | Isolated subject namespaces per tenant; explicit exports/imports share selected subjects or services |
| **JetStream** | Persistence layer: streams, consumers, KV, object store; replicated with Raft |

## 3. Core Routing: Subjects and Interest

### 3.1 Subject matching

```text
Subjects are dot-separated tokens:  orders.created.eu   device.store101.temp
Subscriptions may use wildcards:    orders.*.eu         device.store101.>

Server data structure: a subject TRIE ("sublist") of subscriptions
  - each token is a trie level; '*' and '>' are special children
  - matching a published subject walks the trie: O(number of tokens), not O(subscriptions)
  - results are cached per literal subject (most traffic repeats the same subjects)
```

### 3.2 Publishing path inside one server

```text
1. Client sends PUB <subject> <size> + payload over its TCP connection
2. Server looks up matching subscriptions in the sublist (cached)
3. For plain subscribers: append the message to each subscriber's outbound buffer
   For each queue group: pick ONE member (randomly; prefer members on this server/cluster)
4. Per-connection writer flushes buffers to sockets in batches
No disk, no acknowledgement, no per-message state after the write.
```

The wire protocol is a simple text protocol (`PUB`, `SUB`, `MSG`, `HPUB` with headers, `PING`/`PONG`), which keeps clients small and makes the server's parsing fast.

### 3.3 Queue groups instead of broker-side queues

```text
SUB orders.created.*  billing   (instance 1)
SUB orders.created.*  billing   (instance 2)
SUB orders.created.*  billing   (instance 3)

Each message to orders.created.* goes to exactly one "billing" member.
No queue object is declared; the group exists while members are subscribed.
Scaling a service = starting more instances.
```

## 4. Request/Reply

```text
Requester:  SUB _INBOX.k3J9x.*          (one wildcard inbox per connection, reused)
            PUB pricing.quote  reply-to=_INBOX.k3J9x.42  payload

Server:     routes to ONE member of queue group "pricing" (any region/cluster with interest)

Responder:  PUB _INBOX.k3J9x.42 payload

Requester:  matches token "42" to the pending request future → completes it
```

Design decisions worth explaining:

- **Location transparency** — the requester doesn't know where responders run. Interest propagation finds them in the same cluster first, then across gateways.
- **No service discovery or load balancer** — queue groups do both.
- **"No responders"** — if no subscription matches, the server immediately returns a 503-style status message instead of letting the client wait for a timeout. Fast failure lets callers fall back or retry elsewhere.
- **Timeouts and retries** belong to the client; core request/reply is at-most-once, so commands that must not be lost use JetStream instead.

## 5. Clustering and Interest Propagation

### 5.1 Within a region: full mesh

```text
s1 ─── s2
 │  ╲ ╱  │
 │  ╱ ╲  │       every server has a route to every other server
s3 ─── s4

When a client subscribes on s2, s2 tells its routes "I have interest in orders.created.*".
A message published on s1 is forwarded ONCE to each server with interest (s2),
which delivers it locally. Messages never travel more than one route hop,
so there are no loops and latency is bounded.
```

Full mesh limits cluster size (connections grow as n²), which is fine because clusters stay small (3–7 servers); scale-out beyond that uses more clusters connected by gateways.

### 5.2 Across regions: gateways

```text
Cluster EU ──gateway── Cluster US

Naive approach: send every message to every cluster → wastes WAN bandwidth.
NATS gateways: start optimistic (send, and let the remote side reply "no interest
in this subject"), then switch to INTEREST-ONLY mode per account, where the
remote cluster explicitly registers the subjects it subscribes to.
→ only messages someone actually wants cross the WAN.
```

Queue-group members in the local cluster are preferred; requests cross regions only when no local responder exists — giving automatic regional failover for request/reply.

### 5.3 Edge sites: leaf nodes

```text
Store 101 (leaf node) ──outbound TLS── Cluster EU

  - devices connect to the leaf (low latency, survives WAN outages)
  - local traffic (device.store101.* → local services) never leaves the site
  - the leaf forwards only subjects the hub is interested in, and vice versa
  - the leaf authenticates to the hub with its own credentials and can map a
    local account to a hub account → security boundary at the site
  - WAN down: the site keeps running locally; when the link returns, interest is
    re-exchanged and traffic resumes (persisted data can sync via JetStream sourcing)
```

## 6. Flow Control and Slow Consumers

A fabric that never buffers on disk must protect itself from consumers that can't keep up.

```text
Each client connection has a server-side outbound buffer with limits:
  max_pending (bytes)    — e.g. 64 MB by default
  write_deadline         — max time a socket write may block

If a subscriber's buffer exceeds the limit or a write stalls past the deadline,
the server marks it a SLOW CONSUMER and closes the connection,
so one bad client can't exhaust server memory or slow down publishers.

Client libraries also have pending limits per subscription and report
slow-consumer events when their local buffer overflows (messages dropped).
```

Design implications to state in an interview:

- Core NATS chooses **availability and latency over guaranteed delivery** to slow consumers — the opposite of a durable queue, which would buffer on disk and let a backlog grow.
- Workloads that need back-pressure and durability use **JetStream pull consumers**: the consumer asks for batches when ready, and unprocessed messages wait safely in the stream.
- Scale slow consumers horizontally with queue groups; alert on slow-consumer counts.

## 7. Persistence Layer (JetStream)

```text
Publisher ──PUB orders.created.eu──► server
                                     │ subject matches stream "ORDERS" (orders.>)
                                     ▼
                     Stream ORDERS: Raft group (R3) on s1, s2, s3
                       leader appends → majority replicated → PubAck(seq=1042) to publisher
                                     │
                     Consumer "billing": its own Raft group tracking
                       delivered / acked sequences, redelivery timers, max deliveries
```

| Concern | Design |
|---|---|
| Capture | A stream binds to subjects; publishes to those subjects are stored (publishers get a `PubAck` with the sequence number) |
| Replication | Each stream and each consumer is its own Raft group (R1/R3/R5); a cluster-wide **meta group** decides placement of streams and consumers |
| Retention | `Limits` (log), `Interest` (until all consumers ack), `WorkQueue` (delete on first ack) |
| Consumption | Durable pull consumers with explicit acks, `AckWait`, backoff, `MaxDeliver`; several instances share one consumer |
| De-duplication | Publisher sets `Nats-Msg-Id`; the stream drops duplicates within a time window |
| Replay | New consumer starting by sequence or time |
| Edge sync | Streams at leaf sites can be **mirrored** or **sourced** into hub streams when links are up |
| KV / objects | Key-value buckets and object stores built on streams (config, feature flags, firmware files) |

Making persistence opt-in per subject is the key trade-off: the 95% of traffic that's ephemeral stays on the fast in-memory path, and only critical subjects pay for disk and replication.

## 8. Multi-Tenancy and Security

```text
Operator (root of trust)
  └─ Account "retail"      subjects: orders.>, device.> (isolated namespace)
  │    └─ Users: service creds, leaf-node creds, device creds (JWT + NKey)
  └─ Account "partners"
       └─ imports "retail" service "pricing.quote"  (explicit, revocable)

- Accounts are isolated: the same subject in two accounts never collides.
- Exports/imports share streams of messages or request/reply services explicitly.
- Decentralized JWT auth: accounts and users are signed JWTs; servers verify them
  without a central user database, and changes don't require server restarts.
- Per-user publish/subscribe permissions (allow/deny on subject patterns).
- TLS for clients, routes, gateways and leaf nodes.
```

## 9. Scaling and Bottlenecks

| Problem | Symptom | Solution |
|---|---|---|
| Very high fan-out on one subject | One server's egress saturated | Spread subscribers across servers (clients connect randomly), shard subjects (`ticks.<partition>.>`), or use more clusters |
| Slow consumers | Disconnections, dropped messages | Queue groups to scale out; move to JetStream pull consumers |
| Wildcard-heavy subscriptions | Higher routing CPU | Design subject hierarchies so subscribers use narrow, specific patterns |
| Cross-region bandwidth | Large WAN bills | Interest-only gateways, local queue-group preference, keep chatty traffic regional |
| Huge numbers of edge devices | Too many connections to the cloud | Leaf nodes aggregate devices per site; one outbound connection per site |
| Persistence hotspots | One stream leader overloaded | Split streams by subject partition; spread stream leaders; separate JetStream domains |
| Cluster growth | Full-mesh connection count grows as n² | Keep clusters small; add clusters to the supercluster |

## 10. Monitoring

| Metric | Alert when |
|---|---|
| Slow consumers (server and client) | Count increases |
| Connections, reconnects | Sudden drops or reconnect storms |
| Route / gateway / leaf link status | Any link down for more than a few seconds |
| Message rates and bytes in/out per server | Imbalanced or near capacity |
| Request/reply latency and "no responders" rate | Above SLO / rising |
| JetStream: consumer pending and redeliveries | Growing backlog or redelivery spikes |
| JetStream: Raft leader changes, storage use | Frequent elections, storage near limits |

Servers expose `/varz`, `/connz`, `/routez`, `/gatewayz`, `/leafz` and `/jsz` monitoring endpoints, typically scraped by a Prometheus exporter.

## 11. Interview Questions

**Q: Why doesn't the core layer of this design persist messages, and when is that the right trade-off?**

A: Persisting and acknowledging every message would put disk writes, replication and per-message bookkeeping on the hot path, raising latency from sub-millisecond to milliseconds and making the server responsible for buffering on behalf of every slow or offline subscriber. Much real-time traffic doesn't need that: a stale stock price, a sensor reading superseded a second later, or a request that the client will retry on timeout loses nothing important if it's dropped. By keeping the core layer stateless — route each message to current interest and forget it — the server stays fast, small enough to run at the edge, and resilient, because a failed server holds no data that must be recovered; clients simply reconnect elsewhere. The trade-off is at-most-once delivery, so the design makes persistence opt-in per subject: business-critical subjects are captured by JetStream streams with replication, acks and redelivery, and only those messages pay the durability cost.

---

**Q: How does request/reply work across a cluster and across regions without service discovery?**

A: The requester subscribes once to a unique wildcard inbox and publishes each request with a reply subject under that inbox. Responders are ordinary subscribers on a well-known subject, usually in a queue group, so each request is delivered to exactly one instance. Within a cluster, every server knows which other servers have interest in which subjects, so the request is forwarded in one hop to a server with a responder; the reply travels back the same way to the requester's server. Across regions, gateways propagate interest between clusters, and queue-group members in the local cluster are preferred, so requests only cross the WAN when no local responder exists — which also gives automatic failover if a region's responders disappear. If no responder exists anywhere, the server answers immediately with a "no responders" status, so callers fail fast instead of waiting for a timeout. Service location, load balancing and health are all derived from live subscriptions rather than a registry.

---

**Q: What happens when a subscriber can't keep up?**

A: In the core layer, the server writes messages into each client's outbound buffer and flushes it to the socket. If a subscriber reads too slowly, that buffer grows; once it exceeds the configured pending limit, or a socket write blocks longer than the write deadline, the server classifies the client as a slow consumer and disconnects it. This protects the server's memory and keeps publishers and healthy subscribers fast — one bad client can't degrade everyone. The messages that didn't reach the slow client are lost, consistent with at-most-once delivery. The mitigations are to scale the consumer horizontally with a queue group so each instance receives a fraction of the traffic, to keep handlers fast and offload slow work, and, for traffic that must not be lost, to consume through a JetStream pull consumer, where the consumer requests batches at its own pace and the backlog waits durably in the stream instead of in server memory.

---

**Q: How would you support edge sites that lose connectivity for hours?**

A: Each site runs a small server as a leaf node that connects outbound to a regional cluster. Devices and local services connect to the leaf, so local communication keeps working with no dependency on the WAN, and only subjects of mutual interest cross the link. For data that must reach the cloud even after a long outage, the leaf runs JetStream: device events are captured in a local stream, and the hub cluster has a stream that sources from it. While the link is down, the local stream accumulates messages within its limits; when the link returns, sourcing resumes from the last replicated sequence and catches up, with publish de-duplication preventing duplicates. Commands flowing to the site use the same mechanism in reverse. Security stays local too: the leaf authenticates to the hub with its own credentials and maps local accounts, so a compromised device can't reach other sites' subjects.

---

**Q: When would you choose this design over a Kafka-style log or a RabbitMQ-style task queue?**

A: This design wins when the main need is fast connectivity: low-latency request/reply between many services, real-time fan-out of small messages, and spanning regions and edge sites with location transparency and tenant isolation, all with a small operational footprint. It adds durability where needed through JetStream, which covers moderate event-streaming and work-queue workloads. A Kafka-style log is the better choice when durable, replayable history is the product — very large retained data sets, many independent consumer groups re-reading the same events, stream processing and data integration around a mature ecosystem. A RabbitMQ-style queue is better for background jobs with rich per-message behaviour: complex routing rules, priorities, delayed retries and dead-lettering with tight framework integration. Many architectures combine them, for example NATS as the service and edge fabric with a bridge that copies selected subjects into Kafka for analytics.

## 12. Key Takeaways

- **Fabric, not storage**: the core layer routes each message to current interest and keeps no per-message state — sub-millisecond routing, at-most-once delivery
- **Subjects + interest**: a trie of subscriptions with wildcards; clusters, gateways and leaf nodes exist to propagate interest efficiently
- **Queue groups replace broker-side queues**: load balancing by subscription, no declaration, scale by starting instances
- **Request/reply is first-class**: inboxes, one-hop routing, local-first responders, immediate "no responders" failure
- **Topology**: small full-mesh clusters per region, gateways in interest-only mode between regions, leaf nodes for edge sites
- **Slow consumers are cut off**: protects the server and other clients; use queue groups or JetStream pull consumers for back-pressure
- **Persistence is opt-in**: JetStream streams and consumers as Raft groups, de-duplication, replay, KV — only critical subjects pay the cost
- **Multi-tenancy by accounts**: isolated subject namespaces, explicit exports/imports, decentralized JWT auth
- **Monitor**: slow consumers, link health, no-responder rates, JetStream pending and Raft health
