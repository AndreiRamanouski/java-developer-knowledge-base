# Reliability Patterns

> **Applies to:** RabbitMQ 3.13–4.x · Spring Boot 3.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

"Don't lose messages, and tolerate duplicates" breaks down into guarantees at each hop:

```
Producer ──(1) publish──► Broker ──(2) store──► Queue ──(3) deliver──► Consumer ──(4) side effects
```

| Hop | Risk | Protection |
|---|---|---|
| 1. Publish | Message lost on the way, or unroutable | Publisher confirms, `mandatory` + returns, outbox |
| 2. Store | Broker node fails | Quorum queues, persistent messages, durable exchanges |
| 3. Deliver | Consumer crashes mid-processing | Consumer acknowledgements after processing |
| 4. Side effects | Redelivery repeats a DB write or API call | Idempotent consumers |

**Key Concept**: RabbitMQ gives you **at-least-once** delivery when every hop is configured correctly. Exactly-once processing is something your consumers build on top, with idempotency.

## 1. Durable Topology

```java
@Bean
TopicExchange ordersExchange() {
    return ExchangeBuilder.topicExchange("orders").durable(true).build();
}

@Bean
Queue invoicingQueue() {
    return QueueBuilder.durable("invoicing.order-events")
            .quorum()
            .deadLetterExchange("orders.dlx")
            .build();
}
```

- **Quorum queues** replicate messages across (typically) 3 nodes with Raft. A message is confirmed to the publisher only after a majority has written it. A queue stays available while a majority of its replicas is up.
- **Persistent delivery mode** — Spring's default for `RabbitTemplate`. (Quorum queues persist all messages anyway.)
- Run a **3- or 5-node cluster** for quorum queues. Odd numbers avoid split votes.

### Quorum Queues vs Streams vs Classic

| | Quorum | Stream | Classic |
|---|---|---|---|
| Replicated | ✅ | ✅ | ❌ (RabbitMQ 4.x) |
| Message removed on ack | ✅ | ❌ (retained by size/time) | ✅ |
| Replay | ❌ | ✅ from any offset | ❌ |
| Poison message protection | Delivery limit | — | — |
| Best for | Work queues, business events | Fan-out to many consumers, replay, large backlogs | Temporary/exclusive queues |

## 2. Reliable Publishing

Combine publisher confirms with returns (see [Spring AMQP setup and publishing](2.%20Spring%20AMQP%20setup%20and%20publishing.md#publisher-confirms)):

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
      retry:
        enabled: true          # retries the *send* on connection failures
        max-attempts: 3
        initial-interval: 500ms
```

Publishing is still not atomic with your database. If the app crashes between committing the DB transaction and receiving the confirm, the event may be lost. The fix is the outbox.

## 3. The Transactional Outbox

Store outgoing messages in the same database transaction as the business change; a relay publishes them with confirms and marks them as sent.

```java
@Transactional
public Order placeOrder(PlaceOrder command) {
    Order order = orders.save(Order.from(command));
    outbox.save(OutboxMessage.of("orders", "order.created." + order.getRegion(),
                                 order.getId(), toJson(OrderCreated.from(order))));
    return order;
}
```

```java
@Component
@RequiredArgsConstructor
public class OutboxRelay {

    private final OutboxRepository outbox;
    private final RabbitTemplate rabbitTemplate;

    @Scheduled(fixedDelay = 500)
    @Transactional
    public void publishPending() {
        for (OutboxMessage m : outbox.lockNextBatch(100)) {      // SELECT ... FOR UPDATE SKIP LOCKED
            CorrelationData correlation = new CorrelationData(m.getId().toString());
            rabbitTemplate.convertAndSend(m.getExchange(), m.getRoutingKey(), m.getPayload(),
                    msg -> {
                        msg.getMessageProperties().setMessageId(m.getId().toString());
                        msg.getMessageProperties().setContentType(MessageProperties.CONTENT_TYPE_JSON);
                        return msg;
                    },
                    correlation);
            awaitConfirm(correlation);       // wait on correlation.getFuture() as in the publishing page;
                                             // throws on nack, return or timeout → transaction rolls back
            m.markPublished();
        }
    }
}
```

The relay may publish a message twice (crash after the confirm, before the DB commit) — consumers deduplicate on `messageId`. The same pattern for Kafka, including a Debezium-based variant, is described in [Exactly-once semantics and transactions](../1.%20Apache%20Kafka/5.%20Exactly-once%20semantics%20and%20transactions.md#4-the-transactional-outbox-pattern).

### Why Not AMQP Transactions?

RabbitMQ supports channel transactions (`txSelect`/`txCommit`), and Spring can synchronize them with a database transaction (`channelTransacted=true`). They're slow (a round-trip per commit) and still don't give atomicity across the database and the broker. Publisher confirms + outbox is the recommended approach.

## 4. Reliable Consuming

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto        # ack after the listener returns
        default-requeue-rejected: false
        prefetch: 20
        retry:
          enabled: true
          max-attempts: 4
          initial-interval: 1s
          multiplier: 2.0
```

And in the listener, an inbox/dedup table:

```sql
CREATE TABLE processed_messages (
    message_id   VARCHAR(64) PRIMARY KEY,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```java
@RabbitListener(queues = "invoicing.order-events")
@Transactional
public void onOrderCreated(OrderCreated event, @Header(AmqpHeaders.MESSAGE_ID) String messageId) {
    int inserted = jdbc.update(
            "INSERT INTO processed_messages (message_id) VALUES (?) ON CONFLICT DO NOTHING", messageId);
    if (inserted == 0) {
        return;                                // duplicate
    }
    invoiceService.createFor(event);           // same DB transaction as the dedup insert
}
```

If the DB transaction commits but the ack is lost, the redelivered message hits the dedup row and is acked without side effects.

## 5. Ordering Guarantees

| Setup | Ordering |
|---|---|
| One queue, one consumer | Queue order (requeued messages may come back out of order) |
| One queue, many consumers | None |
| `x-single-active-consumer: true` | Queue order, with standby consumers for failover |
| Consistent hash exchange → N queues, one consumer each | Per key (e.g. per order ID) |

```java
@Bean
Queue orderedQueue() {
    return QueueBuilder.durable("ledger.entries")
            .quorum()
            .singleActiveConsumer()
            .build();
}
```

## 6. Flow Control and Back-Pressure

- When a node exceeds its **memory or disk alarm** thresholds, RabbitMQ **blocks publishing connections** until the alarm clears. Consumers keep working.
- Use separate publisher and consumer connections (`rabbitTemplate.setUsePublisherConnection(true)`) so blocked publishing doesn't stall consumption.
- Bound queues with `x-max-length` + `x-overflow: reject-publish` where a backlog would be harmful; publishers then get a `nack` they can react to.

## 7. Common Pitfalls

### ⚠️ Assuming "durable" means "replicated"

A durable classic queue survives a restart of *its* node, but is unavailable while that node is down. Use quorum queues for availability.

### ⚠️ Treating a publish as a commit

`convertAndSend` returning doesn't mean the broker has the message. Wait for confirms where it matters.

### ⚠️ Exactly-once expectations

Redelivery after a consumer crash is normal behaviour. Without idempotent handlers, it means double charges and duplicate emails.

---

## Summary & Best Practices

- ✓ Quorum queues on a 3+ node cluster; durable exchanges.
- ✓ Publisher confirms + `mandatory` returns; outbox for events tied to DB changes.
- ✓ Ack after processing (Spring `AUTO`), retries with backoff, DLX for failures.
- ✓ Deduplicate on `messageId` in the same transaction as the side effects.
- ✓ Single active consumer or consistent hashing when order matters.
