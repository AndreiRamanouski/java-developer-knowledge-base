# RabbitMQ Fundamentals

> **Applies to:** RabbitMQ 3.13–4.x · Spring Boot 3.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

RabbitMQ is a **message broker**: producers publish messages, the broker routes them into queues, and consumers take messages off those queues. Once a consumer acknowledges a message, it's removed. That makes RabbitMQ a natural fit for:

- **Work queues** — distribute tasks (send email, generate PDF, resize image) across a pool of workers.
- **Flexible routing** — deliver a message to one, some or all interested queues based on routing keys or headers.
- **Request/reply and RPC-style messaging** between services.
- **Per-message features** — priorities, TTLs, delayed redelivery, dead-lettering.

**Key Concept**: Producers never publish directly to a queue. They publish to an **exchange**, and **bindings** decide which queues get a copy. The routing logic lives in the broker, not in the producer.

---

## 1. Core Building Blocks (AMQP 0-9-1)

```text
Producer ──publish(exchange, routingKey)──► Exchange ──binding──► Queue ──► Consumer
                                               │
                                               └──binding──► Queue ──► Consumer
```

| Concept | Description |
|---|---|
| **Connection** | A TCP connection from your app to the broker. Long-lived and expensive; one per app (or a few). |
| **Channel** | A lightweight virtual connection inside a connection. Publishing and consuming happen on channels. Spring manages them for you. |
| **Exchange** | Receives messages and routes them to queues based on its type and the bindings. |
| **Queue** | Stores messages until a consumer acknowledges them (FIFO by default). |
| **Binding** | A rule linking an exchange to a queue, usually with a routing key or pattern. |
| **Routing key** | A string the producer attaches to a message; exchanges match it against bindings. |
| **Virtual host (vhost)** | A namespace with its own exchanges, queues and permissions — e.g. one per environment or team. |

## 2. Exchange Types

### Direct — exact routing key match

```text
Exchange "payments" (direct)
  routingKey "card"   ──► queue card-payments
  routingKey "paypal" ──► queue paypal-payments
```

### Topic — pattern match on dot-separated keys

`*` matches exactly one word, `#` matches zero or more words.

```text
Exchange "orders" (topic)
  binding "order.created.*"  ──► queue invoicing        (order.created.eu ✓, order.created ✗)
  binding "order.#"          ──► queue audit            (everything starting with "order.")
  binding "*.*.eu"           ──► queue eu-analytics     (order.created.eu ✓, order.shipped.eu ✓)
```

### Fanout — broadcast to every bound queue

```text
Exchange "cache-invalidation" (fanout) ──► queue for every instance
```

Routing keys are ignored. Good for broadcasting events to every interested service.

### Headers — match on message headers instead of routing key

Bindings specify header values with `x-match: all` (all must match) or `any`. Rarely needed; topic exchanges cover most cases.

### The Default Exchange

Every queue is automatically bound to the nameless default exchange (`""`) with its own name as the routing key. Publishing to `""` with routing key `emails` delivers straight to queue `emails` — handy, but it couples the producer to the queue name.

## 3. Queue Types

| Type | Characteristics | Use |
|---|---|---|
| **Quorum queue** | Replicated over several nodes using Raft; durable; poison-message handling via a delivery limit | **Default choice** for anything important |
| **Classic queue** | Single-node (not replicated in RabbitMQ 4.x); lightweight | Temporary/exclusive queues, non-critical data |
| **Stream** | Append-only log; non-destructive reads; consumers can replay from an offset | High fan-out, replay, large backlogs — Kafka-like use cases |

⚠️ **Classic mirrored queues were removed in RabbitMQ 4.0.** If you still declare `ha-mode` policies, migrate to quorum queues before upgrading.

### Queue Properties

| Property | Meaning |
|---|---|
| `durable` | Queue definition survives broker restarts (quorum queues are always durable) |
| `exclusive` | Used by only one connection and deleted when it closes |
| `auto-delete` | Deleted when the last consumer unsubscribes |
| `x-message-ttl` | Messages expire after this many ms |
| `x-max-length` | Max number of messages; `x-overflow` decides what happens when full |
| `x-dead-letter-exchange` / `x-dead-letter-routing-key` | Where rejected or expired messages go |
| `x-delivery-limit` (quorum) | Max redeliveries before the message is dead-lettered or dropped |

## 4. Message Lifecycle and Acknowledgements

```text
publish ──► exchange ──► queue ──deliver──► consumer
                           ▲                   │
                           └── nack/requeue ───┤
                                               ├── ack ──► message deleted
                                               └── reject (no requeue) ──► dead-letter exchange
```

- **Consumer acknowledgements** — the broker keeps a delivered message until the consumer acks it. If the consumer's channel closes before the ack (crash, network failure), the message is redelivered to another consumer with `redelivered=true`.
- **Prefetch (QoS)** — how many unacknowledged messages a consumer may hold at once. It controls both throughput and fairness between consumers.
- **Publisher confirms** — the broker acknowledges to the *producer* that it has taken responsibility for a message (written to the quorum, for quorum queues). Without confirms, a publish can be lost silently.
- **Persistent messages** — `deliveryMode=2` (Spring's default) so messages in durable queues survive a restart.

Delivery is **at-least-once** when you use confirms + manual/auto acks. Consumers must handle duplicates.

## 5. Messaging Patterns

| Pattern | Exchange setup | Example |
|---|---|---|
| Work queue (competing consumers) | One queue, N consumers | Image processing workers |
| Publish/subscribe | Fanout or topic exchange, one queue per subscriber | `OrderPlaced` → invoicing, shipping, analytics |
| Routing | Direct/topic with specific keys | Logs by severity |
| RPC | Request queue + reply-to queue + correlation ID | `RabbitTemplate.convertSendAndReceive` |
| Delayed retry | TTL queue → dead-letter back to work queue | Retry after 30 s |

**Pub/sub across services**: each consuming service owns **its own queue** bound to the shared exchange. Every service gets every matching event, and instances of one service compete for messages in that service's queue.

```text
                         ┌──► queue invoicing.order-events ──► invoicing (3 instances compete)
exchange "orders" (topic)┤
                         └──► queue shipping.order-events  ──► shipping  (2 instances compete)
```

## 6. Running RabbitMQ Locally

```yaml
# compose.yaml
services:
  rabbitmq:
    image: rabbitmq:4.0-management
    ports:
      - "5672:5672"      # AMQP
      - "15672:15672"    # management UI: http://localhost:15672 (guest/guest)
```

The management UI shows exchanges, queues, bindings, message rates, and lets you publish and fetch test messages. `rabbitmqctl` and `rabbitmqadmin` cover the same from the command line:

```bash
docker exec rabbitmq rabbitmqctl list_queues name type messages consumers
docker exec rabbitmq rabbitmq-diagnostics status
```

## 7. Common Pitfalls

### ⚠️ Opening a connection per message

Connections are expensive TCP + AMQP handshakes. Spring's `CachingConnectionFactory` reuses one connection and caches channels — use it, and don't create connections manually.

### ⚠️ Unbounded queues

A slow or dead consumer lets a queue grow until the broker hits its memory or disk alarm and **blocks all publishers**. Monitor queue depth, and consider `x-max-length` with `x-overflow: reject-publish` for queues that may back up.

### ⚠️ Auto-ack in the AMQP sense

RabbitMQ's "no-ack" mode removes messages as soon as they're sent, so a consumer crash loses them. (Spring's `AUTO` acknowledge mode is different and safe — see [Consumers and acknowledgements](3.%20Consumers%20and%20acknowledgements.md).)

### ⚠️ Using RabbitMQ as long-term storage

Queues are designed to be close to empty. If you need to retain and replay history, use a RabbitMQ **stream** or Kafka.

## Summary & Best Practices

| Concept | One-line definition |
|---|---|
| Exchange | Router that receives published messages |
| Binding | Rule connecting an exchange to a queue |
| Queue | Buffer from which consumers take messages |
| Quorum queue | Replicated, durable queue — the default for important data |
| Prefetch | Max unacked messages per consumer |
| Publisher confirm | Broker → producer acknowledgement |

- ✓ Publish to exchanges, not queues; let bindings do the routing.
- ✓ Use quorum queues for business-critical messages.
- ✓ Enable publisher confirms and consumer acknowledgements.
- ✓ One queue per consuming service for pub/sub.
- ✓ Keep queues short; alert on queue depth.
