# Error Handling, Retries and Dead Lettering

> **Applies to:** Spring Boot 3.x (Spring AMQP 3.x) · RabbitMQ 3.13–4.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

When a listener throws, you choose between three outcomes — the same as with any broker:

1. **Retry** transient failures (timeouts, unavailable dependencies).
2. **Dead-letter** messages that can't succeed (bad data, business rule violations).
3. **Don't lose anything silently.**

RabbitMQ provides the building blocks — rejection, requeueing, **dead-letter exchanges (DLX)**, TTLs and delivery limits — and Spring AMQP adds in-memory retries with backoff.

**Key Concept**: A message rejected *without requeue* (or expired, or over a length limit) is sent by the broker to the queue's **dead-letter exchange**, with headers describing why. Without a DLX, it's simply dropped.

## 1. Setting Up a Dead-Letter Exchange

```java
@Configuration
public class InvoicingQueueConfig {

    @Bean
    DirectExchange deadLetterExchange() {
        return new DirectExchange("orders.dlx");
    }

    @Bean
    Queue invoicingDeadLetterQueue() {
        return QueueBuilder.durable("invoicing.order-events.dlq").quorum().build();
    }

    @Bean
    Binding invoicingDlqBinding() {
        return BindingBuilder.bind(invoicingDeadLetterQueue()).to(deadLetterExchange()).with("invoicing");
    }

    @Bean
    Queue invoicingQueue() {
        return QueueBuilder.durable("invoicing.order-events")
                .quorum()
                .deadLetterExchange("orders.dlx")
                .deadLetterRoutingKey("invoicing")
                .deliveryLimit(5)                      // quorum queue: dead-letter after 5 redeliveries
                .build();
    }
}
```

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        default-requeue-rejected: false     # rejected messages go to the DLX instead of looping
```

The broker adds an `x-death` header to dead-lettered messages: the original queue, the reason (`rejected`, `expired`, `maxlen`, `delivery_limit`), a count, and the time.

## 2. Spring Retry: In-Memory Retries with Backoff

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        retry:
          enabled: true
          max-attempts: 4            # 1 delivery + 3 retries
          initial-interval: 1s
          multiplier: 2.0            # 1s, 2s, 4s
          max-interval: 10s
        default-requeue-rejected: false
```

How it works:
- The retries happen **inside the listener thread**, without going back to the broker. The message stays unacked, and the consumer handles nothing else meanwhile.
- When the attempts are exhausted, a `MessageRecoverer` decides what to do. The default, `RejectAndDontRequeueRecoverer`, rejects the message → DLX.

### Publishing Failures with Details

`RepublishMessageRecoverer` publishes the failed message to an exchange of your choice **with the exception message and stack trace in headers** — much easier to debug than `x-death` alone:

```java
@Bean
MessageRecoverer messageRecoverer(RabbitTemplate rabbitTemplate) {
    return new RepublishMessageRecoverer(rabbitTemplate, "orders.dlx", "invoicing");
}
```

Spring Boot uses a `MessageRecoverer` bean for the auto-configured retry interceptor. The headers include `x-exception-message`, `x-exception-stacktrace`, `x-original-exchange` and `x-original-routingKey`.

### Not Retrying Some Exceptions

Validation errors won't succeed on retry. Classify exceptions in the retry policy so they fail immediately and go straight to the recoverer:

```java
@Bean
RabbitRetryTemplateCustomizer retryCustomizer() {
    return (target, retryTemplate) -> {
        if (target == RabbitRetryTemplateCustomizer.Target.LISTENER) {
            retryTemplate.setRetryPolicy(new SimpleRetryPolicy(4, Map.of(
                    TransientDataAccessException.class, true,
                    ResourceAccessException.class, true,
                    ValidationException.class, false), true));   // traverse causes
        }
    };
}
```

## 3. Delayed Retries via the Broker

In-memory retries block a consumer. For longer delays (minutes) or many in-flight failures, park messages in a **wait queue** with a TTL whose dead-letter exchange points back to the work queue:

```
work queue ──listener republishes on failure──► wait queue (TTL 30s)
     ▲                                                  │ message expires
     └────────── dead-lettered back via DLX ────────────┘
```

```java
@Bean
Queue invoicingWaitQueue() {
    return QueueBuilder.durable("invoicing.order-events.wait")
            .ttl(30_000)                                   // x-message-ttl
            .deadLetterExchange("")                        // default exchange...
            .deadLetterRoutingKey("invoicing.order-events")// ...routes back to the work queue
            .build();
}
```

The listener decides whether to send the message to the wait queue or the DLQ based on the attempt count in the `x-death` header:

```java
@RabbitListener(queues = "invoicing.order-events")
public void onOrderCreated(Message message) {
    try {
        invoiceService.createFor(convert(message));
    } catch (TransientException e) {
        long attempts = deathCount(message, "invoicing.order-events.wait");
        String target = attempts < 3 ? "invoicing.order-events.wait" : "invoicing.order-events.dlq";
        rabbitTemplate.send("", target, message);          // then return normally → ack the original
    }
}

private long deathCount(Message message, String queue) {
    List<Map<String, ?>> deaths = message.getMessageProperties().getXDeathHeader();
    if (deaths == null) return 0;
    return deaths.stream()
            .filter(d -> queue.equals(d.get("queue")))
            .mapToLong(d -> (Long) d.get("count"))
            .findFirst().orElse(0);
}
```

⚠️ TTL-based delays apply per queue. Use one wait queue per delay length (e.g. 10 s, 1 min, 10 min) rather than per-message TTLs: a message only expires when it reaches the head of the queue, so a short per-message TTL can be stuck behind a long one.

The community **delayed message exchange** plugin (`x-delayed-message`) offers per-message delays, but its state is held on a single node and it isn't suitable for large volumes; check its limitations before relying on it.

## 4. Handling the DLQ

- **Alert** when the DLQ is not empty (`rabbitmq_queue_messages_ready{queue=~".*\\.dlq"} > 0` with the Prometheus plugin).
- **Inspect** messages in the management UI ("Get messages", with *Ack mode: Nack message requeue true* to leave them in place) or via a small admin endpoint.
- **Replay** after a fix: move messages back to the work queue with the shovel plugin, the management UI's *Move messages* (requires `rabbitmq_shovel_management`), or a replay listener:

```java
@RabbitListener(id = "invoicing-dlq-replayer", queues = "invoicing.order-events.dlq", autoStartup = "false")
public void replay(Message message) {
    rabbitTemplate.send("", "invoicing.order-events", message);
}
```

## 5. Poison Messages and Conversion Errors

A message whose body can't be converted (malformed JSON, unknown type) throws `MessageConversionException`. Spring treats it as fatal (`ConditionalRejectingErrorHandler`): the message is rejected without requeue — so it reaches the DLX if one is configured, and is **lost** if not. Always configure a DLX on queues that receive messages from other teams.

Quorum queues add a second safety net: `x-delivery-limit` dead-letters (or drops) a message after N redeliveries, even if the consumer keeps crashing before it can reject it. RabbitMQ 4.0 sets a default delivery limit of 20 for quorum queues.

## 6. Common Pitfalls

### ⚠️ Retries without a DLX

`RejectAndDontRequeueRecoverer` rejects the message after the last attempt. Without a DLX the broker drops it — silently.

### ⚠️ Long in-memory retries

Retrying for minutes inside the listener holds the message (and the consumer thread). Keep in-memory retries short (seconds); use wait queues for longer delays.

### ⚠️ Requeue + retry multiplication

With requeue enabled, each redelivery starts a new round of in-memory retries: 4 attempts × infinite redeliveries. Disable default requeue when retries are on.

### ⚠️ DLQ with no owner

Dead-lettered messages pile up unseen. Every DLQ needs an alert, an owner and a replay procedure.

## Summary & Best Practices

| Failure | Strategy |
|---|---|
| Brief transient failure | Spring Retry with exponential backoff (seconds) |
| Longer outage | TTL wait queues, or pause the listener |
| Bad data / validation | Non-retryable in the retry policy → recoverer → DLX |
| Conversion error | Rejected automatically → DLX |
| Consumer crash loop | Quorum queue delivery limit → DLX |

- ✓ Every important queue: quorum type, DLX, DLQ, alert on DLQ depth.
- ✓ `default-requeue-rejected: false` + Spring Retry + `RepublishMessageRecoverer`.
- ✓ Keep in-memory retries short; use wait queues for long delays.
