# Consumers and Acknowledgements

> **Applies to:** Spring Boot 3.x (Spring AMQP 3.x) · Java 17+ · **Last updated:** 2026-11-21

## Overview

`@RabbitListener` turns a method into a message consumer. A *listener container* manages the channel, receives deliveries, converts the payload, invokes your method, and acknowledges or rejects the message depending on how the method finishes.

**Key Concept**: In Spring's default `AUTO` acknowledge mode, **returning normally acks** the message and **throwing rejects** it. That makes the consumer at-least-once and lets exceptions drive retries and dead-lettering.

---

## 1. A Basic Listener

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class OrderEventsListener {

    private final InvoiceService invoiceService;

    @RabbitListener(queues = "invoicing.order-events")
    public void onOrderCreated(OrderCreated event) {
        invoiceService.createFor(event);
    }
}
```

### Access to Message Metadata

```java
@RabbitListener(queues = "invoicing.order-events")
public void onOrderCreated(@Payload OrderCreated event,
                           @Header(AmqpHeaders.MESSAGE_ID) String messageId,
                           @Header(AmqpHeaders.RECEIVED_ROUTING_KEY) String routingKey,
                           @Header(name = AmqpHeaders.REDELIVERED, required = false) Boolean redelivered) {
    log.info("Got {} via {} (redelivered={})", messageId, routingKey, redelivered);
}

// or the raw message
@RabbitListener(queues = "audit")
public void onAny(Message message) {
    byte[] body = message.getBody();
    MessageProperties props = message.getMessageProperties();
}
```

### Declaring Queue and Binding on the Listener

```java
@RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = "shipping.order-events", durable = "true",
                       arguments = @Argument(name = "x-queue-type", value = "quorum")),
        exchange = @Exchange(name = "orders", type = ExchangeTypes.TOPIC),
        key = { "order.paid.*", "order.cancelled.*" }))
public void onOrderEvent(OrderEvent event) { ... }
```

Convenient for small services; for anything more complex, declare topology as beans (see [Spring AMQP setup and publishing](2.%20Spring%20AMQP%20setup%20and%20publishing.md#2-declaring-topology)).

### Multiple Message Types on One Queue

```java
@Component
@RabbitListener(queues = "shipping.order-events")
public class ShippingListener {

    @RabbitHandler
    public void on(OrderPaid event) { shipping.prepare(event); }

    @RabbitHandler
    public void on(OrderCancelled event) { shipping.cancel(event); }

    @RabbitHandler(isDefault = true)
    public void onUnknown(Object event) { log.warn("Ignoring {}", event.getClass()); }
}
```

The method is chosen by the converted payload type, so the JSON converter must know the target class (type headers or a type mapper).

## 2. Acknowledgement Modes

| `spring.rabbitmq.listener.simple.acknowledge-mode` | Behaviour |
|---|---|
| `auto` (default) | Container acks after the method returns; on exception it rejects (requeue depends on settings, see below) |
| `manual` | You ack/nack via the `Channel` |
| `none` | RabbitMQ's no-ack mode: message is considered delivered on send. **Message loss on crash.** |

### Manual Acknowledgement

```java
@RabbitListener(queues = "payments", ackMode = "MANUAL")
public void onPayment(PaymentEvent event,
                      Channel channel,
                      @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        paymentService.apply(event);
        channel.basicAck(tag, false);
    } catch (TransientException e) {
        channel.basicNack(tag, false, true);    // requeue
    } catch (Exception e) {
        channel.basicNack(tag, false, false);   // don't requeue → dead-letter exchange, if configured
    }
}
```

Use manual acks when you hand the message to asynchronous processing and must ack later. Otherwise `auto` + exceptions is simpler and less error-prone.

### What Happens on Exception (AUTO mode)

| Setting / exception | Result |
|---|---|
| Default: `default-requeue-rejected: true` | Message is **requeued** and redelivered — possibly in a tight loop |
| `default-requeue-rejected: false` | Message is rejected without requeue → DLX if configured, otherwise **dropped** |
| Listener throws `AmqpRejectAndDontRequeueException` | Never requeued, regardless of the setting |
| Listener throws `ImmediateRequeueAmqpException` | Always requeued |
| Message conversion fails (`MessageConversionException`) | Treated as fatal: rejected without requeue |

⚠️ The default requeue behaviour causes infinite redelivery loops for poison messages. Configure retries and dead-lettering — see [Error handling, retries and dead lettering](4.%20Error%20handling%2C%20retries%20and%20dead%20lettering.md).

## 3. Concurrency and Prefetch

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 3          # consumers started per listener
        max-concurrency: 10     # scaled up under load
        prefetch: 20            # unacked messages per consumer (default 250)
```

```java
// Per listener
@RabbitListener(queues = "thumbnails", concurrency = "2-8")
public void onImage(ImageUploaded event) { ... }
```

### Choosing Prefetch

| Prefetch | Effect |
|---|---|
| 1 | Fair dispatch: a slow message doesn't hold others hostage. Lowest throughput. Good for long tasks (seconds+). |
| 10–50 | Good default for typical business events |
| 250 (Spring default) | High throughput for fast, small messages; one consumer may hoard messages while others idle |

### Ordering

With one consumer and prefetch ≥ 1, messages are processed in queue order. With **several consumers**, ordering across messages is lost. If per-entity ordering matters:

- use a single active consumer (`x-single-active-consumer: true` on the queue — other consumers stand by for failover), or
- shard by key across several queues with the **consistent hash exchange** plugin, one consumer per queue.

### Direct vs Simple Container

Spring has two listener container types:

- `simple` (default): the container manages its own consumer threads; supports dynamic `max-concurrency`.
- `direct`: listeners run on the RabbitMQ client's threads; lower overhead, `consumers-per-queue` instead of min/max concurrency.

Stick with `simple` unless you have a reason to change.

## 4. Idempotent Consumers

RabbitMQ redelivers unacked messages after a consumer crash or connection loss, and publishers may republish after a missed confirm. Make handlers idempotent:

```java
@RabbitListener(queues = "invoicing.order-events")
@Transactional
public void onOrderCreated(OrderCreated event, @Header(AmqpHeaders.MESSAGE_ID) String messageId) {
    if (!processedMessages.tryInsert(messageId)) {   // unique constraint on message_id
        return;                                       // duplicate → ack and ignore
    }
    invoiceService.createFor(event);
}
```

Other approaches: upserts keyed by business ID, or state checks ("invoice for order X already exists").

## 5. Lifecycle Control

```java
@RabbitListener(id = "invoicing", queues = "invoicing.order-events", autoStartup = "false")
public void onOrderCreated(OrderCreated event) { ... }

@Service
@RequiredArgsConstructor
class ListenerControl {
    private final RabbitListenerEndpointRegistry registry;

    void start() { registry.getListenerContainer("invoicing").start(); }
    void stop()  { registry.getListenerContainer("invoicing").stop(); }   // finishes in-flight messages
}
```

On application shutdown, containers stop consuming and wait up to `shutdownTimeout` (default 5 s) for in-flight messages; unacked messages go back to the queue.

## 6. Common Pitfalls

### ⚠️ Swallowing exceptions

```java
try { process(event); } catch (Exception e) { log.error("failed", e); }   // ❌ acked → lost
```

Let it propagate (or throw `AmqpRejectAndDontRequeueException`) so retries and dead-lettering work.

### ⚠️ Requeue loops

A message that always fails is redelivered immediately, forever, burning CPU and flooding logs. Disable default requeue, add retries, and use a DLX. Quorum queues also enforce a delivery limit (default 20 in RabbitMQ 4.x).

### ⚠️ Huge prefetch with slow handlers

With prefetch 250 and 2 s per message, a consumer holds 8 minutes of work while new consumers sit idle. Lower the prefetch for slow work.

### ⚠️ Blocking the listener on slow I/O without timeouts

A listener thread stuck on an HTTP call without a timeout stops that consumer. Always set client timeouts.

---

## Summary & Best Practices

- ✓ Keep `AUTO` ack mode; signal failure by throwing.
- ✓ Set `default-requeue-rejected: false` and configure a DLX.
- ✓ Tune prefetch to message processing time.
- ✓ Use single active consumer or consistent hashing when ordering matters.
- ✓ Deduplicate with a `messageId`.
