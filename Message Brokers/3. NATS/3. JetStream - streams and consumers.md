# JetStream: Streams and Consumers

> **Applies to:** NATS Server 2.10+ · NATS Java client (jnats) 2.17+ · Java 17+ · **Last updated:** 2026-11-21

## Overview

JetStream adds persistence to NATS. Messages published to a stream's subjects are stored; **consumers** read them with acknowledgements and redelivery. Because it runs inside the NATS server, there's no extra system to operate — enable it with `-js` (or `jetstream {}` in the config file).

**Key Concept**: A **stream** stores messages; a **consumer** is a server-side view of a stream that tracks delivery and acknowledgement state. Many consumers can read one stream independently, and many application instances can share one consumer to split the work.

---

## 1. Streams

### Creating a Stream

```java
JetStreamManagement jsm = nats.jetStreamManagement();

StreamConfiguration orders = StreamConfiguration.builder()
        .name("ORDERS")
        .subjects("orders.>")                      // captures every subject under orders.
        .storageType(StorageType.File)
        .replicas(3)                               // Raft-replicated across 3 servers
        .retentionPolicy(RetentionPolicy.Limits)
        .maxAge(Duration.ofDays(7))
        .maxBytes(10L * 1024 * 1024 * 1024)        // 10 GiB
        .duplicateWindow(Duration.ofMinutes(2))    // window for Nats-Msg-Id de-duplication
        .build();

try {
    jsm.addStream(orders);
} catch (JetStreamApiException e) {
    jsm.updateStream(orders);                      // already exists → apply changes
}
```

Or with the CLI / infrastructure as code (`nats stream add`, the NACK Kubernetes controller, or Terraform). As with Kafka topics, many teams manage streams outside the application.

### Retention Policies

| Policy | Messages are removed when… | Use for |
|---|---|---|
| `Limits` (default) | Age, count or size limits are exceeded | Event streams with replay (Kafka-like) |
| `Interest` | Every consumer that existed when the message arrived has acked it | Fan-out where storage should shrink as consumers catch up |
| `WorkQueue` | Any one consumer acks it; each subject may have only one consumer | Job queues (RabbitMQ-like) |

### Discard Policy and Limits

When a limit is hit, `DiscardPolicy.Old` (default) deletes the oldest messages; `DiscardPolicy.New` rejects new publishes — use it when losing old data isn't acceptable and back-pressure on producers is preferable.

## 2. Publishing to JetStream

```java
@Service
@RequiredArgsConstructor
public class OrderEventPublisher {

    private final Connection nats;
    private final NatsJson json;

    public void orderCreated(OrderCreated event) {
        JetStream js = nats.jetStream();
        PublishOptions options = PublishOptions.builder()
                .messageId(event.eventId())            // Nats-Msg-Id: duplicates within the window are dropped
                .expectedStream("ORDERS")              // fail if the subject isn't captured by ORDERS
                .build();
        try {
            PublishAck ack = js.publish("orders.created." + event.region(), json.write(event), options);
            if (ack.isDuplicate()) {
                log.debug("Event {} was already stored (seq {})", event.eventId(), ack.getSeqno());
            }
        } catch (IOException | JetStreamApiException e) {
            throw new EventPublishingException("JetStream publish failed for " + event.eventId(), e);
        }
    }
}
```

Unlike core NATS, a JetStream publish **waits for an acknowledgement** from the stream (after replication). For throughput, publish asynchronously and check the futures:

```java
List<CompletableFuture<PublishAck>> acks = events.stream()
        .map(e -> js.publishAsync("orders.created." + e.region(), json.write(e),
                PublishOptions.builder().messageId(e.eventId()).build()))
        .toList();
CompletableFuture.allOf(acks.toArray(CompletableFuture[]::new)).get(10, TimeUnit.SECONDS);
```

The message ID makes retries safe: if the publisher times out and retries, the stream recognises the duplicate within `duplicateWindow`.

## 3. Consumers

### Consumer Configuration

```java
ConsumerConfiguration billing = ConsumerConfiguration.builder()
        .durable("billing")                         // survives client restarts
        .filterSubject("orders.created.>")          // only these subjects from the stream
        .deliverPolicy(DeliverPolicy.All)           // start from the beginning of the stream
        .ackPolicy(AckPolicy.Explicit)              // every message must be acked
        .ackWait(Duration.ofSeconds(30))            // redeliver if not acked in time
        .maxDeliver(5)                              // give up after 5 deliveries
        .backoff(Duration.ofSeconds(1), Duration.ofSeconds(5), Duration.ofSeconds(30))
        .maxAckPending(1_000)                       // flow control across all instances
        .build();

jsm.addOrUpdateConsumer("ORDERS", billing);
```

| Option | Meaning |
|---|---|
| Durable vs ephemeral | Durable consumers keep their state on the server; ephemeral ones are removed when inactive |
| `deliverPolicy` | `All`, `New`, `Last`, `LastPerSubject`, `ByStartSequence`, `ByStartTime` |
| `ackPolicy` | `Explicit` (per message, the normal choice), `All` (acking N acks everything before it), `None` |
| `ackWait` | How long the server waits for an ack before redelivering |
| `maxDeliver` | Maximum delivery attempts; afterwards the message is no longer delivered to this consumer |
| `backoff` | Redelivery delays per attempt (overrides `ackWait` for redeliveries) |
| `maxAckPending` | Max unacked messages in flight for the consumer |

### Pull vs Push

- **Pull consumers** — clients request batches when they're ready. They scale horizontally (several instances pull from the same durable consumer) and give natural back-pressure. **Recommended for new code.**
- **Push consumers** — the server sends messages to a delivery subject. Older style; still useful for some fan-out cases.

### Consuming with the Simplified API

jnats 2.17+ offers a simplified, pull-based API built around `StreamContext` and `ConsumerContext`:

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class BillingConsumer implements SmartLifecycle {

    private final Connection nats;
    private final NatsJson json;
    private final BillingService billing;
    private volatile MessageConsumer consumer;

    @Override
    public void start() {
        try {
            ConsumerContext ctx = nats.getConsumerContext("ORDERS", "billing");
            consumer = ctx.consume(this::handle);       // continuous pull in the background
        } catch (IOException | JetStreamApiException e) {
            throw new IllegalStateException("Cannot start billing consumer", e);
        }
    }

    private void handle(Message msg) {
        try {
            billing.handle(json.read(msg.getData(), OrderCreated.class));
            msg.ack();
        } catch (IllegalArgumentException badPayload) {
            log.error("Unprocessable message seq={}", msg.metaData().streamSequence(), badPayload);
            msg.term();                                  // never redeliver
        } catch (Exception transientError) {
            long attempt = msg.metaData().deliveredCount();
            log.warn("Attempt {} failed, will retry", attempt, transientError);
            msg.nakWithDelay(Duration.ofSeconds(Math.min(60, 1L << attempt)));   // back off
        }
    }

    @Override
    public void stop() {
        if (consumer != null) {
            consumer.stop();                             // stop pulling; in-flight messages finish
        }
    }

    @Override
    public boolean isRunning() {
        return consumer != null && !consumer.isStopped();
    }
}
```

Run several instances of the service and they all pull from the same durable consumer `billing`; the server hands each message to one of them.

### Batch Fetching

```java
ConsumerContext ctx = nats.getConsumerContext("ORDERS", "reporting");
try (FetchConsumer fetch = ctx.fetchMessages(100)) {      // up to 100 messages or until the expiry
    Message msg;
    while ((msg = fetch.nextMessage()) != null) {
        process(msg);
        msg.ack();
    }
}
```

## 4. Acknowledgements

| Call | Effect |
|---|---|
| `msg.ack()` | Done; don't redeliver |
| `msg.ackSync(Duration)` | Ack and wait for the server to confirm it — part of "double ack" for effectively-once processing |
| `msg.nak()` / `msg.nakWithDelay(d)` | Failed; redeliver now / after a delay |
| `msg.inProgress()` | Still working; reset the `ackWait` timer (for long jobs) |
| `msg.term()` | Never redeliver this message (bad data) |

The delivery count is in the message metadata: `msg.metaData().deliveredCount()`.

## 5. Dead Letters

JetStream has no dead-letter queue setting. When a message reaches `maxDeliver`, or is terminated with `term()`, the server publishes an **advisory**:

```text
$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.<stream>.<consumer>
$JS.EVENT.ADVISORY.CONSUMER.MSG_TERMINATED.<stream>.<consumer>
```

The advisory contains the stream sequence of the failed message. A small handler can copy the original message into a DLQ stream:

```java
Dispatcher d = nats.createDispatcher();
d.subscribe("$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.billing", advisory -> {
    long seq = json.read(advisory.getData(), MaxDeliveriesAdvisory.class).streamSeq();
    try {
        MessageInfo original = jsm.getMessage("ORDERS", seq);
        Headers headers = new Headers()
                .add("original-subject", original.getSubject())
                .add("original-seq", String.valueOf(seq))
                .add("reason", "max-deliveries");
        nats.jetStream().publish("dlq.orders.billing", headers, original.getData());
    } catch (Exception e) {
        log.error("Could not dead-letter ORDERS seq {}", seq, e);
    }
});

record MaxDeliveriesAdvisory(@JsonProperty("stream_seq") long streamSeq) {}
```

With `Limits` retention the original stays in the stream until it ages out, so it can also be looked up directly. With `WorkQueue` or `Interest` retention, handle the advisory promptly.

## 6. Ordering and Scaling

- A consumer delivers messages in stream order, but with several instances pulling (or `maxAckPending > 1`) processing order isn't guaranteed.
- For strict ordering, set `maxAckPending(1)` on the consumer (one message in flight at a time) or partition the subject space (e.g. `orders.<partition>.>`) with one consumer per partition. NATS also supports deterministic subject partitioning via subject mapping with `partition(n, token)`.
- **Ordered consumers** (`OrderedConsumerContext`) are lightweight ephemeral consumers that guarantee order for a single reader — good for replaying a stream into memory, not for shared work.

## 7. Common Pitfalls

### ⚠️ Forgetting to ack

With `AckPolicy.Explicit`, an unacked message is redelivered after `ackWait`, forever up to `maxDeliver`. Every code path must `ack`, `nak` or `term`.

### ⚠️ `ackWait` shorter than processing time

Long jobs get redelivered to another instance while the first is still working. Raise `ackWait` or call `msg.inProgress()` periodically.

### ⚠️ No publish de-duplication

Without `messageId`, a retried publish stores the message twice. Always set a message ID for events.

### ⚠️ Replicas 1 in production

A single-replica stream is lost or unavailable when its server is. Use 3 replicas on a 3-node cluster.

---

## Summary & Best Practices

- ✓ One stream per subject space; `Limits` for event logs, `WorkQueue` for jobs.
- ✓ Publish with a message ID; check `PublishAck`.
- ✓ Durable pull consumers with explicit acks, `maxDeliver` and backoff.
- ✓ `term()` bad data, `nakWithDelay()` transient failures, `inProgress()` long work.
- ✓ Turn max-delivery advisories into a DLQ stream and alert on it.
