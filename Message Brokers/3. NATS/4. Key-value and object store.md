# Key-Value and Object Store

> **Applies to:** NATS Server 2.10+ · NATS Java client (jnats) 2.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

JetStream includes two storage abstractions built on top of streams:

- **Key-value (KV) store** — buckets of keys with versioned values, compare-and-set updates, history, TTLs and **watchers** that push changes to clients in real time.
- **Object store** — chunked storage for large blobs (files, models, reports) that exceed the normal message size.

They're handy when you already run NATS and need lightweight shared state — configuration, feature flags, leader election, service registries, session data — without adding Redis or a database for it.

**Key Concept**: A KV bucket is a stream with one subject per key (`$KV.<bucket>.<key>`). Every `put` is a new message, so you get a revision number per write, optional history, and change notifications for free.

## 1. Key-Value Store

### Creating a Bucket

```java
KeyValueManagement kvm = nats.keyValueManagement();

kvm.create(KeyValueConfiguration.builder()
        .name("feature-flags")
        .history(5)                         // keep the last 5 values per key
        .ttl(Duration.ofDays(30))           // entries expire after 30 days without updates
        .replicas(3)
        .storageType(StorageType.File)
        .build());
```

CLI equivalent: `nats kv add feature-flags --history 5 --ttl 30d --replicas 3`.

### Reading and Writing

```java
KeyValue flags = nats.keyValue("feature-flags");

long rev = flags.put("checkout.new-flow", "on");          // returns the revision
KeyValueEntry entry = flags.get("checkout.new-flow");     // null if missing
String value = entry.getValueAsString();
long revision = entry.getRevision();

flags.delete("checkout.new-flow");                        // tombstone (kept in history)
flags.purge("checkout.new-flow");                         // remove history too
```

Keys may contain letters, digits, `-`, `_`, `/`, `=` and `.`; dots let watchers use wildcards (`checkout.*`).

### Optimistic Concurrency

```java
// Create only if the key doesn't exist — a simple distributed lock / leader claim
try {
    flags.create("leader.report-job", instanceId.getBytes(StandardCharsets.UTF_8));
    runReportJob();
} catch (JetStreamApiException alreadyExists) {
    log.info("Another instance holds the leader key");
}

// Update only if nobody changed the value since we read it
KeyValueEntry current = flags.get("pricing.multiplier");
double next = Double.parseDouble(current.getValueAsString()) * 1.1;
flags.update("pricing.multiplier", String.valueOf(next).getBytes(StandardCharsets.UTF_8),
             current.getRevision());                                          // fails on conflict
```

For a lock that must expire if its holder dies, use a bucket with a short `ttl` and have the holder refresh the key periodically with `update(...)`.

### Watching for Changes

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class FeatureFlagCache {

    private final Connection nats;
    private final Map<String, String> flags = new ConcurrentHashMap<>();
    private NatsKeyValueWatchSubscription watch;

    @PostConstruct
    void start() throws Exception {
        KeyValue kv = nats.keyValue("feature-flags");
        watch = kv.watchAll(new KeyValueWatcher() {
            @Override
            public void watch(KeyValueEntry entry) {
                switch (entry.getOperation()) {
                    case PUT -> flags.put(entry.getKey(), entry.getValueAsString());
                    case DELETE, PURGE -> flags.remove(entry.getKey());
                }
            }

            @Override
            public void endOfData() {
                log.info("Loaded {} feature flags", flags.size());   // initial values delivered
            }
        });
    }

    public boolean isOn(String key) {
        return "on".equals(flags.get(key));
    }

    @PreDestroy
    void stop() {
        if (watch != null) watch.unsubscribe();
    }
}
```

The watcher first delivers the current value of every key, calls `endOfData()`, then streams every change as it happens — an always-up-to-date local cache with no polling.

### KV vs Redis

| | NATS KV | Redis |
|---|---|---|
| Data types | Bytes per key (+ history) | Strings, hashes, lists, sets, sorted sets, streams… |
| Change notifications | Built-in watchers with wildcards | Keyspace notifications, pub/sub |
| History / revisions | ✅ per key | ❌ |
| Latency | Low (persisted, replicated) | Very low (in memory) |
| Best for | Config, flags, coordination, small shared state | Caching, rich data structures, rate limiting |

## 2. Object Store

```java
ObjectStoreManagement osm = nats.objectStoreManagement();
osm.create(ObjectStoreConfiguration.builder("reports")
        .storageType(StorageType.File)
        .replicas(3)
        .build());

ObjectStore reports = nats.objectStore("reports");

// Upload: the client splits the stream into chunks
try (InputStream in = Files.newInputStream(Path.of("/tmp/monthly-report.pdf"))) {
    ObjectInfo info = reports.put("2026/11/monthly-report.pdf", in);
    log.info("Stored {} bytes in {} chunks", info.getSize(), info.getChunks());
}

// Download
try (OutputStream out = Files.newOutputStream(Path.of("/tmp/copy.pdf"))) {
    reports.get("2026/11/monthly-report.pdf", out);
}
```

The object store is convenient for moderate-size artifacts inside a NATS-based system, especially at the edge. For large-scale file storage, an S3-compatible object store is still the better fit.

## 3. Common Pitfalls

### ⚠️ Using KV as a general-purpose database

No queries, no secondary indexes, no transactions across keys. Keep it to lookups by key and change notifications.

### ⚠️ Large values

Values are messages: keep them small (KBs). Put large data in the object store or elsewhere.

### ⚠️ Ignoring revisions

Read-modify-write without `update(key, value, revision)` loses concurrent updates.

---

## Summary & Best Practices

- ✓ KV buckets for configuration, feature flags, coordination and small shared state.
- ✓ `create` and `update` with revisions for safe concurrent changes.
- ✓ Watchers instead of polling for local caches.
- ✓ Object store for moderate-size blobs within NATS; S3 for heavy file storage.
- ✓ Replicas 3 for buckets that matter.
