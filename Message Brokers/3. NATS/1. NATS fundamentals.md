# NATS Fundamentals

> **Applies to:** NATS Server 2.10+ · Java 17+ · **Last updated:** 2026-11-21

## Overview

NATS is a lightweight, high-performance messaging system shipped as a single small server binary. It has two layers:

- **Core NATS** — fire-and-forget publish/subscribe, request/reply and load-balanced queue groups over **subjects**. Messages live only in memory and in flight: if nobody is subscribed, the message is gone. Delivery is **at-most-once**.
- **JetStream** — the persistence layer built into the same server. Streams store messages on disk, consumers track their position and acknowledge messages, and delivery becomes **at-least-once** (with publish de-duplication for effectively-once publishing). JetStream also provides a **key-value store** and an **object store**.

Typical uses:

- **Service-to-service request/reply** with built-in load balancing — an alternative to HTTP between internal services.
- **Real-time fan-out** of events, telemetry and notifications where latency matters more than durability.
- **Durable event streams and work queues** with JetStream.
- **Edge and multi-region systems** — leaf nodes and superclusters connect sites into one subject space.

**Key Concept**: Everything in NATS is addressed by **subject**. Publishers send to a subject; subscribers express interest in subjects (with wildcards). There are no exchanges, topics or queues to declare in core NATS — the subject *is* the routing.

## 1. Subjects and Wildcards

Subjects are dot-separated tokens:

```text
orders.created.eu
orders.shipped.us
payments.card.authorized
```

| Wildcard | Matches | Example | Matches | Doesn't match |
|---|---|---|---|---|
| `*` | Exactly one token | `orders.*.eu` | `orders.created.eu` | `orders.created`, `orders.a.b.eu` |
| `>` | One or more tokens, only at the end | `orders.>` | `orders.created`, `orders.created.eu` | `orders` |

Subject design is your routing design. A common convention is `<domain>.<entity-or-event>.<qualifiers>`, most general first, so wildcards can select by domain, event type or region.

## 2. Core NATS Messaging Patterns

### Publish/Subscribe

```text
publisher ──orders.created.eu──► NATS ──► subscriber A (orders.>)
                                      └──► subscriber B (orders.created.*)
```

Every matching subscription gets a copy. Subscribers that aren't connected at the time miss the message.

### Queue Groups (Load Balancing)

```text
                                   ┌──► billing instance 1 ┐
publisher ──orders.created.eu──► NATS ──► billing instance 2 ├─ queue group "billing": one of them gets it
                                   └──► billing instance 3 ┘
                                   └──► audit (plain subscriber): gets every message
```

Subscribers that join with the same **queue name** share the work: each message goes to one member of the group. No server configuration is needed — the group exists while members are subscribed. This is how you scale a service horizontally on core NATS.

### Request/Reply

```text
client ──request: pricing.quote (reply-to: _INBOX.abc)──► NATS ──► pricing service (queue group)
client ◄──────────────── reply on _INBOX.abc ──────────────────────────┘
```

The client creates a unique inbox subject, publishes the request with that inbox as the reply subject, and waits. Responders in a queue group give you load-balanced RPC with no service discovery: any healthy instance subscribed to `pricing.quote` can answer. If no responder is listening, the client gets a "no responders" error immediately instead of waiting for a timeout.

## 3. Delivery Guarantees

| Layer | Guarantee | What happens when… |
|---|---|---|
| Core NATS | At-most-once | …no subscriber is connected: message dropped. …a subscriber is too slow: the server disconnects it or drops messages (**slow consumer**). |
| JetStream | At-least-once | …the consumer crashes before acking: message redelivered after `AckWait`. |
| JetStream + publish dedup + double ack | Effectively once | Producer sets a message ID (`Nats-Msg-Id`), the stream drops duplicates within its duplicate window; consumers confirm acks synchronously. Side effects still need idempotency. |

Choose core NATS when losing a message is acceptable (live updates, metrics, request/reply with client retries). Use JetStream when the message must survive restarts and consumer outages.

## 4. JetStream in One Page

```text
publishers ──orders.>──► Stream "ORDERS" (subjects: orders.>, file storage, 3 replicas)
                              │
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
   consumer "billing"  consumer "shipping"  consumer "audit"
   (durable, pull,     (durable, pull,      (ephemeral,
    explicit ack)       filter orders.paid)   replay from start)
```

- A **stream** captures messages published to its subjects and stores them according to limits (age, count, bytes) and a **retention policy**: `Limits` (keep until limits), `Interest` (keep until all consumers acked), `WorkQueue` (delete once any consumer acked).
- A **consumer** is a server-side cursor over a stream: it tracks which messages were delivered and acknowledged. Durable consumers survive client restarts; several client instances can pull from the same consumer to share work.
- Replication uses Raft: replicas `1`, `3` or `5`.

Details and Java code: [JetStream: streams and consumers](3.%20JetStream%20-%20streams%20and%20consumers.md).

## 5. Topology: Clusters, Superclusters, Leaf Nodes

| Building block | Purpose |
|---|---|
| **Cluster** | 3+ servers in one region, full mesh; clients can connect to any server |
| **Supercluster** | Clusters connected by gateways; interest-based routing between regions |
| **Leaf node** | A server (e.g. at the edge, in a factory, on a ship) that extends a remote cluster's subject space, with its own local traffic and security boundary |
| **Accounts** | Multi-tenancy: each account has an isolated subject namespace; subjects can be explicitly exported/imported between accounts |

Authentication options include username/password, tokens, NKeys and **decentralized JWT-based auth** (operator → account → user), which lets you manage users without restarting servers.

## 6. Running NATS Locally

```yaml
# compose.yaml
services:
  nats:
    image: nats:2.10
    command: ["-js", "-m", "8222"]     # enable JetStream and the HTTP monitoring endpoint
    ports:
      - "4222:4222"    # client connections
      - "8222:8222"    # monitoring: http://localhost:8222/varz, /connz, /jsz
```

The `nats` CLI is the everyday tool for working with subjects, streams and consumers:

```bash
# Core NATS
nats sub "orders.>"                                   # watch everything under orders.
nats pub orders.created.eu '{"orderId":"o-1"}'
nats reply pricing.quote '{"price": 42}'              # a test responder
nats request pricing.quote '{"sku":"p-1"}'

# JetStream
nats stream add ORDERS --subjects "orders.>" --storage file --replicas 1 --defaults
nats stream info ORDERS
nats consumer add ORDERS billing --pull --ack explicit --deliver all --defaults
nats consumer next ORDERS billing                     # fetch and ack one message

# Benchmarks against your own server
nats bench orders.test --pub 1 --sub 1 --msgs 100000
```

## 7. Common Pitfalls

### ⚠️ Expecting core NATS to store messages

Core NATS doesn't queue messages for absent subscribers. If a service restart must not lose events, publish into a JetStream stream.

### ⚠️ Slow consumers

A subscriber that can't keep up fills its pending buffer; the client reports slow-consumer errors and messages are dropped (core NATS). Process quickly, use queue groups to scale out, or move the flow to a JetStream pull consumer.

### ⚠️ Unplanned subject hierarchy

Changing subject structure later breaks every wildcard subscription and stream definition. Agree on a naming scheme early and document it.

### ⚠️ Overlapping streams

Two streams can't capture the same subject. Plan which stream owns which subject space.

### ⚠️ Large payloads

The default maximum payload is 1 MB (`max_payload`). Use the JetStream object store, or external object storage plus a reference, for large data.

## Summary & Best Practices

| Concept | One-line definition |
|---|---|
| Subject | Dot-separated address; wildcards `*` (one token) and `>` (rest) |
| Queue group | Subscribers sharing a queue name split the messages between them |
| Request/reply | Publish with a reply inbox, wait for one response |
| Core NATS | In-memory, at-most-once |
| JetStream | Persistent streams + consumers, at-least-once |
| Stream / consumer | Storage of messages / server-side cursor with acks |

- ✓ Design the subject hierarchy deliberately; most general token first.
- ✓ Use queue groups to scale services on core NATS.
- ✓ Use JetStream for anything that must not be lost.
- ✓ Run a 3-node cluster with JetStream replicas 3 in production.
- ✓ Watch for slow consumers.
