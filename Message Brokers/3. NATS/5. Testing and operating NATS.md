# Testing and Operating NATS

> **Applies to:** NATS Server 2.10+ · NATS Java client (jnats) 2.x · Spring Boot 3.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

NATS is easy to run in tests — the server is a small container that starts in well under a second — and in production a 3-node cluster with JetStream covers most needs. This page covers integration testing, then the configuration, monitoring and security you need to run it.

**Key Concept**: Because Spring Boot has no NATS auto-configuration (and no `@ServiceConnection` support for it), tests wire the container's URL into your own properties with `@DynamicPropertySource`.

## 1. Integration Tests with Testcontainers

```java
@SpringBootTest
@Testcontainers
class BillingFlowIT {

    @Container
    static GenericContainer<?> nats = new GenericContainer<>(DockerImageName.parse("nats:2.10"))
            .withCommand("-js")                    // enable JetStream
            .withExposedPorts(4222)
            .waitingFor(Wait.forLogMessage(".*Server is ready.*", 1));

    @DynamicPropertySource
    static void natsProperties(DynamicPropertyRegistry registry) {
        registry.add("nats.servers", () -> "nats://" + nats.getHost() + ":" + nats.getMappedPort(4222));
    }

    @Autowired Connection connection;
    @Autowired NatsJson json;
    @Autowired InvoiceRepository invoices;

    @Test
    void createsInvoiceForOrder() throws Exception {
        connection.publish("orders.created.eu", json.write(new OrderCreated("e-1", "o-1", "eu", new BigDecimal("42.00"))));
        connection.flush(Duration.ofSeconds(1));

        await().atMost(Duration.ofSeconds(5))
               .untilAsserted(() -> assertThat(invoices.findByOrderId("o-1")).isPresent());
    }
}
```

The data written by a JetStream-enabled container lives inside the container, so each test run starts clean. Within one run, give each test its own subjects or IDs, or purge streams in `@BeforeEach` (`jsm.purgeStream("ORDERS")`).

### Testing Request/Reply

```java
@Test
void pricingResponderAnswers() throws Exception {
    Message reply = connection.request("pricing.quote", json.write(new QuoteRequest("p-1", 2)))
                              .get(2, TimeUnit.SECONDS);

    assertThat(json.read(reply.getData(), PriceQuote.class).amount()).isEqualByComparingTo("19.98");
}
```

### Testing JetStream Redelivery

```java
@Test
void failingMessageIsRedeliveredThenDeadLettered() throws Exception {
    doThrow(new IllegalStateException("db down")).when(billingService).handle(any());

    connection.jetStream().publish("orders.created.eu", json.write(sampleEvent()),
            PublishOptions.builder().messageId("e-dlq-1").build());

    await().atMost(Duration.ofSeconds(20)).untilAsserted(() ->
            assertThat(jsm.getStreamInfo("DLQ").getStreamState().getMsgCount()).isEqualTo(1));
    verify(billingService, atLeast(5)).handle(any());     // maxDeliver = 5
}
```

Shorten `backoff`/`ackWait` in test configuration so redelivery tests take seconds.

### Unit Tests

Keep message handlers as plain methods that take a deserialized object, and test them without NATS. For code that publishes, wrap the `Connection` in a small publisher class and mock that, rather than mocking jnats interfaces.

## 2. Production Cluster

```text
# nats-1.conf (similar on nats-2 and nats-3)
server_name: nats-1
listen: 0.0.0.0:4222
http: 0.0.0.0:8222                 # monitoring

jetstream {
  store_dir: /data/jetstream
  max_file_store: 100GB
}

cluster {
  name: prod-eu
  listen: 0.0.0.0:6222
  routes: [
    nats://nats-1:6222
    nats://nats-2:6222
    nats://nats-3:6222
  ]
}
```

- On Kubernetes, use the official **NATS Helm chart** (StatefulSet with persistent volumes for JetStream).
- Clients list several servers (`nats://nats-1:4222,nats://nats-2:4222,...`); they also learn the rest of the cluster from the server they connect to.
- Use **lame duck mode** (`nats-server --signal ldm`) for rolling upgrades: the server stops accepting new clients and gradually moves existing ones to other servers.

## 3. Monitoring

The HTTP monitoring port serves JSON endpoints:

| Endpoint | Shows |
|---|---|
| `/varz` | Server stats: connections, messages, bytes, slow consumers, memory |
| `/connz` | Per-connection details, including pending bytes and subscriptions |
| `/routez`, `/gatewayz`, `/leafz` | Cluster, supercluster and leaf node links |
| `/jsz` | JetStream: streams, consumers, storage, Raft health |
| `/healthz` | Health check (use for liveness/readiness probes) |

Export to Prometheus with the **Prometheus NATS exporter** (included as a sidecar in the Helm chart). Metrics to alert on:

| Metric | Why |
|---|---|
| Slow consumers (count increasing) | Core NATS subscribers are dropping messages |
| Consumer `num_pending` | JetStream equivalent of consumer lag |
| Consumer `num_ack_pending` / `num_redelivered` | Processing stuck or failing |
| DLQ stream message count | Messages that exhausted retries |
| JetStream storage used vs limit | Streams about to hit limits (discard or reject) |
| Raft / meta leader changes | Cluster instability |

From the CLI: `nats server report jetstream`, `nats consumer report ORDERS`, `nats server check stream`.

## 4. Security

- **TLS** for client and cluster connections.
- **Authentication** — NKeys or JWT-based decentralized auth (operator/account/user, managed with `nsc`). Users carry permissions in their credentials, so no server restart is needed to add or change them.
- **Authorization** — per-user publish/subscribe permissions on subjects, e.g. the billing service may subscribe to `orders.created.>` and publish to `billing.>`.
- **Accounts** — isolate teams or tenants; share specific subjects explicitly with exports/imports.

```java
Options options = Options.builder()
        .servers(servers)
        .authHandler(Nats.credentials("/etc/nats/billing.creds"))   // JWT + NKey seed file
        .sslContext(sslContext)                                      // or use tls:// URLs
        .build();
```

## 5. Common Pitfalls

### ⚠️ No persistent volumes for JetStream

On Kubernetes, JetStream data on ephemeral storage disappears with the pod. Use PersistentVolumeClaims.

### ⚠️ Even-sized clusters

Raft needs a majority. A 2-node cluster can't tolerate any failure for R2+ streams; use 3 or 5 nodes.

### ⚠️ One user for everything

Shared credentials with full permissions make it impossible to restrict or audit services. Give each service its own user and subject permissions.

### ⚠️ Not alerting on slow consumers

On core NATS, a slow consumer means lost messages, not just delay.

## Summary & Best Practices

- ✓ Testcontainers `GenericContainer("nats:2.10").withCommand("-js")` + `@DynamicPropertySource`.
- ✓ 3-node cluster, JetStream on persistent storage, replicas 3.
- ✓ Monitor `/varz` and `/jsz` via the Prometheus exporter; alert on slow consumers, pending and DLQs.
- ✓ TLS, per-service credentials and subject permissions.
- ✓ Lame duck mode for rolling upgrades.
