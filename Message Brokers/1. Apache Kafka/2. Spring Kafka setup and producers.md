# Spring Kafka Setup and Producers

> **Applies to:** Spring Boot 3.x (Spring for Apache Kafka 3.x) · Java 17+ · **Last updated:** 2026-11-21

## Overview

Spring for Apache Kafka (`spring-kafka`) wraps the Kafka Java client with Spring idioms: `KafkaTemplate` for sending, `@KafkaListener` for consuming, and Spring Boot auto-configuration driven by `spring.kafka.*` properties. This page covers project setup, topic creation, serialization and how to send records reliably.

**Key Concept**: A send is asynchronous. `KafkaTemplate.send()` returns immediately with a `CompletableFuture`; the record is batched and sent in the background. Whether a send *succeeded* is only known when that future completes.

## 1. Setup

### Dependencies

```xml
<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
</dependency>

<!-- Tests -->
<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka-test</artifactId>
    <scope>test</scope>
</dependency>
```

The version is managed by Spring Boot's dependency management — don't pin it yourself.

### Minimal Configuration

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      acks: all
      properties:
        enable.idempotence: true          # default since Kafka 3.0; stated for clarity
        delivery.timeout.ms: 120000       # total time allowed for a send, including retries
        linger.ms: 5                      # wait up to 5 ms to fill a batch
        spring.json.add.type.headers: false
```

> Spring Boot 4 / Spring for Apache Kafka 4 move to Jackson 3, and the JSON serializer classes changed. If you're on Boot 4, check the Spring for Apache Kafka migration guide for the new class names.

### Declaring Topics

Spring Boot auto-configures a `KafkaAdmin`, which creates every `NewTopic` bean at startup if the topic doesn't exist yet:

```java
@Configuration
public class KafkaTopicConfig {

    @Bean
    public NewTopic ordersTopic() {
        return TopicBuilder.name("orders")
                .partitions(6)
                .replicas(3)
                .config(TopicConfig.MIN_IN_SYNC_REPLICAS_CONFIG, "2")
                .build();
    }

    @Bean
    public NewTopic customerProfilesTopic() {
        return TopicBuilder.name("customer-profiles")
                .partitions(6)
                .replicas(3)
                .compact()                     // cleanup.policy=compact
                .build();
    }
}
```

⚠️ In many companies topics are managed by a platform team (Terraform, Strimzi `KafkaTopic` resources, GitOps). If so, don't create them from the application — the app may not even have permission.

## 2. Sending Records with KafkaTemplate

### Fire-and-Forget (Don't)

```java
kafkaTemplate.send("orders", order.id(), event);  // ❌ failures are silently ignored
```

### Handling the Result

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderEventPublisher {

    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public CompletableFuture<SendResult<String, OrderEvent>> publish(OrderEvent event) {
        return kafkaTemplate.send("orders", event.orderId(), event)   // key = orderId → per-order ordering
                .whenComplete((result, ex) -> {
                    if (ex != null) {
                        log.error("Failed to publish {} for order {}", event.type(), event.orderId(), ex);
                        return;
                    }
                    RecordMetadata md = result.getRecordMetadata();
                    log.debug("Published to {}-{} at offset {}", md.topic(), md.partition(), md.offset());
                });
    }
}
```

### Waiting for the Broker (Synchronous Send)

When the caller must know the record is stored — for example before returning `201 Created` — block on the future with a timeout:

```java
public void publishAndWait(OrderEvent event) {
    try {
        kafkaTemplate.send("orders", event.orderId(), event).get(10, TimeUnit.SECONDS);
    } catch (ExecutionException e) {
        throw new EventPublishingException("Kafka rejected the event", e.getCause());
    } catch (TimeoutException e) {
        throw new EventPublishingException("Timed out waiting for Kafka", e);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new EventPublishingException("Interrupted while publishing", e);
    }
}
```

Blocking per record limits throughput, because batching can't help much. For bulk sends, send everything first, then wait for all the futures:

```java
List<CompletableFuture<?>> futures = events.stream()
        .map(e -> kafkaTemplate.send("orders", e.orderId(), e))
        .collect(Collectors.toList());
CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new)).get(30, TimeUnit.SECONDS);
```

### Headers and ProducerRecord

```java
ProducerRecord<String, OrderEvent> record = new ProducerRecord<>("orders", event.orderId(), event);
record.headers()
      .add("event-type", event.type().name().getBytes(StandardCharsets.UTF_8))
      .add("schema-version", "2".getBytes(StandardCharsets.UTF_8));
kafkaTemplate.send(record);
```

Spring's `Message` API works too:

```java
Message<OrderEvent> message = MessageBuilder.withPayload(event)
        .setHeader(KafkaHeaders.TOPIC, "orders")
        .setHeader(KafkaHeaders.KEY, event.orderId())
        .setHeader("event-type", event.type().name())
        .build();
kafkaTemplate.send(message);
```

### A Default Topic

```java
@Bean
public KafkaTemplate<String, OrderEvent> orderKafkaTemplate(ProducerFactory<String, OrderEvent> pf) {
    KafkaTemplate<String, OrderEvent> template = new KafkaTemplate<>(pf);
    template.setDefaultTopic("orders");
    return template;
}

// then
orderKafkaTemplate.sendDefault(event.orderId(), event);
```

## 3. Serialization

| Format | Serializer | Pros | Cons |
|---|---|---|---|
| String | `StringSerializer` | Simple, human-readable | You serialize yourself |
| JSON | Spring's `JsonSerializer` | No schema tooling needed, readable | No enforced schema; type info in headers couples producer and consumer packages |
| Avro / Protobuf | Confluent / Apicurio serializers + Schema Registry | Compact, enforced schemas, compatibility checks | Extra infrastructure |

### JSON Type Headers

By default `JsonSerializer` adds a `__TypeId__` header containing the **fully qualified Java class name**. A consumer in another service, with the class in a different package, can't deserialize it. Two fixes:

```yaml
# Option 1: no type headers; the consumer declares the target type
spring.kafka.producer.properties.spring.json.add.type.headers: false
spring.kafka.consumer.properties.spring.json.value.default.type: com.example.billing.OrderEvent

# Option 2: logical type names mapped on both sides
spring.kafka.producer.properties.spring.json.type.mapping: orderEvent:com.example.orders.OrderEvent
spring.kafka.consumer.properties.spring.json.type.mapping: orderEvent:com.example.billing.OrderEvent
```

For schema-managed formats, see [Schema management with Avro and Schema Registry](7.%20Schema%20management%20with%20Avro%20and%20Schema%20Registry.md).

## 4. Producer Reliability Settings

| Property | Recommended | Why |
|---|---|---|
| `acks` | `all` | Wait until all in-sync replicas have the record |
| `enable.idempotence` | `true` | Broker de-duplicates producer retries, so retries can't create duplicates or reorder records in a partition |
| `retries` | default (`Integer.MAX_VALUE`) | Retry transient errors; bounded by `delivery.timeout.ms` |
| `delivery.timeout.ms` | `120000` (default) | Upper bound for a send, including retries. After it, the future fails. |
| `max.in.flight.requests.per.connection` | ≤ 5 (default 5) | Must be ≤ 5 for idempotence to keep ordering |

### Throughput Settings

| Property | Effect |
|---|---|
| `linger.ms` | Wait a few ms to fill batches. Default 5 ms since Kafka 4.0 (0 before). Higher = bigger batches, slightly higher latency. |
| `batch.size` | Max batch size per partition (default 16 KB). Raise to 64–128 KB for high-volume topics. |
| `compression.type` | `lz4` or `zstd` cut network and disk use substantially for JSON payloads. |
| `buffer.memory` | Memory for unsent records (default 32 MB). When full, `send()` blocks up to `max.block.ms`. |

## 5. Observability

```yaml
spring:
  kafka:
    template:
      observation-enabled: true    # Micrometer observation + trace propagation via headers
```

With Micrometer Tracing on the classpath, the trace context is written into record headers, so a consumer with `spring.kafka.listener.observation-enabled=true` continues the same trace.

Kafka client metrics (`kafka.producer.*`: record send rate, error rate, request latency) are bound to the `MeterRegistry` automatically by Spring Boot.

## 6. Common Pitfalls

### ⚠️ Publishing inside a database transaction

```java
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    kafkaTemplate.send("orders", order.id(), OrderPlaced.from(order));
    // ❌ If the DB commit fails after this line, the event was already sent.
    // ❌ If Kafka is down, the order is saved but no event is ever published.
}
```

Kafka and your database can't share one atomic transaction. Use the **transactional outbox** pattern — see [Exactly-once semantics and transactions](5.%20Exactly-once%20semantics%20and%20transactions.md#4-the-transactional-outbox-pattern).

### ⚠️ No key for entity events

Without a key, records are spread across partitions (sticky partitioning), so `OrderCreated` and `OrderCancelled` for the same order can be consumed out of order.

### ⚠️ Ignoring the send future

Errors like `RecordTooLargeException`, authorization failures or a timeout are only reported through the future. Always attach a callback or wait for it.

### ⚠️ Huge messages

The default maximum record size is about 1 MB (`max.request.size` on the producer, `message.max.bytes` on the broker). Store large payloads (files, documents) in object storage and send a reference.

## Summary & Best Practices

```java
kafkaTemplate.send(topic, key, value)          // returns CompletableFuture<SendResult>
    .whenComplete((result, ex) -> { ... });    // always handle the outcome
```

- ✓ Use a meaningful key for ordering per entity.
- ✓ Keep `acks=all` and idempotence on (both are defaults since Kafka 3.0).
- ✓ Handle every send's result; block with a timeout only where the caller needs confirmation.
- ✓ Avoid Java class names in JSON type headers between services.
- ✓ Enable compression and tune `linger.ms`/`batch.size` for high-volume topics.
- ✓ Use the outbox pattern when an event must match a database change.
