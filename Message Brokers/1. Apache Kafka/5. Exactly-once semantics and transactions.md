# Exactly-Once Semantics and Transactions

> **Applies to:** Spring Boot 3.x (Spring for Apache Kafka 3.x) · Java 17+ · **Last updated:** 2026-11-21

## Overview

"Exactly once" in Kafka has a precise, narrow meaning: **reading from Kafka, processing, and writing results back to Kafka** happens atomically — the output records and the consumer's offset commit are part of one Kafka transaction. It does **not** cover side effects outside Kafka (a database write, an email, an HTTP call).

This page covers:
1. The idempotent producer (no duplicates from producer retries).
2. Kafka transactions for consume-transform-produce.
3. Why Kafka and a database can't share a transaction, and what to do instead.
4. The transactional outbox pattern.

**Key Concept**: For anything that touches a database or an external system, the practical guarantee is **at-least-once delivery + idempotent processing**. Kafka transactions solve the Kafka-to-Kafka part.

---

## 1. The Idempotent Producer

Without idempotence, a producer retry after a lost acknowledgement can write the same record twice.

```
Producer ──send(r1)──► Broker (writes r1)
         ◄──ack lost──
Producer ──retry r1──► Broker (writes r1 again)  ❌ duplicate
```

With `enable.idempotence=true` (the default since Kafka 3.0), the producer gets a producer ID and numbers each record per partition. The broker drops duplicates and rejects out-of-order sequence numbers, so retries can't create duplicates or reorder records.

Scope: **one producer session**, writing to Kafka. If your application crashes and sends the same business event again after restart, that's a new record — idempotence doesn't help there.

## 2. Kafka Transactions

A transaction groups writes to several partitions/topics, plus consumer offset commits, so they're all visible or none are.

### Enabling Transactions in Spring Boot

```yaml
spring:
  kafka:
    producer:
      transaction-id-prefix: billing-tx-     # enables transactions + KafkaTransactionManager
    consumer:
      isolation-level: read_committed        # don't read records from aborted/open transactions
      enable-auto-commit: false
```

Setting `transaction-id-prefix` makes Spring Boot create a `KafkaTransactionManager` and makes `KafkaTemplate` transactional. Each producer instance gets a `transactional.id` based on the prefix; in a scaled-out deployment the prefix must result in **unique** IDs per instance (Spring adds a suffix per producer, and for consumer-initiated transactions it reuses producers per group/topic/partition).

### Consume-Transform-Produce

When a listener container has a `KafkaTransactionManager` (Spring Boot sets it up automatically when transactions are enabled), each listener invocation runs in a Kafka transaction:

```java
@Component
@RequiredArgsConstructor
public class InvoiceGenerator {

    private final KafkaTemplate<String, Object> kafkaTemplate;

    @KafkaListener(topics = "orders-completed", groupId = "invoicing")
    public void onOrderCompleted(OrderCompleted event) {
        Invoice invoice = Invoice.from(event);

        kafkaTemplate.send("invoices", invoice.orderId(), invoice);
        kafkaTemplate.send("ledger-entries", invoice.orderId(), LedgerEntry.from(invoice));

        // When this method returns, the container:
        //   1. sends the consumer offset to the transaction,
        //   2. commits the transaction.
        // If it throws, the transaction is aborted: neither record becomes visible
        // to read_committed consumers, and the input record is redelivered.
    }
}
```

### Producer-Only Transactions

```java
kafkaTemplate.executeInTransaction(ops -> {
    ops.send("accounts", from, Debit.of(from, amount));
    ops.send("accounts", to, Credit.of(to, amount));
    return null;
});
```

or with `@Transactional("kafkaTransactionManager")` on a service method that sends several records.

### What It Costs

- Extra round-trips to the transaction coordinator per transaction — batch several records into one transaction where possible.
- Consumers must use `read_committed` to benefit; otherwise they also see records from aborted transactions.
- `read_committed` consumers can only read up to the *last stable offset*: one long-running open transaction delays everyone on that partition.

## 3. Kafka and a Database: No Shared Transaction

A common wish:

```java
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);                                // DB transaction
    kafkaTemplate.send("orders", order.id(), OrderPlaced.of(order));  // Kafka
}
```

Kafka doesn't support XA/two-phase commit, so these can't be one atomic unit. Spring can *synchronize* the two transactions (commit one right after the other), but there's always a window where one commits and the other fails:

| Failure | Result |
|---|---|
| DB commits, Kafka send fails | Order saved, **no event** — downstream never learns about it |
| Kafka commits, DB commit fails | **Event for an order that doesn't exist** |

For consumers the same applies in reverse: if the DB write commits but the offset commit fails, the record is delivered again — which is fine **if the handler is idempotent**.

## 4. The Transactional Outbox Pattern

Write the event to an `outbox` table **in the same database transaction** as the business change. A separate process publishes outbox rows to Kafka.

```
┌─────────────── one DB transaction ───────────────┐
│ INSERT INTO orders ...                            │
│ INSERT INTO outbox (aggregate_id, type, payload)  │
└───────────────────────────────────────────────────┘
                     │
        relay (poller or CDC/Debezium)
                     ▼
               Kafka topic "orders"
```

### Outbox Table

```sql
CREATE TABLE outbox (
    id            UUID PRIMARY KEY,
    aggregate_id  VARCHAR(64)  NOT NULL,   -- becomes the Kafka key
    event_type    VARCHAR(128) NOT NULL,
    payload       JSONB        NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at  TIMESTAMPTZ
);
CREATE INDEX outbox_unpublished ON outbox (created_at) WHERE published_at IS NULL;
```

### Writing to the Outbox

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;
    private final ObjectMapper objectMapper;

    @Transactional
    public Order placeOrder(PlaceOrder command) {
        Order order = orders.save(Order.from(command));
        outbox.save(OutboxEvent.of(order.getId(), "OrderPlaced",
                objectMapper.valueToTree(OrderPlaced.from(order))));
        return order;   // both rows commit together, or neither does
    }
}
```

### Option A: Polling Relay

```java
@Component
@RequiredArgsConstructor
public class OutboxRelay {

    private final OutboxRepository outbox;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 500)
    @Transactional
    public void publishPending() {
        // FOR UPDATE SKIP LOCKED lets several instances run the relay without double-sending
        List<OutboxEvent> batch = outbox.lockNextBatch(100);
        for (OutboxEvent e : batch) {
            kafkaTemplate.send("orders", e.getAggregateId(), e.getPayload().toString())
                         .get(10, TimeUnit.SECONDS);       // wait: only mark as published on success
            e.markPublished();
        }
    }
}
```

```java
public interface OutboxRepository extends JpaRepository<OutboxEvent, UUID> {
    @Query(value = """
            SELECT * FROM outbox
            WHERE published_at IS NULL
            ORDER BY created_at
            LIMIT :limit
            FOR UPDATE SKIP LOCKED
            """, nativeQuery = true)
    List<OutboxEvent> lockNextBatch(int limit);
}
```

The relay is at-least-once: if it crashes after sending but before committing, the rows are sent again. Consumers deduplicate using the outbox `id` (send it as a header or in the payload).

### Option B: Change Data Capture (Debezium)

Debezium reads the database's write-ahead log and publishes outbox inserts to Kafka — no polling, low latency, and the database load is minimal. Its *outbox event router* turns rows into records with the right topic, key and headers. It needs Kafka Connect (or Debezium Server) to run.

| | Polling relay | Debezium CDC |
|---|---|---|
| Infrastructure | None beyond the app | Kafka Connect + Debezium |
| Latency | Poll interval | Near real time |
| DB load | Periodic queries | Reads the WAL/binlog |
| Ordering | By `created_at` per relay | Commit order |

## 5. Common Pitfalls

### ⚠️ Expecting exactly-once side effects

Kafka transactions don't make your `INSERT`, email or HTTP call happen exactly once. Make those idempotent.

### ⚠️ Forgetting `read_committed`

Consumers default to `read_uncommitted` and will see records from aborted transactions.

### ⚠️ Non-unique `transactional.id`

Two live producers with the same transactional ID fence each other off (`ProducerFencedException`). Make the prefix unique per application, and let Spring add per-instance suffixes.

### ⚠️ Deleting outbox rows too early

Keep published rows for a while (or archive them) — they're your audit trail when debugging "the event never arrived".

## Summary & Best Practices

| Need | Use |
|---|---|
| No duplicates from producer retries | Idempotent producer (default) |
| Atomic Kafka → Kafka processing | Kafka transactions + `read_committed` |
| Event must match a DB change | Transactional outbox (polling or Debezium) |
| Consumer writes to a DB | At-least-once + idempotent handler (dedup table, upserts, version checks) |

- ✓ Treat "exactly once" as Kafka-internal; design every consumer to be idempotent anyway.
- ✓ Use the outbox pattern instead of sending to Kafka inside a DB transaction.
- ✓ Put an event ID in every record so consumers can deduplicate.
