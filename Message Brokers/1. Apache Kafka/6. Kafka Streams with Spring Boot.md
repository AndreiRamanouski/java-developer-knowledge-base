# Kafka Streams with Spring Boot

> **Applies to:** Spring Boot 3.x (Spring for Apache Kafka 3.x, Kafka Streams 3.x) · Java 17+ · **Last updated:** 2026-11-21

## Overview

Kafka Streams is a Java **library** (not a cluster) for processing data continuously from Kafka topics into Kafka topics. Your Spring Boot service *is* the stream processor: you scale it by running more instances, and Kafka Streams spreads partitions across them.

Typical uses:
- **Transform and route** — filter, enrich, re-key events.
- **Aggregate** — running totals, counts per customer, windowed metrics.
- **Join** — enrich order events with the latest customer profile.
- **Materialized views** — a queryable, always-up-to-date table built from events.

**Key Concept**: Kafka Streams has two core abstractions. A **KStream** is a stream of independent events ("order placed"). A **KTable** is a changelog where each key's latest value is the current state ("customer 42's address is …").

## 1. Setup

```xml
<dependency>
    <groupId>org.apache.kafka</groupId>
    <artifactId>kafka-streams</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
</dependency>
```

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    streams:
      application-id: order-analytics        # also the consumer group id and state-store prefix
      properties:
        default.key.serde: org.apache.kafka.common.serialization.Serdes$StringSerde
        default.value.serde: org.springframework.kafka.support.serializer.JsonSerde
        spring.json.trusted.packages: com.example.analytics
        processing.guarantee: exactly_once_v2
        num.stream.threads: 2
```

```java
@Configuration
@EnableKafkaStreams          // Spring Boot creates and starts the KafkaStreams instance
public class KafkaStreamsSetup {   // don't name it StreamsConfig: clashes with org.apache.kafka.streams.StreamsConfig
}
```

`application-id` must be the same for all instances of one application and unique across different applications.

## 2. A First Topology

Spring Boot provides a `StreamsBuilder` bean; inject it into a `@Bean` method and define the topology:

```java
@Configuration
public class OrderTopology {

    @Bean
    public KStream<String, OrderEvent> orderStream(StreamsBuilder builder) {
        KStream<String, OrderEvent> orders = builder.stream("orders",
                Consumed.with(Serdes.String(), new JsonSerde<>(OrderEvent.class)));

        // 1. Stateless: route high-value orders to a separate topic
        orders.filter((orderId, order) -> order.total().compareTo(new BigDecimal("1000")) > 0)
              .to("orders-high-value", Produced.with(Serdes.String(), new JsonSerde<>(OrderEvent.class)));

        // 2. Re-key by customer and count orders per customer (stateful)
        orders.selectKey((orderId, order) -> order.customerId())
              .groupByKey(Grouped.with(Serdes.String(), new JsonSerde<>(OrderEvent.class)))
              .count(Materialized.as("orders-per-customer"))
              .toStream()
              .to("orders-per-customer", Produced.with(Serdes.String(), Serdes.Long()));

        return orders;
    }
}
```

### Stateless vs Stateful Operations

| Stateless | Stateful (needs a state store) |
|---|---|
| `filter`, `map`, `mapValues`, `flatMap`, `selectKey`, `branch`/`split`, `peek`, `to` | `count`, `reduce`, `aggregate`, joins, windowing |

State stores are local (RocksDB on disk by default) and backed by a compacted **changelog topic** in Kafka, so state survives restarts and moves with partitions to other instances.

## 3. Re-keying and Repartitioning

Grouping or joining requires records with the same key to be in the same partition. After `selectKey`/`map`, Kafka Streams writes the records to an internal **repartition topic** and reads them back:

```
orders (key=orderId) ──selectKey(customerId)──► order-analytics-...-repartition ──► count
```

That's an extra round-trip through Kafka. Prefer `mapValues` over `map` when the key doesn't change — it avoids repartitioning.

## 4. Windowed Aggregations

```java
// Revenue per product in 5-minute tumbling windows
orders.groupBy((orderId, order) -> order.productId(),
               Grouped.with(Serdes.String(), new JsonSerde<>(OrderEvent.class)))
      .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ofMinutes(1)))
      .aggregate(
              () -> BigDecimal.ZERO,
              (productId, order, total) -> total.add(order.total()),
              Materialized.with(Serdes.String(), new JsonSerde<>(BigDecimal.class)))
      .toStream()
      .map((windowedKey, total) -> KeyValue.pair(
              windowedKey.key() + "@" + windowedKey.window().startTime(), total))
      .to("revenue-per-product-5m", Produced.with(Serdes.String(), new JsonSerde<>(BigDecimal.class)));
```

| Window | Shape | Example |
|---|---|---|
| Tumbling | Fixed, non-overlapping | Orders per 5 minutes |
| Hopping | Fixed size, overlapping (advance < size) | 10-minute average every minute |
| Sliding | Defined by time difference between records | Events within 30 s of each other |
| Session | Activity separated by an inactivity gap | User sessions with a 30-minute timeout |

The **grace period** decides how long late records are still accepted into a window. Windows use event time (record timestamps), not processing time.

## 5. Joins: Enriching Streams with Tables

```java
KTable<String, Customer> customers = builder.table("customer-profiles",
        Consumed.with(Serdes.String(), new JsonSerde<>(Customer.class)));

KStream<String, OrderEvent> ordersByCustomer = orders.selectKey((id, o) -> o.customerId());

ordersByCustomer
        .join(customers,
              (order, customer) -> EnrichedOrder.of(order, customer),        // ValueJoiner
              Joined.with(Serdes.String(), new JsonSerde<>(OrderEvent.class), new JsonSerde<>(Customer.class)))
        .to("orders-enriched", Produced.with(Serdes.String(), new JsonSerde<>(EnrichedOrder.class)));
```

- **KStream–KTable join** — look up the current table value for each event. Both sides must be **co-partitioned**: same key, same number of partitions.
- **GlobalKTable** — the whole table is replicated to every instance, so no co-partitioning is needed. Good for small reference data (countries, product catalog).
- **KStream–KStream join** — joins events within a time window (e.g. payment within 10 minutes of order).

## 6. Interactive Queries

A state store can be queried directly from the service, turning it into a read model:

```java
@RestController
@RequiredArgsConstructor
public class CustomerStatsController {

    private final StreamsBuilderFactoryBean factoryBean;

    @GetMapping("/customers/{id}/order-count")
    public Long orderCount(@PathVariable String id) {
        KafkaStreams streams = factoryBean.getKafkaStreams();
        ReadOnlyKeyValueStore<String, Long> store = streams.store(
                StoreQueryParameters.fromNameAndType("orders-per-customer", QueryableStoreTypes.keyValueStore()));
        return store.get(id);
    }
}
```

⚠️ Each instance holds only the keys of its own partitions. With several instances, find the owner via `streams.queryMetadataForKey(...)` and forward the request (Spring Kafka's `KafkaStreamsInteractiveQueryService` helps with this).

## 7. Error Handling and Operations

```yaml
spring:
  kafka:
    streams:
      properties:
        # Skip (and log) records that can't be deserialized instead of crashing
        default.deserialization.exception.handler: org.apache.kafka.streams.errors.LogAndContinueExceptionHandler
```

```java
@Bean
public StreamsBuilderFactoryBeanConfigurer uncaughtHandler() {
    return factoryBean -> factoryBean.setStreamsUncaughtExceptionHandler(ex -> {
        log.error("Stream thread failed", ex);
        return StreamsUncaughtExceptionHandler.StreamThreadExceptionResponse.REPLACE_THREAD;
    });
}
```

Spring Kafka also offers `RecoveringDeserializationExceptionHandler`, which sends undeserializable records to a dead-letter topic.

Operational notes:
- **State restoration** — a new instance restores state from changelog topics before processing; large stores take time. `num.standby.replicas: 1` keeps warm copies on other instances for faster failover.
- **Persistent volumes** — in Kubernetes, run Kafka Streams apps with persistent state (StatefulSet) to avoid full restores on every restart.
- **Topology changes** — renaming or reordering stateful operators changes internal topic names. Name them explicitly (`Named.as(...)`, `Materialized.as(...)`, `Grouped.as(...)`) so upgrades keep their state.

## 8. Testing with TopologyTestDriver

No broker needed:

```java
class OrderTopologyTest {

    @Test
    void countsOrdersPerCustomer() {
        StreamsBuilder builder = new StreamsBuilder();
        new OrderTopology().orderStream(builder);

        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "test");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "dummy:1234");

        try (TopologyTestDriver driver = new TopologyTestDriver(builder.build(), props)) {
            TestInputTopic<String, OrderEvent> in = driver.createInputTopic("orders",
                    new StringSerializer(), new JsonSerializer<>());
            TestOutputTopic<String, Long> out = driver.createOutputTopic("orders-per-customer",
                    new StringDeserializer(), new LongDeserializer());

            in.pipeInput("o-1", new OrderEvent("o-1", "c-42", new BigDecimal("20"), "p-1"));
            in.pipeInput("o-2", new OrderEvent("o-2", "c-42", new BigDecimal("30"), "p-2"));

            assertThat(out.readKeyValuesToMap()).containsEntry("c-42", 2L);
        }
    }
}
```

`StreamsConfig` here is Kafka's `org.apache.kafka.streams.StreamsConfig`.

## 9. Common Pitfalls

### ⚠️ Joining topics that aren't co-partitioned

A KStream–KTable join silently produces no matches (or the app fails at startup) when the topics have different partition counts or keys. Re-key and check partition counts, or use a `GlobalKTable`.

### ⚠️ Unnamed stateful operators

Auto-generated names like `KSTREAM-AGGREGATE-STATE-STORE-0000000003` shift when the topology changes, and the app loses its state on deploy.

### ⚠️ Using Kafka Streams for request/response

It's built for continuous processing. Calling slow external services inside `mapValues` blocks the stream thread and stalls partitions.

---

## Summary & Best Practices

- ✓ Use KStream for events, KTable for current state, GlobalKTable for small reference data.
- ✓ Name every stateful operator and store explicitly.
- ✓ Prefer `mapValues` over `map` to avoid repartitioning.
- ✓ Use `exactly_once_v2` for Kafka → Kafka correctness.
- ✓ Test topologies with `TopologyTestDriver`; keep integration tests for wiring only.
