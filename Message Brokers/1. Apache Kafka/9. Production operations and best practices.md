# Production Operations and Best Practices

> **Applies to:** Apache Kafka 3.x–4.x · Spring Boot 3.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

Most Kafka incidents in application teams come from a short list: consumer lag nobody noticed, rebalance storms during deploys, topics created with the wrong settings, and poison pills. This page collects the settings, metrics and habits that prevent them.

**Key Concept**: **Consumer lag** — how far a consumer group is behind the end of the log — is the single most important health signal for a Kafka consumer.

---

## 1. Topic Design

### Naming

Pick a convention and enforce it, for example `<domain>.<entity>.<event-type>.v<version>`:

```
orders.order.placed.v1
payments.payment.events.v1      # several event types for one entity on one topic
```

### Settings Checklist

| Setting | Recommendation |
|---|---|
| Partitions | Based on target throughput ÷ per-consumer throughput, with headroom. Fixed for keyed topics. |
| Replication factor | 3 |
| `min.insync.replicas` | 2 |
| `cleanup.policy` | `delete` for events, `compact` for current-state topics |
| `retention.ms` | Long enough to replay after an incident (often 7–30 days) |
| `max.message.bytes` | Leave the default (~1 MB); store large payloads elsewhere |

### One Topic or Many?

- **One event type per topic** — simple schemas and consumers, but no ordering between, say, `OrderPlaced` and `OrderCancelled`.
- **All events of one entity on one topic, keyed by entity ID** — preserves the order of an entity's lifecycle. Usually the better choice for domain events.

## 2. Monitoring

### Consumer Lag

```bash
kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group billing-service

GROUP            TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
billing-service  orders  0          120450          120452          2
billing-service  orders  1          98012           112880          14868   ← falling behind
```

In production, export lag continuously:
- **Kafka Exporter** or **Burrow** → Prometheus, or the lag metrics from your managed service (Confluent Cloud, MSK, Aiven…).
- The consumer client's own `records-lag-max` metric (bound to Micrometer by Spring Boot as `kafka.consumer.fetch.manager.records.lag.max`).

Alert on **lag that keeps growing** or on **time lag** (how old the oldest unprocessed record is), not on a fixed record count — 10,000 records may be seconds of work on one topic and hours on another.

### Key Metrics

| Area | Metric | Watch for |
|---|---|---|
| Consumer | Lag, records consumed rate, commit rate | Growing lag, rate drops to 0 |
| Consumer | Rebalance rate (`kafka.consumer.coordinator.rebalance.*`) | Frequent rebalances |
| Producer | Record error rate, request latency | Errors > 0, latency spikes |
| Listener | `spring.kafka.listener` timers (with observation enabled) | Processing time near `max.poll.interval.ms` |
| DLT | Records per minute on `*-dlt` topics | Anything > 0 should be looked at |
| Broker | Under-replicated partitions, offline partitions | Non-zero |

### Tracing

```yaml
spring:
  kafka:
    template:
      observation-enabled: true
    listener:
      observation-enabled: true
```

Trace context travels in record headers, so a request can be followed from the HTTP call through Kafka into downstream consumers.

## 3. Deployments and Scaling

- **Graceful shutdown** — Spring stops listener containers on shutdown, finishing the current batch and committing offsets. Give pods enough `terminationGracePeriodSeconds` for the slowest batch.
- **Rebalances during rolling deploys** — use the cooperative sticky assignor and static membership (`group.instance.id`), or the new consumer protocol on Kafka 4.x (`group.protocol=consumer`). See [Consumers and consumer groups](3.%20Consumers%20and%20consumer%20groups.md#5-polling-timeouts-and-rebalances).
- **Autoscaling on lag** — KEDA's Kafka scaler can scale a Deployment on consumer lag. Cap replicas at the partition count.
- **Startup** — don't fail the whole app when Kafka is briefly unreachable; the client keeps reconnecting. Use readiness probes that reflect whether the app can do useful work.

## 4. Security

```yaml
spring:
  kafka:
    bootstrap-servers: kafka-1:9093,kafka-2:9093,kafka-3:9093
    security:
      protocol: SASL_SSL
    properties:
      sasl.mechanism: SCRAM-SHA-512
      sasl.jaas.config: >
        org.apache.kafka.common.security.scram.ScramLoginModule required
        username="${KAFKA_USERNAME}" password="${KAFKA_PASSWORD}";
    ssl:
      trust-store-location: file:/etc/kafka/truststore.p12
      trust-store-password: ${KAFKA_TRUSTSTORE_PASSWORD}
      trust-store-type: PKCS12
```

- Encrypt traffic (TLS) and authenticate clients (SASL/SCRAM, mTLS, or OAuth/OIDC with `OAUTHBEARER`).
- Use **ACLs**: each service may only write to its own topics and read the topics it consumes, with its own `group.id` prefix.
- Never log record payloads containing personal data; mask or omit them in DLT tooling too.

## 5. Configuration Cheat Sheet

```yaml
spring:
  kafka:
    producer:
      acks: all
      properties:
        enable.idempotence: true
        compression.type: zstd
        linger.ms: 10
        delivery.timeout.ms: 120000
    consumer:
      auto-offset-reset: earliest      # new consumer groups start from the beginning (choose deliberately)
      max-poll-records: 200
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        max.poll.interval.ms: 300000
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
    listener:
      observation-enabled: true
    template:
      observation-enabled: true
```

Plus a `DefaultErrorHandler` bean with backoff and a dead-letter recoverer — see [Error handling, retries and dead-letter topics](4.%20Error%20handling%2C%20retries%20and%20dead-letter%20topics.md).

## 6. Common Pitfalls

### ⚠️ `auto.create.topics.enable=true` in production

A typo in a topic name silently creates a new topic with default settings (often 1 partition, replication factor of the broker default). Disable it and manage topics as code.

### ⚠️ No lag alerting

Consumers can be "up" and healthy-looking while processing nothing (stuck on a poison pill, paused, or idle after a rebalance). Lag reveals it.

### ⚠️ Resetting offsets casually

`kafka-consumer-groups.sh --reset-offsets` is powerful: `--to-earliest` reprocesses everything. Stop the consumers first, run with `--dry-run`, and confirm handlers are idempotent.

### ⚠️ Using Kafka for request/response

Synchronous request/reply over Kafka (`ReplyingKafkaTemplate`) works, but adds latency and complexity. Prefer HTTP/gRPC for queries and Kafka for events.

---

## Summary & Best Practices

- ✓ Topics as code: naming convention, RF 3, `min.insync.replicas=2`, deliberate retention.
- ✓ Monitor and alert on consumer lag, DLT traffic and rebalances.
- ✓ Enable observation/tracing on templates and listeners.
- ✓ Secure with TLS + SASL/mTLS and per-service ACLs.
- ✓ Keep consumers idempotent; reprocessing is a normal operational tool.
