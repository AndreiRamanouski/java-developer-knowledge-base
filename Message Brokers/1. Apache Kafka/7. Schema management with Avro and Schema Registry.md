# Schema Management with Avro and Schema Registry

> **Applies to:** Spring Boot 3.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

Kafka stores bytes; it doesn't know or check what's inside a record. As soon as several teams produce and consume the same topics, you need an agreed **contract** for the payload and a safe way to **evolve** it. A schema registry provides both:

- Producers register the schema they write with; records carry a small schema ID instead of the full schema.
- Consumers fetch the writer's schema by ID and deserialize, even if their own schema version is different.
- The registry **rejects incompatible changes** before they reach production.

Common registries: **Confluent Schema Registry** (Confluent Community License), **Apicurio Registry** (Apache 2.0), and the registries built into managed services such as AWS Glue Schema Registry.

**Key Concept**: Compatibility rules let producers and consumers be deployed independently. With `BACKWARD` compatibility (the Confluent default), a consumer using the new schema can read data written with the old one.

---

## 1. Choosing a Format

| Format | Schema | Size | Notes |
|---|---|---|---|
| JSON (no schema) | Implicit | Large | Easy to start; nothing stops breaking changes |
| JSON Schema | Yes | Large | Familiar; validation, but weaker evolution story |
| **Avro** | Yes (`.avsc`) | Compact binary | De facto standard in the Kafka ecosystem; strong evolution rules |
| Protobuf | Yes (`.proto`) | Compact binary | Great if you already use gRPC; field numbers drive compatibility |

This page uses Avro with Confluent Schema Registry; the concepts carry over to Protobuf and Apicurio.

## 2. Defining a Schema

```json
// src/main/avro/OrderPlaced.avsc
{
  "type": "record",
  "name": "OrderPlaced",
  "namespace": "com.example.events",
  "fields": [
    { "name": "orderId",    "type": "string" },
    { "name": "customerId", "type": "string" },
    { "name": "total",      "type": { "type": "bytes", "logicalType": "decimal", "precision": 12, "scale": 2 } },
    { "name": "placedAt",   "type": { "type": "long", "logicalType": "timestamp-millis" } },
    { "name": "channel",    "type": ["null", "string"], "default": null }
  ]
}
```

Generate Java classes at build time:

```xml
<plugin>
    <groupId>org.apache.avro</groupId>
    <artifactId>avro-maven-plugin</artifactId>
    <version>${avro.version}</version>
    <executions>
        <execution>
            <phase>generate-sources</phase>
            <goals><goal>schema</goal></goals>
            <configuration>
                <sourceDirectory>${project.basedir}/src/main/avro</sourceDirectory>
                <outputDirectory>${project.build.directory}/generated-sources/avro</outputDirectory>
                <stringType>String</stringType>
                <enableDecimalLogicalType>true</enableDecimalLogicalType>
            </configuration>
        </execution>
    </executions>
</plugin>
```

Many teams keep schemas in a shared repository (or a dedicated "contracts" module) and publish the generated classes as a library.

## 3. Spring Boot Configuration

```xml
<repositories>
    <repository>
        <id>confluent</id>
        <url>https://packages.confluent.io/maven/</url>
    </repository>
</repositories>

<dependency>
    <groupId>io.confluent</groupId>
    <artifactId>kafka-avro-serializer</artifactId>
    <version>${confluent.version}</version>
</dependency>
```

```yaml
spring:
  kafka:
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
    consumer:
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: io.confluent.kafka.serializers.KafkaAvroDeserializer
        specific.avro.reader: true          # deserialize into generated classes, not GenericRecord
    properties:
      schema.registry.url: http://localhost:8081
      auto.register.schemas: false          # in production, register schemas from CI, not from apps
      use.latest.version: true
```

```java
// Producer: just send the generated class
kafkaTemplate.send("orders", order.getId(), OrderPlaced.newBuilder()
        .setOrderId(order.getId())
        .setCustomerId(order.getCustomerId())
        .setTotal(order.getTotal())
        .setPlacedAt(order.getPlacedAt())
        .build());

// Consumer
@KafkaListener(topics = "orders")
public void onOrderPlaced(OrderPlaced event) { ... }
```

### Subjects

Schemas are registered under a **subject**. With the default `TopicNameStrategy`, the subject for values on topic `orders` is `orders-value`, so one topic carries one record type. To put several event types on one topic (useful to keep per-entity ordering — `OrderPlaced`, `OrderShipped` on `orders`), use `RecordNameStrategy` or `TopicRecordNameStrategy`:

```yaml
spring.kafka.properties.value.subject.name.strategy: io.confluent.kafka.serializers.subject.TopicRecordNameStrategy
```

## 4. Schema Evolution

| Compatibility | Guarantee | Allowed changes (Avro) | Deploy order |
|---|---|---|---|
| `BACKWARD` (default) | New schema reads old data | Delete fields; add fields **with defaults** | Consumers first |
| `FORWARD` | Old schema reads new data | Add fields; delete fields **with defaults** | Producers first |
| `FULL` | Both | Add/delete only fields with defaults | Any order |
| `*_TRANSITIVE` | Checked against **all** previous versions, not just the latest | Same as above | — |
| `NONE` | No checks | Anything | Avoid |

Safe change, under any mode:

```json
{ "name": "channel", "type": ["null", "string"], "default": null }   // ✅ new optional field with default
```

Breaking changes (rejected by `BACKWARD`/`FULL`):

- adding a field **without** a default,
- changing a field's type (e.g. `int` → `string`),
- renaming a field (use `aliases` instead).

For a genuinely incompatible change, create a **new topic** (`orders.v2`), dual-publish during migration, and move consumers over.

### Checking Compatibility in CI

```bash
# Test a candidate schema against the latest registered version
curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data "{\"schema\": $(jq -Rs . < src/main/avro/OrderPlaced.avsc)}" \
  http://schema-registry:8081/compatibility/subjects/orders-value/versions/latest
# → {"is_compatible": true}
```

The Confluent Maven plugin (`kafka-schema-registry-maven-plugin`) has `test-compatibility` and `register` goals that do the same in the build.

## 5. Local Development

```yaml
# compose.yaml (add to the Kafka service from "Kafka fundamentals")
  schema-registry:
    image: confluentinc/cp-schema-registry:7.7.1
    depends_on: [kafka]
    ports:
      - "8081:8081"
    environment:
      SCHEMA_REGISTRY_HOST_NAME: schema-registry
      SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS: kafka:9092
```

⚠️ Inside the Compose network the broker must advertise a listener reachable as `kafka:9092`; adjust `KAFKA_ADVERTISED_LISTENERS` (for example, one internal and one external listener).

In tests, the serializers accept `schema.registry.url: mock://test-scope`, an in-memory registry — no container needed.

## 6. Common Pitfalls

### ⚠️ Auto-registering schemas from every service

With `auto.register.schemas: true`, any deployment can register a new version, and a bug becomes the official schema. Register from CI after a compatibility check.

### ⚠️ Generic vs specific records

Forgetting `specific.avro.reader: true` returns `GenericRecord` objects and the listener fails with a `ClassCastException`.

### ⚠️ Mixing serialization formats on one topic

A JSON test message on an Avro topic is a poison pill for every consumer. Use `ErrorHandlingDeserializer` and restrict who can produce to the topic.

---

## Summary & Best Practices

- ✓ Use a schema format (Avro/Protobuf) for topics shared between teams.
- ✓ Keep `BACKWARD` (or `FULL`) compatibility; add new fields as optional with defaults.
- ✓ Check compatibility and register schemas in CI; disable auto-registration in production.
- ✓ Breaking change → new topic version and a planned migration.
