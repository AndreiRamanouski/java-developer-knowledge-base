# Error Handling, Retries and Dead-Letter Topics

> **Applies to:** Spring Boot 3.x (Spring for Apache Kafka 3.x) · Java 17+ · **Last updated:** 2026-11-21

## Overview

A Kafka partition is processed in order, so one record that keeps failing blocks every record behind it. Good error handling decides, per failure, between three outcomes:

1. **Retry** — the failure is transient (database timeout, 503 from a downstream service).
2. **Dead-letter** — the record can't be processed (bad data, business rule violation); park it for inspection and move on.
3. **Stop** — something is badly wrong (e.g. the database is down for everyone); pause rather than dead-letter thousands of good records.

**Key Concept**: In Spring Kafka, a listener signals failure by **throwing**. The container's `CommonErrorHandler` — `DefaultErrorHandler` by default — then decides what to do with the failed record.

---

## 1. The Default Behaviour

Without any configuration, `DefaultErrorHandler`:

- retries a failed record **9 more times** with no delay (`FixedBackOff(0, 9)`),
- then logs the error and **skips** the record (its offset is committed).

That's rarely what you want in production: ten instant retries don't help with transient failures, and skipped records are lost silently.

---

## 2. Retries with Backoff and a Dead-Letter Topic

```java
@Configuration
public class KafkaErrorHandlingConfig {

    @Bean
    public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
        // After retries are exhausted, publish the record to "<topic>-dlt", same partition
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template,
                (record, ex) -> new TopicPartition(record.topic() + "-dlt", record.partition()));

        ExponentialBackOffWithMaxRetries backOff = new ExponentialBackOffWithMaxRetries(4);
        backOff.setInitialInterval(1_000);   // 1s, 2s, 4s, 8s
        backOff.setMultiplier(2.0);
        backOff.setMaxInterval(10_000);

        DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);

        // Errors that retrying can't fix go straight to the DLT
        handler.addNotRetryableExceptions(
                ValidationException.class,
                JsonProcessingException.class,
                IllegalArgumentException.class);
        return handler;
    }
}
```

Spring Boot wires a single `CommonErrorHandler` bean into the auto-configured listener container factory.

What the dead-letter record contains:
- the original key and value (as bytes if deserialization failed),
- headers such as `kafka_dlt-exception-fqcn`, `kafka_dlt-exception-message`, `kafka_dlt-exception-stacktrace`, `kafka_dlt-original-topic`, `kafka_dlt-original-partition` and `kafka_dlt-original-offset`.

⚠️ The DLT must exist and have **at least as many partitions** as the source topic when you route to the same partition number. Create it alongside the main topic.

### How blocking retries work

Retries in `DefaultErrorHandler` are **blocking**: the container seeks back to the failed offset and re-polls, so records after it in that partition wait. With a 1+2+4+8 s backoff, the partition stalls for ~15 s per bad record. The container handles the wait in small increments, so it keeps calling `poll()` and doesn't exceed `max.poll.interval.ms`.

Blocking retries keep **ordering**, which matters for entity event streams.

## 3. Non-Blocking Retries with Retry Topics

When ordering doesn't matter and a stalled partition is unacceptable, move failing records to **retry topics** and keep consuming:

```
orders ──fail──► orders-retry-0 (after 1s) ──fail──► orders-retry-1 (after 2s) ──fail──► orders-dlt
   │                    │                                    │
   └── next records ────┴─────── keep flowing ───────────────┘
```

```java
@Component
@Slf4j
public class PaymentListener {

    @RetryableTopic(
            attempts = "4",                                          // 1 original + 3 retries
            backoff = @Backoff(delay = 1_000, multiplier = 2.0, maxDelay = 30_000),
            exclude = { ValidationException.class },                 // straight to DLT
            topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE)
    @KafkaListener(topics = "payments", groupId = "ledger-service")
    public void onPayment(PaymentEvent event) {
        ledger.post(event);
    }

    @DltHandler
    public void onDeadLetter(PaymentEvent event,
                             @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
                             @Header(name = KafkaHeaders.DLT_EXCEPTION_MESSAGE, required = false) String error) {
        log.error("Payment {} dead-lettered from {}: {}", event.paymentId(), topic, error);
        alerting.notifyOps(event, error);
    }
}
```

Spring creates the retry and DLT topics automatically (configurable), with suffixes `-retry-0`, `-retry-1`, … and `-dlt`.

### Blocking vs Non-Blocking

| | Blocking (`DefaultErrorHandler`) | Non-blocking (`@RetryableTopic`) |
|---|---|---|
| Ordering per key | ✅ Kept | ❌ Lost — a retried record is processed after later ones |
| Partition stalls during retry | Yes | No |
| Extra topics | DLT only | Retry topics + DLT |
| Good for | Entity state changes (order lifecycle) | Independent events (notifications, payments with idempotency keys) |

## 4. Deserialization Errors (Poison Pills)

If a record can't be deserialized, the exception happens inside `poll()` — **before** your listener runs. Without protection, the consumer fails on the same offset forever.

`ErrorHandlingDeserializer` catches the failure and hands the container a record with a `null` value and the exception in a header. `DefaultErrorHandler` treats `DeserializationException` as not retryable and sends the raw bytes to the DLT.

```yaml
spring:
  kafka:
    consumer:
      key-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.key.delegate.class: org.apache.kafka.common.serialization.StringDeserializer
        spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer
```

The dead-letter publisher needs a `KafkaTemplate` that can write the original bytes. A template with `ByteArraySerializer` (or Spring's `DelegatingByTypeSerializer`) handles both raw bytes and normal objects:

```java
@Bean
public KafkaTemplate<Object, Object> dltTemplate(ProducerFactory<Object, Object> pf) {
    // Order matters: with assignable=true the first matching type wins, so byte[] goes first
    Map<Class<?>, Serializer<?>> delegates = new LinkedHashMap<>();
    delegates.put(byte[].class, new ByteArraySerializer());
    delegates.put(Object.class, new JsonSerializer<>());

    DefaultKafkaProducerFactory<Object, Object> dltPf = new DefaultKafkaProducerFactory<>(
            pf.getConfigurationProperties(),
            null,                                                   // key serializer from config
            new DelegatingByTypeSerializer(delegates, true));       // true = match by assignability
    return new KafkaTemplate<>(dltPf);
}
```

## 5. Stopping Instead of Dead-Lettering

If *every* record fails because a dependency is down, dead-lettering them all creates a mess to replay later. Options:

```java
// 1. Treat dependency outages as retryable forever: the partition waits until it recovers
handler.setBackOffFunction((record, ex) ->
        ex instanceof DataAccessResourceFailureException
                ? new FixedBackOff(5_000, FixedBackOff.UNLIMITED_ATTEMPTS)
                : null);   // null = use the default backoff
```

```java
// 2. Stop the container on fatal errors and alert; an operator restarts it
@Bean
public CommonErrorHandler errorHandler() {
    return new CommonContainerStoppingErrorHandler();
}
```

Combine this with a circuit breaker (Resilience4j) around the downstream call, and pause the listener while the breaker is open — see [Consumers and consumer groups](3.%20Consumers%20and%20consumer%20groups.md#6-filtering-pausing-and-lifecycle).

## 6. Reprocessing the DLT

A DLT is only useful if someone looks at it. Typical approaches:

- **Alert** on DLT message rate (e.g. Prometheus alert on the DLT topic's end-offset increasing).
- **Inspect** records with the console consumer, `kcat`, or a UI such as Kafka UI / AKHQ / Redpanda Console, including the `kafka_dlt-exception-*` headers.
- **Replay** after a fix by consuming the DLT and republishing to the original topic:

```java
@KafkaListener(id = "orders-dlt-replayer", topics = "orders-dlt", autoStartup = "false")
public void replay(ConsumerRecord<String, byte[]> record) {
    kafkaTemplate.send("orders", record.key(), record.value());
}
// Start it on demand: registry.getListenerContainer("orders-dlt-replayer").start();
```

⚠️ Replayed records arrive after newer events for the same key. Make sure the consumer can handle stale events (version checks).

## 7. Common Pitfalls

### ⚠️ Retrying non-transient errors

Retrying a validation error 10 times wastes time and stalls the partition. Classify exceptions with `addNotRetryableExceptions`.

### ⚠️ Infinite retries on bad data

`FixedBackOff(1000, UNLIMITED_ATTEMPTS)` for *all* exceptions blocks the partition forever on one bad record. Only retry forever for errors that are clearly infrastructural.

### ⚠️ No `ErrorHandlingDeserializer`

One malformed message — a producer bug, a manual test message — stops the consumer completely.

### ⚠️ DLT with fewer partitions

`DeadLetterPublishingRecoverer` fails if the destination partition doesn't exist, and the failure then loops. Match partition counts or route to partition `-1` (let Kafka choose): `new TopicPartition(topic + "-dlt", -1)`.

---

## Summary & Best Practices

| Failure | Strategy |
|---|---|
| Transient (timeouts, 5xx) | Exponential backoff retries |
| Bad data / validation | Not retryable → DLT immediately |
| Deserialization | `ErrorHandlingDeserializer` → DLT |
| Dependency outage | Retry indefinitely, pause, or stop + alert |

- ✓ Configure `DefaultErrorHandler` with backoff and a `DeadLetterPublishingRecoverer`.
- ✓ Use blocking retries when per-key order matters, `@RetryableTopic` when it doesn't.
- ✓ Monitor and alert on DLTs, and have a documented replay procedure.
