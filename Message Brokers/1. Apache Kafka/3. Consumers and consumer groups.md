# Consumers and Consumer Groups

> **Applies to:** Spring Boot 3.x (Spring for Apache Kafka 3.x) · Java 17+ · **Last updated:** 2026-11-21

## Overview

In Spring Kafka you consume records by annotating a method with `@KafkaListener`. Behind it, a *listener container* runs a poll loop: it calls `consumer.poll()`, invokes your method for each record (or batch), and commits offsets. Understanding that loop — threads, commits and rebalances — explains most consumer bugs.

**Key Concept**: A Kafka consumer is **not thread-safe**, and one partition is processed by one thread at a time. Concurrency comes from partitions, not from handing records to a thread pool.

## 1. Basic Listener

### Configuration

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: billing-service
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer
        spring.json.value.default.type: com.example.billing.OrderEvent
        spring.json.trusted.packages: com.example.billing
```

`ErrorHandlingDeserializer` wraps the real deserializer so that one malformed record doesn't make the container fail on the same offset forever — see [Error handling, retries and dead-letter topics](4.%20Error%20handling%2C%20retries%20and%20dead-letter%20topics.md).

### Listener

```java
@Component
@Slf4j
public class OrderEventsListener {

    private final BillingService billingService;

    public OrderEventsListener(BillingService billingService) {
        this.billingService = billingService;
    }

    @KafkaListener(topics = "orders", groupId = "billing-service")
    public void onOrderEvent(OrderEvent event) {
        billingService.handle(event);
    }
}
```

### Accessing Metadata

```java
@KafkaListener(topics = "orders")
public void onOrderEvent(@Payload OrderEvent event,
                         @Header(KafkaHeaders.RECEIVED_KEY) String key,
                         @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                         @Header(KafkaHeaders.OFFSET) long offset,
                         @Header(name = "event-type", required = false) String eventType) {
    log.info("Order {} ({}) from partition {} offset {}", key, eventType, partition, offset);
}

// or take the whole record
@KafkaListener(topics = "orders")
public void onRecord(ConsumerRecord<String, OrderEvent> record) { ... }
```

## 2. Concurrency

```java
@KafkaListener(topics = "orders", concurrency = "3")
public void onOrderEvent(OrderEvent event) { ... }
```

```text
orders: 6 partitions, concurrency = 3

thread-0  ← P0, P1
thread-1  ← P2, P3
thread-2  ← P4, P5
```

- `concurrency` creates that many consumers (threads) in this application instance.
- Across all instances of the service, the total number of consumers should be ≤ the number of partitions. With 6 partitions, 3 pods × concurrency 2 is ideal; 3 pods × concurrency 4 leaves 6 consumers idle.
- Records from one partition are always processed sequentially, in order.

⚠️ Don't push records into your own `ExecutorService` to "go faster". Offsets would be committed before processing finishes (losing records on a crash), and per-key ordering is lost. If you need more parallelism, add partitions or look at the Confluent *Parallel Consumer* library, which tracks per-record offsets safely.

## 3. Offset Commits and Acknowledgement Modes

Spring Kafka disables Kafka's own auto-commit (`enable.auto.commit=false`) and commits for you, according to `ack-mode`:

| `spring.kafka.listener.ack-mode` | When the offset is committed |
|---|---|
| `BATCH` (default) | After all records returned by one `poll()` have been processed |
| `RECORD` | After each record is processed |
| `TIME` / `COUNT` / `COUNT_TIME` | After a time interval and/or number of records |
| `MANUAL` | When you call `Acknowledgment.acknowledge()`; queued and committed with the next batch commit |
| `MANUAL_IMMEDIATE` | Immediately when you call `acknowledge()` |

With every mode, the commit happens **after** your code returns — that's at-least-once delivery. A crash between processing and commit means the records are delivered again.

### Manual Acknowledgement

```yaml
spring.kafka.listener.ack-mode: manual_immediate
```

```java
@KafkaListener(topics = "payments")
public void onPayment(PaymentEvent event, Acknowledgment ack) {
    paymentService.apply(event);
    ack.acknowledge();             // commit this offset now
}
```

Manual acks are rarely necessary. Prefer the default and let exceptions drive retries through the error handler.

## 4. Batch Listeners

```java
@KafkaListener(topics = "clicks", batch = "true")
public void onClicks(List<ClickEvent> clicks) {
    clickRepository.saveAll(clicks.stream().map(Click::from).toList());   // one bulk insert
}
```

```yaml
spring.kafka.consumer.max-poll-records: 500
```

Batch listeners shine for bulk writes (database, search index). Error handling is different: if one record fails, throw a `BatchListenerFailedException(message, index)` so the error handler knows which record failed and can commit everything before it.

## 5. Polling, Timeouts and Rebalances

The poll loop has two timeouts that cause most "my consumer keeps rebalancing" problems:

| Property | Default | Meaning |
|---|---|---|
| `max.poll.interval.ms` | 300000 (5 min) | Max time between two `poll()` calls. If processing one batch takes longer, the consumer is considered dead and its partitions are reassigned. |
| `max.poll.records` | 500 | Max records per `poll()`. |
| `session.timeout.ms` | 45000 | Heartbeat-based liveness (heartbeats are sent from a background thread). |

**Rule of thumb:** `max.poll.records × worst-case time per record` must stay well below `max.poll.interval.ms`. If a record can take 2 seconds, 500 records take ~17 minutes — lower `max.poll.records` to 50 or so.

### Rebalance-Friendly Settings

```yaml
spring:
  kafka:
    consumer:
      properties:
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
        group.instance.id: ${HOSTNAME}    # static membership: a restarting pod gets its partitions back
```

- **Cooperative sticky assignor** — only the partitions that move are revoked, instead of stopping the whole group.
- **Static membership** (`group.instance.id`) — a pod that restarts within `session.timeout.ms` rejoins without triggering a rebalance. The ID must be unique per instance (the pod name works in Kubernetes StatefulSets and Deployments).
- On Kafka 4.0+ brokers and clients, `group.protocol=consumer` enables the new broker-side protocol (KIP-848), which makes rebalances incremental by design.

### Reacting to Assignment

```java
@Component
public class OffsetAwareListener implements ConsumerSeekAware {

    @Override
    public void onPartitionsAssigned(Map<TopicPartition, Long> assignments, ConsumerSeekCallback callback) {
        // e.g. replay the last hour after a deployment
        callback.seekToTimestamp(assignments.keySet(), Instant.now().minus(Duration.ofHours(1)).toEpochMilli());
    }

    @KafkaListener(topics = "prices")
    public void onPrice(PriceUpdate update) { ... }
}
```

## 6. Filtering, Pausing and Lifecycle

```java
// Filter without committing to process: records failing the filter are skipped (and still committed)
@Bean
public RecordFilterStrategy<String, OrderEvent> onlyEuOrders() {
    return record -> !"EU".equals(record.value().region());   // true = discard
}

@KafkaListener(topics = "orders", filter = "onlyEuOrders")
public void onEuOrder(OrderEvent event) { ... }
```

```java
// Pause/resume a listener, e.g. while a downstream system is in maintenance
@KafkaListener(id = "billingListener", topics = "orders", autoStartup = "true")
public void onOrder(OrderEvent event) { ... }

@Service
@RequiredArgsConstructor
class ListenerControl {
    private final KafkaListenerEndpointRegistry registry;

    void pauseBilling()  { registry.getListenerContainer("billingListener").pause(); }
    void resumeBilling() { registry.getListenerContainer("billingListener").resume(); }
}
```

## 7. Idempotent Consumers

Because delivery is at-least-once, every consumer must tolerate duplicates. Common techniques:

```java
@KafkaListener(topics = "payments")
@Transactional
public void onPayment(PaymentEvent event) {
    // 1. Dedup table with a unique constraint on event ID
    if (!processedEvents.markProcessed(event.eventId())) {   // INSERT ... ON CONFLICT DO NOTHING
        return;                                               // already handled
    }
    accountService.credit(event.accountId(), event.amount());
}
```

Other options:

- **Natural idempotency** — `UPDATE orders SET status = 'SHIPPED' WHERE id = ?` is safe to repeat.
- **Version checks** — ignore an event whose version is ≤ the stored version.
- **Upserts** keyed by a business ID instead of inserts.

## 8. Common Pitfalls

### ⚠️ Slow processing → rebalance storm

Long processing exceeds `max.poll.interval.ms`, the consumer is kicked out, its partitions move, the same records are redelivered to someone else, and it happens again. Lower `max.poll.records`, speed up processing, or raise the interval.

### ⚠️ More consumers than partitions

Extra consumers stay idle. Scaling pods beyond the partition count doesn't increase throughput.

### ⚠️ Catching and swallowing exceptions

```java
try {
    process(event);
} catch (Exception e) {
    log.error("failed", e);   // ❌ offset is committed; the record is lost
}
```

Let the exception propagate so the error handler can retry it or send it to a dead-letter topic.

### ⚠️ Shared `group.id` across unrelated services

Two services with the same group ID split the partitions between them, so each sees only part of the data. Name groups after the consuming service.

---

## Summary & Best Practices

- ✓ One group per consuming service; total consumers ≤ partitions.
- ✓ Keep the default commit-after-processing behaviour (at-least-once) and make handlers idempotent.
- ✓ Keep `max.poll.records × processing time` far below `max.poll.interval.ms`.
- ✓ Use the cooperative sticky assignor and static membership to calm rebalances in Kubernetes.
- ✓ Use `ErrorHandlingDeserializer` for every consumer.
- ✓ Let exceptions reach the error handler — don't swallow them.
