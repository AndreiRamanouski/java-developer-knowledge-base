# Kafka Fundamentals

> **Applies to:** Apache Kafka 3.x–4.x · Spring Boot 3.x · Java 17+ · **Last updated:** 2026-11-21

## Overview

Apache Kafka is a distributed, append-only **event log**. Producers append records to topics, and consumers read them at their own pace by tracking a position (an *offset*) in the log. Records aren't deleted when they're read — they stay until a retention limit is reached — so many independent consumers can read the same data, and a consumer can rewind and replay history.

That design makes Kafka a good fit for:

- **Event-driven microservices** — services publish facts ("OrderPlaced") and others react, without point-to-point coupling.
- **Data pipelines** — moving change events from databases into search indexes, data lakes and caches.
- **Stream processing** — continuous aggregations, joins and enrichment with Kafka Streams or Flink.
- **Audit and replay** — a durable history you can reprocess after fixing a bug.

**Key Concept**: Kafka is a log, not a queue. A queue hands each message to one consumer and forgets it; Kafka keeps the log and lets each *consumer group* keep its own position in it.

## 1. Core Building Blocks

### Topics, Partitions and Offsets

```text
Topic: orders  (3 partitions)

Partition 0:  [0] [1] [2] [3] [4] [5]  ← new records appended here
Partition 1:  [0] [1] [2] [3]
Partition 2:  [0] [1] [2] [3] [4]
                            ▲
                            └─ offset: position of a record inside its partition
```

- A **topic** is a named stream of records, e.g. `orders`.
- A topic is split into **partitions**. Each partition is an ordered, immutable sequence of records stored on disk.
- Every record in a partition has a sequential **offset**.
- **Ordering is guaranteed only within a partition**, never across the whole topic.
- Partitions are the unit of **parallelism**: a consumer group can have at most one active consumer per partition.

### Records

A record has:

| Part | Purpose |
|---|---|
| **Key** (optional) | Decides the partition. Records with the same key go to the same partition, so they stay in order. |
| **Value** | The payload (JSON, Avro, Protobuf, bytes…). |
| **Headers** | Metadata, e.g. trace IDs, event type, schema version. |
| **Timestamp** | Creation time (or log-append time, depending on topic config). |

```text
key = "customer-42"  →  hash(key) % partitions  →  partition 1
```

⚠️ Changing the number of partitions changes the key → partition mapping for **new** records. Keys that used to land in partition 1 may now land elsewhere, which breaks per-key ordering across the change. Choose partition counts up front for keyed topics.

### Brokers and the Cluster

- A **broker** is a Kafka server. A cluster typically has 3+ brokers.
- Each partition has one **leader** replica (which handles reads and writes) and zero or more **follower** replicas on other brokers.
- **KRaft** (Kafka Raft) mode stores cluster metadata in Kafka itself, using a quorum of *controller* nodes. Kafka 4.0 removed ZooKeeper entirely, so every new cluster runs in KRaft mode.

## 2. Replication and Durability

```text
Partition orders-0, replication factor 3

Broker 1: [Leader]    ← producers write here, consumers read here
Broker 2: [Follower]  ← copies from the leader
Broker 3: [Follower]  ← copies from the leader

ISR (in-sync replicas) = {1, 2, 3}
```

- **Replication factor** — how many copies of each partition exist. Use 3 in production.
- **ISR (in-sync replicas)** — replicas that are caught up with the leader. If the leader fails, a new leader is elected from the ISR.
- **`min.insync.replicas`** (topic/broker config) — the minimum number of in-sync replicas that must have a write before a producer with `acks=all` gets success.

The standard durable setup:

| Setting | Value | Effect |
|---|---|---|
| Replication factor | `3` | Survives the loss of up to 2 brokers without losing data |
| `min.insync.replicas` | `2` | A write is acknowledged only when at least 2 replicas have it |
| Producer `acks` | `all` | The producer waits for all in-sync replicas (default since Kafka 3.0) |

With these settings, one broker can be down and the topic stays writable; if two are down, producers get `NotEnoughReplicasException` instead of silently risking data loss.

## 3. Consumer Groups

```text
Topic: orders (4 partitions)

Consumer group "billing"          Consumer group "shipping"
┌────────────┐                    ┌────────────┐
│ consumer A │ ← P0, P1           │ consumer X │ ← P0, P1, P2, P3
│ consumer B │ ← P2, P3           └────────────┘
└────────────┘
```

- Consumers with the same `group.id` form a **consumer group**. Kafka assigns each partition to exactly one consumer in the group.
- Different groups are independent: both `billing` and `shipping` receive every record.
- Adding consumers to a group spreads partitions across them — up to the number of partitions. Extra consumers sit idle.
- When consumers join, leave or crash, the group **rebalances** partitions among the remaining members.
- Each group stores its progress as **committed offsets** in the internal `__consumer_offsets` topic. After a restart, a consumer resumes from its group's committed offset.

`auto.offset.reset` decides where a group starts when it has no committed offset: `latest` (default — only new records) or `earliest` (from the beginning of the retained log).

Kafka 4.0 made the new consumer rebalance protocol ([KIP-848](https://cwiki.apache.org/confluence/display/KAFKA/KIP-848%3A+The+Next+Generation+of+the+Consumer+Rebalance+Protocol)) generally available. It moves assignment to the broker and avoids "stop-the-world" rebalances. Clients opt in with `group.protocol=consumer`.

## 4. Delivery Semantics

| Guarantee | How it happens | Risk |
|---|---|---|
| **At most once** | Commit the offset *before* processing | A crash after commit loses the record |
| **At least once** | Commit the offset *after* processing (Spring Kafka default) | A crash before commit reprocesses the record → **duplicates** |
| **Exactly once** | Idempotent producer + transactions, for Kafka → Kafka flows | Only covers writes to Kafka; side effects in other systems still need idempotency |

In practice most systems use **at-least-once delivery + idempotent consumers**. See [Exactly-once semantics and transactions](5.%20Exactly-once%20semantics%20and%20transactions.md).

## 5. Retention and Compaction

Kafka keeps records according to the topic's **cleanup policy**:

| Policy | Behaviour | Use for |
|---|---|---|
| `delete` (default) | Remove segments older than `retention.ms` (default 7 days) or beyond `retention.bytes` | Event streams, logs, metrics |
| `compact` | Keep at least the **latest record per key**; older values for the same key are cleaned up eventually. A record with a `null` value (a *tombstone*) deletes the key. | Current-state topics: customer profiles, configuration, KTable changelogs |
| `compact,delete` | Compact, and also drop old segments | Large state topics with a time limit |

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic customer-profiles --partitions 6 --replication-factor 3 \
  --config cleanup.policy=compact --config min.insync.replicas=2
```

## 6. Running Kafka Locally

```yaml
# compose.yaml — single-node KRaft broker for development
services:
  kafka:
    image: apache/kafka:3.9.0
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
```

Useful CLI commands (in the container: `/opt/kafka/bin/`):

```bash
# List topics
kafka-topics.sh --bootstrap-server localhost:9092 --list

# Produce from the terminal (key:value)
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:

# Consume from the beginning, printing keys
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders \
  --from-beginning --property print.key=true

# Show a consumer group's lag per partition
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group billing
```

With Spring Boot's Docker Compose support (`spring-boot-docker-compose`), a `compose.yaml` like this is started automatically and the connection details are wired in for you.

## 7. Common Pitfalls

### ⚠️ Assuming topic-wide ordering

Only records in the same partition are ordered. If all events for one order must be processed in sequence, use the order ID as the key.

### ⚠️ Too few partitions

You can't have more active consumers in a group than partitions, so the partition count caps consumer parallelism. Increasing it later reshuffles keys (see above). Size for expected peak throughput with headroom — for example 6–12 partitions for a typical business topic — rather than 1.

### ⚠️ Too many partitions

Each partition costs file handles, memory and leader-election time. Thousands of tiny topics × dozens of partitions add up. Don't default every topic to 100 partitions.

### ⚠️ Treating Kafka as a database

Kafka can replay history, but it isn't designed for ad-hoc queries or lookups by field. Project events into a database or a Kafka Streams state store for reads.

### ⚠️ `replication-factor 1` in production

A single broker failure then means unavailable — or lost — data. Use 3 replicas and `min.insync.replicas=2`.

## Summary & Best Practices

### Quick Reference

| Concept | One-line definition |
|---|---|
| Topic | Named log of records |
| Partition | Ordered shard of a topic; unit of parallelism and ordering |
| Offset | Position of a record in a partition |
| Consumer group | Set of consumers sharing a topic's partitions; each group sees every record |
| ISR | Replicas caught up with the partition leader |
| KRaft | Kafka's built-in metadata quorum (ZooKeeper removed in 4.0) |

### Best Practices

- ✓ Key records by the entity whose events must stay ordered (order ID, customer ID).
- ✓ Replication factor 3, `min.insync.replicas=2`, producer `acks=all`.
- ✓ Create topics explicitly (infrastructure as code) and disable `auto.create.topics.enable` in production.
- ✓ Design consumers to be idempotent — at-least-once delivery means duplicates will happen.
- ✓ Choose retention deliberately: compacted topics for state, time-based retention for events.
